Request Lifecycles Through the Backend

By the end of this lesson, you will be able to...

  • trace a request from bytes and token to response, naming the state and assumption at each stage

  • place parsing, authentication, validation, business decisions, persistence, mapping, and serialization in the right part of the path

  • predict where a request exits on success or failure and identify the signal that explains the exit

Idea in one sentence: A request lifecycle is a sequence of trust upgrades, shape changes, decisions, and exits; each stage must leave an honest assumption for the next stage.

Core Insight

Imagine Alice submits a review:

POST /courses/42/reviews
Authorization: Bearer <token>
{"rating": 5, "comment": "Clear and practical."}

Saying “the endpoint handles it” hides most of the work. At the network edge, the backend has bytes and an unverified token. It does not yet know that the method is allowed, that the JSON is well formed, that Alice is the caller, or that Alice may review course 42. A successful response is the result of several controlled handoffs.

The reasonable initial model is a single function:

request -> controller -> database -> response

This model works for a tiny private service. It becomes misleading when one stage needs an assumption another stage has not established. A middleware component may know how to parse a token but not whether Alice is enrolled. A domain rule may know whether reviews are open but should not know how an Express response object works. The pressure is not “we need more folders.” The pressure is that different decisions require different knowledge.

The Moving Parts and Their Knowledge

Use one stable vocabulary for the path:

Stage Receives Produces It is allowed to decide
HTTP parser bytes, method, path, headers parsed request whether the transport is syntactically readable
Correlation middleware parsed request request id and trace context how this request is identified in telemetry
Authentication credentials or token caller context whether credentials establish Alice’s identity
Boundary validation body and route values request DTO whether the input matches the accepted shape
Handler/adapter DTO, route, caller context application command how transport facts become use-case input
Use case command and repositories domain result or rejection whether Alice may perform the review and what changes
Repository/unit of work entity and transaction committed or failed persistence how durable state is read and written
Response mapper domain result response DTO which public fields and names are exposed
Serializer status, headers, DTO bytes on the wire how the already-decided result is encoded

These are responsibilities, not mandatory classes. Express describes an application as a series of middleware calls in the request-response cycle, and other frameworks expose similar pipelines. The architectural question is what each stage can know and what it must leave for later stages.

The Starting State

Before any application code runs, treat the request as untrusted:

method:        unknown to application policy
path:          raw text
headers:       untrusted strings
body:          bytes
caller:        unknown
course:        not loaded
trace_id:      absent or not yet normalized

The first stage parses the HTTP envelope. It can reject an unsupported method, malformed transfer, or invalid JSON. Parsing does not prove that the caller is Alice. It only changes bytes into a structure the next stage can inspect.

The correlation stage creates a request id such as req_7c1 and attaches a trace context. This value is for joining logs and spans; it is not an authorization credential. Keeping those roles separate prevents a debugging identifier from becoming accidental authority.

The Mechanism Step by Step

1. Parse and correlate

The parser reads the method, route parameter course_id=42, headers, and body. The correlation middleware records req_7c1 before work that may fail. If JSON is malformed, the request exits now with a client-facing syntax error and a trace entry showing the parser failure.

bytes
  -> parsed HTTP request
  -> request + trace_id=req_7c1

The important intermediate state is not the framework object. It is the new assumption: later stages may read structured transport data, but they still cannot trust the caller or the body’s business meaning.

2. Authenticate

Authentication validates the bearer token and produces caller context:

auth_context = authenticate(http_request.headers["Authorization"])
# auth_context = CallerContext(user_id="alice")

If the token is missing or invalid, the path exits with an authentication failure. No enrollment query should run, because the system has no established subject for that query. A valid identity still does not imply permission to review course 42; it only changes caller from unknown to Alice.

3. Apply cross-cutting controls

Rate limits, request-size limits, or abuse controls may reject the request before business work. These controls protect shared resources and usually use route, caller, or network signals. They should not decide product facts such as enrollment unless they have deliberately been given that responsibility.

The ordering is consequential. A body-size limit before parsing can stop an expensive parse. Authentication before a per-user quota supplies a caller key. A domain check before authentication would have no trustworthy user id. The right order follows dependencies between assumptions, not a framework convention.

4. Validate the boundary shape

The body becomes a request DTO:

request_dto = CreateReviewRequest(
    rating=5,
    comment="Clear and practical.",
)

The DTO allowlists client-controlled fields and checks structural constraints such as integer type, rating range, and comment length. It may trim whitespace or normalize a known representation. It must not decide whether Alice is enrolled. That fact requires product state and belongs later.

At this point the state is:

trace_id: req_7c1
caller:   alice (authenticated)
route:    course 42
input:    validated rating=5, comment="Clear and practical."

The phrase “validated request” now has a precise scope. It means the accepted shape is known. It does not mean the action is authorized or durable.

5. Adapt transport facts into a command

The handler combines the DTO with trusted context and route data:

command = CreateReviewCommand(
    user_id=auth_context.user_id,
    course_id=http_request.path_params["course_id"],
    rating=request_dto.rating,
    comment=request_dto.comment,
)

The command says, “Alice is attempting to create a review for course 42.” It contains no raw headers, response methods, or framework-specific request object. A batch importer could construct the same kind of command from a file adapter, with a different authority policy.

6. Run the use case

The use case loads the facts needed for the business decision:

def create_review(command):
    course = courses.get(command.course_id)
    enrollment = enrollments.find(command.user_id, command.course_id)

    if course is None:
        raise ReviewRejected("course_not_found")
    if course.reviews_closed:
        raise ReviewRejected("reviews_closed")
    if enrollment is None:
        raise ReviewRejected("not_enrolled")

    return reviews.create_once(command)

The use case is the first stage that can answer “may Alice do this here?” It may also apply a duplicate-review policy. It should not write the HTTP status directly. Its result or named rejection will be translated outward by an adapter.

7. Commit durable state

reviews.create_once creates an entity and asks the repository to persist it inside a unit of work. A unique database constraint can still reject a duplicate when two requests race. That is not a contradiction: the use case expresses product intent, while persistence protects the invariant at the commit point.

entity created -> INSERT attempted -> constraint checked -> commit succeeds

Until commit succeeds, the response must not claim that the review is durable. If the database times out, the lifecycle takes a dependency-failure exit. The unit of work owns rollback or cleanup according to the persistence design; the handler does not guess.

8. Map and serialize outward

After a successful commit, the mapper creates the public response DTO. It may format the timestamp and include a display name, while omitting internal moderation state. The serializer then chooses the HTTP status, headers, and bytes. Serialization is the last translation; it should not perform a new business decision.

response_dto = review_to_response(review)
return serialize(status=201, body=response_dto)

The outward path reverses the inward path: internal result becomes public shape, then public shape becomes wire representation. A response mapper is a compatibility seam; a serializer is a transport operation.

A Complete Trace

Here is the successful request as a state trace. Values are illustrative.

Step State after the step New assumption Possible exit
0 bytes + token nothing trusted malformed transport
1 parsed request + req_7c1 syntax and correlation available 400 parse error
2 caller alice token identifies a caller 401 authentication error
3 request DTO body shape is accepted 400 validation error
4 review command for (alice, 42) use case has meaningful input adapter/programming error
5 course and enrollment loaded business facts available not found / forbidden / closed
6 review entity pending commit product decision passed duplicate or dependency failure
7 row committed durable state exists commit failure
8 response DTO and 201 public projection chosen serialization failure

The table is a debugging tool. If a log says “validated” but the request failed at step 5, the failure is not a schema problem. If a client sees a 201 while step 7 never committed, the lifecycle has reported success too early.

Failure Exits Are First-Class Paths

There is no single “error path.” Each exit occurs at a stage with a different audience and recovery meaning:

malformed JSON          -> parser/validation exit
missing or bad token    -> authentication exit
course not found        -> application policy exit
not enrolled            -> authorization/domain exit
duplicate race          -> persistence integrity exit
database timeout        -> dependency exit
response encoding error -> serialization exit

The use case can raise ReviewRejected("not_enrolled") without knowing whether the API uses 403 or another contract. The boundary adapter translates that reason into the public error model. Meanwhile, telemetry should retain the trace id, stage, latency, and safe internal cause. The next lesson will classify these failures in more detail; this lesson establishes where they occur.

Trade-off: Explicit Stages Versus a Flat Handler

A staged lifecycle improves ownership, testability, and diagnosis. It costs more wiring, more interfaces, and more places to maintain an explicit contract. A tiny internal endpoint may reasonably combine parsing, mapping, and response creation when one team owns the whole private shape. The boundary becomes worth separating when multiple callers, public clients, independent release schedules, sensitive fields, or production diagnosis create pressure.

The lifecycle does not make every failure recoverable. Authentication can succeed while the database is unavailable. Validation can pass while a race violates a uniqueness rule. Tracing can show where latency grew but cannot make a slow dependency faster. The signal to watch is a mismatch between a stage’s claim and its evidence: a use case receives raw transport data, a middleware decision depends on product state it cannot load, or a success response appears before commit telemetry.

Common Confusions

“Middleware order is the architecture.” Order matters because assumptions flow forward, but names and registration order do not assign business ownership. Draw the knowledge dependency first; then choose the framework order that satisfies it.

“Authentication means the action is allowed.” Authentication establishes who presented valid credentials. Authorization and domain policy still decide whether Alice may review this course.

“The handler should catch everything.” The handler can translate known application outcomes into HTTP. It should not erase persistence causes or turn every dependency timeout into a successful response.

“Observability is outside the request.” Request ids, spans, and stage timings are produced while the request moves. If instrumentation starts only inside the use case, parser and serialization failures become invisible.

Check Your Understanding

Check 1: The token is valid, but Alice is not enrolled. At which stage should the request be rejected, and why not in authentication?

Think first, then reveal.

Answer: The use case or authorization policy should reject it after loading enrollment. Authentication proves Alice’s identity; it does not know the course-specific permission.

Check 2: Two valid requests pass the enrollment check and race to create the same review. Which stage must still protect the invariant?

Think first, then reveal.

Answer: The persistence boundary must enforce uniqueness at commit time. A pre-check is useful for an early explanation but cannot replace a durable constraint under concurrency.

Check 3: A trace has request.validate but no response.map, and the client receives a 500. What does that observation suggest?

Think first, then reveal.

Answer: The failure may be in the outward mapping or serialization stage. The missing span narrows the investigation; it does not prove the mapper is the cause, so inspect the error and stage timing next.

Trace It Yourself: A Rejected Request

Use this input:

POST /courses/42/reviews
Authorization: Bearer valid-token-for-alice
{"rating": 6, "comment": "Useful"}

Assume the request DTO accepts only ratings 1–5. Write the lifecycle until it exits. Then change the rating to 5 and assume Alice is not enrolled. Write the second trace.

A good answer should:

  • create correlation context before the rejection is recorded;
  • distinguish authentication success from input validation failure;
  • stop the first trace before command creation because rating 6 violates the request contract;
  • let the second trace create a command and reach the use case before rejecting not_enrolled;
  • state which public status/problem mapping and telemetry fields would preserve each failure’s meaning.

Key Takeaways

  • A request is not one object: it moves from bytes to parsed input, caller context, DTO, command, domain result, and public response.
  • Each stage narrows uncertainty, adds trusted context, makes a decision, persists a fact, or translates a result; it should not claim knowledge it does not own.
  • Failure exits are part of the lifecycle. Their stage determines their meaning, response mapping, and diagnostic evidence.
  • Explicit stages cost wiring, but they make ownership, ordering, latency, and incorrect assumptions inspectable.
