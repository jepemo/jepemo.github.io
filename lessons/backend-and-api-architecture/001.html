REST and Resource-Oriented APIs

By the end of this lesson, you will be able to...

  • distinguish a resource from a database row, a representation, and a backend function

  • classify common HTTP operations by safety, idempotency, and retry behavior

  • turn a command-shaped endpoint into a resource-oriented contract without forcing every workflow into CRUD

Idea in one sentence: A resource-oriented API gives clients stable things to identify and combines them with honest HTTP semantics, so a request still has predictable meaning when implementations change or networks fail.

Core Insight

A learning platform begins with three endpoints:

POST /createEnrollment
POST /completeLesson
POST /getCourseDetails

The design is reasonable while one team owns one client. Each endpoint names the server function that already exists. The controller receives a request, calls that function, and returns JSON.

Then the mobile client times out after calling /createEnrollment. Did the server create the enrollment? Is it safe to retry? A cache sees /getCourseDetails, but the method says POST, so the cache cannot apply the usual retrieval rules. A second client wants to read completion state, but /completeLesson exposes an action without identifying the state that changed.

The URLs are not the deepest problem. The client has been given a list of remote functions, but not a stable model of the things those functions affect.

Resource-oriented design changes the starting question. Instead of asking, “Which controller should we expose?”, ask:

What does the client need to identify, read, change, retry, or observe over time?

For this platform, the answers include courses, enrollments, progress records, and certificate jobs. Those concepts can survive a controller refactor, a database migration, or a move from one process to several services. They are better candidates for the public contract.

The Confusion: REST Is More Than Noun-Shaped URLs

It is common to call any JSON API with plural nouns “REST.” That shortcut hides two different ideas.

REST is an architectural style described by Roy Fielding for distributed hypermedia systems. Its constraints include client-server separation, stateless interactions, cache semantics, a uniform interface, and layered components. Resources and representations are central to that uniform interface.

A resource-oriented HTTP API is a practical application design that identifies resources with URIs and uses HTTP methods, status codes, headers, and representations deliberately. Many production APIs follow this model without implementing every REST constraint, especially hypermedia-driven navigation.

This lesson focuses on that practical boundary while keeping the distinction honest. A clean route table is not enough to prove that a system follows REST. It is still useful to design resource-oriented contracts because clients, caches, proxies, retry loops, and operators already understand HTTP semantics.

Resource, Representation, and Implementation

These three ideas often look similar in small systems, but they should not be treated as identical.

A resource is the concept the client identifies. It may be course c-42, enrollment e-501, or the progress of learner u-7 through lesson l-3.

A representation is data sent about that resource. The same course might have a JSON representation for an API, HTML for a browser, or a smaller JSON view for a mobile client. Changing a representation does not automatically create a different resource.

The implementation is how the server produces or changes that state. One request may touch several tables, call a payment provider, append an audit record, or enqueue work. The URI does not need to reveal those details.

Consider an enrollment collection:

POST /courses/c-42/enrollments

The request targets the course's enrollment collection. The server may validate eligibility, charge a payment method, insert a row, and schedule a welcome email. None of those internal steps needs its own client-visible endpoint. The public concept is still “create an enrollment for this course.”

A useful stability test is:

If the backend implementation changed tomorrow, would this identifier still mean the same thing to the client?

If the answer is no, the API may be exposing implementation structure instead of product structure.

HTTP Methods Carry Behavioral Promises

The method is part of the contract. It tells a client what kind of interaction it is requesting and what may be reasonable after a failure.

Method Safe? Idempotent by HTTP semantics? Typical resource-oriented use
GET yes yes retrieve a representation
PUT no yes create or replace the state at a known URI
PATCH no no by default apply a partial modification
POST no no by default create beneath a collection or submit processing
DELETE no yes remove the association or state named by the URI

“Safe” does not mean that the server performs no work. A GET can write an access log or increment a metric. It means the client did not ask for a state change as the purpose of the request.

“Idempotent” does not mean that every response is identical. It means that several identical requests have the same intended effect as one request. The first DELETE /enrollments/e-501 might return 204 No Content; a repeat might return 404 Not Found. The responses differ, but the intended resource state—no enrollment at that URI—is unchanged.

Method semantics are promises, not enforcement. A framework will happily let a GET delete data. Doing so makes automated navigation, retries, prefetching, and caching dangerous because those components trust the method's meaning.

Caching also needs more than a GET route. The method must permit caching, and response metadata must say when reuse is valid. Personalized or authorized responses need especially careful cache controls. Resource orientation creates a place for that policy; it does not choose the policy automatically.

Worked Path: Design Enrollment for an Uncertain Network

Assume learner u-7 wants to join course c-42. The system must prevent two enrollments for the same learner and course. The following values are illustrative.

Step 1: Identify the target concept

The naive endpoint is:

POST /createEnrollment

The stable concepts are the course and its enrollment collection, so choose:

POST /courses/c-42/enrollments

The authenticated caller can supply learner identity through trusted request context. The body only needs data the caller is allowed to choose.

Step 2: Define successful creation

If the server creates enrollment e-501 immediately, it can respond:

HTTP/1.1 201 Created
Location: /enrollments/e-501
Content-Type: application/json

{"id":"e-501","courseId":"c-42","state":"active"}

201 Created and Location tell the client that a new resource exists and where to identify it. The response shape is one representation of the enrollment, not the enrollment itself.

Step 3: Make the timeout case explicit

Suppose the server commits e-501, but the connection closes before the client receives the response. A blind repeat of POST could create e-502.

The application can add an idempotency contract:

POST /courses/c-42/enrollments
Idempotency-Key: enroll-u7-c42-attempt-1

A typical implementation scopes the key to the caller and operation, records a fingerprint of the request, and stores the first completed result. A retry with the same key and same input receives the recorded result. Reusing the key with different input is rejected.

This behavior is not supplied by the word POST. It is an application-level promise layered on top of HTTP. The server still needs a uniqueness constraint or equivalent rule to protect the business invariant when different keys race.

Step 4: Separate creation from later state changes

Suppose the client later marks lesson l-3 complete. If it sends the complete desired representation to a known URI, PUT can make the retry behavior clear:

PUT /learners/u-7/progress/l-3
Content-Type: application/json

{"state":"completed","completedAt":"2026-06-12T10:15:00Z"}

Repeating that request asks for the same intended final state. Compare it with this patch document:

{"completedLessonsIncrement": 1}

Applying the increment twice changes the state twice, so that patch is not idempotent. A PATCH can be designed for safer repetition, but the patch format and concurrency policy must make that true. When a patch depends on a known prior version, a strong ETag with If-Match can reject an update if another writer changed the resource first.

Step 5: Give long-running work its own lifecycle

Course completion may trigger certificate generation that takes several seconds. Pretending the work finished inside the progress update makes timeouts hard to interpret. Model the work as an observable resource:

POST /certificate-jobs

{"courseId":"c-42"}

HTTP/1.1 202 Accepted
Location: /certificate-jobs/job-99

The client can now retrieve the job and observe queued, running, completed, or failed. Resource orientation is not limited to database entities. A job, search result, or auditable command can be a resource when clients need to identify and observe it.

So far, the design has not removed failure. It has made failure interpretable. The client knows what was targeted, what success created, which operations can be repeated, and where asynchronous progress can be observed.

The Trade-off: Uniform Meaning Versus Specialized Convenience

The central trade-off is uniformity versus specialization. A custom action endpoint can match one backend function or screen exactly. That directness is useful for a small, controlled client. A resource-oriented interface asks the team to translate the action into stable concepts and shared HTTP semantics. That work takes longer, and the resulting messages may be less specialized for one workflow.

In return, more participants can understand the contract without private knowledge. Clients can reason about retries. Caches can reason about reuse. Operators can group requests by method and resource.

The design is a good fit when those shared predictions matter more than mirroring one implementation. It fits less well when one specialized interaction matters more than uniform semantics. A data stream may need a streaming protocol. A command may be clearer as a command than as a fake resource with a noun-shaped name.

What the Heuristics Do Not Guarantee

Several popular rules help, but none is the definition of a good contract.

“Use nouns, not verbs.” This can reveal server functions disguised as APIs. It can also produce fake nouns such as /completionExecutions. Use a command or job resource when that concept has identity, status, or audit value; otherwise prefer the clearest honest contract.

“Map every table to a resource.” A public resource is a client concept, not a schema export. One resource may combine several tables, and one table may support several representations.

“Stateless means the server stores no state.” REST statelessness concerns request context: each request carries the information needed to understand it without relying on a hidden conversation from previous requests. The server still stores resource state such as courses and enrollments.

“Idempotent means harmless.” DELETE is idempotent but not safe because the client requests a state change. A repeated operation can also repeat incidental work such as logging even when its intended resource effect stays the same.

“REST solves authorization and transactions.” It does not. A clear resource tells the authorization layer what is being accessed, but later lessons must still decide who may act and which writes commit together.

Check Your Understanding

Check 1: An endpoint uses GET /export-and-delete?courseId=c-42. Is it safe because it uses GET?

Think first, then reveal.

Answer: No. The method claims a read-only purpose, but the operation intentionally deletes state. The implementation violates the contract clients and intermediaries associate with GET.

Check 2: The first DELETE /enrollments/e-501 returns 204, and the second returns 404. Does the second response prove that DELETE was not idempotent?

Think first, then reveal.

Answer: No. Idempotency concerns the intended server effect, not identical responses. After either one or several requests, the enrollment is absent.

Check 3: A client retries POST /courses/c-42/enrollments with the same idempotency key but a different payment option. Should the server treat it as the same attempt?

Think first, then reveal.

Answer: No. A sound idempotency contract compares the request input and rejects incompatible reuse of the key. Otherwise one key could silently refer to two different intentions.

Practice: Replace a Cancellation Function

The platform currently exposes:

POST /cancelEnrollment

A client can time out, cancellation must be auditable, and the learner may already be cancelled. Propose a resource-oriented contract. State:

  • the target URI and method
  • what a repeated request means
  • the success or status resource the client can observe
  • one business invariant that HTTP semantics cannot enforce

A good answer may choose DELETE /enrollments/e-501 when cancellation simply means that the enrollment should no longer be active. Repeats should leave the same intended final state. The API must define whether an already absent enrollment returns 204 or 404.

Another good answer may create POST /enrollment-cancellations with an idempotency key when cancellation has its own reason, approval, refund, or audit lifecycle. The response can identify a cancellation resource that the client observes. In either design, HTTP cannot decide whether the caller is authorized, whether a refund is allowed, or whether concurrent state changes violate a business rule.

Key Takeaways

  • A resource is a stable client-visible concept; a representation is data about it, and the backend implementation may change independently.
  • REST is an architectural style, while resource-oriented HTTP API design is one practical way to apply its resource and uniform-interface ideas.
  • HTTP method semantics make safety, idempotency, retry behavior, and caching more predictable, but the application must implement those promises honestly.
  • POST and PATCH can gain application-specific replay protection, but their methods do not make them idempotent automatically.
  • A good contract models jobs or commands explicitly when they have a lifecycle, instead of forcing every operation into table-shaped CRUD.
