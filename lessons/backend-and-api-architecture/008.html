SOLID Principles in Backend Design

By the end of this lesson, you will be able to...

  • use SOLID as a set of review questions about change pressure, contracts, and dependency direction

  • diagnose an enrollment service whose pricing, payment, persistence, and notification changes are colliding

  • reject ceremonial abstractions while defending boundaries that protect a real change

Idea in one sentence: SOLID is most useful as a review lens for keeping backend code easy to change without turning every class into an abstraction exercise.

Core Insight

This track has moved one enrollment behavior through several boundaries. The API translates an outside request. An application service coordinates a workflow. Injected collaborators make runtime choices visible. Repositories and a unit of work keep storage mechanics and commit timing explicit.

Now the service has grown. It supports coupons, enterprise discounts, instructor grants, payment retries, audit records, waitlists, notifications, and imported corporate learners. Each feature looked small when it arrived. Together they create a harder question: which changes should be allowed to travel through the same module?

SOLID is a compact vocabulary for asking that question. It is not five commands to obey. The useful test is whether a principle helps us see a collision that matters in this backend. If a boundary protects no likely change, it may be needless ceremony. If a single module mixes policies that change for different reasons, a small boundary can reduce the blast radius.

What We Can See Now

The earlier lessons give us a map before we apply the names:

HTTP / import / CLI
        -> application workflow
        -> business policy
        -> capability contracts
        -> repositories and unit of work
        -> concrete providers and database

This map is not automatically “SOLID.” It becomes useful when each arrow protects knowledge that changes on a different schedule. HTTP status mapping can change without changing seat policy. A payment provider can change without changing the meaning of an enrollment. A database adapter can change its query without changing the application operation.

The five letters help us inspect those pressures:

Principle Review question Enrollment symptom
SRP Which reason to change owns this code? pricing, payment, and HTTP concerns share one method
OCP Where will the next variant be added? every discount reopens one conditional branch
LSP Can a substitute keep the consumer's behavioral expectations? a fake payment always succeeds while production can reject or time out
ISP Does this consumer depend only on the capability it uses? a service receives a giant platform-services object
DIP Does policy depend on stable capabilities rather than volatile details? enrollment imports an ORM session or provider SDK

The table is a retrieval aid, not a class generator. A single well-shaped module may satisfy several questions without exposing five separate interfaces.

Synthesis Example: The Growing Enrollment Method

Here is the pressure in one place:

def enroll(self, learner_id, course_id, request):
    course = self.db.query_course(course_id)
    if request.user.role == "instructor":
        allowed = True
    elif request.user.enterprise_account_id:
        allowed = self.enterprise_rules.can_enroll(request.user, course)
    else:
        allowed = course.is_open and course.has_available_seat
    if not allowed:
        raise EnrollmentRejected("not_allowed")

    if request.coupon_code:
        price = self.apply_coupon(course.price, request.coupon_code)
    elif request.user.enterprise_account_id:
        price = self.apply_enterprise_discount(course.price, request.user)
    else:
        price = course.price
    self.stripe.charge(learner_id, price)
    enrollment = self.db.insert_enrollment(learner_id, course_id)
    self.email.send_confirmation(learner_id, course_id)
    self.audit.write("learner_enrolled", enrollment.id)
    return enrollment

Review it in sequence rather than naming principles at random.

  1. Separate reasons to change. Eligibility, pricing, payment integration, persistence, and notification are different pressures. This is the SRP question. It does not demand one class per line; it asks whether a pricing change should risk payment code.
  2. Find the next variant. A new campaign currently edits the central if block. This is OCP pressure. Move variable pricing behind price_for(...) only if variants are expected. If the price is fixed and unlikely to change, the extra policy object may not earn its cost.
  3. Name capabilities. The workflow needs pricing, payments, enrollments, and perhaps notifier. This applies ISP and DIP together: the service receives the small operations it understands, not a complete SDK or a “god” context.
  4. Check substitutes. A test payment adapter should represent success, rejection, retryable timeout, and idempotency conflict when those outcomes affect the workflow. Matching the method signature is not enough; the substitute must preserve the behavior the consumer relies on. This is the LSP question.
  5. Keep construction outside. The composition root chooses Stripe or a sandbox adapter, a real repository or an in-memory one, and the appropriate unit-of-work lifetime. Policy does not import those details. That is DIP in the runtime shape.

The resulting workflow can stay small:

def enroll(self, learner_id, course_id, context):
    course = self.courses.get_for_enrollment(course_id)
    price = self.pricing.price_for(course, context)
    charge = self.payments.charge(learner_id, price)
    enrollment = self.enrollments.create(learner_id, course_id, charge)
    self.events.record_enrollment(enrollment.id)
    return enrollment

This is not automatically better. It is better when the named boundaries match real changes and the tests exercise the contracts. The unit of work from the previous lesson may wrap enrollments.create and events.record_enrollment; the payment adapter may remain outside that database transaction because it is an external side effect.

The Concepts That Are Commonly Confused

SRP means one method per class. The useful definition is about reasons to change. A class can coordinate several steps of one workflow and still have one responsibility. A tiny class can violate SRP if it combines unrelated policy and infrastructure.

OCP means never edit existing code. New requirements often require changing a stable contract or fixing a bug. OCP asks whether predictable variants can be added without reopening the most fragile center. It is a pressure test, not a promise of zero modification.

LSP is only about inheritance. A duck-typed fake, adapter, or alternate provider is also a substitute. If the consumer expects retryable errors or idempotency behavior, a fake that erases those cases is misleading.

ISP means every interface must have one method. Small interfaces help when consumers need different capabilities. Splitting a coherent capability into dozens of wrappers can make the dependency graph harder to understand.

DIP means interfaces everywhere. The principle is about dependency direction. A concrete adapter can be perfectly appropriate at the edge. The concern is whether high-level policy imports a volatile detail directly.

Trade-offs and Boundaries

SOLID boundaries buy a smaller change surface and more focused tests. They cost names, wiring, mapping, and the need to keep contracts honest. An abstraction that has one implementation, no test substitution, and no likely variation may be pass-through ceremony. A boundary that protects payment-provider replacement, pricing churn, or database isolation may be worth the indirection.

SOLID also does not decide whether this system should be a modular monolith or several services. A microservice can still contain tangled responsibilities, and a monolith can have clear internal boundaries. The signal to watch is not the number of repositories or deployment units. It is whether a change in one concern forces unrelated code and tests to move.

Retrieval Check

Check 1: A new discount campaign edits the same branch as enrollment eligibility. Which two questions should you ask?

Think first, then reveal.

Answer: Ask which reasons to change are colliding (SRP) and whether the next pricing variant must reopen the central workflow (OCP). Extract pricing only if the change pressure is real.

Check 2: A fake gateway has the same charge() signature as production but never returns a timeout. What is missing?

Think first, then reveal.

Answer: Behavioral contract coverage is missing. LSP requires the substitute to preserve the failure cases that the consumer must handle, not merely the type shape.

Check 3: A service receives PlatformServices with twenty methods and uses two. Which principle points to the problem?

Think first, then reveal.

Answer: ISP. Give the service the two coherent capabilities it needs, unless the broader object is intentionally one stable boundary with no harmful coupling.

Transfer Challenge: Review a Billing Service

A billing service now validates an HTTP request, calculates tax, calls a payment provider, writes an invoice and audit record, and publishes a receipt event. The product team expects new tax jurisdictions and a second payment provider next quarter.

Sketch a review using at least three SOLID questions. Name one boundary you would add, one abstraction you would reject, and one behavioral case a fake must preserve.

A good answer should mention:

  • transport parsing and response mapping can stay at the edge;
  • tax policy and payment integration have different change pressures;
  • a payment capability can hide provider details while the adapter translates errors and idempotency behavior;
  • invoice and audit writes may share a unit-of-work boundary, while receipt publication needs an explicit post-commit handoff;
  • a fake should model at least one rejection or retryable failure that affects billing behavior;
  • no interface is justified solely because the acronym has five letters.

Key Takeaways

  • SOLID is a review vocabulary for change pressure, contract behavior, interface size, and dependency direction.
  • SRP and OCP help decide whether a growing workflow should separate a variant or policy.
  • LSP and ISP make injected collaborators trustworthy and focused on the consumer's real needs.
  • DIP keeps application policy pointed toward stable capabilities while concrete adapters remain at the edge.
  • The right amount of SOLID is the amount that reduces a named coupling problem; more abstractions are not automatically better.
