Repositories, Units of Work, and Persistence Boundaries

By the end of this lesson, you will be able to...

  • shape repository capabilities around an application question instead of mirroring a database or ORM

  • choose and trace a unit-of-work boundary for a multi-write enrollment operation

  • explain why a database commit cannot make an external notification atomic, and design a recoverable handoff

Idea in one sentence: A persistence boundary lets the application state its durable intent while repositories hide query mechanics and a unit of work makes the commit boundary explicit.

Core Insight

The learning platform is adding paid enrollment. For one request, the backend must check that the learner is not already enrolled, reserve one seat, create an enrollment row, and record an audit entry. After the database commit, another component should notify the learner.

The tempting implementation puts ORM calls directly in EnrollmentService. It can work in a small endpoint. But the service then has to speak several languages at once: product policy, SQL filters, row classes, locks, session state, and commit timing. A worker and a repair command may copy those details. A schema change can reach into policy code. A hidden commit can make one write durable while a later write fails.

The stronger model separates two questions:

What durable operations does this use case need?
Which storage changes become durable together?

A repository answers the first question with an application-facing capability. A unit of work answers the second by framing one persistence transaction. They often collaborate, but they are not synonyms. A repository describes access; a unit of work coordinates a set of changes.

The Reasonable First Model

Here is a plausible first version for a course with one remaining seat:

def enroll(learner_id: str, course_id: str, session):
    course = (
        session.query(CourseRow)
        .filter(CourseRow.id == course_id)
        .with_for_update()
        .one()
    )
    existing = (
        session.query(EnrollmentRow)
        .filter_by(learner_id=learner_id, course_id=course_id)
        .first()
    )
    if existing:
        raise EnrollmentRejected("already_enrolled")
    if course.available_seats <= 0:
        raise EnrollmentRejected("course_full")
    course.available_seats -= 1
    enrollment = EnrollmentRow(learner_id=learner_id, course_id=course_id)
    session.add(enrollment)
    session.add(AuditRow(kind="learner_enrolled", entity_id=enrollment.id))
    session.commit()
    return enrollment

This code is not wrong merely because it uses an ORM. It is useful when the service is deliberately close to one store and the transaction question is trivial. Its pressure appears when several entry points need the same operation, when the storage model changes, or when two learners can race for the final seat. The method now owns the locking choice, row mapping, uniqueness behavior, and commit. A reviewer must reconstruct the product workflow from persistence instructions.

Repositories Give the Use Case a Better Vocabulary

A repository is useful when it mediates between application intent and data-mapping mechanics. For enrollment, the application might need these capabilities:

courses.get_for_enrollment(course_id)
enrollments.find_for(learner_id, course_id)
seats.reserve(course_id)
enrollments.add(learner_id, course_id)
audit.record(kind, entity_id)

Those names are not a universal recipe. They are a design test: can the service state its questions without mentioning a query builder, an ORM session, or a table alias? The implementation can still use indexes, row locks, constraints, and SQL. It translates the capability and maps rows at the lower boundary.

Avoid the opposite mistake, a generic repository that exposes only find, save, and delete for every table. Generic methods can be appropriate for simple data access, but they do not tell the application whether saving an enrollment also reserves a seat, checks uniqueness, or writes an audit record. A repository earns its cost when it localizes a change pressure or gives the use case a more truthful language.

The boundary does not erase database knowledge. The database still owns facts such as a unique (learner_id, course_id) constraint. The repository should make that constraint's failure meaningful to the application, for example by translating a duplicate-key error into an enrollment conflict. It should not pretend that an in-memory check alone prevents a race.

A Unit of Work Makes One Commit Visible

Now consider the writes that define one successful enrollment:

reserve a seat
create the enrollment
record the audit entry

If the first write commits and the second fails, the platform has lost a seat. If the enrollment commits but the audit entry does not, the operational record is incomplete. The application needs one database transaction for the changes that must become durable together.

A unit of work is the object or boundary that collects those changes and coordinates their commit. A minimal shape is:

def enroll(learner_id: str, course_id: str):
    with self.uow as uow:
        course = uow.courses.get_for_enrollment(course_id)
        if uow.enrollments.find_for(learner_id, course_id):
            raise EnrollmentRejected("already_enrolled")
        if not course.has_available_seat:
            raise EnrollmentRejected("course_full")

        uow.seats.reserve(course_id)
        enrollment = uow.enrollments.add(learner_id, course_id)
        uow.audit.record("learner_enrolled", enrollment.id)
        uow.commit()
    return enrollment

The exact API is a local choice. What matters is that the reader can answer when the unit of work starts, which repositories participate, and when commit occurs. An exception before commit should leave the database transaction rolled back according to the adapter's contract. A successful commit establishes the durable database fact.

A unit of work is not automatically the same as an ORM session, although an ORM session can implement one. SQLAlchemy, for example, frames begin, commit, and rollback around a session and tracks pending changes. Other data stores may require an explicit transaction object. Keep the architecture concept separate from the library name so the application can state its boundary honestly.

Worked Trace: Two Learners, One Seat

Concurrency makes the boundary concrete. Assume one seat remains and learners A and B submit at nearly the same time. The following is an illustrative trace; exact lock behavior depends on the database and isolation configuration.

Step Transaction A Transaction B
1 begins the unit of work and reads the course begins and tries to read the same course
2 obtains the seat-row lock or conditional update right waits, or receives a failed conditional update
3 verifies no duplicate, reserves the last seat cannot safely treat the old seat count as current
4 adds enrollment and audit entry retries or returns course_full according to policy
5 commits all three database changes observes the committed state after the lock is released

The application-level check “there is a seat” is not enough by itself. The persistence implementation needs a database-enforced strategy, such as a lock or an atomic conditional update, and a uniqueness constraint for duplicate enrollment. The repository exposes a meaningful result like seat_reserved or course_full; it does not promise that a read made earlier remains true forever.

The trace also shows why commit ownership matters. If seats.reserve() committed internally, the service could not roll back the seat when enrollments.add() failed. The unit of work keeps the writes under one decision point. It does not eliminate contention; it makes the contention and its result reviewable.

Database Commit Versus External Notification

The learner should receive EnrollmentCreated after a successful enrollment. A naive implementation publishes the event inside the database transaction and calls both operations atomic. They are not. A database rollback cannot unsend an email or retract a message already accepted by a broker.

Instead, record the intent in the same database transaction:

with self.uow as uow:
    enrollment = uow.enrollments.add(learner_id, course_id)
    uow.outbox.add(
        event_type="EnrollmentCreated",
        payload={"enrollment_id": enrollment.id},
    )
    uow.commit()

After commit, a publisher reads the outbox and sends the event. If the process crashes between commit and publish, the outbox row remains available for a later attempt. The handoff is recoverable, but delivery can still be duplicated, delayed, or rejected. Consumers need idempotency, and the publisher needs retry and visibility rules.

This boundary tells us what the unit of work can promise: the database fact and the outbox intent commit together. It cannot promise that a remote notification, payment provider, or email system shares that transaction. A later track can explore broader saga or distributed-transaction choices; this lesson only needs the boundary to remain explicit.

Design Limits and Failure Modes

Repository as ORM mirror. If the service still chooses eager-loading flags, session methods, and row-specific exceptions, the repository has moved files without moving knowledge.

Hidden commit. A repository that commits after every add makes multi-write intent invisible and can create partial success. Let the unit-of-work boundary or an explicitly named transaction owner decide.

Generic CRUD as false safety. save(enrollment) does not automatically communicate seat reservation, uniqueness, or audit obligations. Use a narrower operation when those rules matter.

Cross-system atomicity fantasy. An outbox improves the handoff from database to broker. It does not make the broker, payment provider, and database one transaction. Retries and duplicate delivery remain part of the design.

Long-lived transactions. Holding a transaction open while waiting for a remote API or a human interaction increases locks and failure exposure. Keep the database unit of work around the durable decision, then coordinate external work separately.

This is the trade-off: the pattern buys a readable persistence language and a visible commit boundary, but it costs interfaces, mapping code, transaction setup, and another abstraction to maintain. Direct ORM use can be the better choice for a simple read or a one-table write when no real boundary is being protected.

Check Your Understanding

Check 1: A repository method commits after writing the enrollment, but the audit insert happens later. What is the risk?

Think first, then reveal.

Answer: The writes can become partially durable. Move commit ownership to the unit of work if enrollment and audit are one consistency boundary.

Check 2: Two requests both read available_seats = 1 before either writes. Which layer must enforce the race-safe outcome?

Think first, then reveal.

Answer: The persistence implementation needs a database-enforced strategy such as a lock or conditional update, plus application handling for a failed reservation. A repository interface alone cannot create atomicity.

Check 3: Why does the outbox row belong in the same unit of work as the enrollment?

Think first, then reveal.

Answer: It records the event intent with the durable enrollment fact. A later publisher can retry after a crash, while the design remains honest about non-atomic external delivery.

Practice: Review a Booking Boundary

A workshop has ten seats. A web request and a CSV import must reserve seats, create bookings, and record an audit entry. A confirmation email is sent by another process. Sketch the repository capabilities, unit-of-work boundary, and one concurrency safeguard.

A good answer should mention:

  • both entry points call one application operation rather than copying SQL;
  • repositories expose booking-relevant capabilities, not a generic session to the application;
  • seat reservation, booking creation, audit, and outbox intent share one database commit when the product requires that consistency;
  • a unique booking constraint and a lock or conditional update handle concurrent requests;
  • the email publisher runs after commit and treats delivery as retryable and potentially duplicated;
  • a simple read-only query may use direct data access if no meaningful persistence boundary is being protected.

Key Takeaways

  • A repository earns its place when it gives the use case a truthful persistence vocabulary and localizes query mechanics.
  • A unit of work makes the set of changes and the commit decision visible; it is related to a transaction but not identical to every ORM session.
  • Concurrency needs database-enforced constraints or conditional coordination; an in-memory check alone is not a guarantee.
  • An outbox can commit event intent with database state, but external delivery remains a separate, retryable, and possibly duplicated step.
  • These patterns are tools for real boundaries, not mandatory wrappers around every table or query.
