Dependency Injection and Runtime Composition

By the end of this lesson, you will be able to...

  • trace how a composition root turns capability declarations into concrete production, test, worker, and local-runtime collaborators

  • choose collaborator boundaries and lifetimes without hiding construction in a service locator

  • diagnose when a container, fake, or abstraction is adding coupling instead of removing it

Idea in one sentence: Dependency injection keeps a use case focused on behavior while a runtime edge decides which concrete collaborators, configuration, and lifetimes make that behavior possible.

Core Insight

The learning platform already has an EnrollmentService from the previous lesson. A learner can enroll from the mobile API, a company import job, or a repair CLI. All three callers should apply the same course and payment rules. Now the service needs four capabilities: read a course, create an enrollment, charge a payment, and notify the learner.

The first implementation hides construction inside the use case. It opens a database connection, creates a payment SDK client, reads credentials, and builds an email client before it checks whether the course is open. That is convenient for one process. It becomes a problem as soon as the same behavior must run without real payments, with a sandbox provider, or with a temporary repository.

Dependency injection names the missing boundary. The use case says what it needs. An outside composition step supplies the objects. The use case still decides whether a closed course can accept enrollment. The runtime decides whether PostgresCourses, StripePayments, or FakePayments will satisfy the required capabilities.

The Reasonable First Model

This is a plausible first version:

class EnrollmentService:
    def enroll(self, learner_id: str, course_id: str):
        db = PostgresClient(os.environ["DB_URL"])
        payments = StripeClient(os.environ["STRIPE_KEY"])
        mailer = SmtpMailer(os.environ["SMTP_HOST"])

        course = db.fetch_course(course_id)
        if not course.is_open:
            raise EnrollmentRejected("course_closed")
        payments.charge(learner_id, course.price)
        enrollment = db.insert_enrollment(learner_id, course_id)
        mailer.send_enrollment_email(learner_id, course_id)
        return enrollment

This model works under a narrow condition: one environment owns one provider for every capability, and no test needs to observe behavior without invoking that provider. It is attractive because the method appears self-contained. The hidden choices are the real issue:

  • PostgreSQL, Stripe, SMTP, and environment variables become part of enrollment behavior.
  • A test must patch constructors or credentials instead of supplying a small scenario.
  • A worker and a CLI inherit HTTP-era or process-specific assumptions.
  • Every call may create a new connection or SDK client, even when those objects should be shared.

The service is mixing two questions: “What should happen when a learner enrolls?” and “Which objects exist in this runtime?” The first is application behavior. The second is composition.

The Better Model: Name Capabilities

Dependency injection does not require a container. A constructor is already an injection point when it receives collaborators:

class EnrollmentService:
    def __init__(self, courses, enrollments, payments, notifier):
        self.courses = courses
        self.enrollments = enrollments
        self.payments = payments
        self.notifier = notifier

    def enroll(self, learner_id: str, course_id: str):
        course = self.courses.get(course_id)
        if not course.is_open:
            raise EnrollmentRejected("course_closed")
        self.payments.charge(learner_id, course.price)
        enrollment = self.enrollments.create(learner_id, course_id)
        self.notifier.enrollment_created(learner_id, course_id)
        return enrollment

The code is not magically shorter. It is more honest. The constructor exposes the collaborators required to perform the operation, while the caller chooses their implementations.

A collaborator should be a capability expressed in the language of the use case, not a giant wrapper around a provider:

from typing import Protocol

class Courses(Protocol):
    def get(self, course_id: str) -> Course: ...

class Payments(Protocol):
    def charge(self, learner_id: str, amount_cents: int) -> None: ...

The protocol is one Python way to describe the required shape; the architectural point does not depend on Python's type system. EnrollmentService needs “get this course” and “charge this amount.” It does not need every method on a database or payment SDK. Small capabilities make a replacement meaningful and reveal when a service has accumulated unrelated responsibilities.

Where the Object Graph Is Built

If the service does not construct its world, some runtime edge must. That edge is often called the composition root: startup code or an entry point that assembles concrete objects and their dependencies.

def build_enrollment_service() -> EnrollmentService:
    pool = create_postgres_pool(os.environ["DB_URL"])
    courses = PostgresCourses(pool)
    enrollments = PostgresEnrollments(pool)
    payments = StripePayments(os.environ["STRIPE_KEY"])
    notifier = QueueNotifier(os.environ["EVENTS_TOPIC"])
    return EnrollmentService(courses, enrollments, payments, notifier)

Read this from the outside inward:

  1. Configuration supplies provider names, credentials, and connection settings.
  2. The composition root creates long-lived infrastructure such as a connection pool.
  3. Adapters receive that infrastructure and expose application-facing capabilities.
  4. The root gives those capabilities to EnrollmentService.
  5. An HTTP handler, worker, or CLI calls the same service without knowing how it was built.

The root is not “just boilerplate.” It is the place where a reviewer can answer which provider is selected, which credential is used, and who owns cleanup. A framework container may generate this graph, but the graph still exists and still needs a readable boundary.

Construction also has a failure policy. If the production database URL is missing, failing during startup can be safer than accepting requests that will fail halfway through enrollment. If a rarely used report adapter is optional, lazy construction may be reasonable, but then its first-use error needs a clear owner and signal. The composition root should make that choice deliberate. It should also close process-owned clients when the runtime stops, rather than leaving each use case to guess who owns a pool or publisher. These concerns are not business rules, yet they affect whether the business rule can run predictably.

Worked Trace: One Behavior, Three Runtimes

Consider the same closed-course check in three runtimes. The application decision should be identical; the object graph around it is different.

Runtime Concrete collaborators What the use case can observe
production API PostgreSQL repositories, Stripe adapter, queue notifier course state, payment result, enrollment result
import worker same repositories, idempotent payment adapter, batch notifier the same policy plus a batch-safe notification result
unit test in-memory course store, recording payment fake, recording notifier deterministic state and recorded calls

The production trace is:

process starts
  -> read DB_URL, STRIPE_KEY, and EVENTS_TOPIC
  -> create one pool and provider adapters
  -> inject capabilities into EnrollmentService
request arrives
  -> handler translates HTTP input into learner_id and course_id
  -> service asks Courses.get(course_id)
  -> closed course raises before Payments.charge()
  -> handler maps the application error to its HTTP response

The test trace keeps the same final three steps. Only the collaborators change. FakeCourses returns a closed course, RecordingPayments records attempted charges, and RecordingNotifier records notifications. The assertion that no charge occurred now tests an application rule rather than a patching trick. An integration test still has to verify that the real adapters speak correctly to PostgreSQL, Stripe, and the queue. Injection enables substitution; it does not certify an adapter.

Lifetimes Are Part of Composition

Choosing an implementation is only half of wiring. The root must also choose how long each object lives. A useful starting model is:

Lifetime Example Risk if chosen poorly
process connection pool, metrics client, queue publisher creating expensive clients per request or leaking them at shutdown
request or unit of work transaction, request context, authorization snapshot sharing mutable state between requests or committing outside the intended boundary
call command object, parsed input, result DTO retaining user-specific data longer than needed

These are design choices, not laws. A pool may be scoped differently by a serverless runtime. The important question is whether the lifetime matches ownership and concurrency. If a request-scoped transaction is stored in a process-global locator, two learners can accidentally share state. If a pool is recreated for every enrollment, connection setup can dominate the operation. Keeping lifetime decisions in composition code makes those risks visible.

Where the Pattern Breaks

Dependency injection can fail even when constructors appear in the code.

Service locator in disguise. A service that calls container.get("payments") still discovers its dependency at runtime. The constructor no longer tells the reader what the service needs, and tests must configure global state. A locator can be a deliberate boundary in some systems, but it is not the same transparency as direct injection.

Provider leakage. Injecting StripeClient and then calling Stripe-specific methods throughout the application exposes a concrete provider behind a variable name. A small application may accept that coupling. If provider replacement matters, define a capability such as charge and translate provider errors at the adapter boundary.

Container-first design. A team can add scopes, annotations, modules, and factories before it can draw the object graph. The result is powerful wiring that nobody can inspect. Start with explicit construction; automate only the repetition that remains.

Over-injection. A constructor with ten collaborators may be honest evidence that the class owns several workflows. Hiding those parameters in a context object makes the signature shorter but the dependency set less visible. Split the behavior when the change pressures are genuinely different.

Fake-only confidence. A fake can prove that the use case reacts to a payment failure, but it cannot prove that a timeout, serialization error, or provider idempotency key is handled correctly. Keep focused unit tests and adapter-level integration tests.

The pattern buys explicit substitution and reviewable construction. It costs constructor ceremony, object-graph maintenance, and another place where lifetime bugs can occur. Use it when those costs protect real environment variation, testing pressure, or ownership boundaries.

Check Your Understanding

Check 1: The import worker must reuse enrollment policy but publish a batch result instead of an HTTP response. Which code should change?

Think first, then reveal.

Answer: The worker entry point and its notifier/result mapping can change. The shared EnrollmentService should receive the worker's capabilities and keep the enrollment decision.

Check 2: A constructor accepts PostgresClient, StripeClient, and SmtpMailer, and the class calls provider-specific methods. What boundary is missing?

Think first, then reveal.

Answer: The service still depends on infrastructure details. Define the smallest application-facing capabilities and let adapters translate those calls to providers.

Check 3: A connection pool is created inside every enroll() call. What should you inspect first?

Think first, then reveal.

Answer: Inspect the composition root and lifetime policy. A process-owned pool may be intended, while a transaction or unit of work may be created per request.

Practice: Compose a Worker Without Changing Policy

The nightly job should enroll a cohort. It needs the same course-capacity and duplicate rules as the API, but payment is a sandbox adapter and notifications are written to a batch report. Sketch the object graph and name the lifetime of the pool, the unit of work, and the per-row command.

A good answer should mention:

  • the worker entry point translates each row and calls the shared application operation;
  • a composition root supplies repository, sandbox-payment, and batch-report capabilities;
  • the pool is shared for the worker process, while a unit of work is scoped to the intended transaction or batch boundary;
  • each row's command is short-lived and does not carry global state;
  • integration tests cover the real repository and sandbox adapter separately from the policy test.

Key Takeaways

  • Injection separates the use case's behavior from the construction of concrete collaborators.
  • A composition root makes provider choice, configuration, ownership, and lifetime visible at a runtime edge.
  • Small capabilities let production, workers, tests, and local tools reuse behavior without pretending to be the same environment.
  • Service locators, provider leakage, container-first design, and fake-only tests can hide the coupling that injection was meant to expose.
  • The pattern is worthwhile when explicit construction protects a real change pressure; it is not a requirement to add an interface to every helper.
