Layered Backend Architecture

By the end of this lesson, you will be able to...

  • place transport translation, application workflow, business policy, and infrastructure mechanics at useful boundaries

  • trace one enrollment use case from HTTP, an import job, and a CLI without duplicating its policy

  • detect when a layer protects a real change pressure and when it is only pass-through ceremony

Idea in one sentence: A backend layer earns its place when it keeps one kind of knowledge from spreading, so the same application behavior can survive a protocol, storage, or entry-point change.

Core Insight

The learning platform adds POST /courses/42/enrollments. The first implementation can fit in one route handler: parse JSON, identify the learner, query the course, check capacity, insert a row, and return an HTTP response.

That implementation works for one client. Then three callers need the same behavior:

mobile app       -> HTTP request
company import   -> background job
repair command   -> CLI invocation

The mobile request should return 201 Created. The import job needs a result it can count. The repair command may need a dry-run report. If the course-full or duplicate-enrollment rule lives inside the HTTP handler, each new caller either copies it or pretends to be an HTTP client.

The pressure is a change in entry point. A good backend keeps the product decision reusable while each edge translates its own protocol. This is the reason for layering. It is not a requirement to create folders named controllers, services, and repositories.

The Promise We Need to Keep

The architecture should make this promise:

An outside adapter translates its protocol into an application request.
The application coordinates a product workflow.
Business rules remain independent of HTTP and storage details.
Infrastructure implements capabilities without deciding public meaning.

“Layer” here means a logical boundary. Several layers can run in one process and deploy as one unit. Physical separation into processes or servers is a tier, not automatically a better layer. Keeping that distinction prevents a useful monolith from being mistaken for a failed architecture.

The Naive Design: One Handler Knows Everything

Here is the tempting first version:

@app.post("/courses/{course_id}/enrollments")
def enroll(course_id: str, request: Request):
    learner_id = request.user.id
    course = db.query("select * from courses where id = ?", course_id)
    if not course["is_open"]:
        return JSONResponse({"error": "course_closed"}, status_code=409)
    if db.exists("enrollments", learner_id=learner_id, course_id=course_id):
        return JSONResponse({"error": "already_enrolled"}, status_code=409)
    row = db.insert("enrollments", {"learner_id": learner_id, "course_id": course_id})
    return JSONResponse({"enrollmentId": row["id"]}, status_code=201)

The code is easy to read because it contains every concern. It also changes for many unrelated reasons: an HTTP status changes, authentication context changes, the SQL driver changes, or the enrollment policy changes.

The first model is attractive under one condition: this route is the only caller and the database row is the application's language. The import job breaks that condition. It should not own HTTP response construction, and it should not silently omit a rule that the route enforces.

A Better Boundary: Separate Knowledge, Not Files

Use a small outside-in map:

HTTP controller / GraphQL resolver / job handler / CLI
    translates protocol input and output

Application use case
    coordinates the enrollment workflow in product language

Domain rule or model
    expresses a rule when it needs a stable, named home

Repository or gateway interface
    describes the capability the workflow needs

Database adapter / external client
    implements storage or integration mechanics

The controller can read request.user.id, but the use case should receive a plain learner_id. The repository can use SQL and an ORM, but the use case should ask for course.get(course_id) or enrollments.exists(...), not build SQL. The use case can return an application result or a typed error; it should not construct a framework response.

Not every endpoint needs every box. A simple read may need an adapter and a thin handler. Add a boundary when the hidden detail has its own change pressure or must be shared by another caller.

Worked Path: One Enrollment, Three Entry Points

Assume the product rule is: an open course accepts a learner once; a full course creates a waitlist entry only when waitlisting is enabled. The values below are illustrative.

Step 1 — Translate at each edge

The HTTP controller creates an application command:

result = enrollment.enroll(
    learner_id=request.user.id,
    course_id=course_id,
)
return enrollment_http_response(result)

The import job creates the same command from a CSV row:

result = enrollment.enroll(
    learner_id=row.learner_id,
    course_id=row.course_id,
)
counts[result.kind] += 1

The repair CLI creates it from flags and can ask for a dry run. None of these callers needs to know how the policy or database query works.

Step 2 — Coordinate the workflow

The use case obtains the course and chooses a product outcome:

class Enrollment:
    def enroll(self, learner_id, course_id):
        course = self.courses.get(course_id)
        if self.enrollments.exists(learner_id, course_id):
            return Result("already_enrolled")
        if course.has_available_seat:
            record = self.enrollments.create(learner_id, course_id)
            return Result("enrolled", record.id)
        if course.waitlist_enabled:
            entry = self.waitlist.add(learner_id, course_id)
            return Result("waitlisted", entry.id)
        return Result("rejected", reason="course_full")

This is application behavior. A later lesson will examine how concrete collaborators are wired; here the important point is that the use case does not depend on a web request or SQL string.

Step 3 — Translate the result outward

The HTTP adapter maps the same application result to its public contract:

enrolled          -> 201 Created
waitlisted        -> 202 Accepted
already_enrolled  -> 409 Conflict
rejected          -> 409 Conflict

The import job maps it to counters. The CLI prints a dry-run decision. One policy has several honest representations because each edge has a different protocol job.

Step 4 — Keep mechanics behind a capability

The concrete repository may use SQL:

class PostgresEnrollments:
    def exists(self, learner_id, course_id):
        return self.db.fetch_value(
            "select 1 from enrollments where learner_id=%s and course_id=%s",
            (learner_id, course_id),
        ) is not None

The application depends on the capability, not on PostgresEnrollments. A test can provide a small fake. A database migration can change indexes or query shape without changing the controller's knowledge.

So far, the visible result is the same enrollment decision. The intermediate states are different by boundary: HTTP bytes become a command; the use case becomes a product result; an adapter becomes SQL or a public response. Those shape changes are the architecture's useful work.

Dependency Direction

The safest default is:

outside details -> application behavior -> capability interfaces
concrete infrastructure -> implements capabilities

This is a dependency rule, not a demand for a particular project layout. The application core should not import a web framework merely to inspect headers. It should not return an ORM object that forces every caller to understand persistence state. It should not let database exception names become the public error contract.

Dependency inversion can put an interface near the application code while an infrastructure adapter implements it. That makes the business rule easier to test and the storage choice easier to replace. The next dependency-injection lesson will show how those implementations are selected at runtime.

The Trade-off: Isolation Versus Indirection

Layering buys change isolation and reuse across entry points. It costs indirection, interfaces, mapping code, and more places to navigate. A five-line read should not become five pass-through classes merely to resemble a diagram.

The trade-off is worthwhile when a boundary hides a real detail: protocol semantics, a shared business rule, a storage technology, or a replaceable external service. It is weak when every layer forwards the same object and adds no decision, translation, or protection.

The signal is change pressure. If changing the HTTP framework forces SQL and domain tests to change, the boundary leaks. If adding a CLI requires copying enrollment rules, the workflow is in the wrong layer. If removing a wrapper changes nothing except file names, the wrapper may be ceremony.

Operational Consequences and Failure Modes

Layered code still needs operational decisions. A use case may return an application error, while an HTTP adapter chooses status and a job handler chooses retry behavior. Keep those translations visible rather than hiding them in a generic exception mapper.

Common failure modes:

  • Fat controller: route code owns course capacity, ownership, or duplicate policy.
  • Pass-through service: a service only calls a repository with the same arguments and name.
  • Leaky repository: application code receives ORM sessions, SQL fragments, or database-specific exceptions.
  • One object everywhere: request DTO, domain entity, database row, and response model are forced to evolve together.
  • Framework-centered core: jobs and tests must construct fake HTTP requests to reuse application behavior.

The boundary does not promise that every detail is hidden. Some systems deliberately use active-record objects or a thin CRUD design. That is a situated choice when the domain is simple and the team accepts the coupling. The design becomes dishonest only when its claimed boundaries do not match the dependencies that code actually has.

Design Review

Check 1: A CSV import needs enrollment decisions but has no HTTP response. Which part should it call?

Think first, then reveal.

Answer: The application use case. The import handler translates the row into an application command and maps the result to counters; it should not call the HTTP controller.

Check 2: The product adds a waitlist rule used by HTTP and import. Where should the decision live?

Think first, then reveal.

Answer: In the shared application workflow or a domain rule with enough meaning to deserve a home. It is product policy, not SQL or HTTP translation.

Check 3: A repository returns an ORM session so the controller can choose which query to run. What boundary has leaked?

Think first, then reveal.

Answer: Persistence mechanics have leaked outward. The application should depend on a meaningful capability, while the adapter owns query construction and session details.

Practice: Review a Multi-Entry-Point Boundary

The platform adds a partner API and a nightly job that enrolls a company cohort. Both must apply the same course-capacity and duplicate rules, but the partner needs HTTP statuses and the job needs per-row outcomes.

Sketch the smallest boundary design. Name:

  • what each edge translates
  • which application operation both callers share
  • one capability the persistence adapter provides
  • one mapping that must stay outside the application core

A good answer keeps partner authentication and status mapping in the partner adapter, row parsing and counters in the job handler, and course/enrollment policy in one application operation. It names a repository capability such as find_course, exists, or create, and keeps SQL, ORM sessions, and HTTP response objects outside that operation. It may choose fewer layers if it explains which change pressure is absent.

Key Takeaways

  • A layer should protect a real kind of knowledge: protocol translation, workflow, business policy, or infrastructure mechanics.
  • Multiple entry points should translate into one reusable application operation instead of copying rules or pretending to be HTTP.
  • Dependency direction should keep outside details and concrete storage behind application-facing capabilities.
  • Layering costs indirection and mapping. Keep a layer only when it reduces coupling, names policy, or makes a real change safer.
  • Logical layers can run in one deployable monolith; deployment tiers and microservices are separate decisions.
