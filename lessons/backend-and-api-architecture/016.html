Backend API Capstone: Design an Evolvable Service Boundary

By the end of this lesson, you will be able to...

  • design a small review-service boundary from client promises inward to use cases, persistence, and dependencies

  • walk one request and one list traversal through authentication, validation, domain rules, errors, transactions, and observability

  • defend an evolution plan with compatibility evidence, rollout steps, failure handling, and a review rubric

Idea in one sentence: An evolvable service boundary makes ownership, client-visible promises, internal workflow, and release evidence agree.

Core Insight

The course platform has five consumers of review data: a web app, a mobile app, a moderation console, an analytics pipeline, and a partner SDK. Reviews began as rows in a monolith. The product now needs moderation states, richer ratings, and a generated client. The team proposes a review-service.

At first, the task looks like deployment work: move the table and expose a few endpoints. That model is attractive because the box is easy to draw. It fails when the first client asks a question the box cannot answer: Who owns enrollment eligibility? Is a duplicate review a 409 or an idempotent success? Can a mobile app keep its old rating field? What happens to a cursor issued before a release?

The capstone is a design review, not a code-generation exercise. We will make one boundary inspectable from the outside inward, then return outward to the promises and evidence that make it safe to evolve.

The Scenario

Our service manages a learner's review of a course. A learner may create one review when the enrollment system says the learner is eligible. The learner may edit or retract that review. Other users can list visible reviews. Moderators can later hide a review, but ordinary learners must not gain arbitrary access to moderator operations.

The service has two important clients today:

  1. Mobile app version 5.4 reads id, rating, comment, and created_at. It cannot receive a breaking SDK update for two weeks.
  2. The web app uses cursor pagination and displays a stable problem.type when a request fails.

The partner SDK is slower-moving than the web app. The analytics pipeline is an internal consumer, but it still depends on a documented export shape. These consumers make the boundary real: a response is not only what the server can produce; it is what another program has learned to rely on.

Constraints

Write these constraints down before choosing a framework or database. They are the tests for the design.

Constraint Consequence for the boundary
One review per learner and course The use case needs a domain rule and the database needs a unique guard
Enrollment is owned elsewhere The service reads an eligibility decision but does not own course or enrollment records
Mobile updates are slow Published response fields and error identifiers need compatibility protection
Reviews can be moderated Visibility is a state decision, not a query accidentally applied in one controller
Lists must remain traversable Sort, filter, cursor binding, and cursor lifetime are public behavior
Storage may change Clients must see DTOs, not table columns or ORM objects
Dependencies can be unavailable The service needs explicit failure categories and a safe retry policy

These constraints also expose what is outside scope. We are not designing identity, enrollment, search ranking, or an analytics warehouse. We are deciding how the review boundary asks those systems for facts and how it behaves when the facts are missing.

Design Goal

The design must answer five questions:

  1. What does the review boundary own?
  2. What can a client call and depend on?
  3. Where does each rule run during a request?
  4. Which state is durable, and who commits it?
  5. How do we detect a breaking change before a client discovers it?

A useful design is small enough to explain on a whiteboard and precise enough to test. It does not claim that one layering arrangement is universal. It chooses a boundary because these consumers update at different speeds and because review rules need one authoritative owner.

Proposed Model

The boundary owns review text, rating, review lifecycle, visibility policy, and the one-review-per-course rule. It references learner identity, course identity, and enrollment eligibility. It may call an enrollment capability or use a short-lived eligibility read model; either choice must name freshness and failure behavior.

The public surface is deliberately narrow:

POST   /courses/{course_id}/reviews       create the caller's review
GET    /courses/{course_id}/reviews       list visible reviews
GET    /courses/{course_id}/reviews/me    fetch the caller's review
PATCH  /courses/{course_id}/reviews/me    update the caller's review
DELETE /courses/{course_id}/reviews/me    retract the caller's review

The nested path says which course is in scope. The /me suffix says that ordinary learners operate on their own review. A moderation API can use a different surface later because its authorization and visibility rules are different. Keeping it separate prevents a learner endpoint from quietly becoming an administrative endpoint.

The request and response DTOs are public shapes, not domain entities:

{
  "rating": 5,
  "comment": "Clear, practical, and well structured."
}

{
  "id": "rev_901",
  "course_id": "42",
  "rating": 5,
  "comment": "Clear, practical, and well structured.",
  "created_at": "2026-06-15T10:03:21Z",
  "updated_at": "2026-06-15T10:03:21Z"
}

The adapter validates the body and path. It takes user_id from authenticated context rather than trusting a body field. It then builds an application command:

CreateReviewCommand
  user_id: trusted authentication context
  course_id: validated path parameter
  rating: validated request value
  comment: validated request value
  request_id: boundary middleware value

The use case receives meaning, not HTTP objects. The repository receives persistence intent, not a raw request. The response mapper decides which durable fields become client-visible.

Walkthrough: Creating a Review

Trace POST /courses/42/reviews for learner u-17 with rating 5. The trace is synthetic, but every state transition is explicit.

1. request_id=req-81 enters the HTTP adapter
2. authentication resolves user_id=u-17
3. validation accepts course_id=42, rating=5, comment length=38
4. enrollment capability returns eligible=true
5. repository attempts review (u-17, 42)
6. unique constraint confirms no existing review
7. unit of work commits review id=rev_901
8. response mapper returns 201 and ReviewResponse
9. trace records dependency timings and release version

Why this order? Authentication must happen before the command receives identity. Validation prevents malformed input from entering the use case. Enrollment is a business precondition, so the use case owns the decision even though another system supplies evidence. The database constraint is the final concurrency guard; a preliminary “does one exist?” check cannot protect two simultaneous requests.

The use case can therefore express product meaning in a transport-neutral form:

def create_review(command):
    if not enrollment_policy.can_review(command.user_id, command.course_id):
        raise ReviewRejected("not_enrolled")
    try:
        review = reviews.create_once(
            user_id=command.user_id,
            course_id=command.course_id,
            rating=command.rating,
            comment=command.comment,
        )
        unit_of_work.commit()
        return review
    except DuplicateReview:
        raise ReviewRejected("review_already_exists")

The adapter translates the result into the public failure contract:

Internal outcome HTTP response Stable problem type
malformed body or path 400 invalid-request
no valid credentials 401 unauthenticated
enrollment says no 403 review-not-allowed
course capability says absent 404 course-not-found
unique constraint fires 409 review-already-exists
enrollment or database timeout 503 dependency-unavailable

The table separates meaning from implementation detail. A raw SQL exception is not a client contract. The response may include a request ID for support, while internal stack traces stay in protected telemetry.

Walkthrough: Listing Reviews

Now trace a different workflow:

GET /courses/42/reviews?sort=newest&rating=5&limit=2&cursor=<opaque>

The repository orders by (created_at, id), where id breaks ties. The cursor encodes the last pair plus the filter and sort context. The token is opaque to clients. The response makes the next decision visible:

{
  "data": [
    {"id": "rev_901", "rating": 5, "created_at": "2026-06-15T10:03:21Z"},
    {"id": "rev_877", "rating": 5, "created_at": "2026-06-14T08:11:03Z"}
  ],
  "page": {"limit": 2, "next_cursor": "opaque-token", "has_more": true}
}

The service validates that the cursor belongs to sort=newest, rating=5, and the promised lifetime. Reusing it with rating=1 should return a clear invalid-cursor problem, not silently start a different traversal. If a review becomes hidden between requests, the next page may contain fewer visible items; the contract should promise stable ordering and cursor behavior, not an impossible frozen snapshot.

The list design also states what it does not promise. It does not promise exact totals unless the product is willing to pay the query and consistency cost. It does not expose database offsets. It does not allow a client to manufacture a cursor. These boundaries reduce accidental coupling.

Failure Review

A design is incomplete until it explains how it fails. Consider these cases:

Failure What the user should see What operators need
enrollment timeout retryable 503 dependency-unavailable dependency name, timeout, trace ID
duplicate simultaneous creates one 409 review-already-exists unique-constraint event and request IDs
malformed cursor 400 invalid-cursor filter/sort validation result, not token contents
database commit timeout retry guidance without claiming success transaction outcome and idempotency assessment
moderation read is stale review may remain visible briefly freshness metric and visibility decision timestamp
unknown client error type generic safe message stable problem type and release version

The commit timeout needs special care. If the client retries immediately, the first transaction may have committed even though the response was lost. A production design can add an idempotency key for create, or document that a retry may produce 409. The choice depends on client behavior and storage cost. The important point is to decide it explicitly rather than promise “exactly once” from an ordinary HTTP retry.

Observability follows the same lifecycle as the request. Record request ID, trace ID, endpoint, authenticated principal class, validation result, enrollment latency, repository latency, commit outcome, response status, and release version. Do not record review text or tokens in logs by default. Metrics should distinguish client mistakes, rejected business actions, dependency failures, and server defects; one request_failed counter hides the decision needed during an incident.

Trade-offs

The proposed boundary buys ownership clarity, but it creates coordination costs.

Synchronous enrollment check. A live check gives fresh eligibility but adds latency and a dependency failure mode. A snapshot lowers request latency but introduces staleness. Choose the live check when permission can change quickly; choose a bounded snapshot when the product can tolerate a stated freshness window.

One service versus a shared review library. A service owns a deployable contract and data lifecycle. A library is cheaper when one team controls every caller, but it cannot protect independently deployed clients. The five consumers and slow mobile release make a contract-bearing service useful here.

Cursor pagination versus offsets. Offsets are easy to inspect but drift when reviews are inserted or hidden. A cursor with a stable sort key is harder to implement and debug, yet it makes traversal behavior explicit for a changing list.

Strict compatibility versus release speed. OpenAPI diffs, consumer contracts, generated SDK checks, and semantic review slow a release. They are justified because mobile and partner clients cannot update together. An internal, co-deployed endpoint could use a lighter gate. The policy should follow consumer update speed and failure cost, not fashion.

Separate moderation surface versus conditional learner endpoints. Separate endpoints duplicate some plumbing, but they make authorization and visibility rules easier to audit. A single endpoint with a growing set of role checks may be smaller initially and harder to reason about later.

Evidence and Readiness

The design is ready for implementation only when its promises have owners and tests. Use this evidence map:

Promise or decision Evidence before release Owner
endpoint paths, parameters, schemas, statuses OpenAPI document and structural diff API owner
learner can create only when eligible use-case tests plus enrollment contract review team + enrollment owner
duplicate rule holds under concurrency integration test with unique constraint persistence owner
list traversal remains stable cursor examples with inserts, filters, and ties API owner
old clients still parse responses consumer contracts and generated SDK compile/smoke test client owners
semantic meaning stays stable examples and human review of sort, totals, and errors product/API owner
failures are diagnosable trace fields, metrics, redacted logs, runbook check operations owner

OpenAPI supplies a machine-readable surface for paths, operations, parameters, schemas, and responses. Consumer-driven contracts add evidence from the clients’ actual requests and response subsets. A compatibility gate should compare both with the last released version. A passing provider test alone is not readiness evidence for an old mobile app.

Use a staged rollout for a breaking product idea such as richer ratings:

1. Add optional rating_details while keeping integer rating.
2. Publish the schema and SDK with compatibility checks.
3. Migrate mobile, web, and partner consumers.
4. Measure old-field usage and announce deprecation.
5. Remove the old field only after the support window and approval.

This plan keeps the public promise while allowing the model to grow. If additive evolution cannot represent the new meaning, publish a versioned path and run both versions during migration. Rollback must include the contract decision, not only the binary deployment: restoring code does not restore a client that already generated a new SDK.

Final Challenge

Design a boundary for a nearby domain: comments on a document, reservations for a room, or alerts for a monitoring service. Submit a one-page review record with:

  1. the resource and the state your boundary owns;
  2. two facts it references but does not own;
  3. three public operations and their success and failure shapes;
  4. one request trace with at least four intermediate states;
  5. one concurrency or dependency failure and its safe response;
  6. one list or search promise, including what the cursor or filter means;
  7. one future change and the evidence that would allow, warn, version, or block it;
  8. the rollout, deprecation, or rollback path and named owners.

A strong submission is not the one with the most endpoints. It names ownership precisely, keeps transport and domain meaning separate, makes a failure observable, and ties every important promise to evidence. If a choice depends on freshness, client update speed, or operational cost, state that constraint instead of presenting the choice as a universal rule.

Key Takeaways

  • A service boundary is an ownership and promise system, not simply a deployed process or a table moved behind a new URL.
  • Start with client-visible resources, DTOs, statuses, and list behavior; then trace those promises inward through auth, validation, use cases, repositories, and transactions.
  • Concurrency guards, dependency failures, semantic errors, and observability are part of the design because clients and operators experience them at the boundary.
  • Evolvability requires evidence: schema diffs, consumer contracts, generated-client checks, semantic review, and an explicit migration or rollback path.
