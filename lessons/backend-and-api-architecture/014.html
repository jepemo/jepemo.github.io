Pagination, Filtering, Sorting, and List API Semantics

By the end of this lesson, you will be able to...

  • define a list contract that states eligibility, filters, order, continuation, and count semantics

  • predict gaps and duplicates when a collection changes during offset or cursor traversal

  • choose a pagination strategy from client needs, stability requirements, and query cost

Idea in one sentence: A list endpoint is a contract for traversing a changing collection, so its cursor, filters, ordering, and totals must describe what the client can safely assume.

Core Insight

The course page shows reviews with:

GET /courses/42/reviews?sort=newest&limit=20

With a few rows, a page number feels like the whole problem. The product grows. New reviews arrive while a phone is scrolling. Moderation hides a review. A partner asks for five-star reviews. Product adds a most_helpful sort. The endpoint still returns an array, but the client now needs a reliable answer to a harder question: “Where do I continue in this changing set?”

The tempting model is pagination as presentation: offset, page size, next button. That model works for a small, mostly static administrative table. It breaks when inserts or removals shift positions, when the sort is not deterministic, or when a cursor is reused with different filters. The stronger model treats list behavior as a public traversal contract.

The List Contract

For GET /courses/{course_id}/reviews, decide these properties before choosing query syntax:

  • Which reviews are eligible? Published only, or pending moderation too?
  • Which filters are supported, and how are invalid combinations rejected?
  • Which sort values exist, and is each order deterministic?
  • How does the client request the next slice?
  • Does the response promise an exact total, an estimate, or no total?
  • What can change between two requests, and can the client see duplicates or gaps?

One possible response is:

{
  "data": [
    {"id": "rev_901", "rating": 5, "created_at": "2026-06-15T10:03:21Z"}
  ],
  "page": {
    "limit": 20,
    "next_cursor": "opaque-token",
    "has_more": true
  }
}

The names are illustrative. The important promise is that next_cursor is evidence from the server: “continue this same traversal after this position.” The client should treat it as opaque. A cursor can encode a timestamp, a unique id, a filter fingerprint, a sort version, or a signed expiry without exposing those implementation choices.

The Initial Model: Offset as a Page Number

Offset pagination says:

GET /courses/42/reviews?limit=20&offset=40

“Skip 40 matching rows and return the next 20.” It is easy to teach, easy to jump to page 3, and often sufficient for a small, stable list.

Now trace a changing collection. At time t0, page 1 returns rows A through T. Before the client requests offset 20, three new reviews U, V, and W arrive at the top. The second request skips the first 20 rows of the new ordering. Rows R, S, and T may appear again, while three older rows move beyond the window. If three rows are deleted instead, the client may skip rows it never saw. The initial model fails because an offset counts positions, not identities.

Large offsets can also cost more work. Depending on the database and indexes, the engine may scan or discard many matching rows before producing the requested window. The exact cost is implementation-dependent; the architectural signal is that “page 5000” can require walking through earlier positions.

Cursor Pagination as a Continuation Point

Cursor pagination replaces a count with a position:

GET /courses/42/reviews?sort=newest&limit=20
GET /courses/42/reviews?sort=newest&limit=20&cursor=<opaque-token>

Suppose the first page ends at (created_at=2026-06-15T10:03:21Z, id=rev_901). Internally, the next query can request rows after that tuple in descending order:

SELECT id, rating, created_at
FROM reviews
WHERE course_id = '42'
  AND (created_at, id) < ('2026-06-15T10:03:21Z', 'rev_901')
ORDER BY created_at DESC, id DESC
LIMIT 20;

The id tie-breaker matters. Two reviews can share the same timestamp. Ordering only by created_at leaves their relative order unspecified, so a boundary can be ambiguous. A deterministic tie-breaker makes “after this item” meaningful even when visible sort values match.

Cursor pagination is not a snapshot. A new review inserted above the cursor may not appear in the current traversal, and a review removed after page 1 cannot be returned on page 2. That is often acceptable for feeds and infinite scroll. If a client needs a frozen report, the API must provide a snapshot or export job rather than implying that a normal cursor freezes time.

Filters and Sorts Travel With the Cursor

The cursor belongs to one query context. If the first request is:

GET /courses/42/reviews?rating=5&sort=newest&limit=20

the next cursor must continue the rating=5, newest traversal. Reusing it with rating=1 or sort=oldest changes the meaning of the position. The server can encode a signed fingerprint of the filter and sort, or reject a mismatched combination with a documented 400 problem.

Sorting choices carry their own boundary. newest can use (created_at, id). most_helpful may depend on votes that change after every request. Items can move between pages as votes change. That behavior may be fine, but the contract should say whether the order is best-effort or snapshot-like. A sort enum is not just a query convenience; it is a promise about how the server orders the traversal.

Filters also need limits. A free-form filter language can create unbounded query cost and ambiguous combinations. A short allowlist such as rating=1..5, status=published, and a few documented sorts gives clients predictable behavior and lets the backend index the important paths.

Totals, Limits, and OpenAPI Evidence

An exact total can be expensive on a large filtered collection and can become stale as soon as a row changes. An administrative report may need an exact count and accept the cost. An infinite-scroll client may need only has_more. An analytics screen may accept an estimate. Do not call every value total without defining whether it is exact, approximate, cached, or scoped to the current filter.

OpenAPI can make the structural part of this contract visible:

parameters:
  - name: rating
    in: query
    schema: {type: integer, minimum: 1, maximum: 5}
  - name: sort
    in: query
    schema:
      type: string
      enum: [newest, oldest, most_helpful]
  - name: cursor
    in: query
    schema: {type: string}
responses:
  "200":
    description: Page of reviews

The schema shows accepted parameters, enum values, and response fields. Prose or examples still need to explain that cursors are opaque, which filters bind them, and what has_more and totals mean. A machine-checkable shape is necessary evidence, but it cannot by itself guarantee stable database ordering.

Worked Comparison

Use the same review collection and change one constraint at a time:

Situation Offset behavior Cursor behavior Design judgment
Small admin table, users jump to page 4 simple and understandable awkward for random jumps offset is reasonable
New rows arrive at the top during scrolling duplicates or gaps possible continues after a known tuple cursor usually fits better
Sort value has ties needs a deterministic ORDER BY too needs a unique tie-breaker both require stable order
User changes filter mid-traversal offset must restart explicitly old cursor must be rejected or restarted bind traversal to query context
Product needs exact total count query may be acceptable count is still separate from cursor document cost and freshness

This comparison avoids a slogan such as “cursor is always better.” The choice is a design decision under client behavior, mutation rate, query cost, and navigation needs.

Failure Modes and Signals

Gaps or duplicates. A changing list plus offset produces repeated or skipped rows. The signal is a client test that inserts or removes rows between page requests. Use a cursor or document that the view is not stable.

Non-deterministic order. ORDER BY created_at DESC leaves ties unresolved. The signal is flaky page boundaries. Add a unique tie-breaker and test equal timestamps.

Leaky cursor. The API returns a raw database id or timestamp and clients start constructing tokens. The signal is a client depending on storage columns. Make the token opaque, and sign or encode internal state as needed.

Filter/cursor mismatch. A cursor from five-star reviews is accepted for one-star reviews. The signal is items from the wrong set or a confusing empty page. Bind a query fingerprint to the cursor or reject the combination.

False snapshot promise. A “most helpful” traversal is documented as fixed while votes reorder rows. The signal is the same item moving across pages. State the consistency level or provide a real snapshot mechanism.

Accidental total. A total field is exact on one endpoint and cached on another. The signal is UI text that implies precision the backend cannot guarantee. Name estimated_total, omit it, or document exactness and scope.

Trade-off: Navigation, Stability, and Cost

Offset pagination buys page-number navigation and a simple mental model. It costs stability under inserts and can cost more work for deep offsets. Cursor pagination buys a meaningful continuation point and often better behavior for changing feeds. It costs a more precise contract, makes random page jumps harder, and usually requires indexes aligned with filters and order.

Neither strategy prevents all inconsistency. A cursor does not freeze data, and an offset can be perfectly adequate for a static report. Choose from named constraints: mutation rate, client navigation, required freshness, query cost, and whether a snapshot is necessary. The signal that the current choice is failing is visible behavior—duplicates, gaps, unstable ordering, slow deep pages, or clients guessing what a token means.

Check Your Understanding

Check 1: The client reads page 1, three new reviews arrive at the top, then it requests offset 20. What can happen?

Think first, then reveal.

Answer: The boundary shifted. The client can repeat rows from page 1 and skip older rows. Offset counts positions in the new result, not the identity of the last item seen.

Check 2: Two reviews share the same created_at. What must a stable newest cursor include?

Think first, then reveal.

Answer: A deterministic unique tie-breaker, such as id, in addition to the timestamp. Otherwise “after this item” is ambiguous.

Check 3: A cursor created for rating=5&sort=newest is sent with rating=1. What should the server do?

Think first, then reveal.

Answer: Reject the mismatch with a documented client error or verify a signed query fingerprint and restart the traversal. It should not silently treat the cursor as universal.

Practice: Design the Review List Contract

Design the smallest contract for GET /courses/42/reviews used by a mobile infinite-scroll client. Choose eligible rows, filters, one default sort, a tie-breaker, cursor fields, a limit policy, and whether to expose a total.

A good answer should:

  • state how the server orders rows and why the order is deterministic;
  • treat the cursor as opaque and bind it to filter/sort context;
  • explain what happens when a review is inserted or moderated between requests;
  • choose exact, estimated, or no total with a cost/freshness reason;
  • include at least one invalid-cursor or unsupported-filter response;
  • name the trade-off between smooth traversal, random page navigation, and query cost.

Key Takeaways

  • A list endpoint promises how a client traverses a changing collection, not merely that it returns an array.
  • Offset is convenient for stable, jumpable lists; cursor is often a better continuation contract for frequently changing feeds.
  • Deterministic ordering needs a unique tie-breaker, and a cursor must stay bound to its filter and sort context.
  • Totals, limits, token opacity, mutation behavior, and invalid-query errors are public semantics that need explicit documentation and tests.
