DTOs, Entities, and Data Mapping

By the end of this lesson, you will be able to...

  • trace one review request through request, command, entity, row, and response shapes

  • choose an allowlisted mapping that prevents over-posting and response leakage

  • explain when the extra mapping cost is justified and when a shared shape is acceptable

Idea in one sentence: A backend becomes easier to change when every boundary receives the smallest shape that matches its trust, business, storage, or public-contract job.

Core Insight

Alice submits a review to a course:

POST /courses/417/reviews
{"rating": 5, "comment": "Clear and practical."}

The endpoint must do more than copy JSON into a table. It must identify Alice, attach course 417, enforce the review policy, generate an id and timestamp, persist moderation state, and return only fields the client is allowed to see. The request body, the use case, the database row, and the response therefore answer different questions.

The tempting first model is one object called Review:

JSON -> Review object -> database -> JSON

That model is reasonable for a private prototype. It starts to fail when a client can send moderation_status, when a database column is renamed, or when a mobile app begins depending on an internal field. The visible bug is often a leaked or rejected field. The deeper problem is that one shape has been asked to carry four different responsibilities.

The Small Situation and Its Initial Model

Keep Alice's request fixed while we inspect each boundary. The client knows the rating and comment. It does not know the authenticated user id chosen by the server, the database-generated review id, or an internal spam score. The route knows the course id. Authentication knows who is calling. The use case knows whether a review is allowed. The database knows how to store a row and enforce durable constraints.

If a handler accepts a dictionary and passes it to an ORM constructor, every key becomes a candidate for mutation. A malicious or merely outdated client might send:

{
  "rating": 5,
  "comment": "Useful",
  "reviewer_id": "admin",
  "moderation_status": "approved",
  "internal_spam_score": 0
}

The initial model treats all keys as equally trustworthy. The observation that changes the model is simple: those fields came from different authorities. A request shape must allowlist client-controlled fields instead of inheriting every field from the internal model. This is the same mass-assignment pressure described by OWASP: bind only fields that are safe for the caller to set. A DTO is useful here because its field list makes that decision visible.

Five Shapes, Five Jobs

The track blueprint asks us to trace five shapes. They are teaching categories, not a requirement that every codebase create five classes.

Shape Who supplies it? What it may contain What it must not decide
Request DTO HTTP client, after parsing rating, comment caller identity, ownership, moderation, generated values
Application command handler plus trusted context user id, course id, accepted values database column names or HTTP objects
Domain entity use case and domain rules identity, invariants, review state, behavior JSON naming or persistence mechanics
Persistence row/model repository and database primary/foreign keys, storage timestamps, indexes, audit columns public exposure policy
Response DTO response mapper stable public fields and display values internal workflow or secrets

In plain English, mapping is a controlled handoff. In this scenario, it is the explicit construction of the next shape from the previous shape plus facts owned by the next boundary. The technical names are DTO (data transfer object), entity (an object with identity and business meaning), and mapper (the code that performs the handoff).

The Mechanism Step by Step

1. Parse into a request DTO

The edge parses JSON and validates the request contract. A Pydantic-like model can reject a missing rating or wrong type and can be configured so unexpected fields do not silently become application input. The result is still request data; validation does not make Alice authorized.

class CreateReviewRequest:
    rating: int
    comment: str

request_dto = CreateReviewRequest(rating=5, comment="Clear and practical.")

The field list is an allowlist. reviewer_id, course_id, created_at, and moderation fields are absent on purpose. If course_id is taken from the route, accepting a second body copy would create an avoidable conflict.

2. Add trusted context to an application command

The handler combines the validated values with facts established elsewhere:

class CreateReviewCommand:
    user_id: str
    course_id: str
    rating: int
    comment: str

command = CreateReviewCommand(
    user_id=auth_context.user_id,       # Alice, established by authentication
    course_id=http_request.path_params["course_id"],  # 417, from the route
    rating=request_dto.rating,
    comment=request_dto.comment,
)

The command is meaningful to the use case: “Alice is attempting to review course 417.” It does not carry a framework request, headers, or raw JSON. This reduces the chance that domain code accidentally reads transport-specific details. It also makes a second entry point, such as a moderation worker, able to call the use case with the same business input.

3. Construct an entity after domain decisions

The use case loads the course and enrollment facts, then applies policy. Suppose Alice is enrolled and reviews are open. The use case creates an internal entity:

review = Review(
    id="rv_8f2",                 # generated by the backend; illustrative id
    course_id=command.course_id,
    reviewer_id=command.user_id,
    rating=command.rating,
    comment=command.comment.strip(),
    moderation_status="pending",
    created_at=clock.now(),
)

The id and timestamp above are illustrative values, not an observed production result. The entity can enforce behavior such as “rating must be between 1 and 5” or “a submitted review cannot be edited after moderation.” Its identity lets the use case distinguish this review from another review with the same text. An entity is not merely a bag of fields, although a small application may represent it with a dataclass or another simple record.

4. Map the entity to a persistence row

The repository translates business names to storage names. A row may use snake-case columns, foreign keys, a database timestamp, and an audit version:

row = ReviewRow(
    review_id=review.id,
    course_id=review.course_id,
    reviewer_id=review.reviewer_id,
    rating=review.rating,
    comment_text=review.comment,
    moderation_state=review.moderation_status,
    created_at_utc=review.created_at,
    row_version=1,
)
reviews.insert(row)
uow.commit()

An ORM can map a Python class to a table, but the ORM mapping does not define the public API. SQLAlchemy’s documentation, for example, describes mapped classes as classes associated with table metadata and a mapper; that association is a persistence concern. Whether the mapped class is also used as a domain entity is a local design choice, not a promise made by the ORM.

5. Map the committed result to a response DTO

After commit, the response mapper chooses the public contract:

class ReviewResponse:
    id: str
    rating: int
    comment: str
    reviewer_name: str
    created_at: str

response = ReviewResponse(
    id=review.id,
    rating=review.rating,
    comment=review.comment,
    reviewer_name="Alice",              # display projection, not reviewer_id
    created_at=review.created_at.isoformat(),
)

moderation_status, internal_spam_score, row_version, and database column names do not cross this boundary. If version 2 wants a nested reviewer object, it can use a second mapper while the internal entity and row remain unchanged:

Review entity -> v1 response mapper -> {reviewerName: "Alice"}
             -> v2 response mapper -> {reviewer: {displayName: "Alice"}}

The mapper is not security by itself. A bug in the mapper can still expose data, and authorization must happen before mapping. The mapper does make the exposure rule reviewable and testable.

A Worked Trace With Intermediate State

Read the same request as a state table. Each row records what changed and what authority was added.

Step Current shape/state New fact or transformation Fields still excluded
0 raw JSON and route bytes parsed; route says course 417 identity, id, moderation
1 request DTO rating 5, trimmed comment accepted user id, internal fields
2 command authentication adds Alice; route adds 417 storage names, response display fields
3 entity policy permits review; id, timestamp, pending state created JSON aliases, row version
4 row/model repository chooses column names; transaction commits public-only presentation fields
5 response DTO mapper exposes id, rating, comment, display name, ISO timestamp moderation score, audit metadata

This table prevents a common mistake: saying “the object is validated” without asking which properties were validated and who supplied them. At step 1, the rating has a structural and domain range. At step 2, Alice’s identity is trusted for this request, but enrollment still belongs to the use case. At step 4, the database is the authority for durable uniqueness and foreign-key checks. At step 5, the response is a projection, not a copy.

Where the Mapping Model Breaks

Over-posting. A broad binder copies every JSON key into an entity. The signal is a client-controlled field changing ownership, moderation, or audit state. Fix the request DTO with an allowlist and add a test that sends an unexpected field.

Response leakage. A handler returns an ORM object directly. The signal is a new internal column appearing in API output or a relationship causing an unexpectedly large query. Fix the response mapper and test the exact public field set.

Lossy mapping. The entity contains information needed for a later decision, but a mapper drops it before that decision runs. The signal is a downstream rule trying to recover data from a display string. Map to an application command before domain work, and map to a response only after the decision is complete.

Stale mapper. A field is renamed internally, but one mapper still reads the old name. The signal is a runtime attribute error or a response silently showing a default. Keep mapper tests close to the contract and fail loudly when a required source field is absent.

False equivalence. Two classes happen to contain the same fields today, so a developer treats them as interchangeable forever. Equality of fields is an observation about this version, not proof that the audiences, lifecycles, or authorities are equal.

Cost, Limits, and Signals

Explicit mapping buys allowlisted input, stable output, clearer authority, and room for independent evolution. The trade-off is additional code, tests, allocations, and sometimes an extra query for display data such as reviewer_name. A mapper also cannot make a transaction atomic, authorize a caller, or repair an incorrect domain rule.

Use one shared shape when the boundary is genuinely private, short-lived, and governed by the same owner; the input and output fields have the same trust and lifecycle; and there is no sensitive or generated state. Use separate shapes when a public or versioned API, multiple clients, security-sensitive fields, independent persistence evolution, or distinct domain behavior creates change pressure.

The useful signal is not “how many classes do we have?” It is a boundary mismatch: a client can set a server-owned field, a schema change unexpectedly breaks a client, a database concern appears in domain code, or a response exposes more than the product promise. Those signals justify another shape. If no mismatch exists, another wrapper may be ceremony.

Check Your Understanding

Check 1: The client sends {"rating": 4, "comment": "Good", "moderation_status": "approved"}. Which step should reject or ignore moderation_status?

Think first, then reveal.

Answer: The request boundary should reject or ignore it according to the API’s unknown-field policy. The request DTO allowlists client-controlled fields; the entity must not be populated from that key.

Check 2: The course id appears both in the URL (417) and in the body (999). Which value should the command use?

Think first, then reveal.

Answer: Use the route value if the endpoint’s contract identifies the resource in the path, and do not accept a competing body field. One authoritative source prevents ambiguous mapping.

Check 3: The database adds moderation_state tomorrow. What should a stable v1 client observe?

Think first, then reveal.

Answer: Nothing unless the public contract intentionally adds that field. The row and entity may change while the v1 response mapper keeps its allowlisted output.

Trace It Yourself: Product Feedback

A product team adds a second endpoint for feedback imported from a partner file. The file contains external_author, rating, comment, and received_at; it does not contain an authenticated user id. Trace the import through a safe design.

A good answer should mention:

  • an import DTO that allowlists file fields and records the source format;
  • an application command that adds a trusted partner id and a course id resolved by the import workflow;
  • an entity that generates the local id, normalizes the comment, and chooses a moderation state;
  • a persistence row that uses local foreign keys and transaction-owned timestamps;
  • a response or report DTO that exposes only fields promised to the consuming product;
  • a decision about whether external_author is public display data or internal provenance, with the reason stated.

If the importer and HTTP endpoint truly share the same command after their separate input mappings, that is a useful reuse point. Reusing the command does not require reusing the request DTO or the response DTO.

Key Takeaways

  • A request DTO, command, entity, row, and response DTO may describe the same review while serving different authorities and lifecycles.
  • Mapping is an explicit trust and contract decision: add facts owned by the next boundary and exclude fields that boundary must not control or expose.
  • An ORM mapping can be useful for persistence without becoming a public API shape; response serialization should be deliberate and allowlisted.
  • Separate shapes cost code and tests, so introduce them when mismatch signals—over-posting, leakage, coupling, or independent evolution—make the boundary valuable.
