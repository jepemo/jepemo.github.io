Authentication, Authorization, and API Trust

By the end of this lesson, you will be able to...

  • separate authentication, authorization, and trust transport in an API request

  • evaluate a permission decision using principal, action, resource, and context

  • choose where an API should enforce and observe resource, field, and service-to-service access rules

Idea in one sentence: A valid credential identifies a principal, but the API earns trust only when it separately decides what that principal may do to which resource under the current conditions.

Core Insight

The learning platform has the REST and GraphQL boundaries from the previous lessons. Now three requests arrive:

GET   /courses/42/progress        student:u-17
PATCH /courses/42                 instructor:u-42
POST  /admin/reindex-search       admin:u-1

All three requests carry credentials that the identity system accepts. It would be easy to treat “token valid” as “request allowed.” That shortcut is attractive because one check produces a clear boolean. It also gives the wrong answer. The student may read only their own progress. The instructor may edit only courses they own or manage. The administrator may run the reindex operation, perhaps with an audit record or stronger verification.

The pressure is therefore not simply “add login.” The backend must turn an external claim about a caller into a decision about a specific action and target. GraphQL makes the pressure sharper: a caller may be allowed to select a course title but not billing state or another learner's progress. An internal worker is also a caller, even when it runs inside the same network.

The useful correction is a chain, not a single gate:

credential or session
  -> verified principal
  -> policy decision for action + resource + context
  -> allowed, denied, audited, or challenged operation

The Promise We Need to Keep

An API trust boundary should make this promise:

The service will identify who or what is acting,
check whether that principal may perform this action on this resource,
and carry only the trust information that the next boundary can verify.

This promise has three distinct jobs.

Authentication answers: “Who is this request acting as?” The result is a principal such as student:u-17, instructor:u-42, service:grading-worker, or an external integration.

Authorization answers: “May this principal perform this action on this resource in this context?” A role, scope, or claim can contribute evidence, but it is not the entire decision.

Trust transport answers: “How did the evidence cross into this service?” A session cookie, signed token, mTLS identity, or delegated access token has an issuer, audience, lifetime, and validation procedure. The service must know which of those facts it can rely on.

These are teaching distinctions that keep the design inspectable. A real deployment may combine the steps in middleware, a gateway, or a policy service. Combining code paths does not make the questions interchangeable.

The Naive Design: Valid Token Means Valid Action

Start with a convenient middleware rule:

if verify_token(request.authorization):
    return next_handler(request)
return unauthorized()

This rule can be useful as an authentication stage. It is not a complete authorization policy. If the handler trusts a client-supplied user_id, the student can ask for somebody else's progress. If it checks only role == "instructor", any instructor may edit any course. If a GraphQL resolver returns every field from a database object, a support-only billing value can leak through a query the UI never displays.

The initial model works only under a narrow assumption: every valid principal has the same authority over every resource. Most products do not have that property. The first request that names another user's record, another tenant, or a more sensitive field breaks it.

A Better Model: Principal, Action, Resource, Context

Write each decision as a four-part question:

Part Question Example
Principal Who or what is acting? student:u-17
Action What is it trying to do? read or edit
Resource Which object or field is targeted? progress for u-17 in course 42
Context Which conditions change the answer? owner, tenant, scope, time, risk

Plain meaning: identity names the actor; authorization compares that actor with a target and an allowed operation.

In our scenario, the resulting policy questions are:

Request Policy question Decision for this example
student reads progress Does the progress record belong to student:u-17? allow own record; deny another learner's record
instructor edits course Does instructor:u-42 own or manage course 42? allow assigned courses only
admin reindexes search Does admin:u-1 have search:reindex in this environment? allow, audit, and possibly require step-up proof

The resource is not always a whole row. In the GraphQL lesson, Course.billingState is a resource-sensitive field. In a multi-tenant service, the tenant can be part of the resource context. For a service account, the principal may be a workload identity rather than a human.

Worked Path: One Request Across the Boundary

Trace the student request, using illustrative values:

GET /courses/42/progress
Authorization: Bearer <access-token>

Step 1 — receive evidence. The API extracts the credential. It does not yet know whether the credential is genuine, intended for this service, or still valid.

Step 2 — establish a principal. The verifier checks the issuer, signature or session lookup, audience, expiry, and any required token type. The result is principal=student:u-17. This is an authentication result. The server should not accept user_id=u-99 from the request body as a replacement for that principal.

Step 3 — resolve the target. The route identifies course 42 and the application loads the progress record for the principal. The target is now “progress owned by u-17 for course 42,” not “any progress row the caller can name.”

Step 4 — evaluate policy. The authorization rule checks principal, action read, resource ownership, and tenant context. If the record belongs to another learner, the policy denies even though the credential remains valid.

Step 5 — produce evidence. The service returns the permitted representation and records a decision outcome. Logs should identify a request or trace ID, principal class, resource class, action, and result without copying secrets or sensitive token contents.

The intermediate states matter. A request can be authenticated and still be denied. It can be authorized for one resource and denied for another. It can be allowed but require an audit event. A single 401/403 choice does not replace the internal policy model; it only translates an outcome for the client.

Carrying Trust: Sessions, JWTs, OAuth, and OIDC

The transport mechanism answers different questions from the policy decision.

  • Session cookie: the client presents a handle; the service looks up server-held session state. Central state can simplify revocation and policy changes, but the service must protect the browser session and its request context.
  • JSON Web Token (JWT): the client presents signed claims. Local verification can avoid a lookup, but lifetime, key rotation, audience, and revocation strategy need explicit decisions. A claim is evidence, not automatic permission.
  • OAuth 2.0: a delegation framework. A client can obtain an access token with a scope and lifetime to call a protected resource on behalf of a resource owner or on its own behalf. The token is not the user's password and the resource server still validates it.
  • OpenID Connect (OIDC): an identity layer built on OAuth 2.0. It helps a client learn who authenticated; it does not turn an ID token into a universal API access token.

The practical review questions are stable across mechanisms:

Who issued this credential?
Who is its audience?
What action or scope does it represent?
When does it expire, and how can it be revoked or rotated?
Which resource-level decision must this API still make?

OAuth's roles make the boundary visible: an authorization server issues access tokens, a client presents them, and a resource server protects the resource. Current security guidance updates some older OAuth deployment advice, so do not choose a grant by memorizing a list of flows. Name the client type, threat model, redirect behavior, and revocation needs.

Design Alternatives and Trade-offs

Choice Helps with Costs or risks
server-managed session central revocation and mutable policy session storage, browser controls, lookup dependency
self-contained signed token local validation and distributed calls stale claims, key rotation, revocation complexity
delegated OAuth access limited third-party or service access more roles, scopes, and trust relationships to audit
centralized policy service consistent decisions across APIs network dependency and policy-service availability

The trade-off is distribution and convenience versus control and freshness. Local token verification can reduce a dependency, but a token may outlive a permission change. Central sessions or policy checks improve revocation visibility, but add state and latency. A good choice depends on browser behavior, service topology, change frequency, and the cost of an incorrect allow decision.

No choice makes authorization disappear. A gateway may reject an invalid token, while the application still owns course ownership and field sensitivity. A policy service may return “allow,” while the application still has to load the correct resource and use the decision for the correct action.

Operational Consequences and Limits

Enforce the rule at the boundary that has enough knowledge. A UI can hide an edit button, but only the API or resolver can stop a direct call. A gateway can validate an issuer and audience, but it may not know course ownership. A repository can restrict a query by tenant, but it should not invent a product role.

Watch signals that reveal drift:

  • authentication failures by issuer, audience, or expiry reason
  • authorization denials by action, resource type, tenant, and policy version
  • unusual increases in service-account access or sensitive-field selection
  • audit records for privileged actions, without storing bearer secrets
  • policy-decision latency and failures when a central policy service is used

The boundary is also a privacy boundary. “Internal” is not a permission model: workers, cron jobs, and backend services need identities and least privilege. Logging every token or returning a detailed denial reason can create a new leak. Prefer stable request IDs and safe reason classes for operators, with minimal detail in public responses.

Design Review

Check 1: A request has a valid token for student:u-17 but asks for progress belonging to u-99. Which stage should reject it?

Think first, then reveal.

Answer: Authorization. Authentication already established the principal. The resource and ownership context make the read disallowed.

Check 2: An instructor role is present in a token, but course 42 belongs to another instructor. Is role == instructor enough?

Think first, then reveal.

Answer: No. The rule needs a relationship between this principal and this course, such as ownership or an explicit assignment.

Check 3: A gateway validates a JWT before forwarding a GraphQL query. May the resolver return billingState to every request that reaches it?

Think first, then reveal.

Answer: No. Token validation establishes trusted identity evidence. The resolver or policy layer still enforces field-level permission.

Practice: Build a Trust-Chain Matrix

The platform adds a grading worker, a support console, and a partner integration. The worker may write grades but must not read billing. Support may read billing but must not regrade. The partner may read course metadata for tenant t-9 only.

Design a small trust-chain matrix. For each caller, state:

  • principal and credential evidence
  • action and resource
  • context or scope that limits the decision
  • enforcement point and audit signal

A good answer should distinguish identity proof from permission, bind the partner to tenant t-9, deny the worker billing access even if its token is valid, and name an audit event for support reads or grading writes. It should also state what the credential verifier does not decide, such as course ownership or field sensitivity.

Key Takeaways

  • Authentication establishes a principal; authorization evaluates that principal against an action, resource, and context.
  • A session, JWT, OAuth token, or OIDC result transports evidence. None replaces resource ownership, tenant, scope, or field-level policy.
  • Gateways can verify shared credential facts, but the boundary with product knowledge must enforce the product rule.
  • Local verification, central sessions, delegated access, and policy services trade distribution and convenience against control, freshness, latency, and auditability.
  • Treat people, workers, integrations, and fields as explicit trust subjects, then observe both allowed and denied decisions safely.
