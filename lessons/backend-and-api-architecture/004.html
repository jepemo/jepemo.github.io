API Versioning and Contract Evolution

By the end of this lesson, you will be able to...

  • classify an API change by its effect on client assumptions, not only by its schema diff

  • design an expand–migrate–contract path for a breaking response change

  • choose a versioning or deprecation mechanism and define the evidence needed before removal

Idea in one sentence: API evolution is compatibility management: change the contract in a way that gives real consumers a safe path from the old promise to the new one.

Core Insight

The learning platform has shipped a mobile app, an instructor dashboard, and a partner integration. The course-progress response currently contains:

{
  "courseId": "course-42",
  "completed": false
}

The product now wants a percentage, the next lesson, and the time of the last activity. The clean-looking proposal is to rename completed to progress, publish /v2, and move on. The mobile app still parses completed tomorrow morning. The partner may release once a month. A version label does not tell either consumer how to migrate.

The real question is:

Which existing client assumption becomes unsafe if this change ships today?

That question shifts the design from a URL naming exercise to a compatibility investigation. An API contract includes field names and types, but also field meaning, requiredness, status codes, error shapes, pagination order, authorization behavior, and side effects. A change can preserve valid JSON while still causing a client to make the wrong decision.

The Promise We Need to Keep

The provider should promise a migration path, not permanent immobility:

Existing consumers keep the old meaning for a known window.
New consumers can adopt the better contract.
The provider can observe progress and remove old behavior only with evidence.

This promise has limits. A provider cannot control a partner's release calendar, and no telemetry sees an offline client. Compatibility is therefore both technical and social. The design must identify owners, communication channels, and a date or condition for the old behavior to end.

The Naive Design: Rename, Fork, and Hope

There are two tempting shortcuts.

First, change the response in place:

{
  "courseId": "course-42",
  "progress": {
    "completedPercent": 40,
    "nextLessonId": "lesson-8"
  }
}

The mobile client may fail to render because completed is missing. A strict decoder may reject the unknown shape. Even a tolerant client may silently treat missing data as false.

Second, create /v2 without a migration plan. That isolates the new behavior, but it also creates two contracts, two sets of docs and alerts, and a future question: when is /v1 safe to remove? A version boundary contains a breaking change; it does not pay the migration cost for you.

The initial model works only when the provider controls every consumer and can release them together. Independent clients break that assumption.

Classify the Change Before Choosing a Version

Use a compatibility ledger. The classifications below are teaching categories; a real decision still needs consumer tests.

Change Typical risk Why a parser or schema diff may miss it
Add an optional field often compatible if clients ignore unknown fields strict decoders or generated clients may reject it
Add a new endpoint usually isolated clients still need discovery and permission changes
Rename or remove a field shape-breaking old clients cannot read the promised name
Change a scalar into an object shape-breaking the JSON token type changes
Make an optional value required shape-breaking older clients may omit it or expect null
Add an enum value client-dependent closed-set parsers may reject an unknown value
Keep a field but change its meaning semantic-breaking parsing succeeds while product decisions become wrong
Change sorting, pagination, status, or side effects behavioral-breaking the schema can remain identical

The “usually” and “client-dependent” labels matter. Additive change is a useful default, not a guarantee. Check generated SDK behavior, deserializers, and consumer assumptions before calling it safe.

Worked Path: Evolve completed Safely

The following numbers and dates are illustrative. The provider wants to introduce the richer progress object while keeping old clients working.

1. Record the old promise

Old field: completed: boolean
Meaning: true only when the course is complete under the current product rule
Consumers: mobile app, instructor dashboard, partner integration

The meaning belongs in the ledger. It is not enough to write “field exists.” If the old field actually meant “at least one lesson completed,” changing that meaning is breaking even if its type remains boolean.

2. Expand the representation

For a compatibility window, return both fields:

{
  "courseId": "course-42",
  "completed": false,
  "progress": {
    "completedPercent": 40,
    "nextLessonId": "lesson-8",
    "lastActivityAt": "2026-06-12T09:30:00Z"
  }
}

The provider documents progress as the preferred field. It keeps completed computed from the same authoritative rule, rather than asking clients to infer one from the new object. The temporary duplication costs maintenance, but it preserves the old promise.

3. Migrate consumers

Week 0: publish the new field and migration example.
Week 1: update first-party clients and generated SDKs.
Week 2: notify the partner and provide a test environment.
Weeks 2–8: measure old-field reads and watch error reports.

The exact window depends on release cadence and risk. A daily internal client may need days; a regulated partner may need months. Communication is part of the contract because a client cannot migrate to a replacement it does not know exists.

4. Gather evidence

Instrument the old field or endpoint in a privacy-safe way. Useful data includes client identity, version, endpoint, and count of requests that still depend on the old behavior. Do not log tokens or sensitive progress values merely to count usage.

Telemetry is evidence of observed use, not proof that no unobserved client exists. Combine it with an inventory, partner confirmation, consumer-driven contract tests, and support-owner review.

5. Contract only when ready

When the agreed conditions hold—known consumers migrated, old usage below a stated threshold, and owners notified—the provider can remove completed or place it behind an explicit old version. Announce the removal and keep a rollback plan during the change.

The result is less clean during the window, but the transition is inspectable. The learner can point to the old promise, the new promise, the intermediate representation, and the evidence that justified removal.

Design Alternatives

Mechanism What it makes visible Cost or risk
additive evolution one contract can grow without a fork duplicated fields and client-dependent tolerance
path versioning (/v1, /v2) old and new boundaries are easy to address parallel docs, tests, fixes, and operations
header or media-type versioning one URL can negotiate representations behavior is less visible in links and tooling
GraphQL add-and-deprecate field-level replacement in a typed schema clients must consume deprecation signals and provider must measure usage
client or SDK capability gate known clients receive behavior they can handle conditional behavior grows if capabilities are not retired

Choose the smallest mechanism that can express the compatibility boundary. If a field can be added without changing old meaning, do that first. If pagination, authentication, error semantics, and response shapes must all change together, a new explicit version may be clearer than many hidden conditions.

The Trade-off: Clean Design Versus Continuity

The trade-off is clean new design versus continuity for consumers with independent release cycles. Keeping old fields or a /v1 endpoint costs code, tests, documentation, monitoring, and sometimes storage. Removing them early transfers that cost—and the outage risk—to clients that may not be able to upgrade immediately.

The right choice depends on named constraints: number and ownership of clients, release cadence, legal or operational notice requirements, risk of stale data, and ability to observe usage. “Always version” and “never version” are both weaker than a compatibility ledger tied to evidence.

Deprecation and Operational Consequences

Deprecation means “still supported, but migration should begin.” It is an operational workflow:

  • state the replacement and preserve its meaning
  • mark the old field or route in docs, schema metadata, or an appropriate response signal
  • publish a migration example and a target date or condition
  • measure use by client and version
  • contact owners who telemetry cannot identify reliably
  • keep old behavior stable through the window
  • remove only after the exit criteria are reviewed

GraphQL's @deprecated directive is one schema-level signal. HTTP APIs can also use documented deprecation or sunset response headers where their clients and tooling support them. These signals do not force a client to migrate; they make the request visible.

Failure can hide in semantics. Suppose completed remains present but changes from “all required lessons complete” to “some lesson complete.” The response still parses, status is still 200, and dashboards may show incorrect badges. Monitor product outcomes and contract tests, not only HTTP errors.

Design Review

Check 1: A response adds an optional lastActivityAt field. Is a new major version automatically required?

Think first, then reveal.

Answer: No. First check whether clients tolerate unknown fields and whether the new field changes any old meaning. If they do, additive evolution may be enough.

Check 2: A provider keeps completed but changes what true means. Which classification applies?

Think first, then reveal.

Answer: A semantic-breaking change. Parsers can succeed while clients make wrong decisions, so it needs a compatible migration or an explicit version boundary.

Check 3: An old endpoint has almost no traffic in telemetry. Is that alone proof that removal is safe?

Think first, then reveal.

Answer: No. Telemetry shows observed use. Cross-check client inventory, partner confirmation, contract tests, and the agreed removal criteria before deleting behavior.

Practice: Plan a Progress Migration

The platform wants to replace GET /courses/42/progress with a response that includes a status enum, a cursor for recent activity, and a new permission rule for instructors. The mobile app releases weekly; a partner releases quarterly; two internal tools use generated clients.

Write a migration plan. State:

  • which changes are shape, semantic, or behavioral breaks
  • whether you would evolve in place, add a version, or combine mechanisms
  • what old and new clients receive during the window
  • which telemetry, tests, owners, and exit criteria you need

A good answer should flag the new permission rule and cursor behavior as contract changes even if JSON remains valid. It should preserve old behavior or isolate it behind a clear version, provide an upgrade path for the generated clients and quarterly partner, and define evidence before removal. A plan that says only “ship /v2” has named a location, not a migration.

Key Takeaways

  • Start API evolution by asking which consumer assumption breaks, including meaning, permissions, status, pagination, and side effects.
  • Additive change is often useful, but verify unknown-field, enum, SDK, and decoder behavior with real consumers.
  • Expand, migrate, and contract gives clients a path forward; telemetry is evidence for removal, not proof that every client has been seen.
  • A version boundary isolates incompatible behavior but creates parallel support work. Deprecation is a workflow, not a warning label.
  • Choose the mechanism from client ownership, release cadence, risk, and observability—not from URL aesthetics.
