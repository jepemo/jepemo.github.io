Validation at Backend Boundaries

By the end of this lesson, you will be able to...

  • place structural, trust, domain, and persistence checks at the boundary that owns the needed knowledge

  • trace one review request from raw bytes to a safe application result and a committed integrity guard

  • distinguish useful layered validation from repeated ceremony and map each failure to meaningful API behavior

Idea in one sentence: Validation works when each boundary narrows a different uncertainty, from input shape and caller trust to product meaning and durable integrity.

Core Insight

The learning platform accepts course reviews through:

POST /courses/417/reviews
{
  "rating": 5,
  "comment": "Clear and practical."
}

The request can fail in several different ways. The JSON may be malformed. rating may be a string or outside the allowed range. The caller may have no authenticated identity. Alice may be authenticated but not enrolled in course 417. The course may be archived. Two browser tabs may submit the same valid review at almost the same time.

Calling all of these cases “bad input” hides the design question. Each boundary knows something different. The HTTP edge knows the request shape. Authentication can establish a caller identity. The application can inspect enrollment and course policy. The database can protect an invariant when concurrent writes race.

The goal is not to validate everywhere. The goal is to move the request through increasingly stronger assumptions without asking one layer to answer a question it cannot know.

The Reasonable First Model

A team may begin with one controller check:

def create_review(request):
    if not 1 <= request.json["rating"] <= 5:
        return {"error": "bad_request"}, 400
    if not current_user.is_authenticated:
        return {"error": "unauthorized"}, 401
    if not enrollment_exists(current_user.id, request.course_id):
        return {"error": "not_allowed"}, 403
    save_review(request.json)
    return {"ok": True}, 201

This is attractive because all failures appear close to the request. It works while the endpoint is the only caller and the database has no concurrency surprises. It starts to break when a worker imports reviews, another endpoint reuses the use case, or the request contains values that need product state to interpret. It also assumes that a preflight duplicate check can protect the database when two requests run together.

The missing model is a sequence of boundaries. Each one should answer: “What can I know here, and what uncertainty can I safely remove?”

Four Boundaries, Four Kinds of Knowledge

Use this path as a map:

untrusted bytes
   -> structural contract
   -> caller and context
   -> product meaning
   -> committed integrity

Structural validation checks syntax and shape. The request parser can reject invalid JSON, a missing rating, a non-integer value, or a comment longer than the API allows. These checks are cheap and should happen before application code receives raw transport data. A typed request model can turn the accepted shape into a value the next boundary can trust.

Caller and context validation establishes what the request is allowed to attempt. Authentication may produce user_id=alice. Tenant, account, or role context may be required for the operation. This is not yet proof that Alice may review this particular course. Identity answers “who is calling?”; resource authorization and domain policy answer “may this action happen here?”

Domain validation checks meaning that depends on product state. Alice's request can be perfectly shaped and authenticated yet invalid because she is not enrolled, the course is archived, reviews are closed, or she already has a review. The application has the repositories and policy needed to explain those conditions.

Persistence validation protects facts at the point where they become durable. A unique constraint on (user_id, course_id) prevents duplicate rows even if two application checks race or a maintenance script bypasses the normal use case. A foreign key or check constraint protects a relationship or value range that must never be committed.

The database is the final integrity guard, not the first user interface. The controller is the first shape guard, not the owner of every business rule.

Worked Path: One Review Request

Start with Alice's valid-looking request:

1. HTTP parser reads JSON and path parameter course_id=417.
2. Request schema accepts rating=5 and a short comment.
3. Authentication middleware attaches user_id=alice.
4. Use case loads course and enrollment facts.
5. Domain policy decides whether Alice may review course 417.
6. Repository attempts the insert inside its transaction boundary.
7. Database constraints guard duplicate and referential integrity.
8. Handler maps the application result or failure to the API contract.

The important movement is not the number of steps. It is the change in knowledge. The domain operation receives a command, not a request object:

class CreateReviewCommand:
    user_id: str
    course_id: str
    rating: int
    comment: str


def create_review(command, courses, enrollments, reviews, uow):
    course = courses.get(command.course_id)
    if course.is_archived:
        raise ReviewRejected("course_archived")
    if not enrollments.exists(command.user_id, command.course_id):
        raise ReviewRejected("not_enrolled")

    with uow:
        review = reviews.add_once(command)
        uow.commit()
    return review

The command contains accepted shape and authenticated context. The use case adds product meaning. The repository and unit of work translate the final intent into storage operations. This is a teaching model; a real application may combine or split components differently if the ownership remains clear.

Failure Semantics Follow the Boundary

Different failures deserve different handling because they tell different stories:

Observation Boundary with evidence Possible API result
malformed JSON or rating: "great" request parser/schema 400 Bad Request
no usable identity authentication boundary 401 Unauthorized
Alice is known but not enrolled application authorization/policy 403 Forbidden or a documented domain error
course is archived or reviews are closed domain state 409 Conflict or 422 Unprocessable Content, by API convention
unique constraint rejects a racing duplicate persistence boundary mapped duplicate-review response

Status codes are part of the API contract, so a track may choose a different consistent mapping. The architectural requirement is to preserve the distinction. Returning one generic “validation failed” response makes clients guess whether they should fix their payload, authenticate, request access, or retry later.

Layered Checks Without Accidental Duplication

Suppose the use case checks not already reviewed and the database also has a unique constraint. That overlap is useful because the checks protect different moments. The application check can give Alice a clear result before a write. The database constraint remains authoritative when two requests race or a second write path appears.

Now compare three copies of rating <= 5: the request schema, the application service, and the repository, all rejecting the same malformed value for the same reason. That is usually ceremony. Keep a database check constraint as a durable backstop if the invariant must hold for every write, but do not make every layer repeat a schema rule without adding knowledge or a different failure contract.

Use this test:

same question + same reason       -> likely duplication
same concept + different timing   -> often justified layering
different knowledge or consequence -> separate responsibility

Validation can also happen for data that did not arrive from a browser. Imports, partner feeds, queued messages, and repair scripts are untrusted inputs from the application's point of view. They should enter through a boundary that checks their own shape before they call the shared use case.

Trade-offs and Limits

Early validation reduces wasted work and gives clients clearer errors. It costs schemas, mapping, and decisions about which error vocabulary is stable. Domain checks may require reads and can become stale before commit. Persistence constraints are strong at commit time, but their raw errors are poor public explanations unless an adapter translates them.

Validation is not a complete security control. A range check does not prevent every injection or output-encoding error, and an authenticated identity does not grant resource permission. Validation also cannot make an external side effect atomic with a database commit. The signal that the design is drifting is a rule appearing in a layer that lacks the facts to explain it, or the same check being copied until its owners disagree.

Check Your Understanding

Check 1: { "rating": "great" } reaches the application service. Which boundary missed its job?

Think first, then reveal.

Answer: The structural request boundary. The service should receive an accepted command, not raw JSON whose type still needs interpretation.

Check 2: Alice is authenticated but has never enrolled in course 417. Should a database check constraint decide this?

Think first, then reveal.

Answer: No. Resource permission depends on application state and product policy. The use case should decide it and map the failure according to the API contract.

Check 3: Two requests both pass the duplicate preflight. What still protects the invariant?

Think first, then reveal.

Answer: A database uniqueness constraint or equivalent persistence guard at commit time. The application should translate the conflict instead of assuming the preflight was atomic.

Practice: Place the Checks

An organization accepts a CSV import and a public API for course reviews. Both require a rating from 1 to 5, an enrolled learner, an open course, and at most one review per learner and course. Design the boundary table and one failure mapping for each condition.

A good answer should mention:

  • parser/schema checks for CSV fields and JSON shape;
  • authenticated or imported caller context before the shared use case;
  • enrollment and course-state rules in application/domain policy;
  • a unique database constraint as the final duplicate guard;
  • consistent error mapping for the API, while the batch job records row-level outcomes;
  • no claim that client-side checks or the service preflight alone protects committed integrity.

Key Takeaways

  • Structural shape, caller trust, product meaning, and durable integrity are different validation jobs.
  • A boundary should reject what it can know, while deeper boundaries protect facts that depend on state or concurrency.
  • Application preflight checks improve clarity, but database constraints remain necessary final guards.
  • Layered validation is justified when checks protect different timing windows, knowledge, or failure contracts.
  • The goal is not the most validators; it is an honest chain of increasingly stronger assumptions.
