Backend Error Handling and Failure Semantics

By the end of this lesson, you will be able to...

  • classify a backend failure before choosing its HTTP representation

  • preserve one failure’s meaning for both the client and the operator without leaking internals

  • decide when a retry is safe, unsafe, or impossible to classify after an uncertain write

Idea in one sentence: Good error handling keeps the failure’s meaning intact long enough for each boundary to produce the right client action, retry signal, and diagnostic evidence.

Core Insight

One Request, Several Kinds of Failure

Alice submits a review:

POST /courses/42/reviews
Authorization: Bearer <token>
{"rating": 5, "comment": "Clear and practical."}

The successful path is familiar from lessons 009–011. The request is parsed, authenticated, validated, authorized, mapped, committed, and serialized. Now change one fact at a time:

  • the body is malformed;
  • the token is missing;
  • Alice is authenticated but not enrolled;
  • Alice already has a review;
  • the database times out during the write;
  • the server commits, but the client connection closes before the response arrives.

All six cases stop the same endpoint. They do not mean the same thing, and the client should not react to them in the same way. A malformed body asks the client to correct input. A missing token asks the user to sign in. A timeout may justify a bounded retry. An uncertain write may require a status lookup instead of another create request.

The tempting model is exception -> 500 -> log. It is easy to implement, but it destroys the distinction needed by user interfaces, automated clients, support staff, and incident response. The stronger model treats each failure as a named exit from the lifecycle. First classify what the system knows. Then translate that meaning at the boundary that owns the next audience.

The Failure Taxonomy

Start with meaning, not status codes. The following table is a teaching model for the review endpoint; a real API may choose a different mapping if it documents the choice consistently.

Stage and failure Internal meaning Likely client action Operator signal
JSON cannot be parsed or rating is 6 input cannot become an accepted request fix fields; do not retry unchanged validation counter and field location
token missing or invalid no caller identity established authenticate, then retry auth-failure counter, route, request id
Alice not enrolled or reviews closed business policy rejects this action show denial; do not retry unchanged policy code, course, caller-safe identifier
review already exists current state conflicts with requested change show existing state or stop retrying conflict count and uniqueness cause
database timeout before commit is known dependency did not answer in budget bounded retry only if operation is idempotent dependency span, timeout budget, attempt
stack bug or unknown exception backend could not fulfill its contract retry only if the client contract allows it exception class, trace, deployment version

400, 401, 403, 409, 500, and 503 are protocol language at the edge. They are not a substitute for the internal classification. A conflict and a dependency timeout might both be “not successful,” but one usually tells the client to stop while the other may permit a carefully bounded retry.

The trade-off is precision versus implementation effort. A catch-all handler is fast for a prototype. A small, stable vocabulary pays for itself when tests assert behavior, clients branch on problem types, and operators need to distinguish normal denials from an outage.

Keep Meaning Inside the Application

The use case should report what it discovered, not which web framework status to send:

class ReviewRejected(Exception):
    def __init__(self, code, *, retryable=False):
        self.code = code
        self.retryable = retryable


def create_review(command):
    course = courses.get(command.course_id)
    if course is None:
        raise ReviewRejected("course_not_found")
    if course.reviews_closed:
        raise ReviewRejected("reviews_closed")
    if not enrollments.exists(command.user_id, command.course_id):
        raise ReviewRejected("not_enrolled")

    try:
        return reviews.create_once(command)
    except DuplicateReview:
        raise ReviewRejected("review_already_exists")

This code can run behind an HTTP endpoint, an administration command, or an import worker. It names application meaning and leaves transport translation to an outer adapter. The adapter can choose 403 for not_enrolled, 409 for review_already_exists, and 404 for course_not_found according to the public contract.

An unknown exception should not be reclassified as a user error merely because the handler needs a response. Preserve the exception as private diagnostic evidence and use a generic public problem for the unexpected case.

Build a Safe Public Problem

HTTP status codes alone are often too coarse for non-human API consumers. RFC 9457 defines a problem-details format with machine-readable members such as type, title, status, detail, and instance; it uses the application/problem+json media type. The format is an option, not a requirement, but its separation between a stable problem type and occurrence-specific detail is a useful design pattern.

def problem_from_error(error, request_id):
    mapping = {
        "course_not_found": (404, "course-not-found", "Course not found"),
        "not_enrolled": (403, "review-not-allowed", "You cannot review this course"),
        "reviews_closed": (409, "reviews-closed", "Reviews are closed"),
        "review_already_exists": (409, "review-already-exists", "Review already exists"),
    }
    status, problem_type, title = mapping.get(
        error.code,
        (500, "internal-error", "Unexpected error"),
    )
    return {
        "type": f"https://api.example.com/problems/{problem_type}",
        "title": title,
        "status": status,
        "instance": f"urn:request:{request_id}",
    }

The type is a stable identifier for client branching. The title is short and human-readable. A detail field, if included, should help the client correct the request rather than reveal a stack trace. An instance or request id connects this occurrence to support evidence. Clients should not parse unstable prose as if it were a code.

The response is a public contract. If a mobile client uses review-already-exists to open the existing review, changing that type silently can break behavior even when the status remains 409. Error schemas therefore belong in the same compatibility review as success schemas.

Two Views of the Same Exit

Clients and operators need different levels of detail. Keep one semantic cause, but produce two views:

duplicate review
  client: 409 + stable type + safe title + request id
  operator: trace id + course id + conflict source + timing

database timeout
  client: 503 (or documented generic error) + retry guidance + request id
  operator: dependency name + timeout budget + attempt + exception chain

Returning raw exception text can reveal SQL, table names, file paths, library versions, or service topology. It also creates accidental compatibility around a message that was never designed to be stable. The OWASP guidance on error handling reinforces the boundary: detailed diagnostics belong in protected logs, not in production responses.

At the same time, a generic 500 without a correlation id leaves support unable to connect “my review failed” to a trace. Record the request id before work that may fail. In the operator view, include stage, latency, dependency, safe route parameters, and a caller identifier that follows the project’s privacy policy. Never log the bearer token or raw sensitive body.

Retry Semantics and Unknown Outcomes

Retry advice is part of failure meaning. A validation error, authentication failure, and enrollment denial are normally not useful to retry unchanged. A conflict usually requires a state change or a read. A transient dependency failure may be retryable within a time and attempt budget, but a create operation also needs idempotency protection.

The hardest case is an uncertain write:

client sends create
server writes row
network fails before response
client cannot tell whether the row exists

Calling create again can produce a duplicate unless the operation has an idempotency key or a uniqueness rule that turns the second attempt into a known conflict. Alternatively, the client can query an operation id. The honest response is not always “created” or “not created”; sometimes the system must expose a way to resolve uncertainty.

Do not infer retryability from 5xx alone. A programming bug may repeat the same failure, and a timeout after commit may make another attempt dangerous. Include retry guidance only when the operation and failure class support it. Retry-After can be appropriate for a documented temporary condition, but it does not make a non-idempotent side effect safe by itself.

Where Error Handling Breaks

Translating too early. The repository throws an HTTP response, so a worker cannot reuse the use case. Keep application or dependency meaning inside; translate at the HTTP boundary.

Collapsing denial and outage. A not-enrolled result increments the same alert as a database timeout. Separate expected business exits from operational faults in metrics and alerts.

Leaking diagnostics. A stack trace is returned in detail. Keep the client message safe and put exception chains in protected telemetry.

Changing codes casually. A team renames review-already-exists to duplicate without a compatibility review. Treat stable problem types and extensions as public contract.

Claiming certainty after a timeout. The response says “not created” even though the commit outcome is unknown. Use idempotency, operation status, or a follow-up read to resolve the state.

Check Your Understanding

Check 1: Alice is authenticated but not enrolled. Should the client retry the same request automatically?

Think first, then reveal.

Answer: No. This is a policy denial, not a transient dependency failure. The UI may explain the denial or offer enrollment, but an unchanged retry will not add permission.

Check 2: A database timeout occurs after the insert may have committed. Which response is most honest?

Think first, then reveal.

Answer: Return a safe, documented temporary/unknown outcome with a request or operation id, and provide a status lookup or idempotency mechanism. Do not assert “not created” without evidence.

Check 3: A client wants to branch on problem.type. What must the API team protect?

Think first, then reveal.

Answer: The type identifiers and their meanings are part of the public contract. Document them, test them, and evolve them with the same compatibility discipline as success fields.

Practice: Classify Five Exits

For the review endpoint, classify these cases: malformed JSON, missing token, not enrolled, duplicate review, and database timeout. For each case write:

  1. the internal failure class;
  2. a likely public status and stable problem type;
  3. whether an unchanged retry is useful;
  4. one safe operator signal.

A good answer distinguishes input, authentication, policy, conflict, and dependency meaning; avoids raw exception details in the response; and explains any retry using idempotency or uncertainty rather than status code alone.

Key Takeaways

  • Classify the failure before selecting an HTTP status; status codes are boundary language, not the whole internal meaning.
  • Keep application and dependency failures named inside the workflow, then translate them into stable, safe public problem details.
  • Clients need actionable contract fields; operators need richer private evidence. A request or trace id links the two views.
  • Retry semantics depend on the failure class, operation idempotency, and whether a write outcome is known—not on 5xx alone.
