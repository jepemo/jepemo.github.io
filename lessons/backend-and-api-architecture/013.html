OpenAPI, Schema-First Contracts, and Client SDKs

By the end of this lesson, you will be able to...

  • turn one endpoint’s behavior into a precise OpenAPI contract, including errors and examples

  • compare schema-first and code-first workflows under explicit ownership and client constraints

  • classify a proposed schema change as additive, breaking, or requiring a migration

Idea in one sentence: An API schema is useful when it becomes shared evidence, but every precise promise can become a compatibility obligation for clients and generated SDKs.

Core Insight

The course platform serves a web app, a mobile app, and a partner integration. They all call:

POST /courses/42/reviews

The backend team changes the response from "rating": 5 to "rating": {"score": 5, "scale": 5}. Server tests pass. Deployment succeeds. The mobile client then fails because its generated model expects a number.

The first explanation is “the mobile serializer is buggy.” The stronger explanation is contract drift: the server and clients held different beliefs about a public shape. OpenAPI gives those beliefs one explicit artifact. The specification describes a language-agnostic HTTP interface so humans and tools can discover paths, parameters, request bodies, responses, schemas, and security requirements without reading server source. Once a client generates code or validates responses from that artifact, the schema is evidence, not decoration.

The Contract We Need to Keep

For the review endpoint, “there is a POST route” is too vague. A useful contract answers:

  • What is the path parameter’s type and authority?
  • Which request fields are required, and which unknown fields are rejected?
  • Which success status and response fields are stable?
  • Which authentication requirement applies?
  • Which expected errors can the client act on?
  • Which examples represent realistic success and failure bodies?

Here is a deliberately small contract fragment:

paths:
  /courses/{course_id}/reviews:
    post:
      operationId: createCourseReview
      security:
        - bearerAuth: []
      parameters:
        - name: course_id
          in: path
          required: true
          schema: {type: string}
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/CreateReviewRequest"
      responses:
        "201":
          description: Review created
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/ReviewResponse"
        "400":
          description: Invalid request body
          content:
            application/problem+json:
              schema:
                $ref: "#/components/schemas/Problem"
        "403":
          description: Caller cannot review this course
          content:
            application/problem+json:
              schema:
                $ref: "#/components/schemas/Problem"
        "409":
          description: Review already exists
          content:
            application/problem+json:
              schema:
                $ref: "#/components/schemas/Problem"

The fragment forces decisions that code alone may hide. course_id is a string in this contract. The API documents a 403 and a 409 instead of leaving clients to guess. The error shape connects to lesson 012’s problem types. The OpenAPI Specification defines paths, operations, parameters, request bodies, responses, reusable components, and schema constraints as parts of the interface description; the exact version is a tooling choice, but the contract responsibility remains.

The Initial Model: Documentation After the Code

Many teams begin code-first. A developer writes a route, serializer, and exception handler. A tool then extracts an OpenAPI document. This is efficient when one team owns a private API and the implementation is already the source of truth.

The pressure appears when extraction captures accidental behavior. A serializer may expose a database field because it was present on an object. A default exception handler may produce a 500 shape that no client should depend on. A nullable field may appear because a value was missing, not because the product chose to promise null.

Schema-first reverses the order. The team designs the public contract, reviews it with client owners, and implements the endpoint to satisfy it. This is valuable when several clients, generated SDKs, or external partners update at different speeds. A mobile engineer can ask whether an enum needs an unknown fallback before code ships. A partner can build against examples while the persistence layer is still under construction.

Neither workflow wins by slogan. The decision is about authority and feedback:

Constraint Code-first fit Schema-first fit
One owner, private clients, rapid prototype implementation can be authoritative may add ceremony
Multiple clients or external consumers accidental fields are risky early cross-team review is valuable
Generated clients and compatibility gates extracted spec still needs review contract can drive generation and checks
Fast-changing internal details convenient if exposure is intentional useful only if promises are stable enough

The healthy workflow connects the artifact to reality regardless of direction:

contract decision
  -> generated types or server stubs
  -> request/response validation
  -> example and integration tests
  -> compatibility diff in CI
  -> reviewed release

A schema that is never checked becomes a wish list. A generated schema that is never reviewed becomes a record of accidental behavior.

Worked Compatibility Review

Assume the current response contract is:

ReviewResponse:
  type: object
  required: [id, course_id, rating, comment]
  properties:
    id: {type: string}
    course_id: {type: string}
    rating: {type: integer, minimum: 1, maximum: 5}
    comment: {type: string}

A generated TypeScript client may contain:

type ReviewResponse = {
  id: string
  course_id: string
  rating: number
  comment: string
}

Now evaluate proposals:

Change Compatibility judgment Reason
Add optional rating_details object usually additive old clients can ignore it
Change rating from integer to object breaking old parsers and types expect a number
Add a new required response field breaking for strict clients existing responses lack it
Add an enum value potentially breaking clients may reject or mishandle unknown values
Rename problem.type breaking if clients branch on it identifier is machine-readable contract
Clarify an example without changing schema documentation-only if behavior is unchanged no client-visible shape change

An additive design keeps the old field and introduces a new one:

rating_details:
  type: object
  required: [score, scale]
  properties:
    score: {type: integer}
    scale: {type: integer}

New clients can use rating_details; old clients continue using rating. A later removal of rating requires deprecation evidence, a migration timeline, or a new version. The schema makes the decision inspectable before release instead of discovering it through a crash.

The same reasoning applies to the error response. If a client opens an existing review when problem.type equals https://api.example.com/problems/review-already-exists, that URI and its meaning are a public promise. The status alone is not enough to preserve behavior.

What Generated SDKs Encode

An OpenAPI generator can create typed functions, models, exception classes, authentication hooks, and status handling. A client may call:

createCourseReview(courseId, CreateReviewRequest) -> ReviewResponse

This removes repeated URL construction and ad-hoc dictionary parsing. It also hardens assumptions. Required fields become constructor requirements. Nullable fields become option types. Enum values become generated constants. A changed response type can fail compilation, runtime decoding, or a consumer test. A partner may update its SDK monthly while the backend deploys daily, so a “small” schema edit can have a long migration tail.

Review a schema from the client’s point of view:

  • Required means the client may rely on presence.
  • Optional means the client must handle absence.
  • Nullable means null is intentional, not merely convenient for an empty value.
  • Enum values need a plan for future values or an explicit unknown branch.
  • Error types and codes need stable identifiers when clients branch on them.
  • Examples should include realistic success and failure payloads.
  • readOnly and writeOnly fields should reflect which direction owns a value.

Precision remains valuable. A vague schema often pushes clients toward untyped maps, which move the same uncertainty into every consumer. The goal is not to avoid promises. It is to promise only what the service can keep and to test those promises.

Failure Modes and Boundary Signals

Spec drift. The server emits a field that the schema omits. The signal is a response-validation or consumer-test failure. Fix the implementation or update the contract through review; do not silently accept divergence.

Happy-path-only contract. The schema documents 201 but not 400, 403, 409, or a temporary dependency failure. The signal is client code guessing whether to show a form error, stop retrying, or ask the user to sign in. Add expected error responses with stable problem schemas.

Generated-client surprise. An SDK regeneration changes a type or enum and the change is noticed only after release. The signal is a generated diff with no compatibility classification. Run generation and contract diffs in CI before publishing the client.

Overly loose schema. Most properties are free-form objects or strings. The signal is each client implementing a different parser and disagreeing about null, enum, or date behavior. Tighten fields that drive decisions, while leaving deliberate extension points where evolution is expected.

Schema as a wish list. Schema-first files describe behavior the server never implements. The signal is a passing documentation review but failing integration tests. Tie examples and validation to a running endpoint or contract test.

The trade-off is precision versus change freedom. Precise schemas make compatibility evidence, generated code, and earlier review possible. They also increase governance and make accidental detail harder to remove. Vague schemas reduce short-term friction but distribute ambiguity and breakage across every client.

Check Your Understanding

Check 1: Existing clients expect rating to be an integer. Product wants a score plus scale. Which proposal is safest?

Think first, then reveal.

Answer: Keep rating stable and add an optional rating_details object. Deprecate or version the old field later with a migration plan.

Check 2: A generated SDK adds a new required response field. Why can that be breaking even if the server still returns all old fields?

Think first, then reveal.

Answer: Existing responses or test fixtures may not contain the new field, and strict decoders can reject them. Making a response field required changes what clients must receive.

Check 3: A client branches on problem.type. What should a compatibility review protect?

Think first, then reveal.

Answer: The type identifier and documented meaning. Renaming it or changing its semantics can break behavior even if the HTTP status remains the same.

Practice: Review One Endpoint Contract

Choose an endpoint you have built or used. Write a compact contract containing its request schema, success response, at least two expected errors, authentication requirement, and one realistic example. Then propose one change, such as adding an enum value or making a field required.

A good review should:

  • identify which artifact is authoritative when code and schema disagree;
  • classify the change as additive, breaking, or requiring migration;
  • explain how a generated client or strict decoder might react;
  • state which test or compatibility diff would catch the problem before release;
  • name the trade-off behind the chosen evolution path.

Key Takeaways

  • OpenAPI is useful when it is shared evidence that humans review and tools validate, not merely a page of documentation.
  • Schema-first and code-first are workflow choices; the critical question is which artifact is authoritative and how drift is detected.
  • Required fields, enum values, response types, error identifiers, and pagination tokens can all become compatibility promises.
  • Generated SDKs improve consistency while encoding assumptions into client code, so schema changes need explicit compatibility evidence.
