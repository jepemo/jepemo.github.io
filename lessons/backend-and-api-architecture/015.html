Contract Testing and Backward Compatibility Gates

By the end of this lesson, you will be able to...

  • distinguish provider correctness from consumer compatibility

  • turn schema diffs, consumer expectations, generated-client checks, and semantic review into a release decision

  • choose an additive change, deprecation, version, approval, or block when a contract promise changes

Idea in one sentence: A compatibility gate asks whether the next provider version still satisfies the promises that real consumers can observe and depend on.

Core Insight

The course platform releases a new review backend. Its unit tests pass. The endpoint returns 200. The new web client works. An older mobile app, which cannot update for two weeks, still expects rating to be an integer, next_cursor to be optional, and problem.type to use the old identifier.

The server is internally consistent, but the release can still break a consumer. The first model—“if provider tests pass, the release is safe”—checks only one side of a shared boundary. The pressure for contract testing comes from the missing side: a client’s expectation must become evidence that the provider can verify before deployment.

What Counts as a Contract

A contract is any client-visible behavior that a reasonable consumer can rely on. For the review service, examples include:

  • ReviewResponse.rating remains an integer from 1 to 5;
  • sort=newest remains accepted and keeps its documented meaning;
  • next_cursor is absent or present according to the list contract;
  • duplicate reviews use a stable problem type and status;
  • generated SDK methods and model types remain usable;
  • a successful request returns the documented fields and status.

Some promises are structural. A schema diff can see a removed field, changed type, new required property, missing response status, or removed enum value. Some promises are behavioral. A test must observe that the provider accepts a request, returns a field, preserves ordering, or keeps an error meaning. Some are semantic. The schema may remain unchanged while sort=newest silently changes from creation time to moderation time.

The contract should protect what a consumer uses, not freeze every incidental byte. A mobile client that reads id, rating, and page.has_more should not accidentally block the provider from adding an unrelated optional field. The aim is a narrow, meaningful contract.

The Gate as a Release Mechanism

A compatibility gate is a decision point, not just a report:

proposed provider change
  -> unit and integration tests
  -> diff against last released schema
  -> provider verifies consumer contracts
  -> generated SDK compile or smoke test
  -> semantic review for behavior not captured by schemas
  -> allow, warn, require approval, or block

The gate compares against the last released contract, not only the branch’s new schema. This matters because a field can disappear between releases even when the current server and current tests agree. Keep the released artifact and the known-consumer inventory available to CI.

The gate also needs explicit outcomes. “Breaking change found” is not a policy. A safe additive change can pass automatically. A risky enum addition may require approval. A type change can block until the old field remains, a new version is published, or a migration is complete.

Worked Example: Changing rating

The current public shape is:

ReviewResponse:
  type: object
  required: [id, rating, comment]
  properties:
    id: {type: string}
    rating: {type: integer, minimum: 1, maximum: 5}
    comment: {type: string}

A proposed change replaces the integer with an object:

 ReviewResponse:
   properties:
-    rating: {type: integer, minimum: 1, maximum: 5}
+    rating:
+      type: object
+      properties:
+        score: {type: integer}
+        scale: {type: integer}

The schema diff reports a type change. The generated mobile model still expects rating: number. A consumer contract may make the same expectation executable:

{
  "request": {
    "method": "GET",
    "path": "/courses/42/reviews",
    "query": "sort=newest&limit=20"
  },
  "expected_response": {
    "status": 200,
    "body_contains": {
      "data[0].rating": "number",
      "page.has_more": "boolean"
    }
  }
}

The gate should produce an actionable result:

CHANGE: ReviewResponse.rating integer -> object
EVIDENCE: schema diff + mobile consumer contract + generated model mismatch
DECISION: block
OPTIONS: keep rating and add rating_details, or publish a planned version/migration

The additive alternative keeps the old promise:

rating: {type: integer, minimum: 1, maximum: 5}
rating_details:
  type: object
  required: [score, scale]
  properties:
    score: {type: integer}
    scale: {type: integer}

Old clients continue to read rating. New clients opt into rating_details. A later removal needs deprecation evidence and a support-window decision. The gate did not forbid product evolution; it made the migration explicit.

Provider and Consumer Evidence

Provider contract tests verify that the server’s actual behavior matches its documented contract. They might validate responses against OpenAPI or exercise every documented status. Consumer-driven tests start from the other side: a consumer records the request and the subset of the response it needs, then the provider verifies that interaction.

Pact describes this relationship as consumer and provider and distinguishes contract-by-example tests from a static schema. Both forms are useful because they answer different questions. A schema can describe all possible states and make structural changes visible. A consumer example can show the exact behavior a mobile app or partner uses. Neither proves every semantic promise; a human or domain-specific test may still be needed.

Generated SDK checks add another signal. Regenerate the client from the proposed schema and compile or run a smoke test. A changed required field, enum, nullable property, or response type may be harmless for one language and breaking for another. Treat the generated diff as evidence to review, not as an automatic verdict.

Classify Proposed Changes

Proposed change Typical gate result Why
Add optional response field allow old clients can ignore it
Add a new endpoint allow existing surface is unchanged
Add optional request parameter with old default allow or warn old callers keep previous behavior
Remove field, endpoint, status, enum, or sort value block existing callers may rely on it
Change field type or requiredness block generated and strict clients can fail
Add response enum value warn or block clients may reject unknown values
Rename a stable error type block clients may branch on the identifier
Change default sort or total semantics semantic review schema may not reveal behavior change
Invalidate old cursors earlier than promised block clients can hold issued cursors
Tighten authentication requirement block or migration existing callers lose access

These are defaults, not universal laws. Google’s compatibility guidance separates source, wire, and semantic compatibility: code may compile yet receive behavior that no longer matches reasonable expectations. The gate must name which dimension is at risk.

Semantic Changes Need Human Evidence

A schema diff cannot see that total changed from exact to approximate, that newest uses a different timestamp, or that a 409 conflict now means “duplicate request” instead of “review already exists.” Add examples, consumer scenarios, changelog rules, or a reviewer who owns the public promise.

This is where false confidence often enters. A green provider test proves the new provider satisfies its own assertions. It does not prove that an old client handles the new meaning. A green schema diff proves no structural incompatibility according to the tool’s rules. It does not prove that a new field keeps the old business semantics.

Failure Modes and Operational Signals

Provider-only confidence. Server tests pass while an older consumer breaks. The signal is no consumer contract or released-schema comparison in CI. Add both to the gate.

Over-broad snapshots. A test freezes every response key. The signal is harmless optional additions blocking releases. Assert the fields and semantics the consumer actually uses.

Unowned warnings. CI reports a breaking diff but release authority is unclear. The signal is a warning that never changes deployment. Define allow, warn, approval, and block outcomes with named owners.

Late discovery. Compatibility is checked only at release time. The signal is a large redesign after SDKs and clients are already built. Run diffs and consumer verification in pull requests.

Invisible consumers. An old partner or mobile version is absent from the inventory. The signal is a production break from a client nobody remembered. Track supported SDK versions, app windows, and partner contracts.

False safe change. A semantic behavior changes without a schema change. The signal is a client test or support report showing different ordering, totals, or error meaning. Require semantic review and examples for behavior changes.

Trade-off: Release Speed Versus Shared Safety

Without a gate, a backend team can ship quickly and discover client breakage later. With a gate, the team spends time generating clients, maintaining contracts, and reviewing diffs. That is a real cost. It is justified when consumers update slowly, the API is public, a partner depends on it, or a failed client release is expensive.

The gate should remain proportional. A private endpoint owned and deployed by one team may need a lightweight schema check. A public mobile API may require released-contract diffs, consumer verification, SDK smoke tests, and approval for semantic changes. Contract tests should protect meaningful promises while leaving internal implementation free to change.

Check Your Understanding

Check 1: The provider’s unit tests pass, but the old mobile contract expects rating to be a number. What evidence is missing?

Think first, then reveal.

Answer: Consumer compatibility evidence. Compare with the released schema, verify the mobile contract, and inspect the generated model before allowing the release.

Check 2: The team adds a new response enum value. Why might this need a warning instead of an automatic pass?

Think first, then reveal.

Answer: Some clients reject unknown values or use exhaustive switches. The change can be safe only when consumers have an unknown-value strategy or the gate has evidence that they tolerate it.

Check 3: The schema is unchanged, but sort=newest now uses moderation time. Which gate catches this?

Think first, then reveal.

Answer: A semantic review, example-based consumer test, or explicit behavior test. Structural schema diff alone cannot see the changed meaning.

Practice: Design a Compatibility Gate

Choose one change: remove a response field, add an enum value, change a cursor shape, rename an error type, or change list totals from exact to estimated. Write a gate record with:

  1. the old promise;
  2. the proposed change;
  3. structural, consumer, generated-client, and semantic evidence;
  4. the decision: allow, warn, approval, block, or version;
  5. the migration or rollback path.

A good answer protects the consumer’s actual dependency, avoids freezing unrelated fields, names the compatibility dimension at risk, and assigns an owner for any exception.

Key Takeaways

  • Provider correctness is not consumer compatibility; a release must compare against released contracts and known consumer expectations.
  • Compatibility gates combine schema diffs, consumer contracts, generated SDK checks, and semantic review into an explicit release decision.
  • Narrow contracts protect the fields and behaviors consumers use without freezing incidental response details.
  • Breaking changes can be intentional, but they require a documented migration, deprecation, version, approval, or block path.
