Service Discovery and Dynamic Topology

By the end of this lesson, you will be able to...

  • trace how a caller reaches a healthy service instance while instances are replaced;

  • distinguish service identity, membership, readiness, and load balancing; and

  • diagnose whether a failed call came from stale topology knowledge or from the selected service.

Idea in one sentence: Service discovery lets callers use one stable service name while the platform continually changes which concrete instances are safe to receive traffic.

Core Insight

Consider a course platform during a rollout. Billing needs to ask enrollment-service whether it can grant a learner access. At 10:00, there are three enrollment instances. At 10:02, one is draining, another has stopped unexpectedly, and a new instance has started but is not ready yet.

The first model is understandable: put the addresses of the three instances in billing’s configuration and choose one. It works while the process list stays still. It fails as soon as a deployment, autoscaler, or node failure changes that list. Billing has learned a temporary coordinate, not a durable dependency.

The stronger model is that billing depends on a logical service identity and a discovery mechanism keeps a changing set of eligible endpoints beneath that identity. A concrete address can be present, alive, ready, draining, or absent. Those are different states. The point is not merely to find an IP address. The point is to route a new request only to an instance that currently belongs in the service’s usable set.

This lesson uses a simplified rollout trace. Its addresses, times, and health results are illustrative. The state transitions, however, are the reason discovery exists in dynamic infrastructure.

The Small Situation

Keep four actors in view:

Actor What it knows or does What it must not assume
Billing Needs an enrollment decision for the current request One particular enrollment address will remain valid
Discovery source Records the current members and their eligibility Every running process can receive traffic
Router or client Selects one eligible endpoint Its cached view is permanently fresh
Enrollment instance Starts, becomes ready, drains, or fails Being alive is the same as being ready

At the start, the logical name resolves to three ready instances:

logical name: enrollment-service

e1  10.0.14.8:8080   ready
e2  10.0.14.9:8080   ready
e3  10.0.15.2:8080   ready

Billing does not need to know which node runs e2. It needs a usable enrollment service. The stable name expresses that dependency. The endpoint set is an implementation detail that must be updated as the runtime changes.

Plain meaning: discovery keeps a current enough answer to “where may I send this request?”

In this scenario: the answer for enrollment-service is a short list of instances that have joined and passed the rule for receiving new traffic.

Technical name: that mapping from logical service identity to a changing endpoint set is service discovery.

Why a List of Addresses Is Not Enough

It might seem that discovery only needs a registry:

enrollment-service -> [e1, e2, e3]

That list is incomplete. An instance can still have a network address after it has started shutting down. It can be running while its application has not connected to its dependencies. It can disappear without sending a clean goodbye. Sending new work to any such instance makes the system look unpredictable during ordinary rollout activity.

The discovery view therefore needs a lifecycle, not a one-time lookup:

instance starts
  -> registers or becomes visible
  -> proves readiness
  -> enters the routing set
  -> drains before planned removal
  -> deregisters or expires

Membership answers, “Which instances claim to be part of this service?”

Readiness answers, “Which members may receive a new request now?” Load balancing answers, “Which eligible member receives this particular request?”

Some platforms combine these functions behind one service address. The distinction still matters when diagnosing an incident. A missing service name points to discovery or membership. A request sent to a draining instance points to eligibility or stale routing information. An overloaded but ready instance may point to the balancing policy or capacity, not discovery itself.

The Mechanism Step by Step

Now trace the rollout. Assume billing has a discovery view that refreshes periodically or receives updates. The exact update mechanism—DNS, a registry watch, or a platform proxy—is outside this small teaching model. What matters is how the routing set changes.

Starting state

At 10:00, all three instances are ready:

Instance Process state Eligible for new traffic? Why
e1 running yes Ready and serving
e2 running yes Ready and serving
e3 running yes Ready and serving

The routing set is [e1, e2, e3]. A client-side resolver or an infrastructure router may choose one member. That selection happens after discovery provides the eligible set.

Step 1: a replacement starts

At 10:01, the platform starts e4 on a new node. The process is alive, but its application is still loading configuration and connecting to its database.

e4  10.0.16.4:8080   running, not ready

The tempting mistake is to add e4 to traffic as soon as a process exists. That creates a race: billing can reach the address before e4 can safely answer. A readiness check is the evidence that corrects the model. Until readiness succeeds, discovery records that e4 exists but the routing set remains [e1, e2, e3].

Step 2: an old instance drains

At 10:02, the platform asks e1 to stop. It should not vanish from every record instantly. It may have in-flight requests that need time to finish. But it should stop receiving new requests.

e1: draining
routing set: [e2, e3]

Draining is a separate state from failure. A failed instance cannot serve work. A draining instance may finish existing work, but the router should not select it for a new enrollment request. If it remains eligible until the process finally exits, new requests can land on an instance just as it closes connections.

Step 3: the replacement becomes ready

At 10:03, e4 passes readiness. Now the discovery source can add it to the usable set:

e2: ready
e3: ready
e4: ready

routing set: [e2, e3, e4]

Billing still asks for enrollment-service. It does not edit its configuration or learn e4’s address. This is the practical benefit: topology changes under a stable dependency.

Step 4: an instance disappears without notice

At 10:04, the node running e3 fails. There may be no clean deregistration. A healthy discovery system therefore needs a way to remove members whose membership or health information is no longer credible. That may be an expiry lease, a missed health check, or a platform controller updating the endpoint set.

Until the view updates, some callers may still select e3. That is not proof that discovery is pointless; it is the normal consequence of information that propagates over time. The system needs a bounded stale period and a call policy that handles the occasional failed attempt. The prior lesson supplied that policy: deadline, safe retry posture, evidence, and a truthful fallback.

A Worked Request Trace

Follow one billing request at 10:04. The numbers are illustrative.

Time Event Discovery or routing state What billing can conclude
10:04:00.000 Billing requests enrollment-service. Cached eligible set is [e2, e3, e4]. The service name resolved; the view may still contain e3.
10:04:00.002 Router selects e3. e3 is stale because its node just failed. The chosen endpoint may not answer.
10:04:00.120 Connection attempt fails. A transport failure is observed. Billing has not learned whether enrollment performed the command.
10:04:00.150 Health or membership update removes e3. New set is [e2, e4]. Future selections should avoid e3.
10:04:00.170 Billing follows the operation’s safe retry rule. Router selects e4. The retry must reuse the logical operation, not invent a second enrollment.

The trace separates two questions that are often mixed together. Discovery answers whether e3 should still be considered. The remote-call policy answers what billing does after the failed attempt. Discovery reduces the duration of bad routing; it does not prove that the first attempt did nothing.

So far, we have built the mechanism from visible states. A service name stays stable. Membership records possible endpoints. Readiness and drain state form the eligible set. A client or router selects one endpoint. Health updates and expiry remove endpoints that are no longer safe. The remaining uncertainty is handled at the call boundary, not denied by the discovery layer.

Where Topology Knowledge Lives

The same mechanism can be placed in different layers.

client-side discovery:
billing -> resolver or registry -> chooses e2/e3/e4 -> calls chosen instance

server-side discovery:
billing -> stable service address -> router or proxy chooses e2/e3/e4

With client-side discovery, billing or a shared client library knows how to resolve and select instances. This can offer direct control over caching and selection. It also requires all callers to implement that logic consistently.

With server-side discovery, billing calls a stable virtual address. A platform router, proxy, or load balancer resolves the backend set. This keeps application code simpler and can centralize traffic policy. The router then becomes an important component to observe and operate.

The trade-off is local control versus shared consistency. Client-side discovery can suit a platform that deliberately gives services sophisticated client libraries. Server-side discovery can suit a platform that wants uniform routing behavior. Neither choice removes the need for correct readiness, drain, and expiry signals.

Where It Breaks

Discovery makes topology manageable. It does not make topology instantaneous or eliminate every failed request.

Stale views. A cache or update stream can retain e3 briefly after failure. This improves availability by avoiding a registry lookup for every request, but costs freshness. Watch endpoint age, update lag, and connection failures to recently removed instances.

Flapping health. If a readiness rule changes rapidly between ready and not ready, the routing set churns. Removing an instance on every short blip may concentrate traffic on the remaining members. Watch readiness transitions and the size of the eligible set, not only aggregate error rate.

Too-permissive readiness. A process can answer a shallow probe while it cannot perform the workload that callers need. In this example, a readiness rule that ignores a required enrollment dependency can send billing traffic to an instance that accepts connections but fails every command. The signal is a gap between readiness success and real request success.

Confusing discovery with balancing. Discovery can offer three healthy members while a poor balancing rule overloads one. Compare the eligible set with per-instance request rate and latency before blaming the registry.

Assuming a successful connection proves the workflow succeeded. Discovery only got the request to a candidate endpoint. The enrollment owner and the operation identifiers establish whether access was granted.

Cost, Limits, and Signals

This mechanism buys deployment flexibility. Instances can be replaced, scaled, and moved without editing every caller’s configuration. It costs a runtime control path: membership data, readiness evidence, caches, health checks, and observability must stay credible.

It is a good fit when endpoints change more often than application releases, which is common for orchestrated workloads. It becomes risky when the routing set changes faster than the system can observe it, or when readiness hides the real ability to serve. It does not solve capacity, semantic retries, or authorization between services.

Use these signals to decide where the boundary is:

Signal What it reveals First question
Eligible endpoint count Whether the service still has enough ready capacity Did a rollout, health failure, or readiness rule remove members?
Endpoint update lag How long callers can use old topology Are cache or watch updates behind the source of truth?
Requests to draining endpoints Whether routing respects lifecycle state When was the endpoint removed from the eligible set?
Per-instance latency and errors Whether balancing or an unhealthy instance is the problem Are failures concentrated on one selected endpoint?
Readiness transitions Whether health is flapping Is the probe measuring the ability to serve this workload?

Trace It Yourself

Check: e4 is running but has not passed readiness. Billing’s resolver can see its address. Should a new enrollment request be routed to e4?

Think first, then reveal.

Answer: No. Registration or visibility says that an instance exists. Readiness is the evidence that it may receive new work. Keep e4 out of the eligible routing set until that condition is true.

Check: A router selected e3, then the connection failed. Does that prove enrollment did not grant the learner access?

Think first, then reveal.

Answer: No. It proves that the caller did not complete a conversation with that endpoint. Use the operation identifier and enrollment’s authoritative state to settle the result. Discovery should remove e3 for later requests; the call policy decides whether and how the logical operation is retried.

Practice

An image-processing service runs four instances. During a deployment, one old instance is draining, one new instance is running but not ready, and two old instances are ready. A client cache still lists all four.

Draw the eligible routing set now. Then name one signal that would tell you whether the cache is stale and one rule that prevents a new upload from being sent to the draining instance.

A strong answer uses only the two ready old instances in the set. It names endpoint update lag, requests sent to draining instances, or a cache age metric as evidence of staleness. It also says that the router must remove a member from new-request selection when that member enters drain state, even if the process remains alive to finish in-flight work.

Connections

Key Takeaways

  • A logical service name is stable; the endpoint set behind it is not.
  • Membership, readiness, draining, and expiry determine which instances are eligible for new traffic.
  • Discovery provides a usable endpoint set, while load balancing selects one endpoint and call policy handles ambiguous outcomes.
  • Dynamic topology is expected during deployments and failures, so its state transitions need explicit signals and ownership.
