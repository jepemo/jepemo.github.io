Inter-Service Communication Patterns

By the end of this lesson, you will be able to...

  • classify a service interaction as a request, command, or event from the business need;

  • choose which parts of a workflow must complete before a user receives an answer; and

  • review an interaction for hidden responsibility, recovery state, and timing coupling.

Idea in one sentence: Choose communication by the responsibility and timing it creates, then choose a protocol that can carry that promise.

Core Insight

Suppose a learner buys a course. The checkout service must not show “enrolled” until it knows whether payment was accepted. A receipt email, an analytics record, and a recommendation update also matter. They do not all need to finish while the learner waits at checkout.

It is tempting to start with a technology question: “Should this use HTTP, gRPC, or a message broker?” That question comes too early. Each option can carry more than one kind of meaning. The useful first question is: what is this service asking another service to be responsible for, and when must the answer be known?

The initial model is simple: every interaction is a request and every request should return success before the workflow continues. It works for a small system with one or two dependencies. It breaks when checkout waits for every downstream consumer. An email outage then prevents a paid learner from receiving access. A slow analytics job becomes part of the payment path for no product reason.

The stronger model separates three intents:

  • A request says, “I need information or a decision before I can continue.”
  • A command says, “Please own this named piece of work.”
  • An event says, “This fact has already happened; react if it matters to you.”

These words describe semantics, not transports. A command may be delivered synchronously or asynchronously. An event may travel through a broker or be exposed through a feed. The important part is that the receiver, caller, and operators agree about waiting, ownership, and recovery.

The Promise We Need to Keep

The course platform makes a small, visible promise: a learner who sees a completed purchase should be able to access the course. Let us keep the actors small:

Actor Can decide or change Must not silently own
Checkout What response the learner sees The internal rules of payment or enrollment
Billing Whether a payment attempt is authorized Course access
Enrollment Whether a learner receives a seat Payment authorization
Notification Whether a receipt is sent Whether payment or enrollment succeeded

The distinction matters because “purchase complete” can mean several things. A card authorization might exist while enrollment is still pending. An enrollment can exist while a receipt is delayed. If the system uses one vague success signal for all of them, it cannot tell the learner or an operator what is actually true.

For this lesson, assume billing is the authority for payment and enrollment is the authority for course access. Those are design choices for this product. A different product may require a reservation before charging or may sell an item with limited stock. The method still applies: name the promise, name the authority, and then choose the communication intent.

The Naive Design: Make Every Service Wait

The first implementation might put all work on one synchronous chain:

checkout -> billing -> enrollment -> notification -> analytics
                                      \-> recommendations

Checkout waits for each arrow to return. This has one attractive property: a single request seems to produce one clear answer. It is reasonable when every downstream result is genuinely required before the user can proceed.

Now apply pressure. Notification has a configuration error. Billing has authorized the card and enrollment has granted access, but the receipt call times out. Should checkout show payment failed? That would be false. Should it retry the whole chain? That may repeat already-completed work. Should it wait forever for a nonessential email? That turns a secondary effect into a user-facing dependency.

The trace exposes the missing distinction:

Step What checkout knows What it still needs before its answer
Billing returns authorized A payment decision is available An access decision
Enrollment records granted The learner may receive the course Nothing for the completion promise
Notification is unavailable A receipt has not been sent Nothing for the completion promise

The evidence is not a slogan about “async being scalable.” It is the state of the workflow. Once billing and enrollment have established the promised outcome, making checkout wait for notification does not add truth. It only adds timing coupling.

Three Intentions, Three Responsibilities

First, a request asks for an answer now. Checkout might ask billing:

authorize payment for attempt pay-418?

Checkout waits because it cannot truthfully decide how to proceed without billing’s answer. The request creates a tight timing relationship: while checkout waits, billing latency and availability affect the learner path. The next lesson turns that relationship into a deadline, retry, and recovery policy. Here, the design decision is only that the answer is a prerequisite.

Second, a command asks a receiver to take responsibility for work. After authorization, checkout can send enrollment:

grant one seat for learner L42 in course C7, linked to pay-418

The command names an owner and desired action. It is not merely a notification that someone paid. Enrollment must validate its own rules, record its result, and make a result discoverable. Checkout may wait for that result if access must be confirmed in the same screen, or it may show enrollment_pending if the product can complete it later. The intent remains a command in both cases.

Third, an event announces a fact after its authoritative change:

enrollment.granted { enrollment_id: E91, learner: L42, course: C7 }

Notification, analytics, and recommendations can each react without asking enrollment for permission. No single consumer is entitled to treat this event as an instruction that enrollment must wait for. A notification failure means “receipt not yet sent,” not “enrollment was undone.”

This is the key boundary: a command assigns required responsibility to a known receiver. An event publishes history for interested receivers. If one consumer is mandatory, hiding that need behind an event makes responsibility invisible.

A Worked Purchase Path

Here is one possible design. The exact transport is deliberately left open.

Step Message and intent State after the step What can fail without breaking the learner promise?
1 Checkout requests a payment decision from billing. Payment is authorized, declined, or still uncertain. Nothing yet: checkout needs a truthful payment outcome or pending state.
2 Checkout commands enrollment to grant the seat after authorization. Enrollment becomes granted, rejected, or pending. Nothing yet if the screen promises immediate access.
3 Enrollment publishes enrollment.granted. Independent consumers learn the fact over time. Notification, analytics, and recommendation processing.
4 Consumers record their own result. Receipt may be sent later; analytics may lag. Their delay, provided it is visible and repairable.

The intermediate states matter. Do not jump from “payment request sent” to “purchase complete.” A slow or ambiguous payment result may require payment_pending. An enrollment command may return pending when seat allocation has a separate constraint. Those are honest states, not failures of the model.

Consider one failure path. Billing authorizes payment. Checkout delivers the enrollment command but loses the response. Checkout cannot infer whether enrollment acted from the lost response alone. The correct next move is to look up or reconcile the named enrollment operation, using its stable identifiers. It should not casually send a second unrelated “grant seat” action. That detail belongs to the command’s recovery design, even if the delivery mechanism is asynchronous.

So far, the design has separated a user-facing prerequisite from downstream consequences. The learner can receive a truthful result as soon as payment and access are established. Later consumers can work independently, but their work has a named state and owner rather than disappearing into a queue.

The Trade-off Is About Time, Not Fashion

Synchronous requests buy immediate clarity. They cost availability and latency coupling: the caller waits for the callee’s answer. They are a good fit when a decision changes the current user promise.

Commands and events can reduce that timing coupling. They cost lifecycle work: contracts, deduplication, ordering decisions, monitoring, and repair paths. They are a good fit when the work can finish later or when a fact has independent consumers.

This trade-off does not mean “use events everywhere.” An event is a poor substitute for a required decision. If checkout publishes payment_requested and assumes enrollment will eventually grant access, it still needs to answer: who owns the case where enrollment never acts? If the answer is “checkout waits and retries until enrollment does it,” the system has recreated a command but hidden its accountability.

Nor does a message broker make a command safe by itself. A broker can retain or redeliver a message. It cannot decide whether two deliveries represent one enrollment, whether the seat should still be granted, or what the learner sees while the result is unknown. Those are domain decisions.

The boundary appears in observable signals. For a request, inspect latency, timeout rate, and the number of operations left without a result. For a command, inspect pending age, duplicate recognition, and failed work by owner. For an event, inspect consumer lag, delivery failures, and whether each consumer can recover its own projection. These signals tell the team whether the promise still matches the real system.

Design Review

Use this sequence before choosing a protocol:

  1. Write the business statement. “Checkout must know payment before it claims success” is clearer than “make a synchronous API.”
  2. Name the authority. Which service owns the decision or state that makes the statement true?
  3. Classify the intent. Is the caller asking for an answer, assigning work, or announcing a completed fact?
  4. State the waiting rule. Does the user wait for this result, see a pending state, or never need to see it?
  5. Name recovery. When delivery or a reply is ambiguous, which identifier and authoritative record settle it?
  6. Choose the transport last. HTTP, gRPC, a queue, or a broker should support the prior answers rather than define them.

The method is a situated preference, not a universal sequence enforced by every team. Small services may use one request-response API for several intentions. The benefit of naming intent remains: a later split will not have to reverse-engineer whether a payload was a required action or an optional fact.

Common Confusions

Confusion: “Asynchronous means nobody waits.”

Why it is tempting: the sender can return before a consumer finishes.

Better model: someone still owns the unfinished work. The system needs a pending state, an owner, and a recovery path even when the original caller has moved on.

Confusion: “An event is a command with a friendlier name.”

Why it is tempting: both can be delivered as messages.

Better model: a command asks a known receiver to act. An event reports that a fact occurred and lets receivers choose their reaction.

Confusion: “One successful response proves the whole purchase workflow is complete.”

Why it is tempting: a request-response UI wants a single outcome.

Better model: define which authoritative states satisfy the user promise. Later effects may be incomplete without invalidating payment or access.

Check Your Understanding

Check: The product team says that a recommendation refresh may take ten minutes after a purchase, but course access must appear before checkout reports success. Which interactions should block checkout?

Think first, then reveal.

Answer: Billing and enrollment results should block only to the extent needed to establish a truthful payment and access outcome. The recommendation refresh should consume a completed fact later. Its lag is an operational concern, not a reason to deny access.

Check: Analytics receives enrollment.granted and, if its database is down, no report is produced. Has enrollment failed?

Think first, then reveal.

Answer: Not necessarily. Enrollment already announced its authoritative fact. Analytics owns recovery for its projection. The system should measure and repair that consumer failure, but it should not rewrite enrollment history to make the analytics database feel current.

Practice

Review this addition to the course platform: after a learner receives access, the platform must create a tax invoice. Finance needs the invoice eventually, but the learner does not need it before entering the course.

Choose an intent for the interaction between enrollment and invoicing. Then state the owner, the visible completion state, and one recovery signal.

A strong answer says that enrollment can publish an authoritative enrollment.granted event while invoicing owns invoice creation. It does not call the event a command merely because finance considers the work important. It names a state such as invoice_pending or invoice_created and a signal such as the age of pending invoices or failed consumer deliveries. If a jurisdiction instead requires an invoice before access, the constraint changes: invoice completion becomes part of the synchronous product promise or a command with a visible pending outcome.

Connections

The preceding migration lesson established that billing and enrollment need real ownership and authoritative writes. This lesson decides what their boundary says: a request for a needed decision, a command for owned work, or an event for a completed fact.

The next lesson makes the request and command edges operational. It adds deadlines, retry safety, workload identity, evidence, and truthful fallbacks when a network response is ambiguous. Later gateway and service-mesh lessons can enforce traffic controls, but they do not choose the business meaning of a message.

Key Takeaways

  • A communication pattern makes a promise about timing, responsibility, and recovery; it is not only a protocol choice.
  • Requests need an answer before the caller can continue, commands assign work to an owner, and events announce completed facts.
  • A user-facing workflow should wait only for the authoritative states that make its promise true.
  • Asynchronous work still needs visible state, an owner, and repair signals.
