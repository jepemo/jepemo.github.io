API Gateway Patterns

By the end of this lesson, you will be able to...

  • decide whether a client problem needs a gateway boundary or a direct service API;

  • design a composed gateway response with required data, optional data, and truthful degraded states; and

  • identify the point where edge adaptation becomes hidden domain ownership.

Idea in one sentence: An API gateway gives clients a stable, useful public edge, but it must translate and compose without taking over the business decisions of the services behind it.

Core Insight

Suppose a learner opens the mobile dashboard. The screen needs the learner’s name, active courses, subscription message, and one suggested next course. Those pieces belong to different services for good internal reasons. Identity owns the profile. Enrollment owns course access. Billing owns subscription state. Recommendations owns the suggestion.

The client should not need a map of that internal topology. It should ask for one screen. At first, the obvious solution is to let the mobile app call every service directly. That works while there is one client, internal APIs happen to fit its needs, and the service graph stays still.

It breaks when a service moves, when a browser and a mobile app need different shapes, or when each client must independently implement deadlines and partial-failure behavior. The mobile team becomes responsible for internal routing and every internal change becomes a client release.

The stronger model is a public edge. An API gateway receives the client request, applies boundary rules, calls the internal services needed for the public contract, and returns a client-shaped answer. The gateway owns the public shape and the edge behavior. It does not own whether a learner has access, whether a payment is valid, or which course is eligible.

The Promise We Need to Keep

The dashboard makes a small promise: it should show a learner’s core learning state quickly, and it should be honest when a secondary panel is not available.

Part of the response Domain owner Required for the core dashboard? Gateway’s job
Learner name Identity Yes Put the owner’s answer in the public response
Active courses Enrollment Yes Put the owner’s answer in the public response
Subscription banner Billing No Show it when available; use a defined absence or safe cached form otherwise
Recommendation panel Recommendations No Omit or mark unavailable without inventing a recommendation

This table is a teaching model for one product surface. Another product could make a billing result required before opening the screen. The key is to decide that from the user promise, not from whichever downstream call is easiest to make.

The public API is therefore not a mirror of service boundaries. Internal boundaries follow data authority and team ownership. The dashboard contract follows a client task. A stable public response lets the internal graph change more often than mobile client code.

The Naive Design: Expose the Service Graph

Without a gateway, the mobile app might execute this fanout:

mobile app
  -> identity/profile
  -> enrollment/active-courses
  -> billing/subscription
  -> recommendations/next

This approach is attractive because every call looks direct and simple. It also makes the client decide which request is mandatory, how long to wait, what headers to pass, and what to do when one call fails. A second client—say, the web dashboard—must repeat much of that logic.

Now apply pressure. The recommendations service takes 1.8 seconds during a deployment. The mobile user should still see their active course in a timely response. If every client has made recommendations a required call, the visible dashboard fails even though the core learning data is healthy. If one client silently omits the panel and another shows an old answer, users receive different promises by accident.

The observed request trace is the evidence that changes the design:

Dependency Result at the gateway deadline What the public contract needs to say
Identity Responded The learner name can appear
Enrollment Responded Active courses can appear
Billing Timed out The banner is unavailable or uses an explicitly safe fallback
Recommendations Timed out The panel is absent or marked temporarily unavailable

The problem is not that a mobile app is incapable of calling services. The problem is that the client has been made responsible for private topology and inconsistent failure semantics. A gateway can make the boundary decision once, close to the public contract.

A Better Boundary: Compose, Do Not Decide

The dashboard gateway endpoint can be described as a client contract first:

GET /mobile/dashboard

required:
  profile summary
  active courses

optional:
  subscription banner
  recommendation panel

Then the gateway maps that contract to internal calls:

gateway
  -> identity: profile summary             required
  -> enrollment: active courses            required
  -> billing: subscription display state   optional
  -> recommendations: next suggestion      optional

The gateway can own response field names, pagination shape, mobile-friendly aggregation, correlation context, coarse request validation, and a budget for each internal call. These are edge concerns because they describe how a client reaches the platform and receives a usable answer.

Enrollment still decides whether a course is active. Billing still decides what subscription state is true. The gateway must not recalculate those decisions from copied data or put its own eligibility rule between the client and the service owner. If a rule changes in the domain, the domain service should evolve its contract; the gateway should adapt the public representation only when necessary.

This is the boundary sentence to keep: the gateway may decide how to present a domain answer; the domain owner decides what the answer means.

A Worked Dashboard Request

Assume a 900 ms public response budget. The values below are illustrative rather than universal targets.

Step Gateway action Intermediate result Public consequence
1 Authenticate the caller and attach a correlation id. The request has a known client context. Reject invalid edge requests before fanout.
2 Request profile and active courses in parallel. Both are required for the core screen. If either cannot return a truthful answer within budget, return a clear retryable failure.
3 Request billing and recommendations with smaller remaining budgets. Both are optional panels. Their failure must not silently change enrollment or profile.
4 Compose the response. Profile and courses are present; recommendations timed out. Return the core screen without the recommendation panel.
5 Emit edge evidence. Correlation id, dependency outcome, response class, and timing are recorded. Operators can see which dependency caused degradation.

The gateway’s response might have a deliberate state rather than a pretend success:

{
  "learner": { "name": "Maya" },
  "active_courses": [{ "title": "Cloud Foundations" }],
  "subscription_banner": { "state": "unavailable" },
  "recommendation": null
}

Whether the word unavailable, an omitted field, or a cached display is right depends on the public contract. The important rule is that the response does not create false domain facts. A timeout from billing does not mean the learner has no subscription. A missing recommendation does not mean no recommendation exists.

So far, the gateway has simplified the client without pretending that a distributed fanout is a local function call. Required dependencies protect the core user promise. Optional dependencies have named degradation. The public response is stable even when internal services move or change their private APIs.

The Boundary Under Pressure

The same central position that helps the gateway can tempt teams to add business rules there:

healthy gateway:
  authenticate, route, adapt, compose, enforce public-edge rules

unhealthy gateway:
  decide enrollment eligibility, pricing, refunds, catalog publishing

Imagine a product request: “Only learners with an active subscription may begin the premium course.” A gateway could call billing and enrollment, then return a denial. That may look convenient. But who owns the rule when subscription grace periods, refunds, institutional licenses, and course exceptions arrive? If the gateway owns it, billing and enrollment become incomplete owners of their own facts.

A better design puts the policy with the service or workflow that owns access. The gateway can carry the caller identity and route the request. It can translate the owner’s result into a stable public response. It should not become the hidden source of truth for a business rule merely because it sees all the inputs.

The warning signals are practical:

  • domain teams must edit gateway code to change their own policy;
  • internal services shrink into data wrappers while the gateway makes outcomes;
  • an incident requires gateway code to explain a billing or enrollment decision; or
  • gateway releases become coupled to unrelated domain changes.

These signals reveal boundary erosion, not just a large codebase.

The Trade-off and Operational Consequences

A gateway improves client simplicity and protects clients from internal topology. It costs another critical request-path component. Aggregation adds latency, partial failures, and dependency budgets. A gateway outage can affect many client flows, so it needs clear ownership, telemetry, capacity planning, and carefully bounded work.

It is a good fit when external consumers need a stable contract that differs from internal ownership boundaries, or when several clients would otherwise repeat the same edge adaptation. It is less useful when it only forwards one service API without adding a public-boundary benefit. In that case, it can be another hop with another failure mode.

The gateway does not solve discovery, safe retries, authorization semantics, or service-level reliability. It depends on the earlier lessons for those concerns. It also does not make every internal call optional. A well-designed endpoint fails when its required information is unavailable, and degrades only where the product promise permits it.

Watch these signals:

Signal What it reveals
Public endpoint latency by dependency Whether one aggregated dependency consumes the response budget
Required versus optional failure rate Whether degradation matches the promised response shape
Fanout count per endpoint Whether a “small” public request is becoming an expensive distributed workflow
Gateway release coupling Whether domain changes are accumulating at the edge
Response fields omitted or marked unavailable Whether clients experience a real, observable degraded mode

Common Confusions

Confusion: “A gateway is just a reverse proxy with a new label.”

Why it is tempting: both can route traffic.

Better model: a gateway earns its role by managing a public contract, client adaptation, and explicit edge behavior. A forwarding-only layer may still be useful, but it has not yet solved a gateway problem.

Confusion: “The gateway should centralize all cross-service rules.”

Why it is tempting: the gateway can see many requests and responses.

Better model: visibility does not create domain authority. Keep business decisions with the services and workflows that own their data and consequences.

Confusion: “One public request should either fully succeed or fully fail.”

Why it is tempting: the response is one JSON object.

Better model: define which parts make the product promise true. Optional data may degrade, but that state needs an honest, observable contract.

Check Your Understanding

Check: A mobile dashboard needs profile and active courses. Its recommendation panel is slow. Should the gateway return the core dashboard?

Think first, then reveal.

Answer: Yes, if the contract marks recommendations as optional. Return the profile and active courses, then omit or mark the recommendation panel unavailable. The gateway should record the dependency failure; it should not report that the learner has no recommendation.

Check: A gateway receives a request to enroll in a premium course and has responses from billing and enrollment. Where should the premium-access rule live?

Think first, then reveal.

Answer: With the service or workflow that owns access policy and its consequences. The gateway may authenticate, route, and present the result, but it should not become the independent owner of enrollment eligibility.

Practice

A partner integration needs one shipment-status endpoint. Internally, the platform has order, warehouse, carrier, and returns services. The partner needs order identity and current shipment state; carrier tracking detail is useful but may be delayed.

Design the smallest gateway contract. Mark the required and optional internal data, choose one truthful degraded response, and name one rule that must remain in a domain service.

A strong answer makes order identity and the owner’s current shipment state required. It treats carrier detail as optional and returns a defined unavailable or delayed tracking state rather than a false delivery claim. It keeps rules such as whether a return cancels shipment with the order or returns owner, not in the gateway.

Connections

The preceding scheduling and discovery lessons explain why internal endpoints can move without changing a client contract. A gateway is one public surface over that dynamic interior; it still relies on discovery and call policies beneath it.

Key Takeaways

  • A gateway stabilizes a public client contract while the internal service graph can evolve.
  • A composed response needs explicit required data, optional data, deadlines, and truthful degraded states.
  • The gateway owns translation and presentation at the edge; domain services own the meaning of business decisions.
  • A gateway that collects unrelated domain rules becomes a new central bottleneck.
