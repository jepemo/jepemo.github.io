Kubernetes and Declarative Cloud Operations

By the end of this lesson, you will be able to...

  • trace how a declared workload becomes running, ready capacity;

  • investigate why a rollout has stopped without treating an applied manifest as proof of success; and

  • distinguish a platform control loop from application-level correctness.

Idea in one sentence: Kubernetes stores the state we want, repeatedly compares it with what the cluster can see, and uses controllers to narrow the gap—but it can only act on truthful workload signals and declared constraints.

Core Insight

The learning platform runs three enrollment replicas. On Monday, the team releases enrollment:v2. The deployment command succeeds. Five minutes later, only the old version receives traffic, and the rollout has not completed.

The first reasonable model is: a deployment command starts new containers, so a successful command means the new version is live. This model works in a small manual setup, where one operator starts one process and immediately sees it running.

It stops working when a platform must survive node loss, restarts, scaling, and gradual rollout. A command can record the requested change while the cluster still lacks a place to run a pod, cannot pull an image, or has a running process that is not safe for traffic. The command changed the intention. It did not prove the outcome.

Kubernetes uses a different operational model: desired state plus reconciliation. A declaration says what should be true. Controllers observe live state, act to reduce the difference, and observe again. This makes routine recovery repeatable. It also makes the system indirect: to debug it, an engineer must read the gap between intent, observed state, controller status, and workload evidence.

The Small Situation

Keep four actors in view:

Deployment:   enrollment should have 3 available replicas of v2
Controller:   notices when the live workload differs from that target
Pods:         run the containers that may eventually serve enrollment traffic
Service:      sends traffic only to pods that are ready

The exact object graph has more detail in a real cluster. For this lesson, it is a teaching model. The important relationship is that Kubernetes separates a stable request—“keep three usable enrollment replicas”—from the changing processes and machines that may satisfy it.

Suppose the team changes the desired image from v1 to v2 and asks for a gradual rollout. The goal is not merely three container processes. The learner-facing goal is three replicas that can safely serve enrollment requests while the old version is replaced.

That distinction gives us two observable states:

desired:   3 available enrollment:v2 replicas
observed:  3 available enrollment:v1 replicas; 0 available v2 replicas

The difference is the reconciliation gap. Kubernetes does not need an operator to write a separate “start one new process” command each time reality changes. Controllers keep working toward the declared target until they converge, wait on a constraint, or report a failure condition.

The Initial Model Breaks During a Rollout

Imagine the team applies the update and sees a success response from the API. It is tempting to stop there. But “accepted the declaration” and “reached the declared state” are different facts.

Statement What it actually establishes What it does not establish
The update was accepted. The API stored a new desired configuration. A new pod exists or is healthy.
A new pod is running. A process has started. The process can serve enrollment traffic.
A pod is ready. The workload reported that it can receive the traffic covered by its readiness contract. The release is semantically compatible with every dependency.
The rollout is complete. The controller sees its declared availability and rollout conditions satisfied. The product change is correct for every business case.

This is the pressure that makes declarative operations useful. If a node disappears after the rollout, the desired state remains “three available replicas.” The controller can notice fewer available replicas and create replacement work. A one-shot command has no such continuing promise unless another system rebuilds it.

The stronger model is therefore not “YAML runs containers.” In plain English, it is a persistent desired condition with a feedback loop around it. The technical name for the loop is reconciliation.

The Moving Parts in a Reconciliation Loop

At a useful level of detail, the loop has four stages:

1. Desired state:   Deployment says what should exist and how it should roll out.
2. Observed state:  The platform records pods, readiness, availability, and conditions.
3. Controller work: It creates, replaces, scales, or waits to narrow the gap.
4. Evidence:        Status fields, events, probes, and workload telemetry explain the result.

The loop repeats. It is not a transaction that makes the cluster instantly correct.

declared v2, 3 available replicas
        |
        v
compare with observed capacity
        |
        +--> gap exists: create or replace workload
        |
        +--> constraint: wait and report condition
        |
        v
observe again

This loop explains why status is a first-class operational interface. The manifest tells us what was requested. Status and events tell us what the platform believes happened while trying to satisfy it. Logs and metrics from the workload tell us whether the application’s own claim of readiness is honest.

A Worked Rollout Trace

Use a deliberately small rollout. The timings and names are illustrative.

desired rollout policy: keep old replicas serving until a v2 replica is ready
desired final state:    3 available enrollment:v2 replicas
starting state:         3 available enrollment:v1 replicas

The following trace exposes the intermediate states that a successful apply hides.

Step Desired and observed state Controller or platform response What an engineer should infer
0 Desired and observed both say 3 available v1. No gap needs work. The prior rollout converged.
1 Desired image changes to v2; observed remains 3 available v1. The rollout controller creates work for one v2 replica. The request is stored; the rollout is not complete.
2 A v2 pod is scheduled and its container starts. The platform waits for the readiness signal. Running is not the same as available.
3 The v2 pod reports not ready because its required configuration is missing. The new pod is kept out of ready endpoints; the rollout cannot safely advance. The controller is preserving the old capacity rather than declaring victory.
4 Status and events show an unavailable new replica; application logs name the configuration error. The controller continues to observe and waits for corrected input. The problem is the workload or its declared configuration, not a controller that needs “rerunning.”
5 The team corrects the configuration; a v2 pod becomes ready. The rollout can retire an old replica and repeat the pattern. The gap is shrinking with evidence.
6 Three v2 pods are ready and old replicas are gone. Observed state now satisfies the declared rollout conditions. The workload rollout has converged.

So far, the controller has made the rollout inspectable. It did not guess that a configuration error was safe, and it did not send traffic to the unready pod. The old replicas remain useful capacity while the new one cannot satisfy its readiness contract.

What should the team inspect at step 4? Start from the outside and move inward:

  1. Read the Deployment’s intended replica count, image, rollout policy, and readiness configuration.
  2. Read its status and events to see whether the gap is scheduling, image retrieval, readiness, quota, or rollout progress.
  3. Inspect the new pod’s state and events.
  4. Inspect the workload logs and the signal behind readiness.
  5. Fix either the declaration or the application, depending on which one is wrong; then watch the next reconciliation cycle.

This investigation sequence matters because it prevents a common bad response: repeatedly reapplying the same manifest. Reapplying may be harmless, but it does not change a missing configuration value or make an unready workload truthful.

Readiness, Liveness, and Traffic Are Different Questions

Kubernetes needs workloads to report useful signals. A process can be alive yet unable to serve its contract: it may still be loading configuration, waiting for a required migration, or unable to initialize a critical dependency.

Signal or state Question it answers A safe enrollment example
Container running Did the process start? The enrollment binary is executing.
Readiness Should this replica receive enrollment traffic now? It has the configuration and local state needed to handle a request safely.
Liveness Is the process stuck such that restart is likely to help? A deadlocked process no longer makes progress.
Startup protection Should liveness wait while a known slow startup is still normal? A large cache warm-up is expected during the first minute.

Readiness and liveness are not two names for “healthy.” Readiness controls whether traffic should reach a pod. Liveness helps decide whether a restart is useful. If a liveness check is too eager, the platform can restart a slow process over and over. If a readiness check says “ready” when the service cannot honor its request contract, the platform can faithfully route traffic to a broken replica.

The readiness contract needs judgment. It should cover conditions that make the service unsafe for the traffic it receives. It should not automatically include every optional dependency. For example, if enrollment can record a request and show a pending payment state when an optional notification service is down, notification failure need not make every enrollment replica unready. The correct signal follows the service’s real degraded-mode design.

What Kubernetes Does—and Does Not—Control

Kubernetes improves operational repeatability. It can keep declared replica capacity present, replace failed workload instances, control a gradual rollout, and respect readiness when routing is configured around it.

This buys the team recovery from ordinary infrastructure drift. It costs indirectness: an engineer must understand controller conditions, delayed convergence, and health signals instead of expecting a single imperative command to prove the result. It can still fail when the desired declaration is wrong, the cluster lacks resources, probes lie, or the application has a semantic defect that process health cannot see.

The trade-off is repeatable convergence versus direct control: Kubernetes removes many one-off recovery steps, but the team must diagnose through a control loop whose result arrives over time.

Most importantly, Kubernetes does not define the service contract. A pod may be ready while enrollment:v2 emits an event that billing cannot interpret. A rollout may converge while a migration corrupts a business rule. The platform has proved a workload condition, not cross-service compatibility, idempotency, or product correctness. Those remain responsibilities from the boundary and communication lessons.

The signal to watch is the gap itself: desired replicas versus available replicas, rollout conditions, readiness failures, scheduling events, and user-facing error or latency signals. Seeing “three pods exist” is weaker evidence than seeing the declared availability condition and the relevant service behavior together.

Common Confusions

Confusion: “Applying a manifest deploys the application.”

Why it is tempting: the API accepts the declaration immediately.

Better model: applying requests a target state. Deployment is a continuing process of reconciliation, observed through status and workload evidence.

Confusion: “A running container is ready.”

Why it is tempting: starting a process is visible and easy to test.

Better model: running proves much less than safe traffic handling. Readiness must express the service contract for that traffic.

Confusion: “Kubernetes makes rollout safe.”

Why it is tempting: it can replace replicas and pause on failed readiness.

Better model: Kubernetes makes workload convergence controllable. API compatibility, data migration safety, and domain behavior still need their own design and evidence.

Check Your Understanding

Check: A rollout has three old replicas serving traffic, one new replica running but not ready, and a Deployment condition showing insufficient available replicas. What is the most useful next question?

Think first, then reveal.

Answer: Ask why the new replica is not ready. Read the Deployment and pod status/events, then the workload’s readiness evidence and logs. The controller is already showing the reconciliation gap; deleting old replicas or rerunning the manifest would remove useful capacity without resolving it.

Check: A pod passes liveness but fails readiness. Should the platform restart it immediately?

Think first, then reveal.

Answer: Not from that evidence alone. Liveness says whether a restart is likely to help. Readiness says whether traffic is safe now. A process can be alive, still initializing, or waiting for a condition that restart will not fix.

Trace It Yourself

An enrollment release requires three available replicas. After an update, two old replicas are ready, one new replica is running but not ready, and one replacement pod is pending because no node currently has sufficient requested resources.

Describe the reconciliation gap and choose the first two evidence sources you would inspect. Then name one fix that changes desired state and one fix that changes the workload or cluster reality.

A good answer should mention:

  • that the declared availability target is not yet met;
  • that readiness and scheduling are separate blockers with separate evidence;
  • Deployment/pod status and events as the first sources, followed by relevant workload signals;
  • a declaration change only if the requested resources or rollout policy are wrong; and
  • a reality change such as freeing capacity, adding suitable nodes, or fixing the readiness failure when the declaration is correct.

Key Takeaways

  • Kubernetes reconciles a stored desired state with observed cluster state; an accepted declaration is not a completed rollout.
  • A rollout trace must distinguish running, ready, available, and semantically correct.
  • Readiness governs traffic, while liveness guides restart decisions; both signals must tell the truth about their different questions.
  • Controllers make infrastructure convergence repeatable, but they do not replace service compatibility or domain correctness.
