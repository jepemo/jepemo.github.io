Progressive Delivery and Runtime Traffic Control

By the end of this lesson, you will be able to...

  • distinguish deploying a version from exposing users to it;

  • turn a canary into an evidence-based promote, pause, or rollback decision; and

  • identify the compatibility condition that makes traffic rollback meaningful.

Idea in one sentence: Progressive delivery limits exposure to a change, measures the result, and moves traffic only when predefined technical and product evidence supports the next step.

Core Insight

Suppose enrollment version 2 changes seat reservation for a popular certification. The new workload starts successfully in the cluster. The tempting conclusion is that the release is complete. It works only if a running pod is the same thing as correct user behavior.

It is not. A new version can be healthy while duplicating reservations, increasing payment uncertainty, or confusing a small cohort of learners. The stronger model separates three actions:

deployment: make v2 runnable
exposure: choose which traffic reaches v2
promotion: expand exposure only after evidence

Progressive delivery is the control loop that joins them. The platform deploys v2, exposes a small and deliberate slice, observes both traffic and domain outcomes, then promotes, pauses, or removes exposure. A canary without a decision rule is merely a slower broad release.

The Production Situation

The platform keeps enrollment v1 and v2 running together. The risk is not only an HTTP error. A learner can see a successful seat hold while billing receives a mismatched attempt, or an old version can be unable to read a record written by the new version.

Actor Role during the change Evidence it needs
Orchestrator Keeps both versions runnable Workload readiness and capacity
Gateway or mesh Sends an eligible cohort to one version Route and cohort outcome
Enrollment owner Defines correct reservation behavior Conflicts, pending age, and user state
Billing owner Checks payment relationship Attempt mismatch or duplicate evidence
Release owner Makes promotion decision Predefined technical and domain signals

The first model says “send five percent to v2.” The missing question is why five percent is safe, what success looks like, and what happens if it is not. Exposure is a product-risk decision, not just a routing percentage.

A Worked Canary Plan

Assume these illustrative steps:

Step Exposure Required evidence before the next step Action if evidence fails
0 v2 receives no learner traffic Readiness and compatibility checks complete Do not expose
1 Internal test cohort Expected reservation and payment trace Pause and repair
2 1% of eligible learners Error, latency, conflict, and mismatch rates remain within the agreed baseline Route cohort back to v1 or disable the changed behavior
3 5%, then 25% The same signals remain healthy over the agreed window Hold or reduce exposure
4 100% Support and reconciliation evidence agrees with traffic signals Complete rollout only when rollback boundary remains understood

The values are a teaching model, not universal rollout thresholds. The reasoning is the point. A release criterion must be written before traffic moves; otherwise operators can rationalize a bad signal while the cohort grows.

Trace one failure. At 5%, v2’s HTTP error rate remains low, but seat-reservation conflicts double and billing sees more unmatched attempts. Infrastructure health alone says “green.” Product evidence says that a core promise is breaking. The release owner pauses promotion and routes the cohort back to v1, or disables the new reservation behavior if that is the narrower safe control.

This is why traffic routing, feature flags, and workload rollout must form one plan. The gateway may select public learners. A mesh may direct the internal checkout-to-enrollment call. A feature flag may enable the changed reservation rule. The orchestrator keeps both versions available. If those layers make independent decisions, the team cannot explain which control exposed the defect.

Compatibility Makes Rollback Real

Routing traffic away from v2 is not always a rollback. It is only useful when v1 can still read the relevant records and users are not left with irreversible side effects.

Before exposure, answer:

  • Can v1 and v2 read the same enrollment state?
  • Does an API or event change remain compatible for the coexistence window?
  • Which effects cannot be undone by a routing change, such as a payment, email, or reservation?
  • Which owner reconciles a learner whose request crossed versions during the pause?

The traffic policy limits who sees risk. Compatibility limits whether the platform can recover after a bad signal. A version that writes an unreadable format can make a green rollback button misleading.

Make the Decision Auditable

The release owner should be able to reconstruct one affected learner path without guessing. For a learner in the canary cohort, record the version selected, the routing rule or feature flag that selected it, the logical enrollment and billing attempt identifiers, and the decision made at the exposure step. These are not decorative logs. They connect a user report to the release control that changed the path.

For example, suppose the first conflict appears at 5%. The useful question is not simply “is v2 broken?” Compare one v2 attempt with a matching v1 attempt. Did both reach the same reservation rule? Did the new version create a different state transition? Did a flag select the new behavior even when routing selected v1? This short trace prevents teams from rolling back the wrong layer.

A good pause condition is actionable. “Error rate is high” is weak when the user harm is duplicate seat holds. “Pause when reservation conflicts for the canary cohort exceed the agreed baseline, then route new cohort traffic to v1 and reconcile open attempts” names a signal, a boundary, and an owner. It improves decision speed, but it costs preparation: teams must agree on the baseline and repair path before the launch window.

The plan remains useful only when that decision record stays available during the incident.

Investigation and Signals

When a canary is unhealthy, inspect in this order:

  1. Identify the cohort, version, route, and flag state for the affected request.
  2. Compare v1 and v2 latency, errors, retries, saturation, and route decisions.
  3. Check domain evidence: reservation conflicts, pending attempt age, payment mismatches, and learner-visible outcomes.
  4. Pause expansion before trying to explain the metric away.
  5. Use the predesigned rollback or flag control, then reconcile work that crossed the boundary.
Signal Why it matters
Error and latency by version and cohort Shows whether v2 changes the request path
Reservation conflicts Tests the new domain behavior directly
Billing mismatch and pending age Finds harm that an HTTP success may hide
Retry volume Shows whether clients amplify a degraded version
Route and flag state Makes exposure explainable during investigation

The Trade-off and Boundary

Progressive delivery improves safety by slowing broad exposure. It costs time, routing complexity, telemetry, compatible versions, and an operator decision loop. It does not solve a bad service boundary, unsafe retry semantics, or an irreversible data migration.

It is useful when change risk is meaningful and the team can observe the effect. A one-off change with no compatible rollback path may need a different migration plan rather than a superficial canary. The boundary is visible when the platform cannot name the cohort, criteria, rollback action, or reconciliation owner.

Common Confusions

Confusion: “Deployed means released.”

Better model: a deployed workload can receive zero traffic. Release is the decision to expose users.

Confusion: “A healthy pod proves a safe version.”

Better model: infrastructure health is necessary evidence. Domain outcomes and user-visible behavior determine whether promotion is safe.

Confusion: “Traffic rollback reverses every effect.”

Better model: routing can reverse exposure. Data and side effects need compatibility and reconciliation plans.

Check Your Understanding

Check: v2 has normal latency but its reservation-conflict rate doubles at 5% exposure. Should the team promote?

Think first, then reveal.

Answer: No. Pause or reduce exposure according to the plan. The domain signal contradicts the idea that the version is safe, even if the infrastructure metrics look healthy.

Practice

Design a three-step rollout for a change to invoice generation. Name the cohort, one technical signal, one domain signal, the pause condition, and the rollback or reconciliation action.

A strong answer separates deployment from exposure, uses a small cohort, observes invoice duplicates or pending age as a domain signal, and explains how old and new versions can coexist before traffic is restored.

Key Takeaways

  • Deployment, exposure, and promotion are separate release decisions.
  • Canary signals must include domain outcomes as well as infrastructure health.
  • Traffic rollback is useful only when compatibility and reconciliation keep user state coherent.
  • A release plan needs a cohort, signals, pause action, and owner before exposure begins.
