Microservices Migration and Operating Model

By the end of this lesson, you will be able to...

  • plan one small service-extraction slice with ownership, evidence, and rollback;

  • investigate whether a migration is creating distributed cost without real autonomy; and

  • decide when to pause expansion because the operating model is not ready.

Idea in one sentence: A service extraction succeeds only when the new runtime boundary gains a real owner, an authority boundary, observable contracts, and a safe way to change or reverse the first workflow slice.

Core Insight

Suppose the learning platform has decided that billing is a credible service boundary. Billing owns payment attempts, refunds, invoices, and the audit trail that explains them. The team now wants enrollment to call a new billing service for a paid-course authorization.

The tempting model is: move the billing code to a new repository, add an API, and migrate every caller. It looks like progress because a new deployable exists.

On the first incident, the limitation appears. Enrollment times out while billing is being deployed. A support tool still writes a payment record directly into the old database table. Nobody can say which path created an invoice. The billing team owns the code, but a central release group still approves every change and only another team can see the cross-service trace.

The runtime is distributed. The operating model is still monolithic.

The stronger model is an incremental migration that proves four things together: who owns the behavior, who may write authoritative state, what contract callers use, and how operators see and reverse the change. Extraction is not a code relocation project. It is a controlled change to responsibility.

The Small Situation

The first slice covers paid enrollments for one course family. Enrollment asks billing to authorize one payment attempt. Billing records that attempt, and enrollment can either confirm access or show pending_payment. The observable failure is simple: if the learner sees pending, an operator must be able to find the same attempt and decide what happens next.

The Production Symptom

During the first paid-course migration slice, a learner sees payment pending after enrollment has called billing. Support asks a simple question: “Did we charge the learner?” The answer should be reachable from one trace and one authoritative payment attempt.

Instead, the team finds:

enrollment log:       request to new billing API timed out
new billing service:  deployment was in progress
old billing module:   support tool can still insert a payment row
dashboard:            only the platform team can link the request path

This is not merely a deployment failure. It reveals a migration design gap. Several paths can create or alter a payment fact, the operation has no single support owner, and the evidence does not tell an operator which state is authoritative.

The user impact is not only delay. An ambiguous payment can lead to duplicate charges, missing access, or a support escalation that requires a room full of people. The operational goal is to make one path, one owner, and one recovery state visible before more traffic depends on the new boundary.

The First Slice Should Be Small Enough to Explain

Do not begin by moving every billing behavior. Pick one path whose result can be compared and supported. For example:

scope: paid enrollment for one course family
new responsibility: billing service authorizes and records payment attempts
caller: enrollment service
fallback: show pending_payment; do not silently grant paid access
old path: remains available only for traffic not yet migrated

This is a teaching example. The important property is bounded blast radius. A migration slice has a named caller group, one business outcome, known evidence, and an explicit stop condition.

Before routing production traffic, the team should be able to fill this table:

Question Evidence that makes the answer real
Who owns billing’s production promise? A team receives the alerts, owns the runbook, and can change the service.
Which state is authoritative? Billing is the only writer for payment attempts; other systems use its contract or projections.
How does enrollment call it? A versioned request/response or message contract with a clear timeout and pending outcome.
How can an operator trace one attempt? Trace context plus enrollment and billing attempt identifiers join logs and records.
How can the team stop the change? A documented traffic switch or rollback that preserves the authoritative attempt record.

If a row remains vague, the team has learned something useful: extraction is not ready to expand.

The Migration Path Is a Sequence of Authority

The safe path starts before a network call. First make billing behave like an owner inside the existing application. Then move a narrow workflow across the boundary.

1. Protect the billing module and stop new direct writes.
2. Establish billing as the authority for payment attempts.
3. Expose one stable internal contract and record common identifiers.
4. Route one caller slice through the new service.
5. Observe outcome, supportability, and rollback evidence.
6. Retire the old path only after the new path owns the slice.

The phrase “stop direct writes” needs care. A transitional shared database can exist while a system is being untangled. It is not proof that the boundary is healthy. The direction of travel matters: billing should become the single decision-maker for payment writes, and every temporary bypass needs a named owner, limit, and removal plan. Otherwise the database remains the real integration layer and the API is decoration.

Likewise, a contract is more than an endpoint. Enrollment needs to know the possible payment outcomes, the idempotency identity of a request, and what it should show if billing cannot answer promptly. Billing needs to know which callers are allowed and which fields form the audit record. The next lesson will choose synchronous requests, commands, and events in more depth; this lesson only requires a contract that makes the migration inspectable.

A Worked Migration Trace

Follow one paid enrollment through the first slice.

Step What changes Evidence to inspect Decision
0. Baseline The old module handles the course family. Existing success/error rate, support path, and payment records. Define the comparison point.
1. Authority test Enrollment and support tools stop creating payment attempts directly. Audit or access evidence shows billing owns the write. Do not route traffic until bypasses are controlled.
2. Contract test Enrollment sends authorize(enrollment_id, amount, idempotency_key). Contract test and trace show the same identifiers on both sides. Verify callers do not depend on billing internals.
3. Limited route A small cohort uses the new billing service. Payment outcomes, timeout rate, duplicate-attempt count, and pending age. Expand only if results and support evidence agree.
4. Incident Billing is slow during a deployment. Trace, billing attempt record, and route state identify the source. Keep enrollment at pending_payment; pause expansion if recovery is unclear.
5. Repair Team fixes the deployment or dependency issue. The same attempt reconciles to authorized, declined, or failed. Resume the slice only after the runbook works.
6. Retirement New path owns the cohort consistently. No old writes or old-route traffic for the slice. Retire the old behavior for that slice, then choose the next one.

The values and routes are illustrative. The reasoning is the point. The team does not need two independent payment truths. It needs one authoritative attempt whose result can become visible even when the first request is ambiguous.

So far, the migration has tested autonomy in production without betting the whole billing domain on one release. A successful request is weak evidence. A successful support investigation and a safe rollback are stronger evidence that the operating model has changed too.

Investigate Before You Expand

Treat these signals as migration readiness checks:

Signal What it may reveal First response
Direct writes still appear outside billing Authority remains split. Block or replace the bypass before widening traffic.
Missing trace links or unmatched attempt ids The workflow cannot be supported under uncertainty. Fix correlation and runbook evidence.
New-path error or timeout rate rises above its agreed baseline The contract or runtime path is not stable enough. Pause expansion and inspect the failing dependency path.
Many old-path fallbacks remain The slice is not actually owned by the new boundary. Identify why callers still bypass it.
One central group must approve or repair every change Team ownership is not yet operational. Clarify alert, deployment, and decision authority.

An alert should point to a decision, not merely a graph. For example, a rising count of pending_payment attempts older than the agreed recovery window tells the billing owner to reconcile attempts and tells the migration owner to stop routing additional cohorts. A generic “service error rate is high” is helpful, but it does not alone say whether money or access is at risk.

Mitigation and Prevention

When evidence is incomplete, contain the migration before trying to make it look successful.

  1. Pause expansion. Keep the current cohort small; do not migrate more callers while authority or recovery is ambiguous.
  2. Preserve a truthful user state. Use a visible pending outcome rather than inventing payment success or failure.
  3. Reconcile from the owner’s record. Billing, not the gateway or a copied table, determines the payment attempt result.
  4. Use the designed rollback. Stop new routing to the slice if needed. Do not restore old direct writes that would create a second authority path.
  5. Fix the missing capability. It may be a contract, trace, alert route, access rule, deployment control, or team responsibility—not necessarily code.

Prevention is not a bigger migration meeting. It is a stronger operating envelope: clear ownership, protected writes, consumer-compatible contracts, cross-service telemetry, a practical runbook, and a release path the owning team can operate. Shared platform standards help, but they must support autonomy rather than recreate a universal approval queue.

The trade-off is migration speed versus evidence-backed independence. Moving slowly costs time and may retain a real monolith bottleneck. Moving faster than the organization can observe and recover creates a distributed monolith with more failure paths. The useful choice is the smallest slice that creates enough evidence to justify the next one.

Common Confusions

Confusion: “A new repository creates a new owner.”

Why it is tempting: repository boundaries are visible.

Better model: ownership is real when a team can protect writes, deploy, observe, respond, and evolve the service contract without hidden central coordination.

Confusion: “A shared database is always forbidden during migration.”

Why it is tempting: shared storage is a common service-boundary failure.

Better model: a temporary shared store may be a migration constraint, but the write authority must move toward one owner. Treat every bypass as debt with a removal path, not as a permanent integration strategy.

Confusion: “Contract tests prove the migration is safe.”

Why it is tempting: they make interface compatibility visible before deployment.

Better model: contract tests are necessary evidence, not complete operational evidence. Production traces, outcome reconciliation, support practice, and rollback behavior test the system under its real failure paths.

Check Your Understanding

Check: Enrollment calls billing successfully, but a support tool can still insert payment attempts directly into the old table. Has billing become the authoritative service?

Think first, then reveal.

Answer: Not yet. The direct-write bypass means more than one actor can create the state that billing is supposed to own. Protect the write boundary and provide support through billing’s contract or controlled operations before expanding the migration.

Check: A new billing cohort has a low error rate but operators cannot connect an enrollment timeout to a payment attempt. Should the team migrate more traffic?

Think first, then reveal.

Answer: No. Low error rate does not make ambiguous outcomes supportable. Add shared identifiers, traces, and an authoritative reconciliation path first; otherwise the migration will fail precisely when timing becomes uncertain.

Practice

The platform wants to extract refund handling next. Refunds are rare but audit-sensitive. The billing team owns payment records, while support needs a controlled way to initiate refunds and enrollment needs to react when a refund is complete.

Design the first migration slice. A good answer should mention:

  • the owner of the refund decision and authoritative write;
  • one caller or refund class to migrate first;
  • a contract, identifier, and trace that allow reconciliation;
  • a truthful pending or review state when an external provider is slow; and
  • the specific signal that would pause expansion or trigger rollback.

One reasonable answer routes staff-initiated refunds for one course family through billing first. Support submits a refund command with a refund id; billing records the authoritative attempt and publishes a completed fact for enrollment. If the provider result is uncertain, the refund stays pending rather than being repeated blindly. The team pauses expansion when pending refunds age beyond the recovery window or when direct writes reappear outside billing.

Key Takeaways

  • An extraction becomes real only when ownership, authoritative writes, contracts, evidence, and rollback mature with the deployable unit.
  • Migrate one explainable workflow slice and use supportability as production evidence before expanding.
  • A temporary shared store is a constraint to unwind; permanent shared writes erase the authority boundary.
  • Pause a migration when outcomes cannot be reconciled or the owning team cannot operate the path independently.
