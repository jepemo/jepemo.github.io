Day 084: Cache Invalidation and Freshness Control

Caching becomes difficult not when you store data, but when the source changes and you must decide who is allowed to keep believing the old answer for how long.

Today's "Aha!" Moment

The insight: Cache invalidation is really a freshness-control problem. The hard part is choosing when stale data is acceptable, when it must be replaced immediately, and how to keep those rules understandable under real traffic.

Why this matters: Almost every useful cache eventually faces the same question: what happens when the source of truth changes? If the answer is vague, stale reads, race conditions, and cache stampedes follow.

Concrete anchor: The learning platform updates a course price from 49 to 59. If some caches keep serving the old price for too long, the product experience and business logic may diverge in confusing ways.

The universal pattern: Source update + cached copies + unclear freshness rule -> stale or inconsistent behavior.

How to recognize when this applies:

  • Cached values are derived from data that changes.
  • Several cache layers may keep independent copies.
  • Some fields are harmless to show stale and others are not.
  • Traffic spikes happen when a hot key expires.
  • Teams talk about caching benefits but not about cache replacement rules.

Common misconceptions:

  • [INCORRECT] "A short TTL solves cache invalidation."
  • [INCORRECT] "Strong freshness always requires deleting everything immediately."
  • [CORRECT] The truth: TTL, explicit invalidation, versioning, and refresh strategies are different ways to control freshness. The right one depends on the domain and the operational cost of staleness.

Real-world examples:

  1. TTL-based expiry: Good for data that can be briefly stale.
  2. Event-based invalidation: Better when changes should quickly propagate.
  3. Versioned cache keys: Useful when new content should coexist with old content until references update.
  4. Stampede protection: Helps when many requests race to refill one hot key.

Why This Matters

The problem: A fast cache that serves the wrong value too long can be worse than a slower system that stays correct and predictable.

Before:

  • Picking TTLs arbitrarily.
  • Invalidating some keys manually while others expire whenever they happen to.
  • Discovering stale-read problems only after users report them.

After:

  • Defining freshness requirements explicitly by data type and workflow.
  • Choosing invalidation mechanisms that match domain needs.
  • Planning what happens when hot keys expire or many readers arrive at once.

Real-world impact: Strong freshness control reduces confusing user behavior, protects hot systems during refill events, and makes caching safer to operate at scale.

Learning Objectives

By the end of this session, you will be able to:

  1. Explain why invalidation is hard - Connect stale reads to source changes, multiple cache layers, and unclear freshness rules.
  2. Compare invalidation strategies - Distinguish TTL-based, event-based, and version-based approaches conceptually.
  3. Reason about refill behavior - Understand why hot-key expiration and cache stampedes need deliberate handling.

Core Concepts Explained

Concept 1: TTL Is Simple but Only Works When Bounded Staleness Is Acceptable

Concrete example / mini-scenario: The course description can remain stale for two minutes without much harm, so a short TTL may be enough even if updates do not propagate instantly.

What it is: TTL-based invalidation lets cache entries expire automatically after a chosen interval.

Why it matters: TTL is easy to implement and often good enough for data that does not require immediate freshness.

How it works: The cache keeps a value until the TTL ends. After expiry, the next request must refetch or recompute the value.

Mental model: TTL is a freshness timer attached to every cached answer.

When to use it:

  • [Ideal situation] Read-heavy data where a bounded stale window is acceptable.
  • [Anti-pattern] Critical values where even short stale windows cause user or business problems.

Concept 2: Event-Based or Versioned Invalidation Fits Stronger Freshness Needs

Concrete example / mini-scenario: The course price changes and the system emits an update event that deletes or supersedes the cached key quickly, because checkout should not keep reading the old value.

What it is: Event-based invalidation reacts when the source changes, while versioned invalidation uses new keys or versions so readers naturally move to fresh values.

Why it matters: Some domains need fresher reads than TTL alone can safely provide.

How it works: On source update, the system deletes affected cache keys, refreshes them, or points readers to a new versioned key namespace.

Mental model: TTL waits for time to pass. Event-based invalidation listens for change. Versioning publishes a new edition instead of rewriting the old one in place.

Code Example (If applicable):

def update_course_price(db, cache, course_id, new_price):
    db.update_course_price(course_id, new_price)
    cache.delete(f"course:{course_id}:price")

Note: This is the simplest invalidation flow. Real systems may invalidate several derived keys or publish a change event for other services.

When to use it:

  • [Ideal situation] Data whose freshness matters closely to correctness or user trust.
  • [Anti-pattern] Immediate invalidation everywhere without considering operational cost or derived-key complexity.

Concept 3: Refill Strategy Matters When Hot Keys Expire Under Load

Concrete example / mini-scenario: A very popular course page cache key expires, and thousands of users arrive within seconds. If every request refills independently, the database gets hammered all at once.

What it is: Refill strategy covers how the system handles cache misses, especially for popular keys and synchronized expiry moments.

Why it matters: A cache can shift load from the source most of the time but still create dangerous bursts if many readers miss simultaneously.

How it works: Systems may use request coalescing, jittered TTLs, prewarming, or stale-while-revalidate behavior so hot keys do not cause synchronized refill storms.

Mental model: The hardest moment for a cache is often not the hit; it is the crowd that arrives just after expiration.

When to use it:

  • [Ideal situation] Hot keys, bursty traffic, or expensive recomputation paths.
  • [Anti-pattern] Letting all misses refill independently on the most popular content.

Troubleshooting

Issue: Choosing TTLs by habit instead of by domain meaning.

Why it happens / is confusing: It is easy to pick round numbers like 60 seconds or 5 minutes without asking what stale data means for the actual workflow.

Clarification / Fix: Tie TTL and invalidation choice to user expectations, business correctness, and operational cost.

Issue: Forgetting that invalidation must include derived or aggregated views.

Why it happens / is confusing: Teams often remember the primary object key but forget list views, summary pages, or precomputed response caches built from that object.

Clarification / Fix: Map the full set of read paths that depend on the changed data, not just the most obvious key.

Advanced Connections

Connection 1: Invalidation ↔ Consistency Design

The parallel: Cache invalidation is one concrete form of consistency management because it determines how quickly readers observe updates.

Real-world case: Product prices, inventory counts, and profile changes all place different demands on freshness and stale-read tolerance.

Connection 2: Invalidation ↔ Traffic Shaping

The parallel: Expiration policy changes how load arrives at the source of truth, especially around hot keys and synchronized expiry.

Real-world case: Jittered TTLs and stale-while-revalidate often help prevent expensive thundering-herd behavior.

Key Insights

  1. Invalidation is a freshness-control problem - The difficulty is deciding when stale data stops being acceptable.
  2. Different freshness needs imply different strategies - TTL, event-based invalidation, and versioning each fit different domains.
  3. Hot-key refill needs design too - Cache misses under load can become their own production failure mode.

Knowledge Check (Test Questions)

  1. When is plain TTL-based invalidation often a reasonable choice?

    • A) When the system can tolerate a bounded stale window and simplicity is valuable.
    • B) When every update must be visible instantly to every reader.
    • C) When the team wants to ignore freshness entirely.

  2. What does event-based invalidation try to improve over TTL alone?

    • A) It reacts closer to the time of source changes when freshness matters more strongly.
    • B) It guarantees there will never be cache misses.
    • C) It removes the need to think about derived cached views.

  3. Why can hot-key expiration be dangerous?

    • A) Because many requests may race to refill the same expensive value and overload the source of truth.
    • B) Because it forces the cache to become permanent storage.
    • C) Because only one user can read the key afterward.

Answers

1. A: TTL works well when the system can name an acceptable stale window and simplicity outweighs the need for instant propagation.

2. A: Event-based invalidation is useful when waiting for TTL expiry would leave data stale for too long.

3. A: Popular keys can create a stampede after expiry if many requests all refill independently.
