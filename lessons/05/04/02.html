Day 097: Health Checks and Circuit Breakers

Resilient systems need mechanisms that answer two different questions clearly: should traffic still come here, and should this dependency still be called right now?

Today's "Aha!" Moment

The insight: Health checks and circuit breakers solve different resilience problems. Health checks tell the platform whether an instance should receive traffic. Circuit breakers tell the caller whether it is wise to keep calling a failing dependency.

Why this matters: Teams often group both patterns under "failure handling," but they act at different boundaries. One protects routing decisions. The other protects call chains from cascading failure.

Concrete anchor: The learning platform API depends on Redis and a payment provider. If one app instance loses database access, it should stop receiving traffic. If the payment provider starts timing out, callers should stop hammering it temporarily.

The universal pattern: Partial failure + repeated dependency calls + need to contain blast radius -> health and circuit policies.

How to recognize when this applies:

  • Some instances may be alive but not truly ready to serve traffic.
  • A failing dependency can drag many callers into timeout and retry storms.
  • Routing and dependency-call decisions need different signals.
  • The platform must isolate unhealthy parts without taking everything down.
  • Failure cascades matter more than a single error.

Common misconceptions:

  • [INCORRECT] "A /health endpoint solves all resilience concerns."
  • [INCORRECT] "Circuit breakers are only useful in microservices."
  • [CORRECT] The truth: Health checks and circuit breakers are separate control tools. One influences who should receive traffic; the other influences whether a caller should keep attempting a risky dependency call.

Real-world examples:

  1. Liveness checks: Detect whether a process is running.
  2. Readiness checks: Decide whether an instance should receive traffic.
  3. Circuit breaker open state: Stop calling a failing downstream service temporarily.
  4. Fallback behavior: Return degraded but safe behavior when a dependency is unhealthy.

Why This Matters

The problem: Partial failure is normal in production, but systems without control mechanisms often react by spreading that failure wider than necessary.

Before:

  • Unhealthy instances still receive traffic.
  • Callers keep hitting failing dependencies until everything times out.
  • One local problem turns into a broader outage.

After:

  • Traffic stops going to instances that are not ready.
  • Callers back off from dependencies that are currently unhealthy.
  • The system contains failure instead of amplifying it.

Real-world impact: These patterns reduce cascading outages, improve deploy safety, and help services degrade more predictably under dependency trouble.

Core Concepts Explained

Concept 1: Liveness and Readiness Answer Different Questions

Concrete example / mini-scenario: The API process is running, so liveness is fine. But the database connection pool is broken, so the instance is not ready to serve real traffic.

What it is: Liveness usually asks whether the process is alive at all, while readiness asks whether it should currently receive requests safely.

Why it matters: A process can be alive yet still harmful to route traffic toward.

How it works: Platforms and load balancers often use these checks to decide whether to restart an instance or remove it from traffic rotation.

Mental model: Liveness asks "are you breathing?" Readiness asks "can you do the job right now?"

When to use it:

  • [Ideal situation] Any service participating in orchestration, rolling deploys, or load-balanced traffic.
  • [Anti-pattern] Returning "healthy" from every endpoint just because the process has not crashed.

Concept 2: Circuit Breakers Protect Callers from Repeated Dependency Failure

Concrete example / mini-scenario: The payment provider begins timing out. Without a breaker, every checkout request waits, retries, and ties up application threads. With a breaker, the system quickly stops calling the provider for a while and returns a controlled failure or fallback.

What it is: A circuit breaker is a policy that temporarily stops calls to a dependency after repeated failure, then probes for recovery later.

Why it matters: This prevents one unhealthy dependency from consuming all of the caller's time and resources.

How it works: The breaker tracks recent failures, opens when a threshold is reached, rejects calls for a recovery interval, and later allows limited test calls in a half-open state.

Mental model: A breaker is a fuse for dependency calls. It trips when repeated failure suggests more calls are currently wasteful or dangerous.

Code Example (If applicable):

def call_payment_service(breaker, payment_request):
    return breaker.call("payment_provider", payment_request)

Note: The key point is policy, not the API surface. The breaker decides whether another call is currently wise.

When to use it:

  • [Ideal situation] Slow or failure-prone dependencies where repeated calls can create cascades.
  • [Anti-pattern] Wrapping every tiny in-process function with breaker logic.

Concept 3: Resilience Includes Safe Degradation, Not Just Error Detection

Concrete example / mini-scenario: If the recommendation service is down, the platform can still show the basic course page. If payments are down, checkout must fail, but it should fail quickly and clearly rather than hanging for 30 seconds.

What it is: Resilient design means deciding how the system should behave when some dependencies are unhealthy, not just how to detect the failure.

Why it matters: Detection without policy leaves users facing unpredictable latency and poor error behavior.

How it works: The system defines fallback responses, timeouts, retries, and degraded modes appropriate to the dependency and workflow.

Mental model: Resilience is not only knowing that a component is sick. It is knowing how the rest of the system should behave while it is sick.

When to use it:

  • [Ideal situation] Any important dependency with distinct graceful-degradation options.
  • [Anti-pattern] Letting every dependency failure turn into the same long timeout experience.

Troubleshooting

Issue: Treating liveness as enough for traffic routing.

Why it happens / is confusing: Process-level health is easy to expose, so teams may stop there.

Clarification / Fix: Add readiness checks that reflect whether the instance can actually serve requests with its required dependencies.

Issue: Using circuit breakers without defining fallback behavior.

Why it happens / is confusing: The breaker policy can feel like the whole resilience story.

Clarification / Fix: Decide what the caller should do when the circuit is open: fail fast, serve cached data, degrade gracefully, or queue work for later.

Advanced Connections

Connection 1: Health Checks ↔ Deployment Safety

The parallel: Readiness checks are one of the mechanisms that let platforms add or remove instances safely during deploys.

Real-world case: Rolling and canary rollouts depend on accurate readiness signals before traffic is shifted.

Connection 2: Circuit Breakers ↔ Cascading Failure Control

The parallel: Circuit breakers turn repeated dependency failure into bounded local failure instead of system-wide resource exhaustion.

Real-world case: Payment, search, and recommendation dependencies often need timeout and breaker policies together.

Key Insights

  1. Health checks and circuit breakers answer different questions - One controls routing, the other controls dependency calls.
  2. Readiness matters more than mere process survival - An alive instance can still be unsafe to serve traffic.
  3. Resilience requires behavior under failure, not just detection - Fallbacks and fast failure matter once problems are detected.

Knowledge Check (Test Questions)

  1. What is the main difference between a readiness check and a circuit breaker?

    • A) Readiness decides whether an instance should receive traffic, while a circuit breaker decides whether a caller should keep calling a failing dependency.
    • B) They solve exactly the same problem.
    • C) Circuit breakers only matter for databases.

  2. Why can liveness alone be misleading?

    • A) Because a process may still be alive even when it cannot safely serve real requests.
    • B) Because liveness checks only apply to frontend apps.
    • C) Because readiness always replaces liveness entirely.

  3. What is one benefit of opening a circuit breaker after repeated downstream failure?

    • A) It prevents the caller from repeatedly wasting time and resources on a currently unhealthy dependency.
    • B) It guarantees the dependency has recovered.
    • C) It removes the need for timeouts.

Answers

1. A: Readiness is about routing traffic to instances, while circuit breakers are about dependency-call policy.

2. A: A process can remain alive while essential dependencies or local state make it unready for useful traffic.

3. A: Breakers contain repeated failure by cutting off unproductive calls until recovery is plausible.
