Authorization Caching and Consistency

By the end of this lesson, you will be able to:

  • identify what an authorization cache entry means and which facts can make it stale;

  • choose a freshness requirement for a grant, revocation, or low-risk read;

  • trace a permission change through policy, relationship data, tokens, caches, and enforcement.

Idea in one sentence: A cached allow is evidence about a past authorization state, so a safe design states how long that evidence may be used and what happens when revocation must be visible sooner.

Core Insight

Maya is removed from the refund-approver role at 09:00 after moving teams. At 09:01, she opens the approval page and receives an allow from an API gateway cache populated at 08:59. The policy database already reflects the removal, but the gateway does not ask it again until the cached decision expires at 09:10. The system has not failed to revoke the role; it has failed to define whether a cached allow may outlive that revocation.

Caching authorization is often necessary. A permission check may traverse group membership, document hierarchy, tenant relationships, policy versions, and attributes. Recomputing every check can add latency and load to a critical path. But an authorization cache is not a normal performance cache: a stale product thumbnail is annoying, while a stale privileged allow can expose customer data or allow an irreversible action.

Consistency here means the relationship between the authorization state a check observed and the state the product requires it to observe. In plain language, ask: “after we grant or revoke access, when must the next check notice?” The answer differs for a low-risk dashboard refresh, a new document share, a support session, and a production key rotation.

The trade-off is latency reduction versus stale privilege. Do not settle it with one global TTL. Name the decision class, the acceptable staleness, the source that owns the change, the cache key, the invalidation or version mechanism, and the safe behavior when freshness cannot be proved.

What Can Be Stale?

Authorization depends on several independently changing inputs. Caching one can be correct while another makes the final answer unsafe.

decision cache:       “Maya may approve refund R-774”
relationship data:    Maya is in refund-approver
token claim:          token says Maya has role refund-approver
policy artifact:      refund approval policy version 42
resource attribute:   refund R-774 is not under legal hold
session or grant:     Maya’s support session is still active

A decision cache stores an allow or deny for a particular principal, action, resource, tenant, and relevant context. Its key must include every fact whose change could change the answer: at minimum the subject, permission, resource or scope, tenant, policy version, and often a relationship or attribute revision. Caching only user:maya -> allow turns a narrow decision into accidental global access.

Token claims are also a cache. A signed access token can remain cryptographically valid after a role is removed because it represents the claims issued earlier. Short lifetimes reduce that window but do not create immediate revocation. A token that says admin must still be interpreted with the tenant, audience, issuer, and current risk required by the operation.

Pause and predict: Does reducing every authorization cache TTL to one second guarantee that revocation is safe?

Check: No. It reduces one staleness window but does not cover a stale token claim, an old policy bundle, a delayed relationship update, an unscoped cache key, or a high-impact action that needs immediate visibility. The guarantee must describe the whole decision path.

Worked Path: Revoking a Refund Approver

At 09:00, an administrator removes Maya from refund-approver. The authorization source writes a new membership revision, membership-v92. A robust path makes that revision useful:

1. Admin writes the membership removal and receives revision membership-v92.
2. The role-management event publishes Maya, refund-approver, tenant, and revision.
3. Gateways invalidate matching cached decisions or mark them older than v92.
4. Maya requests refunds.approve for tenant acme-eu.
5. Gateway checks cache key plus required minimum revision.
6. A pre-v92 allow is rejected; evaluator reads at least v92 and returns deny.
7. Decision log records the revision, policy version, cache outcome, and deny reason.

The crucial mechanism is not a specific cache product. It is a freshness token or revision that says, “evaluate no earlier than this authorization state.” An application can store the revision returned by a relationship or policy write alongside the protected resource, then require later checks to be at least that fresh. Some systems call these Zookies or ZedTokens; the durable idea is causal read-after-write for authorization data.

For an ordinary read after a grant, the product may accept eventual visibility: Maya shares a non-sensitive project, and the recipient might need to refresh once before it appears. For a revocation before approving refunds or exporting tenant data, a brief stale allow may be unacceptable. The latter check can bypass the cache, request at-least-a-given revision, or deny while the required state is unavailable. The cost is higher latency or lower availability for that decision class.

Pause and predict: A cache invalidation event is delayed. Can the gateway safely use an old cached allow for a destructive refund approval?

Check: Not if the revocation promise requires the removal to be visible. The gateway needs a revision check, a strongly current evaluation, or a deny outcome. Event invalidation improves speed; it is not by itself a proof that every cache observed the change.

So far: invalidation is an optimization. A consistency requirement, revision, or freshness check is the correctness contract that tells an enforcement point when an old allow is unusable.

Choose Freshness by Consequence

Classify decisions before choosing mechanics:

eventual visibility: non-sensitive list or dashboard after a new grant
read-after-write:   the next share check must see the share just created
prompt revocation:  a removed user must not approve or export after revocation
fully current:      a high-impact admin or break-glass action needs latest state now

“Fully current” is not free. It may bypass cache layers, wait for replication, or make the permission store a synchronous dependency. Use it where the consequence justifies it. Conversely, declaring every check fully consistent can turn authorization into a latency bottleneck and create a larger outage blast radius. A design is mature when it can explain why each class picked its promise.

Policy deployment has the same shape. A cached decision may be correct under policy version 41 but wrong under version 42. Include policy or bundle revision in decision metadata, invalidate where practical, and decide whether a restrictive emergency policy must be visible before the next operation. A local evaluator with an old verified bundle may be acceptable for low-risk reads; it is not automatically acceptable for a newly denied key rotation.

Attribute freshness matters too. A device posture service may say the device was managed five minutes ago. A legal-hold value may be read from a lagging replica. Cache policy decisions only with an explicit understanding of the source revision or bound. Do not call a check “consistent” merely because the decision cache responded quickly.

Cache Keys, Invalidations, and Failure Modes

A cache key should be a compact representation of the security question, not merely the principal:

tenant:acme-eu
principal:maya
permission:refunds.approve
resource:refund:R-774
policy:42
context:managed-device=true
minimum_revision:membership-v92

Not every field belongs literally in a key; some belong in a revision or in an invalidation domain. The point is to identify all dimensions that affect the result. If policy includes time of day, risk score, or a support-session expiry, either include a bounded representation or do not cache beyond the earliest change.

Common failures are predictable:

  • Role-only keys: a decision for one tenant or resource leaks to another scope.
  • Best-effort invalidation: a lost event leaves a stale allow with no revision safety net.
  • Deny caching without care: a new grant remains invisible longer than intended and looks like a product outage.
  • Stale token authority: a long-lived claim is accepted as current membership after revocation.
  • Cache stampede: mass expiry forces a permission store overload, then callers fail open to preserve availability.
  • Missing evidence: operators cannot tell cache hit, policy version, relationship revision, or source freshness for a disputed allow.

Fail closed for operations where stale privilege is worse than interruption. For low-risk reads, a bounded last-known decision or eventual result may be reasonable. Record the cache result, decision revision, policy revision, and consistency mode in decision evidence; without them, an incident team cannot tell whether the policy or the freshness contract failed.

Operationally, measure the decision path rather than only the cache hit rate. A high hit rate can hide a dangerous revocation window; a low hit rate can signal an invalidation storm or an overly detailed key. Track cache hit and miss by decision class, age of served decisions, invalidation delivery lag, revision-check latency, source-read errors, and denials caused by freshness requirements. Alert separately when a relationship write cannot publish its invalidation event, when evaluators report an old policy revision, or when a cache suddenly serves allows after a restrictive policy rollout.

Protect the permission store during synchronized expiry. If thousands of entries expire at the same moment, callers can stampede the evaluator and turn a normal role change into an outage. Use bounded lifetimes with jitter where suitable, request coalescing, safe negative caching, and capacity limits. Never solve a cache stampede by changing a permission-store timeout into an automatic allow. A temporary denial or a clearly degraded read-only experience is often safer than extending stale privilege under load.

For change streams, handle restart and ordering explicitly. A consumer that resumes after downtime needs a durable checkpoint or revision and a way to rebuild state from a snapshot; otherwise it may miss a revocation and believe its local cache is current. Test a dropped invalidation, a delayed policy bundle, a permission-store outage, and two rapid grant/revoke changes. The expected result should be stated for each decision class before the incident occurs.

Design Check

Start with a nearby case. An administrator revokes a contractor's invoice.read membership at 10:00. The contractor may tolerate a short delay before a new dashboard grant appears, but must not download exports after revocation.

dashboard read:
  bounded eventual cache acceptable; short TTL and clear refresh state

export download:
  check membership at least as fresh as revocation revision
  cache key includes tenant, resource scope, permission, policy revision
  deny if required relationship source is unavailable
  record cache hit/miss and revision in decision evidence

Now choose one grant and one revocation in a system you know. For each, write the decision key, owner of the changed fact, acceptable staleness, invalidation signal, required revision or consistency mode, and failure behavior. Accept the design only if it answers when the next check must notice the change and how an operator will prove which state it used.

Key Takeaways

  • A cached allow represents a past policy, relationship, attribute, and session state; it is never permission without a freshness contract.
  • Choose consistency by consequence: low-risk reads may tolerate bounded staleness, while revocation and high-impact actions often need a revision-aware or fresh check.
  • Invalidation improves cache performance, but revisions and enforcement behavior provide the correctness guarantee when invalidation is delayed or lost.
  • Log cache outcome, data revision, policy version, and consistency mode so authorization incidents can be explained rather than guessed at.
