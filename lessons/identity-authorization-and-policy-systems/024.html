Identity Capstone: Design an Authorization Platform

By the end of this lesson, you will be able to:

  • design a platform path from authentication to policy decision, enforcement, audit evidence, tests, and incident response;

  • identify which facts are authoritative for users, service accounts, tenants, resources, sessions, and policy;

  • critique an authorization architecture for stale decisions, confused deputies, weak evidence, and untestable rules.

Idea in one sentence: An authorization platform is a chain of trust decisions, not one service: every request must carry authenticated identity, scoped authority, current policy inputs, enforced boundaries, and evidence that can survive tests and incidents.

Core Insight

Imagine a B2B SaaS platform called LedgerWorks. It serves many tenants, supports enterprise SSO, SCIM provisioning, service accounts, API keys, support impersonation, fine-grained invoice access, background exports, and emergency key rotation. A user signs in through Acme's identity provider, opens an invoice, requests an export, and later a support engineer impersonates the user to debug a failed payment.

The dangerous version of this platform grows feature by feature. SSO creates users just in time. SCIM updates groups when it works. API services check roles locally. Workers trust internal job messages. Support impersonation has a special bypass. Audit logs exist, but they do not show policy version, tenant, field masks, freshness, or delegated service authority. Every piece has a reasonable explanation; together they form a system where nobody can prove why access was allowed.

The capstone design pressure is to make authority traceable end to end. Authentication answers "who is this actor?" Provisioning answers "what local identity state should exist?" Authorization answers "may this actor perform this action on this resource in this tenant under this context?" Enforcement answers "which component refuses when the answer is no?" Audit and tests answer "can we prove the decision and prevent regressions?" Incident operations answer "can we change trust state quickly when credentials are suspect?"

The trade-off is security rigor versus product and operational complexity. A platform with no central policy discipline leaks data and fails audits. A platform that sends every page render through a brittle global decision service may create latency, availability, and developer-friction problems. The design goal is not centralization for its own sake. It is clear ownership of facts, decisions, enforcement points, evidence, and failure behavior.

The Platform Shape

Start by drawing the facts that move through LedgerWorks:

identity facts:
  user id, tenant membership, SCIM external id, active status, MFA/session state

authority facts:
  role, group, relationship, service account, delegated support purpose

request facts:
  action, resource, tenant, requested fields, token audience, device/risk context

policy facts:
  policy bundle version, relationship revision, data classification, freshness mode

evidence facts:
  decision id, allow/deny reason, enforcement point, cache result, audit event

A workable architecture has several cooperating components:

IdP / SSO              authenticates enterprise users
SCIM provisioning      syncs user and group lifecycle into local identity store
session/token service  issues scoped credentials and tracks revocation
policy engine          evaluates structured decisions against current facts
enforcement points     gateways, APIs, workers, database/query layers, serializers
audit pipeline         records decision evidence and operator actions
test harness           turns permission matrices and incidents into executable checks
incident controls      rotate keys, revoke credentials, invalidate sessions, communicate

The exact product boundaries may differ. Some systems embed the policy engine as a library. Some call a central decision API. Some enforce tenant predicates in the database and field masks in the application. The capstone rule is that each component must say what it owns, what it merely observes, and what it refuses when evidence is missing.

Worked Design: Acme Invoice Export

Trace one complete workflow: Priya from Acme exports invoice summaries.

1. Authentication:
   Priya signs in through Acme SAML SSO.
   SP validates issuer, signature, audience, recipient, time, and replay state.

2. Local identity:
   Priya maps to local user usr_92 through stable external id.
   SCIM state says usr_92 is active and in Finance Analysts.

3. Request:
   Priya requests invoice.export for tenant acme-eu.
   Session token audience is ledgerworks-api and tenant is acme-eu.

4. Policy input:
   subject=usr_92
   action=invoice.export
   resource=invoice_summary:month-2026-06
   tenant=acme-eu
   role=billing_analyst
   relationship_revision=rel-v481
   policy_version=policy-v77

5. Decision:
   policy allows monthly summary export, denies full card fields,
   requires export worker token scoped to job_771.

6. Enforcement:
   API creates job_771 with tenant=acme-eu and field plan.
   export worker validates audience=export-service, action, tenant, expiry, replay.
   worker query includes tenant predicate and safe projection.

7. Evidence:
   audit logs record Priya, tenant, job id, policy version, relationship revision,
   fields included/denied, cache mode, worker token id, and output location.

8. Tests:
   permission matrix has positive export case plus denies for refund.issue,
   other-tenant export, stale revocation, wrong token audience, and card_token field.

This path synthesizes the track. SSO proves the login assertion, not product authorization. SCIM supplies lifecycle state, not automatic admin power. The policy engine returns a plan, not merely "yes." The worker is a deputy and must enforce constrained intent. Audit evidence includes revisions and reasons. Tests make the expected allows and denials executable.

Pause and predict: Which component should be allowed to skip tenant checks because another component already checked them?

Check: None by default. Components can rely on a verified, constrained decision artifact only if the design defines that artifact, its audience, freshness, and failure behavior. Otherwise gateways, APIs, workers, queries, and serializers each need the tenant boundary appropriate to their layer.

Design Boundaries and Trade-offs

Choose where decisions run by consequence and latency. A low-risk dashboard count may tolerate cached decisions and eventual SCIM updates. A refund approval, support impersonation, key rotation, or tenant export should require fresh enough identity and policy state. The platform should name these classes instead of pretending every operation needs identical consistency.

Central decision services improve reuse, review, and audit consistency. They can also become latency-critical dependencies. Local policy libraries reduce network hops but make rollout, versioning, and evidence harder. Database row-level security protects against accidental overbroad queries but cannot express every business workflow. Application field masks are flexible but can leak if exports, logs, or search indexes bypass them.

The mature design uses layers deliberately:

  • authenticate at the edge, but authorize close to the resource;
  • keep tenant and resource predicates near data access;
  • keep field masks near serialization and export creation;
  • keep service-to-service delegation narrow and audience-bound;
  • keep audit evidence in one queryable shape even if enforcement is distributed;
  • keep policy tests tied to real routes, workers, and response shapes.

Availability also needs explicit behavior. If the policy engine is down, do high-risk actions fail closed? If the relationship store is stale, can low-risk reads use bounded stale state? If audit logging is delayed, does the action continue with durable buffering or block? If SCIM is behind, which users are prevented from high-risk access until lifecycle state catches up? These are product decisions with security consequences.

Failure Review

Review LedgerWorks against the failure modes from the track:

  • Stale privilege: cached role or token claims outlive revocation.
  • Tenant leakage: route checks tenant but worker/export/search path omits tenant predicate.
  • Field leakage: API masks card data but CSV export includes raw token.
  • Confused deputy: service with all-tenant database access accepts unconstrained job message.
  • Federation confusion: valid SAML signature is accepted for wrong tenant or audience.
  • Lifecycle drift: SCIM marks user inactive but local role or API key remains active.
  • Untestable policy: role intent exists in prose but not in permission matrices.
  • Unoperable incident: signing key rotates but verifiers keep accepting old kid.

Each failure should map to a control and an evidence field. If stale privilege is the risk, record relationship revision and consistency mode. If field leakage is the risk, record field plan and mask reasons. If confused deputy is the risk, record requester, deputy, token audience, job id, tenant, and action. If incident response is the risk, record key id, verifier cache age, and revocation result.

Pause and predict: Why is audit logging after the fact not enough to make support impersonation safe?

Check: Audit evidence is necessary, but enforcement must also require approval, purpose, tenant scope, time limit, visible actor separation, and field restrictions. Logging an unsafe allow only makes the incident easier to investigate.

Capstone Design Review

Use this checklist to critique your own authorization platform.

Identity:
  How do users, service accounts, external ids, sessions, and tenants map?
  Which lifecycle facts are authoritative, and how are stale facts detected?

Credentials:
  What does each token, key, cookie, assertion, and API key authorize?
  Are issuer, audience, scope, tenant, expiry, and revocation checked?

Policy:
  Which component owns policy evaluation?
  Does the decision return enough structure: allow/deny, fields, reason, revision?

Enforcement:
  Where are route, tenant, resource, field, worker, export, and support boundaries enforced?
  What fails closed, and what can use bounded stale state?

Evidence:
  Can an operator reconstruct subject, action, resource, tenant, policy version,
  relationship revision, cache/freshness mode, and enforcement point?

Testing:
  Do permission matrices cover nearby denies, tenant separation, field masks,
  delegated workers, revocation, and incident regressions?

Operations:
  Can the team rotate keys, revoke sessions/tokens, disable service accounts,
  prove blast radius, and tell customers what action is required?

Now apply it to a nearby system you know. Pick one high-impact action such as exporting tenant data, impersonating a customer, issuing a refund, rotating a signing key, or approving an admin role. Trace it from authentication through policy, enforcement, evidence, tests, and incident response. Accept the design only if you can name the authoritative fact at each step and the component that refuses when that fact is missing or stale.

Architecture Synthesis Pass

A complete platform design should also say how teams change it. Authorization systems fail when policy changes, product launches, and incident tooling evolve independently. LedgerWorks needs a change path that keeps product intent, policy code, application enforcement, tests, and audit evidence moving together.

For a new action such as invoice.refund.approve, start with a decision shape:

subject: finance_admin or delegated approver
action: invoice.refund.approve
resource: refund request and invoice
tenant: tenant owning the invoice
context: amount, support/finance purpose, device risk, revocation freshness
decision output: allow/deny, limit reason, required approval, evidence fields

That shape becomes a policy rule, but it also becomes API contract, worker contract, audit schema, and permission-matrix fixture. The API route must pass the same action name. The worker must reject job tokens that do not carry that action. The audit event must record amount threshold and policy version. The test suite must include own-tenant allow, other-tenant deny, revoked approver deny, over-limit require-approval, wrong-audience worker token deny, and disputed audit reconstruction.

This is why "authorization platform" is broader than "policy engine." The policy engine can be correct while the product remains unsafe if a worker bypasses it, a serializer leaks forbidden fields, a cache ignores revocation freshness, or an incident runbook cannot revoke affected sessions. The platform is the set of agreements that prevent those gaps from becoming normal.

Ownership should be explicit:

  • identity platform owns user links, sessions, token issuance, revocation, and federation configuration;
  • tenant platform owns tenant identity, membership boundaries, and customer-admin configuration;
  • product services own resource state and action semantics;
  • policy platform owns decision language, versioning, simulation, and reason shape;
  • data services own row predicates, field projections, and export boundaries;
  • security and operations own incident runbooks, key lifecycle, and escalation criteria.

Shared ownership does not mean shared ambiguity. Each boundary should have one owner for the authoritative fact and one owner for enforcement. The identity platform may own whether a user is active, but the invoice API owns refusing a refund request when the user is inactive. The policy engine may produce a field plan, but the export worker owns ensuring the CSV follows it.

Readiness Signals

Before promoting an authorization platform from "works in happy paths" to "ready for high-risk use," look for signals that the system can be operated under pressure.

First, decision evidence should be queryable. An operator should be able to answer: "Why did Priya export this invoice summary?", "Which policy version was active?", "Was the decision cached?", "Which relationship revision was used?", "Which fields were removed?", and "Which worker produced the file?" If those answers require reading code and correlating raw logs manually, the platform is not yet auditable enough.

Second, revocation should be measurable. Remove a user from a role, disable a service account, rotate a signing key, revoke a refresh token family, or end a support session. The platform should show when high-risk decisions stopped accepting the old authority. If the answer is "eventually, probably," the design needs freshness contracts.

Third, tests should fail for realistic escapes. Create a matrix case for a valid object in another tenant, a forbidden field in an export, a replayed worker token, a stale support session, and a SAML assertion for the wrong audience. These tests should run automatically and point to the boundary that allowed access.

Fourth, incident drills should produce evidence, not only confidence. During a key-rotation exercise, teams should prove new issuance, verifier convergence, old-key rejection, customer impact, and alert behavior. During a compromised service-account exercise, teams should prove what the account could access, where it was used, and how it was disabled.

Finally, developer ergonomics matter. If secure authorization requires every feature team to manually remember ten hidden rules, the platform will drift. Provide typed decision inputs, shared middleware, policy test helpers, fixture tenants, audit-event builders, and review checklists. Good platform design reduces the number of bespoke decisions a product engineer must make while still exposing the hard security boundaries.

Pause and predict: Is a platform with excellent policy code but poor developer integration ready?

Check: No. Authorization quality depends on the policy being invoked with correct inputs at every enforcement point. If integration is hard or invisible, teams will bypass it, call it too late, or omit evidence.

Final Transfer

Design the smallest credible authorization platform for this scenario: a SaaS product supports enterprise SSO, SCIM, service accounts, support impersonation, invoice exports, and admin role management. Write one page with these headings:

Authoritative facts
Credential types
Decision API or library
Enforcement points
Audit evidence
Permission tests
Revocation and rotation controls
High-risk failure behavior

For each heading, write what is owned, where it is enforced, what evidence proves it worked, and what happens when the dependency is unavailable. Then pick one high-risk flow and walk it through the design. The result does not need to be a perfect enterprise architecture. It should be clear enough that another engineer can find the trust boundaries and challenge weak assumptions.

Key Takeaways

  • An authorization platform is an end-to-end trust path: identity, credentials, policy inputs, enforcement, evidence, tests, and operations must agree.
  • Design around authoritative facts and refusal points; every component should know what it owns, observes, trusts, and denies.
  • Security rigor becomes operable when decisions include revisions, freshness, reasons, field plans, and audit evidence.
  • A platform is not ready until its high-risk paths can be tested, explained, revoked, rotated, and communicated during incidents.
