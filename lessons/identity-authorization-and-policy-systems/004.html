Tokens, JWTs, and Opaque Reference Tokens

The core idea: a token is portable evidence about a subject, issuer, audience, and permission snapshot; JWTs make that evidence locally verifiable, while opaque tokens keep the decision behind a lookup boundary.

Core Insight

Elena is now signed in to the finance product from the previous lessons. Her browser session lets her use the web app, but the system also has an API used by a mobile app, an internal reporting tool, and a worker that exports statements. Those clients cannot all share the same browser-cookie flow. They need a compact way to say, "this request is acting for this subject, for this audience, with this limited permission, until this time."

That compact object is usually called a token. A token is not magic identity. It is evidence issued by a component the receiver trusts. The receiver still has to ask: who issued it, who is it about, who is allowed to consume it, what action does it cover, when does it expire, and what changed since it was issued?

Now add the failure that makes token design interesting. Elena is moved out of the finance-admin group at 10:05. At 10:06, her mobile app calls POST /reports/export with a token issued at 09:55 that still contains scope: reports:export. Should the API accept it?

The answer depends on the token contract. A JSON Web Token, or JWT, can be validated locally by checking a signature and claims. That is fast and resilient to an unavailable central service, but the token is also a snapshot. If the API trusts the snapshot until expiration, a removed permission may continue to work for a while. An opaque reference token is just an unguessable handle; the API must ask an authorization server or token service what it means. That adds latency and dependency, but revocation and freshness are easier to centralize.

The practical design question is not "JWTs or opaque tokens?" in the abstract. It is "which component owns the freshest decision, and what evidence is safe to carry across this boundary?"

What Is Actually Moving?

A bearer token is a string that grants authority to whoever presents it. If an attacker steals a valid bearer token, the server usually cannot tell whether the request came from the original client. That is why exposure, lifetime, audience, and logging discipline matter as much as the token format.

A JWT has visible structure:

base64url(header).base64url(payload).base64url(signature)

The header says how the token was signed, often with an algorithm and key id:

{
  "typ": "JWT",
  "alg": "RS256",
  "kid": "key-2026-06"
}

The payload contains claims. Claims are statements, not automatically facts the whole system must obey forever:

{
  "iss": "https://auth.finance.example.test",
  "sub": "user:elena",
  "aud": "reports-api",
  "scope": "reports:export reports:read",
  "tenant": "tenant:acme",
  "iat": 1781350500,
  "nbf": 1781350500,
  "exp": 1781351400,
  "jti": "tok_71f2"
}

The signature lets the API detect tampering. If a client changes scope from reports:read to reports:export, signature verification fails. But signature verification does not prove the permission is still fresh. It proves that a trusted issuer signed this payload at some time, for some audience, under some key.

An opaque token looks more like this:

f3e65e1c7f9c4b2d9c5b0a...

The API cannot learn anything from the string itself. It must call a trusted service:

token handle -> introspection lookup -> active subject, audience, scopes, expiry

That lookup can consult revocation state, current account status, tenant policy, device posture, or a cached decision. The token is a pointer to authority, not a self-contained bundle of claims.

JWT Validation, Step by Step

Imagine the reports API receives:

POST /reports/export HTTP/1.1
Host: reports-api.finance.example.test
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

A careful JWT validation path looks like this:

1. Extract the bearer token from the Authorization header.
2. Decode the header enough to choose a configured verification key.
3. Reject algorithms that are not explicitly allowed for this issuer.
4. Verify the signature with the issuer's trusted public key.
5. Check `iss`: was this token issued by the expected authority?
6. Check `aud`: was it meant for this API, not some other service?
7. Check time claims: `exp`, `nbf`, and acceptable clock skew.
8. Check token purpose and scope: can it request `reports:export`?
9. Check tenant and resource boundary: does `tenant:acme` match the target data?
10. Apply local authorization or policy checks that are not safely encoded in the token.
11. Record enough decision evidence for debugging and audit.

This path has a clear strength: the API can decide without a network hop to the authorization server. If the auth service has a brief outage, already-issued tokens may still work. If the reports API is deployed in several regions, local validation avoids a central bottleneck.

The same path has a clear limit. The API is validating a signed snapshot. If Elena's admin role was removed after the token was issued, the old token can remain valid until one of these things happens:

the token expires
the API checks a token version or revocation list
the API calls a policy service for sensitive actions
the signing key is rotated in a way that invalidates the token

Short lifetimes reduce stale authority, but they create more refresh traffic and more visible failures when refresh handling breaks. Long lifetimes improve offline or low-latency behavior, but they increase the blast radius of theft and stale claims.

Opaque Token Validation, Step by Step

Now use an opaque access token for the same export request:

Authorization: Bearer f3e65e1c7f9c4b2d9c5b0a...

The reports API cannot validate the token locally. It asks a token service:

POST /introspect
token=f3e65e1c7f9c4b2d9c5b0a...
audience=reports-api

The service responds with a decision-shaped description:

{
  "active": true,
  "sub": "user:elena",
  "aud": "reports-api",
  "scope": "reports:read",
  "tenant": "tenant:acme",
  "exp": 1781351400
}

The API denies reports:export because the current token state no longer has that scope:

request scope needed: reports:export
introspection scope: reports:read
decision: deny
reason: insufficient_scope

Opaque validation moves freshness to a service boundary. If Elena's role is removed, the token service can mark the token inactive, update the scope result, or combine the token lookup with current authorization state. The API no longer has to infer everything from a signed snapshot.

The price is operational. Every request may now depend on a token service, unless the API caches introspection results. Caching improves latency but partially reintroduces staleness:

cache ttl = 60 seconds
role revoked at 10:05:00
cached "active with export" decision valid until 10:05:45
possible stale authorization window = 45 seconds

That is not automatically wrong. The important part is to make the window explicit. A payroll export endpoint may need near-immediate revocation. A low-risk read-only endpoint may tolerate a short cache because availability and latency matter more.

Choosing the Boundary

JWTs tend to fit when receivers are numerous, latency-sensitive, or must keep working during brief auth-service trouble. They work best when access tokens are short lived, claims are minimal, audiences are narrow, and permissions in the token are coarse enough that short staleness is acceptable.

Opaque tokens tend to fit when revocation, central policy, privacy, or claim freshness matters more than local validation. They are common behind API gateways, backend-for-frontend patterns, and systems where the resource server should not learn or store detailed user claims.

A useful way to name the trade-off is this: a JWT moves evidence closer to the resource server, while an opaque token keeps meaning closer to the authority that issued it. Moving evidence outward improves local autonomy. Keeping meaning central improves coordination when facts change. Neither direction is automatically more secure. A long-lived JWT with broad claims can be dangerous because old evidence travels far. An opaque token with an overloaded introspection service can be dangerous because one slow dependency can block many APIs. The design has to choose the failure it can observe and tolerate.

A useful design review compares the two formats against the same questions:

Who issues the token?
Who is allowed to consume it?
What resource or API is it for?
What claims are safe to expose to the holder?
How long can stale authority be tolerated?
How is revocation represented?
What happens if the token service is slow or down?
Can operators explain a deny or allow decision later?

Do not put every useful fact into a token just because the format allows it. A token crosses boundaries. It may be logged, copied into bug reports, stored in mobile crash dumps, exposed to browser JavaScript, or replayed by a proxy. Prefer minimal claims: stable subject, audience, issuer, expiry, token id, and limited scopes. Use lookup or policy checks for facts that are sensitive, fast-changing, or resource-specific.

Also separate token type from login type. An ID token says something about an authentication event and is meant for a client. An access token is meant for a resource server. Calling an API with an ID token is a common token-confusion failure: the token may prove that Elena authenticated to a client, but not that the reports API was the intended audience.

Worked Design Pass

For the finance reports export, choose a hybrid:

client -> short-lived access token -> reports API
reports API -> local JWT validation for ordinary reads
reports API -> policy check for export and admin actions
refresh token -> kept away from ordinary API calls

The access token contains:

iss = auth service
sub = user:elena
aud = reports-api
scope = reports:read
tenant = tenant:acme
exp = 10 minutes from issue
jti = unique token id

It does not contain Elena's email, full group list, billing tier, or every admin flag. Those details either leak too much or change too often.

When Elena requests an export, the API first validates the JWT. Then, because export is sensitive, it asks a policy service:

subject=user:elena
action=reports:export
resource=tenant:acme/report-batch
token_jti=tok_71f2

If the policy service says Elena no longer has export permission, the API denies the action even though the token signature is valid. The JWT remains useful as authentication evidence and request context, but it is not treated as the final authorization truth for a high-risk operation.

This design spends extra latency only on sensitive decisions. It avoids a token-service call for every read, but it does not let old coarse claims authorize dangerous actions for the full token lifetime.

Failure Modes

Failure: accepting the wrong audience. A token issued for profile-api should not work at reports-api. Always validate aud, not just signature and expiry.

Failure: trusting claims as current reality. A signed role or group claim may be stale. Use short lifetimes, token versions, revocation checks, or policy lookups where freshness matters.

Failure: logging bearer tokens. If access tokens appear in logs, traces, analytics events, browser history, or support tickets, they become replay material. Redact them at ingress and in observability pipelines.

Failure: key rotation without a plan. JWT validation depends on keys. APIs need predictable JWKS caching, key overlap during rotation, and alerts for unknown kid values or signature failures.

Failure: using token format as security architecture. "We use JWT" says little by itself. The real architecture is issuer trust, audience boundaries, lifetime, revocation, storage, exposure, and policy enforcement.

Readiness Check

Close the lesson and review one token in a system you know:

Is it a bearer token?
Is it a JWT or an opaque reference?
Who issued it?
Which audience should accept it?
What claims are checked locally?
Which claims can become stale?
How long is stale authority acceptable?
Where is revocation represented?
Could this token appear in logs or browser storage?
What evidence would explain a deny decision?

If you cannot answer issuer, audience, lifetime, and revocation, the token is carrying authority without a clear boundary.

Key Takeaways

  • A token is portable evidence, not automatic current truth; the receiver must validate issuer, audience, expiry, purpose, and freshness needs.
  • JWTs buy local validation and lower dependency on a central service, but stale claims and revocation become design problems.
  • Opaque tokens centralize meaning and revocation, but they add latency, availability, and caching trade-offs.
  • Sensitive authorization should not rely only on a token's old claims when the decision depends on current policy or resource state.
