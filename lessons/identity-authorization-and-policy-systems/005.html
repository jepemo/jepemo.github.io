OAuth 2.0 Actors and Authorization Code Flow

The core idea: OAuth 2.0 authorization code flow lets one application receive limited delegated access without seeing the user's password, but only if each redirect, code, client, and token boundary is validated as part of the same transaction.

Core Insight

Elena uses the finance product from the earlier lessons. She wants to connect a forecasting tool called PlanBoard so it can read monthly statement totals and build a cash-flow projection. PlanBoard does not need Elena's password. It does not need the ability to change her email, reset MFA, invite users, or export payroll. It needs delegated access: Elena approves a narrow action, and the finance system gives PlanBoard a token that the reports API can understand.

That is the pressure OAuth 2.0 was built for. OAuth is not "login with a logo" at its core. It is a framework for delegated authorization. A user can authorize a client to access a protected resource without handing that client the user's primary credentials.

The authorization code flow is the most important browser-based OAuth pattern. It uses the user's browser for consent and redirects, but it does not put the access token directly in the redirect URL. Instead, the authorization server returns a short-lived authorization code to the client. The client then exchanges that code for tokens over a back-channel request.

The trade-off is that OAuth removes password sharing by adding a redirect protocol. Redirects are useful because they move Elena to the trusted authorization server, but they are also fragile: a wrong redirect URI, missing state, confused client identity, or leaked authorization code can turn delegated access into account confusion or token theft. The flow is safe only when the pieces are bound together.

The Four Actors

OAuth vocabulary is easier if you start with who sees what.

resource owner       Elena, the person who can approve access
client               PlanBoard, the app requesting access
authorization server finance auth service, where Elena signs in and consents
resource server      finance reports API, where protected data lives

The resource owner is usually the user, but the term is wider than "human." It means the party that can grant access to a protected resource.

The client is the application asking for access. A client may be confidential, such as a server-side web app that can keep a client secret, or public, such as a mobile app or browser-only app that cannot reliably hide a secret. The next lesson goes deeper on public clients and PKCE. For this lesson, keep the basic boundary: do not assume every OAuth client can keep secrets.

The authorization server authenticates Elena, gathers consent or applies policy, issues authorization codes, and issues tokens. It is the authority for the OAuth transaction.

The resource server hosts the API PlanBoard wants to call. It validates access tokens and enforces the allowed action. The resource server should not accept "Elena was logged in somewhere" as enough. It needs a token meant for this API, with appropriate scope, issuer, audience, lifetime, and policy context.

These actors are often run by the same company, but they are different security roles. In a small system, the authorization server and resource server may be one deployment. The mental model still matters because bugs appear at the boundaries.

The Authorization Code Flow, Step by Step

Start from Elena clicking "Connect PlanBoard" in PlanBoard.

PlanBoard creates an authorization request and redirects Elena's browser to the finance authorization server:

GET https://auth.finance.example.test/authorize?
  response_type=code&
  client_id=planboard&
  redirect_uri=https%3A%2F%2Fplanboard.example.test%2Foauth%2Fcallback&
  scope=reports.read&
  state=af0ifjsldkj

Several fields carry the transaction:

  • response_type=code asks for an authorization code, not an access token in the front-channel redirect.
  • client_id=planboard names the registered client.
  • redirect_uri says where the authorization server may send the browser after the decision.
  • scope=reports.read asks for limited access.
  • state is an unguessable value PlanBoard stores locally so it can detect a forged or mismatched callback.

The authorization server checks the request before showing anything to Elena:

client_id known: yes
redirect_uri exactly registered: yes
scope allowed for this client: yes
state present: yes, but stored by client, not interpreted as authority

Then Elena authenticates to the finance authorization server if she is not already signed in. She reviews the consent screen:

PlanBoard wants to read monthly statement totals.
It will not be able to transfer funds or manage users.

If policy and consent allow the request, the authorization server creates a short-lived authorization code:

code = code_8a91
bound client = planboard
bound redirect_uri = https://planboard.example.test/oauth/callback
bound scope = reports.read
bound resource owner = user:elena
expires quickly
single use

The browser is redirected back to PlanBoard:

GET https://planboard.example.test/oauth/callback?
  code=code_8a91&
  state=af0ifjsldkj

PlanBoard checks that state matches the value it created for this browser session. If it does not match, PlanBoard stops. A matching state tells PlanBoard that this callback belongs to the authorization request it started, not to an attacker trying to inject a code from another flow.

Now PlanBoard exchanges the authorization code with a direct server-to-server call:

POST https://auth.finance.example.test/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code=code_8a91&
redirect_uri=https%3A%2F%2Fplanboard.example.test%2Foauth%2Fcallback&
client_id=planboard

For a confidential client, this request also authenticates the client, for example with a client secret or another configured method. The authorization server checks:

code exists and not expired
code has not been used before
code was issued to client planboard
redirect_uri matches the original request
client authentication is valid when required
requested token audience and scope are allowed

Only then does it issue tokens:

{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 600,
  "scope": "reports.read"
}

PlanBoard calls the reports API:

GET /monthly-statements/2026-05/summary HTTP/1.1
Host: reports-api.finance.example.test
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

The reports API validates the access token using the boundaries from the previous lesson: issuer, audience, expiry, scope, tenant, and any local policy. OAuth got the token issued. The resource server still has to enforce the resource decision.

Why the Code Is Not the Token

The authorization code is a temporary handoff artifact. It travels through the browser, where URLs can pass through history, logs, browser extensions, proxies, referrers, and crash reports. A code is still sensitive, but it is safer than sending the access token directly through that front channel.

The access token is issued only after the client proves it can complete the token exchange. That back-channel exchange lets the authorization server check the client, redirect URI, code lifetime, single-use status, and, in modern flows, PKCE binding.

This split creates a useful failure boundary:

front channel: browser redirect carries short-lived code
back channel: client exchanges code for token with stronger checks
resource call: client presents access token to API

If an attacker sees only the initial redirect to /authorize, they do not get a token. If an attacker injects a callback with a code from a different flow, state, redirect URI binding, client binding, and code checks should stop it. If an authorization code leaks, short expiry, single use, client authentication, and PKCE reduce what the attacker can do.

The key word is "reduce." OAuth does not make redirect bugs harmless. It gives you places to bind the transaction so each component can reject a mismatch.

Rejections should be observable without leaking secrets. When the authorization server refuses a code exchange, operators need to know whether the reason was expired code, reused code, redirect mismatch, invalid client, or disallowed scope. When the client rejects a callback, it should record that the state check failed without storing the full code in logs. This evidence is what lets a team distinguish a broken integration from an active attack.

Delegation Is Not Authentication by Itself

Many products use OAuth-like flows for sign-in, but OAuth 2.0 by itself does not define user authentication for the client. It defines how a client obtains access to resources. OpenID Connect, covered later in the track, adds ID tokens and authentication claims on top of OAuth.

This distinction matters in design reviews. If PlanBoard receives an access token for reports.read, that token lets it call the reports API. It does not necessarily tell PlanBoard every fact about Elena's login event, MFA strength, session age, or identity profile. Those may be separate claims, separate endpoints, or separate protocols.

Similarly, a resource server should not treat every token as proof for every action. A reports.read scope should not allow reports.export, and a token for the profile API should not work at the reports API. OAuth gives the system a way to carry delegated access; it does not remove the need for authorization checks at the resource boundary.

Failure Modes

Failure: open redirect or loose redirect matching. If the authorization server accepts arbitrary redirect URIs, an attacker may route authorization codes to a domain they control. Redirect URIs should be registered and matched exactly, with careful handling of paths, schemes, hosts, ports, and query parameters.

Failure: missing or weak state. Without state, the client may accept a callback it did not initiate. That can create login CSRF, account linking confusion, or code injection. Treat state as an unguessable transaction binding stored by the client.

Failure: over-broad scopes. If PlanBoard only needs statement summaries, issuing reports:* or admin scopes turns a narrow delegation into a broad capability. Scopes should be understandable, limited, and enforced by the resource server.

Failure: thinking consent replaces policy. Elena may click approve, but the organization may still prohibit third-party access to payroll, exports, or admin data. Consent and policy are different checks.

Failure: logging codes and tokens. Authorization codes and bearer tokens should be redacted from logs, analytics, traces, and error pages. A short-lived code is still sensitive during its lifetime.

Worked Review of the PlanBoard Flow

A sound review follows the transaction instead of asking whether "OAuth is enabled."

1. PlanBoard starts a request for `reports.read`.
2. PlanBoard stores `state=af0ifjsldkj` in Elena's local client session.
3. Browser goes to the finance authorization server.
4. Authorization server validates client and redirect URI.
5. Elena authenticates and sees the requested delegation.
6. Authorization server creates a short-lived, single-use code.
7. Browser returns to PlanBoard with code and state.
8. PlanBoard verifies state.
9. PlanBoard exchanges code at the token endpoint.
10. Authorization server verifies code, client, redirect URI, expiry, and reuse.
11. PlanBoard receives an access token scoped to `reports.read`.
12. Reports API validates token and enforces the requested resource action.

The interesting review questions are in the mismatches:

What if the callback state is missing?
What if redirect_uri differs by one path segment?
What if the same code is exchanged twice?
What if Elena is allowed to read reports but not export them?
What if PlanBoard asks for a scope it was never approved to request?
What if the reports API sees a token with the wrong audience?

Each answer should name the component that rejects the request and the evidence it records. If nobody owns the rejection, the flow has a boundary gap.

Key Takeaways

  • OAuth 2.0 authorization code flow is a delegated authorization flow, not password sharing and not complete authentication by itself.
  • The central mechanism is transaction binding across redirects, authorization codes, client identity, redirect URI, scopes, and token exchange.
  • The main trade-off is replacing password sharing with a redirect protocol whose safety depends on exact validation at each boundary.
  • Resource servers still own authorization enforcement; receiving an OAuth access token does not remove scope, audience, tenant, and policy checks.
