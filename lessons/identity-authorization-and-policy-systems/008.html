Token Lifetimes, Refresh, Revocation, and Rotation

The core idea: token lifetime design controls how long stale or stolen authority remains useful; short access tokens limit blast radius, while refresh, revocation, and rotation decide how sessions survive and how compromise is detected.

Core Insight

Elena signs in to PlanBoard with OpenID Connect and connects the finance reports API. Everything works during the first ten minutes. Then her access token expires. If PlanBoard simply fails, Elena gets logged out constantly. If the token never expires, a stolen token may keep working for days. If the app quietly refreshes forever, a lost phone or leaked refresh token may become a long-lived back door.

Token lifetime design is the part of identity systems where "secure" and "usable" stop being slogans and become numbers. How many minutes should an access token live? How long should a refresh token remain valid? What happens when Elena logs out, resets her password, reports a device stolen, or loses admin access? What evidence tells operators whether a token failure is normal expiry, clock skew, replay, or active theft?

The important trade-off is short-lived safety versus user continuity and server state. Short access tokens reduce the window where a stolen token works. Refresh tokens keep the user experience usable by getting new access tokens without asking Elena to sign in every few minutes. Revocation and rotation add server-side memory so the system can end or detect sessions before natural expiry.

The practical lesson is that a token is not only a string. It is part of a lifecycle. You should be able to trace the lifecycle from issuance, to API use, to refresh, to revocation, to incident evidence.

Access Tokens Should Be Cheap to Lose, Not Harmless

An access token is what PlanBoard sends to a resource server:

GET /monthly-statements/2026-05/summary HTTP/1.1
Host: reports-api.finance.example.test
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

If it is a bearer token, whoever presents it can usually use it. The resource server may not know whether the request came from the original client. That is why access tokens are usually short lived.

A common lifecycle looks like this:

issue access token at 10:00
token expires at 10:10
API accepts it from 10:00 through 10:10
API rejects it after expiry
client uses refresh token to get a new access token

Short lifetimes limit stale authority. If Elena is removed from a role at 10:05, a ten-minute token may still carry old claims until 10:10 unless the API checks current policy. That is a bounded stale window. If the access token lasts twelve hours, the stale window is much bigger.

But short lifetimes are not free. They increase token refresh traffic, expose clock-skew bugs, and make outages at the token endpoint visible faster. If every client refreshes at the same fixed interval, a deployment or regional recovery can trigger a refresh storm. Good clients refresh with a little jitter, handle ordinary expiry gracefully, and treat repeated refresh failures as a session problem rather than retrying forever.

The design question is not "what is the secure lifetime?" It is:

How damaging is stale or stolen access for this audience and scope?
How quickly can policy change?
Can the resource server check current policy for sensitive actions?
How much token endpoint traffic can the system absorb?
What happens during token-service outage?

For low-risk read access, ten or fifteen minutes may be acceptable. For payroll export, fund movement, or admin actions, the API may need a fresh policy check or step-up even if the token has not expired.

Refresh Tokens Carry the Longer Session

A refresh token is not normally sent to the resource server. It is sent to the authorization server to get new access tokens:

POST /token
grant_type=refresh_token&
refresh_token=rt_4f89...

The authorization server responds:

{
  "access_token": "new_access_token",
  "expires_in": 600,
  "refresh_token": "rt_92ab..."
}

The access token carries short-term API authority. The refresh token carries the longer-lived ability to continue the session. That makes the refresh token more valuable. If an attacker steals it, they may keep minting fresh access tokens even after the original access token expires.

This is why refresh tokens need stronger handling:

store only where the client can protect them
bind them to a client, device, or session record when possible
limit absolute lifetime
expire after inactivity
rotate on each use for public clients
revoke on logout, password reset, or device removal
monitor reuse as a theft signal

For server-side web apps, the refresh token can live on the backend, outside the browser. For mobile or desktop public clients, it may live in platform-protected storage, but the system should assume compromise is possible. For browser-only apps, long-lived refresh tokens are especially sensitive because JavaScript and browser storage are exposed to XSS and extension risk. Many modern designs prefer a backend-for-frontend or refresh token rotation with strict controls rather than long-lived tokens sitting in browser storage.

Refresh Token Rotation, Step by Step

Rotation means the refresh token changes every time it is used. The previous token becomes invalid after a successful refresh.

Start with Elena's PlanBoard mobile app:

device session = ds_123
current refresh token family = fam_abc
active refresh token = rt_1
access token = at_1, expires at 10:10

At 10:09, PlanBoard refreshes:

client sends rt_1
authorization server verifies rt_1 is active
authorization server marks rt_1 used
authorization server issues at_2 and rt_2
client stores rt_2 and discards rt_1

Now the server state is:

rt_1 = used
rt_2 = active
token family fam_abc = active

If an attacker had copied rt_1 earlier and tries to use it at 10:11, the server sees reuse:

received refresh token = rt_1
state of rt_1 = already used
decision = deny
security event = refresh_reuse_detected
response = invalid_grant
optional action = revoke token family fam_abc

That reuse signal is valuable. Without rotation, the attacker and real device might both keep refreshing with the same token. With rotation, reuse of an old token indicates that at least one copy escaped the intended client state.

The harsh response is to revoke the whole token family, forcing Elena to sign in again. That may annoy a user if the reuse was caused by a race or buggy retry. The permissive response is to deny only the old token and let rt_2 continue. That may leave a thief active if the current token is also stolen. The right choice depends on risk, client reliability, and product expectations.

Revocation Is Server-Side Memory

Natural expiry says "this token stops working at a time." Revocation says "this token or session stops working because the authority changed."

Revocation can be represented in several ways:

delete or deactivate opaque token record
mark refresh token family revoked
store revoked token ids until expiry
increment user token_version after password reset
disable device session
rotate signing keys in an emergency
require introspection for high-risk actions

Opaque tokens are easier to revoke centrally because every use may involve a lookup or introspection. JWT access tokens are harder to revoke immediately if resource servers validate them locally and do not check server state. You can still use short lifetimes, token-version checks, deny lists, or policy lookups for sensitive operations, but each option has a cost.

This is the same trade-off from the token-format lesson, now viewed through time. Local validation improves availability and latency. Central state improves revocation and freshness. A good system chooses where immediate revocation matters and where bounded expiry is enough.

Logout is a common place where this distinction matters. If Elena clicks logout, the client should clear local tokens. The authorization server should also revoke the refresh token or device session when supported. Clearing local storage alone does not invalidate a token already copied elsewhere.

Password reset and MFA recovery are stronger signals. They should usually revoke existing refresh tokens and sessions, or at least the sessions that do not satisfy the new assurance requirement. A role change may not require ending every user session, but it should stop future high-risk actions from using stale authority.

Worked Design Pass

Design PlanBoard's finance connection with these choices:

access token lifetime: 10 minutes
refresh token: rotating
refresh token idle timeout: 30 days
refresh token absolute lifetime: 90 days
reuse response: revoke token family and require sign-in
logout: revoke current token family
password reset at finance provider: revoke delegated refresh tokens
high-risk export: check current policy, not only token scope

Now trace one normal hour:

10:00 Elena connects finance account
10:00 auth server issues at_1 and rt_1
10:09 PlanBoard refreshes with rt_1
10:09 auth server issues at_2 and rt_2, marks rt_1 used
10:19 PlanBoard refreshes with rt_2
10:19 auth server issues at_3 and rt_3, marks rt_2 used

Trace theft:

10:04 attacker copies rt_1 from a compromised device
10:09 real PlanBoard refreshes rt_1 -> receives rt_2
10:12 attacker tries rt_1
10:12 authorization server sees reuse of used token
10:12 server revokes family fam_abc
10:12 PlanBoard's next refresh fails
10:12 Elena is asked to sign in again
10:12 security event links reuse to device session ds_123

The user impact is real: Elena may be interrupted. The security benefit is also real: the system detected a copied long-lived credential and ended that token family. The design should make that interruption understandable, logged, and recoverable.

Operational Signals

Token lifetime problems are hard to diagnose if every failure becomes invalid_grant in a client log. The authorization server and resource servers should expose enough categories to show what boundary failed:

access token expired
access token revoked
access token audience mismatch
refresh token expired by idle timeout
refresh token expired by absolute lifetime
refresh token reused after rotation
token family revoked
device session disabled
policy changed after token issue

Those categories do not all need to be returned to the end user. Some are too sensitive. But operators need them in structured logs, metrics, and audit events. A spike in expired access tokens may mean a clock-skew issue. A spike in refresh reuse may mean a client retry bug after a bad mobile release, or it may mean a real credential leak. A spike in audience mismatches may reveal token confusion between APIs.

Good user-facing behavior also depends on the reason. Natural expiry can trigger silent refresh. Revoked refresh tokens should usually require sign-in. Reuse detection may require a security message and device review. Treating all failures as "try again" makes attacks noisier and incidents harder to understand.

Failure Modes

Failure: refresh tokens never rotate. A stolen refresh token can keep producing access tokens until absolute expiry or manual revocation. Rotation turns old-token reuse into a detection signal.

Failure: access tokens last too long because refresh is hard. Long access-token lifetimes hide refresh complexity by expanding the stolen-token window. Fix refresh behavior rather than making bearer authority last all day.

Failure: revocation only clears the client. Deleting local tokens helps that device, but copied tokens remain useful unless the server refuses them.

Failure: every refresh retry consumes a token. Client retry bugs can accidentally reuse rotated tokens. Token endpoints need idempotency or careful client guidance around network timeouts, and logs should distinguish race from theft when possible.

Failure: no audit trail for lifetime decisions. If an access token is rejected, operators need to know whether the reason was expiry, issuer mismatch, revoked family, reused refresh token, unknown device, or policy change.

Readiness Check

Close the lesson and review one token design:

How long does an access token live?
What damage can happen inside that window?
Is there a refresh token?
Where is the refresh token stored?
Does refresh rotate?
What happens on reuse of an old refresh token?
What does logout revoke server-side?
What does password reset revoke?
Which APIs need current policy checks despite valid tokens?
What event appears when revocation or reuse happens?

If the answer to revocation is "the client deletes the token," keep tracing. The authority ends only when the component that validates the token refuses it.

Key Takeaways

  • Access tokens should usually be short lived because bearer authority is useful to whoever presents it.
  • Refresh tokens carry the longer session and therefore need stronger storage, rotation, revocation, and monitoring.
  • Refresh token rotation turns reuse of an old token into a compromise signal, but it must handle client retry and race behavior carefully.
  • Revocation is a server-side validation decision; clearing a client token is not enough if a copied token can still be accepted.
