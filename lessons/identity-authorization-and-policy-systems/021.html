Threats: Confused Deputy, Token Theft, and Privilege Escalation

By the end of this lesson, you will be able to:

  • distinguish confused deputy, token theft, and privilege escalation in one authorization path;

  • trace how audience, scope, tenant, caller, and resource checks stop an overpowered action;

  • review a service-to-service design for places where borrowed authority becomes unsafe.

Idea in one sentence: Authorization threats often appear when a system accepts authority without checking who it was meant for, what it may do, and whose privilege is actually being used.

Core Insight

Acme's finance admin asks your SaaS app to export invoice data. The web app cannot generate the file directly, so it sends a job to an internal export service. That export service has broad database credentials because it must generate exports for every tenant. A small shortcut turns this normal architecture into a security flaw: the export service trusts the web app's request and uses its own broad authority without rechecking tenant, caller, resource, and purpose.

An attacker does not need root access to exploit that shape. They might trick the web app into asking for another tenant's export, steal a token meant for one API and replay it to another, or find an endpoint where a low-privilege role can trigger an admin-only side effect. These are different threat names, but they share a mechanism: a boundary accepts an action under the wrong authority.

A confused deputy is a component with legitimate power that is tricked into using that power for someone who should not have it. In the export scenario, the export service is the deputy. It can read all tenant invoices for operational reasons, but it must not let a caller choose any tenant merely because the service itself has database access.

Token theft is the capture or misuse of a credential that represents some authority: session cookie, API key, access token, refresh token, service token, or signed assertion. Theft becomes worse when tokens are broad, long-lived, accepted by the wrong audience, or usable without sender constraints.

Privilege escalation is the movement from less authority to more authority. It may happen vertically, such as viewer to admin, or horizontally, such as Acme user to Beta tenant data. The trade-off is feature flexibility versus attack surface: delegation, automation, background jobs, integrations, and support tooling are useful precisely because they let one component act for another. The design work is to keep that borrowed authority narrow and inspectable.

What Authority Is Moving?

Before choosing controls, name the authority in the request. In the export path, several kinds of authority are present:

human authority:
  Priya is finance_admin for tenant acme-eu

application authority:
  web app may enqueue export jobs after authorization

service authority:
  export service can read invoice tables for all tenants

token authority:
  job token says action=invoice.export, tenant=acme-eu, audience=export-service

resource boundary:
  export job may read invoices where tenant_id=acme-eu

The service account's database credential is not the permission the user requested. It is an implementation capability. The real security question is whether Priya, through this workflow, may export this tenant's invoices now. If the export service forgets that distinction, its implementation capability becomes user-visible power.

Audience is one of the simplest checks that prevents authority from drifting. A token issued for the billing API should not be accepted by the export service. A SAML assertion meant for one service provider should not be accepted by another. An access token with aud=profile-api should not authorize invoice.export. Audience says "who this credential was meant for."

Scope and permission say "what this credential may do." Tenant and resource say "where it may do it." Caller and subject say "on behalf of whom." Freshness and revocation say "whether the facts behind it are still usable." A robust authorization boundary does not replace these with a single "token valid" or "internal caller" check.

Worked Path: Safe Export Delegation

Trace the Acme export as a safe delegated action.

1. Priya requests invoice export for tenant acme-eu.
2. Web app authenticates Priya's session.
3. Web app authorizes invoice.export for Priya in acme-eu.
4. Web app creates a job with tenant=acme-eu, requester=priya, purpose=finance_export.
5. Web app sends the job to export service with a narrow token:
   audience=export-service
   action=invoice.export
   tenant=acme-eu
   job_id=job_771
   expires_at=short window
6. Export service validates token signature, issuer, audience, expiry, and replay state.
7. Export service checks that job tenant, token tenant, and query tenant match.
8. Export service reads only invoices where tenant_id=acme-eu.
9. Export service writes decision evidence and output metadata.
10. Download endpoint checks Priya or approved recipients before release.

Now compare the unsafe path:

1. Web app receives tenant=beta-us in a request parameter.
2. Web app checks only that Priya is logged in.
3. Web app asks export service to export beta-us.
4. Export service trusts any internal web app call.
5. Export service uses all-tenant database access.
6. Beta invoice data is exported under Acme's request.

The unsafe path is a confused deputy. The export service had real authority, but it used that authority based on an untrusted or under-checked caller instruction. The fix is not merely "make the export service less powerful," although least privilege helps. The deeper fix is to carry the user's authorized intent as constrained, verifiable context and make the deputy enforce that context before acting.

Pause and predict: If the export service is reachable only on a private network, can it skip tenant and audience checks?

Check: No. A private network reduces exposure, but it does not prove the caller's user, tenant, action, or intent. Internal boundaries still need authorization because bugs, SSRF, compromised services, and confused deputies often operate from inside the network.

Token Theft and Replay

Token theft changes the question from "is the workflow correct?" to "what can someone do if they capture this credential?" A stolen token is most damaging when it is accepted broadly and lives long enough to be useful.

Common token mistakes are concrete:

  • accepting an access token at an API that is not its audience;
  • using one token for user sessions, API calls, and service jobs;
  • putting bearer tokens in URLs, logs, browser storage, or referrers;
  • issuing long-lived tokens without rotation, revocation, or sender constraints;
  • treating a refresh token as if compromise is just a normal session event;
  • failing to bind a token to tenant, resource, client, or permission.

A bearer token is usable by whoever possesses it. That is why storage and transport matter. Server-side sessions, secure cookies, short-lived access tokens, refresh token rotation, proof-of-possession mechanisms, mTLS-bound tokens, and device or client binding all reduce different parts of the theft window. None of them remove the need for audience, scope, tenant, and freshness checks at the receiving API.

In the export scenario, the job token should not be a reusable user access token. It should be narrow, short-lived, addressed to the export service, tied to job_771, and rejected after use if replay would be dangerous. The export service should log enough evidence to detect odd patterns: duplicate job token use, audience mismatch, expired token attempts, tenant mismatch, or exports requested shortly after a privilege change.

Also notice what the receiving service can learn without knowing the user's password or session cookie. It can see whether this credential was made for this service, whether the requested action fits the token, whether the tenant in the token matches the tenant in the job, and whether the resource query stays inside that tenant. Those checks make stolen-token incidents smaller. A captured token may still be serious, but it cannot silently become an all-purpose credential for every API if each receiver enforces its own boundary.

Privilege Escalation Patterns

Privilege escalation often hides behind product features that are useful in legitimate workflows. The question is not "does this feature involve power?" It is "whose power is being used, and where is that power constrained?"

Common patterns:

  • Horizontal tenant escalation: a user changes tenant_id, account_id, or object ID and reaches another tenant's resource.
  • Vertical role escalation: a viewer finds an endpoint that performs admin action because the UI hid the button but the API did not check permission.
  • Deputy escalation: a low-privilege caller triggers a service, worker, or integration with broader service credentials.
  • Token substitution: a token issued for one audience, client, or purpose is accepted somewhere else.
  • Callback or redirect abuse: an attacker controls a redirect, webhook, or callback URL and captures codes, tokens, or signed results.
  • Impersonation leakage: support or admin impersonation continues after purpose, approval, or session boundary should end.

The corrective mental model is to separate capability from authority. A worker may have the capability to update any row because deployment is simpler that way. It has authority to update only the rows named by a verified, authorized job. A support tool may have the capability to view customer accounts. It has authority only within an approved support session, with decision evidence, purpose, and tenant binding.

Pause and predict: A low-privilege user cannot see the "delete project" button, but can call DELETE /projects/{id} directly. Which threat is this?

Check: It is vertical privilege escalation caused by missing server-side authorization. UI hiding is not an enforcement boundary.

Design Check

Review any delegated or token-based path with this checklist:

Caller:
  Who initiated the action?
  Is the caller authenticated and authorized for this tenant and resource?

Credential:
  What token or service identity is presented?
  Is issuer, signature, audience, client, expiry, and replay state checked?

Delegation:
  Is the service using its own broad capability or a constrained user intent?
  Where is tenant, action, resource, and purpose carried?

Enforcement:
  Does the worker/API recheck the boundary closest to the resource?
  Are UI checks duplicated by server-side policy?

Evidence:
  Can an incident reviewer see caller, deputy, token audience, scopes,
  tenant, resource, decision reason, and output?

Apply it to the export service. A strong design issues a job-scoped token to the export service, validates audience and expiry, binds tenant in the job and query, requires invoice.export, rejects replay, and records the human requester plus service actor. A weak design accepts any internal request from the web app with a tenant_id parameter and trusts the export service's all-tenant credential as proof that the action is allowed.

Close the lesson and reconstruct the path from memory: user intent, local authorization, constrained delegation, audience check, tenant/resource check, resource access, evidence. If one step says "internal service, so trusted," inspect it as a likely confused deputy.

Key Takeaways

  • Confused deputy, token theft, and privilege escalation are different names for authority crossing a boundary without the right constraints.
  • A valid credential is not enough; the receiver must check audience, issuer, scope, tenant, resource, expiry, replay, and local authorization context.
  • Delegated services need constrained intent, not just broad service credentials and internal network trust.
  • Treat every powerful workflow as an evidence trail: who asked, which deputy acted, what token was accepted, what resource was touched, and why it was allowed.
