PKCE, Public Clients, and Native Apps

The core idea: PKCE protects authorization code flow for clients that cannot keep a secret by proving, at token exchange time, that the same client instance that started the flow is the one redeeming the code.

Core Insight

Elena connects PlanBoard to the finance product using the OAuth authorization code flow from the previous lesson. That worked cleanly when PlanBoard was a server-side web app: the server could store a client secret, receive the callback on a registered HTTPS URL, and exchange the authorization code from a controlled backend.

Now PlanBoard ships a mobile app. Elena taps "Connect finance account" inside the app. The app opens the system browser, Elena approves access at auth.finance.example.test, and the authorization server redirects back to the app. The redirect may use a custom URI scheme such as planboard:/oauth/callback, an app link, a universal link, or a localhost loopback callback on desktop.

This is a different security shape. A native app or browser-only app is a public client: anything embedded in the app can be extracted, copied, or imitated. A client secret in the mobile binary is not really secret. Another app on the device may also try to register a similar custom scheme or intercept the authorization code on the way back.

PKCE, pronounced "pixy," exists for that problem. It adds a one-time secret created by the client instance before the redirect. The authorization server stores a transformed version of that secret with the authorization code. Later, when the client redeems the code, it must present the original secret. An attacker who only intercepts the code does not have the secret needed to exchange it.

The trade-off is that PKCE adds proof to a flow designed for portability. It does not make public clients confidential. It does not replace redirect URI validation, state, token audience checks, or secure token storage. It narrows one dangerous gap: an authorization code should not be useful unless redeemed by the same client instance that initiated the request.

Public Clients Cannot Prove Identity the Same Way

A confidential client can authenticate to the token endpoint with a secret stored on a backend server:

client secret lives on server
browser only receives redirect
server exchanges code for tokens
attacker needs server credential to redeem code

A public client cannot rely on that shape:

mobile app installed on user device
binary can be inspected
client secret can be copied
redirect may leave and re-enter the app
token exchange may happen from the device

That does not mean public clients are forbidden. It means the protocol must stop pretending that a static client secret proves much. The useful proof has to be created per authorization attempt, not shipped forever inside the app.

PKCE uses two values:

code_verifier  = high-entropy random string kept by the client instance
code_challenge = transformed value sent in the authorization request

In the common and recommended S256 method:

code_challenge = base64url(SHA256(code_verifier))

The client sends the code_challenge before authorization. It keeps the code_verifier local. The authorization server stores the challenge next to the authorization code. When the code is redeemed, the client sends the verifier. The server hashes the verifier and compares it with the stored challenge.

The shape is similar to leaving a lock at the authorization server and keeping the key with the client instance. The code is not enough. The token endpoint asks for the key.

PKCE Step by Step

Start with Elena in the PlanBoard mobile app.

The app creates fresh values for this attempt:

state = st_8f2a
code_verifier = vr_5ZpW9...long-random-value...
code_challenge = base64url(sha256(code_verifier))
code_challenge_method = S256

The app stores state and code_verifier locally for this in-flight transaction. Then it opens the system browser with an authorization request:

GET https://auth.finance.example.test/authorize?
  response_type=code&
  client_id=planboard-mobile&
  redirect_uri=https%3A%2F%2Fapp.planboard.example%2Foauth%2Fcallback&
  scope=reports.read&
  state=st_8f2a&
  code_challenge=Gr9n...&
  code_challenge_method=S256

The authorization server validates the client, redirect URI, requested scope, and PKCE parameters. It does not need to know the verifier yet. It records:

authorization_code = code_91cc
client_id = planboard-mobile
redirect_uri = https://app.planboard.example/oauth/callback
scope = reports.read
stored_code_challenge = Gr9n...
method = S256
expires = soon
used = false

Elena signs in and approves the delegation. The authorization server redirects the browser back:

GET https://app.planboard.example/oauth/callback?
  code=code_91cc&
  state=st_8f2a

PlanBoard checks state. That check answers: "does this callback belong to an authorization request I started?" If state is missing or wrong, the app stops before token exchange.

Then PlanBoard exchanges the code:

POST https://auth.finance.example.test/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
client_id=planboard-mobile&
code=code_91cc&
redirect_uri=https%3A%2F%2Fapp.planboard.example%2Foauth%2Fcallback&
code_verifier=vr_5ZpW9...long-random-value...

The authorization server checks the ordinary code-flow bindings and the PKCE binding:

code exists: yes
code unused: yes
code unexpired: yes
client matches original request: yes
redirect_uri matches original request: yes
hash(code_verifier) == stored_code_challenge: yes
decision: issue tokens

If another app intercepted code_91cc but did not have the verifier, the token endpoint rejects:

code exists: yes
code unused: yes
client maybe claims planboard-mobile
hash(attacker_verifier) == stored_code_challenge: no
decision: deny
reason: pkce_verifier_mismatch

That is the central mechanism. PKCE does not hide the authorization code. It makes the code insufficient by itself.

What PKCE Does Not Replace

PKCE and state are often confused because both involve random values. They protect different boundaries.

state
  generated by client
  returned through callback
  checked by client
  binds callback to the local browser/app transaction

PKCE verifier
  generated by client
  transformed challenge sent to authorization server
  verifier checked by authorization server at token endpoint
  binds code redemption to the initiator

Use both. state protects the client from accepting the wrong callback. PKCE protects the authorization server from issuing tokens to someone who only obtained the code.

PKCE also does not remove the need for exact redirect URI validation. If an authorization server sends codes to arbitrary redirect URIs, an attacker may route the browser to infrastructure they control. PKCE reduces what the attacker can do with the code, but loose redirect handling still creates account confusion, phishing surface, and debugging chaos.

PKCE does not make a static client secret useful in a mobile app. If the "secret" ships with every copy of the app, an attacker can extract it and use it. Treat native apps, single-page apps, command-line tools, and desktop apps as public unless there is a real protected backend involved.

Native App Redirect Choices

Native apps need a way for the browser to return to the app. Common patterns include:

private-use URI scheme: planboard:/oauth/callback
claimed HTTPS app link: https://app.planboard.example/oauth/callback
loopback redirect: http://127.0.0.1:{random-port}/callback

Private-use URI schemes are easy, but multiple apps may try to claim similar schemes. Claimed HTTPS app links or universal links can give the platform more evidence that the domain owner controls the app association, but they require correct platform setup. Loopback redirects are useful for desktop apps and command-line tools that can listen briefly on a local port.

The important design question is not just "which redirect works on this platform?" It is:

Who can receive this redirect?
Can another app imitate it?
Is the redirect URI exactly registered?
Does PKCE bind the code to the initiating app instance?
What happens if the browser returns twice?
What logs prove why token exchange failed?

For mobile flows, prefer the system browser or platform authentication session over embedded web views. Embedded web views can train users to type credentials into an app-controlled surface and may interfere with the authorization server's security controls. A system browser gives the user and identity provider a clearer trust boundary.

After PKCE, Tokens Still Need Care

PKCE protects the authorization code exchange. It does not protect the access token after the token endpoint has issued it. Once PlanBoard receives a bearer token, the normal bearer-token rule applies: whoever can present it can usually use it until it expires or is revoked.

That means the mobile app still needs a storage and lifetime design:

access token -> short lived, kept out of logs and crash reports
refresh token -> higher value, stored in platform-protected storage when used
logout -> clear local tokens and call revocation when supported
device compromise -> assume tokens may be copied

Some systems avoid giving long-lived refresh tokens to public clients. Others issue refresh tokens with rotation, sender constraints, or device binding. Those are separate controls. PKCE should not be described as "making tokens safe on the device." It only proves the code exchange belongs to the app instance that started the flow.

A backend-for-frontend can change the design. If PlanBoard's mobile app talks only to PlanBoard's backend, and that backend performs the OAuth token exchange and stores tokens server-side, the mobile app may avoid holding finance API tokens directly. That buys central control and easier revocation, but it also means PlanBoard now operates a backend session and must secure its own API. Again, the trade-off moves authority; it does not erase it.

When reviewing a public-client design, ask where the token goes after PKCE succeeds. If the answer is "we used PKCE, so storage is solved," the design is skipping the next boundary.

Worked Failure: Code Interception

Trace the failure PKCE was designed to reduce.

Without PKCE:

1. PlanBoard opens the browser for authorization.
2. Elena approves access.
3. Authorization server redirects with code=code_91cc.
4. Malicious app intercepts the redirect.
5. Malicious app sends code_91cc to the token endpoint.
6. If client identity is weak and no verifier is required, tokens may be issued.

With PKCE:

1. PlanBoard creates code_verifier and code_challenge.
2. Authorization server stores challenge with code_91cc.
3. Malicious app intercepts code_91cc.
4. Malicious app lacks PlanBoard's verifier.
5. Token endpoint hashes the presented verifier.
6. Hash does not match stored challenge.
7. Token endpoint denies the exchange.

The difference is not that the redirect became impossible to intercept. The difference is that interception no longer gives the attacker the missing proof.

This is why the verifier must be high entropy and generated for each transaction. If the verifier is predictable, reused, logged, or shared across attempts, the binding gets weaker. The verifier should not be placed in the authorization request URL. Only the challenge goes through the front channel.

Failure Modes

Failure: using plain when S256 is available. The plain method sends a challenge equal to the verifier. Prefer S256 so the front-channel value does not reveal the secret needed at token exchange.

Failure: reusing a verifier. A verifier should be fresh per authorization attempt. Reuse creates correlation and can make replay or confused transaction bugs harder to reason about.

Failure: treating PKCE as consent. PKCE proves possession of the verifier. It does not prove that the requested scope is appropriate, that Elena understood the consent screen, or that the resource server should allow every action.

Failure: weak redirect ownership. If another app can receive the callback, PKCE helps with code redemption but the user experience and account-linking flow may still be confused. Use platform-recommended redirect patterns and exact registration.

Failure: invisible verifier mismatch. A verifier mismatch should be logged as a security-relevant denial without logging the code or verifier. Operators need evidence, not secrets.

Readiness Check

Close the lesson and trace one public-client OAuth flow:

Is this client confidential or public?
Where is the authorization request created?
Where is code_verifier stored?
Which code_challenge_method is used?
Who checks state?
Who checks the PKCE verifier?
Can another app receive the redirect?
Is redirect_uri matched exactly?
What happens if the same code is redeemed twice?
What audit event appears on verifier mismatch?

If the answer is "the app has a client secret," ask whether that secret is truly protected by a backend or merely packaged into public code.

Key Takeaways

  • Public clients cannot rely on embedded static secrets; PKCE creates per-transaction proof instead.
  • state binds the callback to the client transaction, while PKCE binds authorization-code redemption to the initiating client instance.
  • PKCE reduces authorization-code interception risk, but it does not replace redirect URI validation, consent, scope enforcement, token validation, or secure storage.
  • For native apps, the redirect method is part of the security design because it affects who can receive the authorization response.
