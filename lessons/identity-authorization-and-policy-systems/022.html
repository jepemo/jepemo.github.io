Testing Auth Systems and Permission Matrices

By the end of this lesson, you will be able to:

  • turn roles, actions, resources, tenants, and contexts into an executable permission matrix;

  • choose policy unit tests, integration tests, negative tests, and regression fixtures for auth behavior;

  • review whether auth tests prove denials, not just happy-path allows.

Idea in one sentence: Authorization tests convert security intent into executable evidence, trading test volume and fixture complexity for confidence that permission changes do not silently widen access.

Core Insight

Your team adds a new role called billing_analyst. Product says the role can view invoices, export monthly summaries, and inspect payment status, but cannot issue refunds, see full card details, manage users, or read another tenant's invoices. The implementation touches an API gateway, a policy engine, a background export worker, field masks, and frontend navigation. A code review says the role "looks right." Two weeks later, a customer reports that billing_analyst can call a refund endpoint directly.

That failure is not only a missing if statement. It is a missing executable contract. The team knew the intended rule in prose, but no test enumerated the subject, action, resource, tenant, and context combinations that must allow or deny. The UI hid the refund button, the API handler reused an admin helper, and the regression escaped because the test suite checked only successful invoice reads.

Authorization systems need tests because the real behavior emerges from combinations. A role name alone does not decide access. A decision may depend on tenant, resource owner, relationship, field, purpose, policy version, token audience, support session, device posture, or time since revocation. Humans are bad at remembering every cross-product when a feature changes.

A permission matrix is a compact table of expected decisions. It says which principal, role, group, or relationship may perform which action on which resource under which conditions. The matrix is not valuable because tables are neat. It is valuable because each row can become a fixture, a policy unit test, an API integration test, or a regression case after an incident.

The trade-off is coverage versus rule complexity. A matrix that tries every possible combination becomes noisy and brittle. A matrix that tests only "admin can do everything" is almost useless. The craft is to test boundaries: least privilege, tenant separation, field-level restrictions, delegation, freshness, and the negative cases attackers actually exploit.

What Belongs in the Matrix?

Start with the shape of a decision, not the shape of the UI. For the billing_analyst role, a useful matrix includes the dimensions that change the answer:

subject:   user, role, group, tenant membership, support session
action:    invoice.read, invoice.export, refund.issue, user.manage
resource:  invoice, tenant, customer, field, export job
context:   tenant, purpose, device posture, token audience, policy version
expected:  allow, deny, mask, require approval, require fresh check
evidence:  decision reason, policy id, test fixture id

A first cut might look like this:

case                         expected
billing_analyst reads own-tenant invoice summary      allow
billing_analyst reads other-tenant invoice            deny
billing_analyst exports monthly summary               allow
billing_analyst issues refund                         deny
billing_analyst reads full card token                 mask or deny
finance_admin issues refund under limit               allow
finance_admin issues refund after revocation          deny or fresh-check
support_agent reads invoice with active ticket        allow limited fields
support_agent reads invoice without ticket            deny

Do not confuse this table with a spreadsheet stored in a wiki. The durable version is executable. It may live as JSON fixtures, policy-engine tests, parameterized integration tests, or generated cases from a source-of-truth table. What matters is that the expected decisions run in CI and fail when the implementation widens access.

The matrix should include denials as first-class cases. Security regressions often appear as "this should have been denied" rather than "this should have been allowed." If your tests create an admin user, make a successful request, and stop there, they prove the easiest part of authorization.

Worked Path: Testing a New Role

Trace how the team could add billing_analyst safely.

1. Product names the role intent:
   view invoices, export summaries, no refunds, no card details.

2. Security and engineering translate intent into matrix rows:
   subject=billing_analyst
   action=refund.issue
   resource=invoice:own_tenant
   expected=deny

3. Fixtures create representative tenants:
   acme-eu with billing_analyst Priya
   beta-us with separate invoices
   invoice with ordinary fields and sensitive card token

4. Policy unit tests check the evaluator directly:
   decision(policy_input) == expected
   reason includes role, tenant, field, or freshness boundary

5. API integration tests call real endpoints:
   GET /invoices/{own} -> 200 with masked fields
   GET /invoices/{other_tenant} -> 403 or 404 by design
   POST /refunds -> 403

6. Worker tests check delegated paths:
   export job token carries tenant=acme-eu and action=invoice.export
   worker rejects tenant mismatch and replay

7. Regression tests are added for every discovered escape.

The important mechanism is layered evidence. A policy unit test says the decision function understands the rule. An API test says the route actually calls the decision function with the right input. A worker test says delegated services do not bypass the rule. A response-shape test says forbidden fields are not serialized. No one layer proves the whole boundary alone.

Pause and predict: If a policy unit test denies refund.issue, why still test the refund API endpoint?

Check: The endpoint might not call the policy, might pass the wrong tenant or action, might use an admin helper, or might perform the side effect before checking. Unit tests prove the policy logic; integration tests prove the policy is wired into the real path.

Negative Tests and Boundary Fixtures

Good auth tests make the wrong path easy to see. Every allow should have nearby denies.

For tenant isolation, create at least two fixture tenants with similar-looking resources. If all tests use one tenant, a missing tenant predicate may still pass. Test own-tenant allow and other-tenant deny with the same role and action. Include resource IDs that are valid but out of scope; otherwise the test may pass because the object does not exist, not because authorization worked.

For field-level access, assert response shape. A billing_analyst may receive card_last4 but not card_token. A support user may see shipping status but not fraud notes. Tests should inspect serialized responses, exports, search results, and logs when those paths can carry sensitive fields.

For delegation, test the worker or service boundary directly. A background job should reject a token with the wrong audience, an action outside scope, a tenant mismatch, an expired timestamp, or a replayed job id. This connects directly to confused-deputy and token-substitution threats.

For revocation and caching, test a state transition. Grant access, observe allow, revoke access, then assert the next high-risk action denies or requires a fresh check. If the product accepts bounded staleness for low-risk reads, encode that promise explicitly instead of leaving the test ambiguous.

Pause and predict: A cross-tenant test requests an invoice ID from another tenant and receives 404. Is that always a passing authorization test?

Check: Only if the product intentionally hides existence and the test proves the object exists in the other tenant. Otherwise the 404 may be a fixture mistake, not a tenant-boundary proof.

Keeping Tests Maintainable

The risk with permission matrices is combinatorial explosion. Ten roles, fifty actions, five resource types, and several contexts can produce thousands of cases. Do not test every combination with equal weight. Test representative boundaries and generate repetitive cases from a smaller source of truth.

Useful patterns:

  • Policy unit tests: fast tests for pure decision logic, edge cases, and reason codes.
  • Parameterized matrix tests: one table generates many allow/deny assertions.
  • Integration smoke tests: a smaller set of routes proves policy wiring and response shape.
  • Negative regression tests: every auth incident or near miss becomes a named case.
  • Property or fuzz tests: random unauthorized tenant/resource combinations should never allow.
  • Fixture tenants: stable, readable tenants with clear roles, resources, and relationships.

Reason codes make tests easier to debug. A deny because tenant_mismatch is different from a deny because missing_role or stale_revision. Do not assert every internal string in brittle ways, but do record enough reason structure that a failed test points at the boundary that changed.

Authorization tests also need ownership. If the product team changes a role, the matrix must change in the same review as policy and UI updates. If the platform team changes token validation, service-boundary tests must run. If customer support adds an impersonation feature, tests should cover purpose, approval, session expiry, and audit evidence. A matrix maintained by no one becomes stale documentation.

Regression tests deserve special treatment. When an incident or near miss reveals an authorization escape, write the smallest test that would have failed before the fix. Name it after the failure, not after the implementation detail: billing_analyst_cannot_issue_refund, export_worker_rejects_other_tenant_job, or support_session_expires_before_sensitive_field. This makes future reviewers understand the security promise without reconstructing the incident.

Do not limit regression tests to the exact endpoint that failed. Ask which family of boundaries failed. A missing tenant predicate in one export query suggests testing neighboring report, search, and download paths. A token accepted with the wrong audience suggests testing every service that validates the same token type. A role that leaked one sensitive field suggests checking serialized API responses, CSV exports, search snippets, and background notifications. The goal is not to punish the codebase with endless cases; it is to turn each discovered pattern into a durable guardrail.

The operational signal from test failures should be specific enough to act on. "Expected deny, got allow" is useful. "Expected deny for tenant_mismatch on case matrix-tenant-004, got allow from export_worker" is much better. Good auth tests fail loudly at the boundary that widened.

Design Check

Use this review when adding a role, action, integration, or policy engine rule.

Decision shape:
  Which subject, action, resource, tenant, and context fields affect the answer?

Matrix:
  What are the nearest allows and denies?
  Which negative cases would catch tenant, role, field, and token mistakes?

Fixtures:
  Are there at least two tenants and real out-of-scope resources?
  Are sensitive fields present so masking tests can fail?

Layers:
  Is policy logic tested directly?
  Are API routes, workers, exports, and response shapes tested where relevant?

Evidence:
  Can failed tests show the decision reason and fixture case?

Apply it to billing_analyst. A strong test set proves own-tenant invoice reads, other-tenant denials, masked card fields, refund denial, export worker tenant binding, and revocation before high-risk export. A weak test set logs in as an admin, checks that the invoice page loads, and assumes the hidden buttons represent authorization.

Close the lesson and reconstruct the testing ladder from memory: matrix row, fixture, policy unit test, route integration test, worker or export test, response-shape assertion, regression case. If a permission rule exists only in prose, it is not yet a durable authorization control.

Key Takeaways

  • A permission matrix is useful only when it becomes executable evidence, not static documentation.
  • Strong auth tests include nearby denials: other tenant, wrong role, wrong audience, stale revocation, forbidden field, and unsafe delegation.
  • Policy unit tests, API integration tests, worker tests, and response-shape assertions prove different layers of the same boundary.
  • Keep matrices maintainable by focusing on boundary cases, generated fixtures, reason evidence, and regression tests for every discovered escape.
