Identity, Authentication, and Authorization Boundaries

The core idea: identity systems stay understandable when you separate the principal being named, the credential that proves control, the authentication event that establishes a session, and the authorization decision that permits one action on one resource.

Core Insight

Imagine a document product with workspaces. Maria belongs to the Acme workspace and signs in successfully. A support ticket reports that she can open this URL:

GET /workspaces/zephyr/docs/doc_742

The application checks that Maria is logged in. It sees a valid session cookie. The handler returns the document. Every local check seems to pass: the user is real, the session is not expired, and the document id exists. The bug is that the system answered the wrong question. It proved "this request came from a signed-in user," but it did not prove "this signed-in user may read this document in this workspace."

That distinction is the foundation of identity engineering. Identity names an entity in the system. Authentication proves that the caller controls some credential or session associated with that entity. Authorization decides whether that authenticated entity may perform a specific action on a specific resource in a specific context. The words are often used together, but mixing them in code creates real security failures.

The useful mental model is a chain of boundaries. A credential enters the system. An authentication component validates it and produces a subject. A request handler asks for a decision about an action and resource. A policy or permission model answers allow or deny. An audit trail records enough evidence to explain the decision later. Each step should have a narrow job. If one step silently does the job of another, the design becomes hard to review and easy to bypass.

The trade-off is clarity versus convenience. It is convenient to check is_logged_in everywhere and assume the rest follows. It is clearer, but more work, to model principals, sessions, resources, actions, tenants, and decision evidence separately. The payoff is that access rules become testable, incidents become explainable, and later lessons on tokens, OAuth, policy engines, tenancy, and audit logs have a stable vocabulary.

The Pieces You Need to Name

Start one level below the familiar words. A login form, cookie, API key, service account, and authorization policy are not interchangeable. They play different roles in a request path.

A principal is an entity the system can talk about. It may be a human user, a service account, a workload, an organization, or sometimes a device. A principal is not automatically allowed to do anything. It is just a named participant.

A credential is evidence the caller presents to prove control: a password, passkey, client certificate, API key, session cookie, bearer token, or signed assertion. Credentials are dangerous because whoever holds them may be able to act as the principal until the credential expires or is revoked.

An authentication event validates a credential and establishes what the system currently believes about the caller. The output is usually a subject in a session or token:

credential presented -> credential validated -> subject established

An authorization decision evaluates a subject against an action, a resource, and context:

subject + action + resource + context -> allow or deny

The resource matters. "Maria is an admin" is incomplete unless you know admin of what. She might be an admin of Acme, a viewer of Zephyr, and have no relationship to Nimbus. The action matters too. Reading a document, changing billing details, inviting a user, exporting data, and deleting an audit log are different operations even when they involve the same account.

Finally, an audit record is decision evidence. It should say who acted, what they tried to do, which resource was involved, which policy or permission path was used, what the result was, and enough request context to investigate abuse or mistakes later. Audit is not just "log the URL." It is evidence about a trust decision.

A Request Path with the Boundaries Visible

Return to Maria's request:

GET /workspaces/zephyr/docs/doc_742 HTTP/1.1
Host: docs.example.test
Cookie: session=sess_abc

A weak implementation may do this:

1. Read session cookie.
2. Load user from session.
3. If user exists, load doc_742.
4. Return document.

The bug is in step 3. The handler jumped from "authenticated user exists" to "resource may be returned." It skipped the authorization decision. A better path keeps each boundary explicit:

1. Extract credential:
   session cookie = sess_abc

2. Authenticate:
   session sess_abc is valid
   subject = user:maria
   session assurance = normal browser login

3. Parse request:
   action = document.read
   workspace = zephyr
   resource = document:doc_742

4. Load authorization facts:
   user:maria is member of workspace:acme
   user:maria has no membership in workspace:zephyr
   document:doc_742 belongs to workspace:zephyr

5. Decide:
   may user:maria perform document.read on document:doc_742?
   result = deny

6. Respond and record:
   HTTP 403 Forbidden
   audit: subject=user:maria, action=document.read, resource=document:doc_742,
          workspace=zephyr, result=deny, reason=no_workspace_membership

This is the same user and the same session. The difference is that the system asked a resource-specific question instead of accepting authentication as enough.

The boundary also changes what gets cached and propagated. The session service may cache session validity. The authorization layer may cache membership facts for a short time. The application may cache the document body. Those caches have different risk. A stale session cache might allow a recently logged-out session to work for a few seconds. A stale authorization cache might allow access after a user is removed from a workspace. A stale document cache might expose a document if it is keyed without tenant or permission context. "Cache auth" is not one decision.

Authentication Answers "Who Is Calling?"

Authentication is about evidence of control. In a browser app, the evidence may start as a password plus MFA or a passkey ceremony. After login, the request usually carries a session cookie. In an API, the evidence may be a bearer token. In service-to-service traffic, it may be a client certificate or workload identity token.

The authentication layer should answer a limited set of questions:

Was a credential presented?
Is it valid?
Has it expired or been revoked?
Which subject does it establish?
How strong was the authentication event?
Which tenant or client was involved, if known?

It should not smuggle broad permission claims into places that cannot verify them. A token may contain useful claims, but claims are not magic truth. They have an issuer, audience, timestamp, signature, and freshness boundary. Later lessons will cover JWTs, opaque tokens, introspection, refresh, and revocation. For now, the important point is simpler: authentication creates a subject that authorization can reason about. It does not finish the access decision.

This is why naming matters. A variable called user often becomes overloaded. Does it mean a database user record? A principal id? A browser session? A token subject? An account owner? A member of the current workspace? When code uses one vague object for all of those, authorization bugs become easier to hide.

Prefer names that preserve the boundary:

principal_id
authenticated_subject
session_id
actor_id
tenant_id
resource_owner_id
authorization_context

Clear names do not make a system secure by themselves, but they make the next check visible.

Authorization Answers "May This Action Happen?"

Authorization is a decision about action on resource under context. A good authorization check is narrow enough to be tested:

can(subject=user:maria,
    action=document.read,
    resource=document:doc_742,
    context={workspace: zephyr, request_ip: ..., session_assurance: ...})

The policy might be simple:

allow document.read when
  subject is a member of the resource workspace
  and membership role is viewer, editor, or admin
  and document is not archived with legal_hold

The policy might later become RBAC, ABAC, ReBAC, or policy-as-code. The first design question is not which model is fashionable. It is which facts the decision needs. Role-based access control uses roles such as admin, editor, or viewer. Attribute-based access control uses attributes such as department, region, sensitivity, or device posture. Relationship-based authorization uses graph-like facts such as "Maria is a member of Acme" and "doc_742 belongs to Zephyr."

Whatever model you choose, the decision needs an enforcement point. The policy enforcement point is where the system refuses or allows the request: an API gateway, backend handler, database proxy, object storage layer, or UI backend. The policy decision point is where the allow/deny answer is computed. In a small app they may be the same function. In a larger platform they may be separate services. Separating the names helps you ask whether every path is actually enforced.

The safest default is denial. A missing relationship, missing role, unknown tenant, expired session, malformed resource id, or unreachable policy dependency should not quietly become permission. Some products choose degraded modes for availability, but high-risk authorization usually degrades toward refusal, narrower access, or manual review. That choice should be explicit because it changes both user experience and incident behavior.

Do not rely on UI hiding as authorization. If the "Delete workspace" button is hidden but the backend endpoint accepts the request, the authorization boundary is in the wrong place. The UI can reduce mistakes; the server must enforce the decision.

Failure Modes

Failure: login check treated as permission. The handler checks only that a subject exists. Fix it by requiring action/resource checks at backend boundaries.

Failure: tenant id trusted from the URL alone. A request path includes /workspaces/zephyr, but the handler never verifies the subject belongs to that workspace. Fix it by loading resource ownership and membership facts before returning data.

Failure: stale permission facts hidden by caching. A user is removed from a workspace, but cached authorization facts still allow access. Fix it by defining freshness requirements, cache TTLs, invalidation, and high-risk actions that must re-check authoritative state.

Failure: audit logs record only success. Denied requests are often the evidence of probing, broken integrations, or confusing UX. Record both allows and denies for sensitive decisions, with enough policy context to investigate.

Failure: service identity confused with user identity. A backend service may call another service "as itself" or "on behalf of Maria." Those are different actors. Preserve both when needed:

actor = service:export-worker
on_behalf_of = user:maria
action = document.export

Without that distinction, a service account may accidentally get broad power that no human request should have.

Readiness Check

Close the lesson and reconstruct the Maria incident from memory:

What credential entered the system?
Which subject did authentication establish?
What action and resource were requested?
Which facts were needed for authorization?
Where was the decision enforced?
What response should the client see?
What audit evidence should exist afterward?

Then apply the same questions to one endpoint you know: "invite user," "download invoice," "rotate API key," or "delete project." If the answer is "we check if the user is logged in," the endpoint probably has an authorization boundary hidden inside it.

Key Takeaways

  • Authentication establishes a subject; authorization decides whether that subject may perform one action on one resource.
  • Principal, credential, session, actor, resource, policy, enforcement, and audit evidence are separate concepts even when one code path touches all of them.
  • A correct authorization check needs action, resource, subject, and context; "is logged in" is not enough.
  • Good identity systems preserve decision evidence so access bugs and abuse reports can be investigated without guessing.
