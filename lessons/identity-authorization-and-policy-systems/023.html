Operating Identity Incidents and Key Rotation

By the end of this lesson, you will be able to:

  • trace a suspected signing-key exposure from detection through rotation, revocation, and validation;

  • separate containment actions for keys, tokens, sessions, service accounts, and customer integrations;

  • identify the evidence needed to judge blast radius and communicate accurately.

Idea in one sentence: Identity incidents are controlled by changing which credentials are trusted, proving which credentials may have been used, and balancing fast containment against avoidable user and customer disruption.

Core Insight

At 02:13, an engineer finds a private signing key in a build log. The key signs access tokens for your SaaS API. It may have been visible for twelve minutes before log retention rules removed the artifact, but you cannot yet prove whether anyone read it. The immediate temptation is to delete the key and force every user to log in again. That may be right, but it is not a complete incident response.

An identity incident is a trust-state problem. Some credential, key, token, session, assertion, or integration secret may no longer mean what the system thought it meant. The operational question is: "Which trust decisions could this credential influence, how quickly can we stop trusting it, and what evidence tells us whether it was used?"

Key rotation is the visible move, but the incident is larger than one key. A signing key may affect access tokens, refresh tokens, service-to-service credentials, mobile clients, webhook signatures, SAML integrations, cached JWKS documents, customer SDKs, and audit evidence. Rotating without understanding those dependents can either leave a gap open or break legitimate traffic unnecessarily.

The trade-off is fast containment versus user disruption. Slow containment extends risk if the key was used. Overbroad containment can log out every customer, break integrations, cause retry storms, and obscure the evidence needed to investigate. A mature system makes the safe path visible: add new trust, move issuance, retire old trust, revoke affected credentials, monitor for old use, and communicate the measured blast radius.

What Trust State Must Change?

Start by naming the credential and what it can do. In the build-log scenario:

exposed material:
  private key kid=api-signing-2026-04

used for:
  signing access tokens for api.invoices.example

accepted by:
  API gateways through JWKS cache
  background workers that validate bearer tokens
  customer-hosted integrations using cached public keys

possible impact:
  forged access tokens until old kid is no longer accepted
  replayed existing tokens until expiry or revocation
  uncertainty about who used the key during exposure window

The key identifier, often kid, matters because it lets verifiers choose a public key and lets operators see which key signed a token. The trust store matters because deleting a key from the issuer does not instantly delete it from every gateway, cache, SDK, or service. The token lifetime matters because tokens signed before rotation may remain valid until expiry unless the system can revoke by token id, user, session, tenant, or key id.

Not every incident has the same containment scope. A leaked webhook signing secret may require rotating one customer integration and replay-protecting recent deliveries. A leaked SAML private key may require metadata updates with enterprise customers. A leaked refresh-token database may require invalidating sessions, not merely rotating a signing key. The first operational task is to match the action to the credential's authority.

Worked Path: Rotating a Suspect Signing Key

Trace the API signing-key incident as an operational path.

1. Detect:
   build log contains private key kid=api-signing-2026-04.

2. Freeze and preserve evidence:
   restrict log access, snapshot relevant logs, record exposure window.

3. Add replacement trust:
   generate kid=api-signing-2026-05 in key management system.
   publish public key to JWKS without removing old key yet.

4. Move issuance:
   token issuer starts signing new tokens with api-signing-2026-05.

5. Wait for verifiers to learn new key:
   observe JWKS cache refresh and validation success across gateways/workers.

6. Contain old trust:
   stop accepting api-signing-2026-04 or mark tokens signed by old kid as requiring revocation/fresh auth.

7. Revoke or shorten affected credentials:
   invalidate high-risk sessions, refresh tokens, service tokens, or tenants inside the exposure window.

8. Monitor:
   alert on tokens signed by old kid, unknown kid, replay patterns, and validation failures.

9. Communicate:
   report what changed, who is affected, customer action required, and residual risk.

The order matters. If verifiers remove the old key before they can fetch the new one, legitimate traffic breaks. If the issuer starts signing with the new key before verifiers know it, every new token fails. If the old key remains trusted too long, a forged token remains possible. Rotation is a distributed state change, not a button.

Pause and predict: Why not delete the old public key from JWKS immediately after generating the new key?

Check: Immediate deletion may break verifiers that have not learned the new key and may also fail to revoke already issued tokens if other caches still trust the old key. Safe rotation coordinates issuance, verifier cache state, old-key retirement, and monitoring.

Revocation Is Different From Rotation

Rotation changes which keys will be used and trusted. Revocation changes whether specific credentials, sessions, or grants are still valid. You often need both.

If an attacker has the old signing key, rotating future issuance is not enough while any verifier still accepts the old kid. If an attacker stole already issued refresh tokens, rotating the signing key may do nothing because refresh tokens may be opaque database records. If an attacker stole a user's session cookie, rotating the API signing key may not end that browser session.

Containment tools operate at different scopes:

  • Key retirement: stop accepting tokens or signatures under a key id.
  • Token revocation: reject token ids, refresh token families, or grants.
  • Session invalidation: force reauthentication for users, tenants, or risk cohorts.
  • Service credential rotation: replace API keys, client secrets, mTLS certificates, or workload identities.
  • Policy restriction: temporarily require fresh checks, step-up authentication, or deny high-risk actions.
  • Customer integration rotation: coordinate SAML certs, webhook secrets, SCIM bearer tokens, or OAuth clients.

Choose the narrowest scope that safely contains the plausible impact. A leaked low-privilege integration secret for one tenant should not automatically force every user in every tenant to reauthenticate. A leaked global signing key may justify broad revocation because the forged-token blast radius is wide. The decision should be based on authority, exposure window, evidence, and available controls.

Blast Radius and Evidence

Incident response depends on proving what could have happened and what did happen. You need evidence before, during, and after containment.

Useful evidence includes:

key evidence:
  kid, creation time, activation time, retirement time, owners, storage path

exposure evidence:
  where secret appeared, who could access it, time window, download/read logs

token evidence:
  tokens by kid, issuer, audience, tenant, subject, session, jti, issued-at

verifier evidence:
  which gateways accepted old kid after retirement, JWKS cache age, failures

behavior evidence:
  unusual token issuance, impossible travel, unknown clients, replay, denied attempts

The previous lesson on testing applies here: operational response should have rehearsed checks. A rotation runbook should have tests or dashboards that prove new tokens validate, old tokens fail when expected, caches converge, revocation lists are read, and customers with integrations can recover. Without those checks, operators may confuse "we ran the command" with "the trust state changed everywhere."

Communication also depends on evidence. Customers need to know whether they must rotate their secrets, reauthenticate users, update metadata, or monitor logs. Internal teams need to know whether the incident was contained, whether residual old-key traffic exists, and whether high-risk actions were blocked during uncertainty.

Pause and predict: A gateway still accepts tokens signed by the retired kid thirty minutes after key retirement. Is that a logging issue or a containment issue?

Check: Treat it as containment until proven otherwise. It may be a stale JWKS cache, a verifier not wired to the new trust store, or a service bypassing central validation. The evidence tells you where trust state failed to converge.

Runbooks and Customer Impact

An identity runbook should be specific enough that operators do not invent the trust model during the incident. A useful runbook names the credential type, authority, owners, dashboards, commands, customer-facing effects, and rollback constraints. "Rotate key" is not a runbook. "Create new signing key, publish JWKS, switch issuer, verify gateways have fetched new kid, disable old kid, invalidate refresh families issued after exposure, and alert on old-key validation" is much closer.

Runbooks should also say what not to do. Do not delete evidence while trying to remove the secret. Do not paste a private key into a chat channel to ask whether it is real. Do not disable every customer integration before checking whether the exposed credential can affect those integrations. Do not announce "no customer impact" merely because no exploit is obvious yet; say what evidence has been checked and what uncertainty remains.

Customer communication should be action-oriented. If customers need no action, explain why: the exposed key was only used for first-party API tokens, was retired at a named time, old-key attempts are blocked, and customer-managed secrets are not affected. If customers need action, give a narrow task: rotate webhook secret, upload new SAML metadata, restart an integration, or reauthorize an OAuth client. Good communication avoids both panic and vagueness.

Finally, rehearse identity incidents. A tabletop that walks through a leaked signing key, stolen refresh-token database, compromised service account, and SAML certificate rollover will reveal missing inventory before a real incident does. The rehearsal should end with concrete improvements: shorter token lifetimes, better kid telemetry, revocation by tenant, verifier cache dashboards, or clearer customer templates.

Design Check

Use this review before an incident, not only during one.

Inventory:
  Which keys, tokens, sessions, service accounts, and customer secrets exist?
  Which systems trust each one, and how long do caches keep trust state?

Rotation:
  Can you add a new key before removing the old one?
  Can issuance move separately from verifier trust?
  Can you observe which kid signs and validates live traffic?

Revocation:
  Can you revoke by user, tenant, session, token id, refresh family, key id, or client?
  Which high-risk actions require fresh auth during uncertainty?

Evidence:
  Can you reconstruct exposure window, token use, verifier behavior, and customer impact?

Communication:
  Which customers or teams need action, and what exact action can they take?

Apply it to the build-log incident. A strong system has key ownership, non-exportable key storage where possible, short token lifetimes, JWKS cache visibility, key-id telemetry, revocation levers, rehearsed rotation, and customer-facing status language. A weak system has one long-lived global signing key, no kid telemetry, no revocation list, unknown verifier caches, and no way to distinguish forged old-key traffic from normal traffic.

Close the lesson and reconstruct the incident path from memory: detect, preserve evidence, add replacement trust, move issuance, verify cache convergence, retire old trust, revoke affected credentials, monitor old use, communicate blast radius. If one step depends on "we would figure it out during the incident," that step needs design work before the incident.

Connections

Permission matrices created executable evidence before a change ships. Incident operations need the same discipline during a crisis: checks that prove trust state moved, credentials were revoked, and old authority is no longer accepted.

The final capstone asks you to combine identity, authorization, policy, audit, tests, and operations into one platform design. Key rotation and incident response are where the platform proves whether its boundaries are actually operable.

Key Takeaways

  • Key rotation changes trust state; incident response also needs revocation, monitoring, blast-radius evidence, and customer communication.
  • Safe rotation is ordered: add new trust, move issuance, confirm verifier convergence, retire old trust, then watch for old use.
  • Match containment scope to credential authority and evidence; too narrow leaves risk open, too broad creates avoidable disruption.
  • Operable identity systems expose key ids, token use, cache state, revocation levers, and audit evidence before an incident happens.
