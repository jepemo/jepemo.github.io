API Keys, Service Accounts, and Machine Identity

The core idea: machine credentials should identify an owned workload or integration with limited authority; API keys are simple handles, while service accounts and client credentials make ownership, scope, rotation, and auditability explicit.

Core Insight

Elena's finance platform now has user login, OAuth delegation, OIDC sign-in, and token lifetime rules. But not every caller is a human sitting in a browser. A nightly billing exporter sends invoice summaries to a warehouse. A partner integration imports statement totals. A CI job deploys reports. A scheduled worker rebuilds search indexes. These callers need credentials too.

The dangerous shortcut is to treat machine access like a user session with no user. A developer creates one API key, names it prod-integration, stores it in three jobs, gives it broad write access, and forgets it. Six months later, the partner integration is retired. The key remains active. At 02:00, an old container image still has the key and writes stale production data.

This is the machine identity problem. The system must answer: which machine or integration is calling, who owns it, what may it do, where is the secret stored, when does it rotate, and how do we shut it off without breaking unrelated workloads?

The trade-off is automation simplicity versus long-lived secret risk. API keys are easy to issue and easy to paste into an environment variable. That simplicity is why they spread. It is also why they become hard to inventory, rotate, scope, and audit. Service accounts, OAuth client credentials, workload identity, and short-lived tokens add machinery, but they make the caller's authority easier to reason about.

Do Not Pretend Machines Are Users

A user identity has human lifecycle signals: login, MFA, recovery, employee offboarding, device review, consent, and user-visible sessions. A machine identity has different signals:

workload owner
deployment environment
runtime location
secret storage path
allowed API scopes
rotation schedule
last used timestamp
incident contact
decommission date

If a batch job calls the reports API, the audit log should not say only user:elena unless Elena is actually the actor. A better event separates the machine caller from the business reason:

caller = service_account:billing-exporter-prod
owner = team:finance-platform
action = reports.summary.write
resource = warehouse:finance/monthly-summary
requested_for = scheduled_export
decision = allow

This separation protects both security and operations. If a job misbehaves, the team can find the owner. If Elena leaves the company, the job does not silently die because it depended on her personal token. If the job is retired, the service account can be disabled without touching unrelated users.

Machine identity should have a name that tells the truth. admin-key is not enough. billing-exporter-prod is better. partner-acme-statement-import-readonly is better still when the credential is for an external integration.

API Keys Are Handles, Not Policy

An API key is often a long random string:

sk_live_7f9a3e...

The caller sends it with a request:

POST /imports/statements HTTP/1.1
Host: api.finance.example.test
Authorization: Bearer sk_live_7f9a3e...

The server looks up the key:

key hash -> key record -> owner, scopes, environment, status, expiry

The string itself should not be treated as the policy. It should be a handle to a server-side record. That record can say:

name = partner-acme-statement-import-readonly
owner = team:partnerships
environment = production
scopes = statements:read, imports:create
tenant = tenant:acme
created_by = user:marina
created_at = 2026-06-01
expires_at = 2026-09-01
last_used_at = 2026-06-18
status = active

Store a hash of the key, not the raw value, when the server only needs to verify presented secrets. Show the raw key only once at creation. Redact it in logs, traces, analytics, error reports, and support tools.

The key record is where lifecycle lives. You can disable one key, create a replacement, check which team owns it, alert when it has not been used, and limit it to a tenant or API scope. Without that record, a key is just a powerful password with no context.

Service Accounts Give the Caller a Durable Identity

A service account is an identity for software rather than a person. It can own credentials, roles, scopes, and audit events. The credential might be an API key, an OAuth client credential, a signed JWT assertion, a cloud IAM token, or a short-lived workload token. The important point is that the identity is not a human account reused for automation.

For the billing exporter, a service account design could look like this:

service account: billing-exporter-prod
owner: team:finance-platform
environment: prod
allowed actions:
  - reports.summary.read
  - warehouse.monthly-summary.write
not allowed:
  - users.manage
  - payroll.export
  - tenant.admin
credential type: short-lived token from workload identity
break-glass contact: oncall-finance-platform

Now a request carries a machine identity:

caller = service_account:billing-exporter-prod
token audience = warehouse-api
scope = warehouse.monthly-summary.write
expiry = 15 minutes

The warehouse API can authorize that service account just like it would authorize a user, but with a machine lifecycle. The audit log can show which job wrote which rows. Rotation and revocation can be handled without asking a human user to log in.

OAuth client credentials are one common pattern for machine-to-machine access:

POST /token
grant_type=client_credentials&
client_id=billing-exporter-prod&
client_secret=...

The authorization server authenticates the client and returns an access token for the service. This works best when the client secret is stored in a backend secret manager or runtime identity system, not copied into many scripts.

Worked Design Pass: Retiring an Integration

Trace the abandoned key scenario with a better design.

Initial setup:

integration = acme statement importer
service account = partner-acme-statement-import
owner = team:partnerships
scope = statements:read, imports:create
tenant = tenant:acme
credential = key k_2026_06
expires = 90 days
last_used_at = updated on every accepted request

A request arrives:

1. API receives Authorization header.
2. API hashes presented key.
3. API finds key record k_2026_06.
4. API checks status: active.
5. API checks expiry: not expired.
6. API checks tenant binding: tenant:acme.
7. API checks scope: imports:create.
8. API records last_used_at and decision evidence.
9. API allows the import.

Now the partner integration is retired. The owner disables the service account or credential:

status = disabled
disabled_reason = partner_contract_ended
disabled_by = user:marina
disabled_at = 2026-08-10

At 02:00, an old container image tries to use the old key:

key hash found: yes
status: disabled
decision: deny
reason: credential_disabled
owner: team:partnerships
alert: old integration still running

This denial is useful. It does not just block the request; it tells operators which retired integration is still alive. The system can page the owning team, not the whole company.

If the key had no owner, no expiry, no last-used timestamp, and broad write access, the same old container could keep writing until someone noticed bad data. The credential record turns a string into an operable identity boundary.

Rotation Without Breaking Production

Machine credentials need rotation, but rotation is not just generating a new secret. A safe rotation path usually has overlap:

1. Create new credential k_2026_09 for the same service account.
2. Deploy the new credential to the workload.
3. Observe traffic using the new credential.
4. Disable the old credential k_2026_06.
5. Remove old secret material from stores and deployment configs.
6. Alert if the old credential is used after disablement.

This dual-key window is a deliberate trade-off. It reduces deployment risk by allowing old and new credentials briefly. It also means both credentials are valid during the window, so the window should be short and monitored.

Short-lived workload identity can reduce the need for long-lived static secrets. Instead of storing an API key forever, a workload can prove where it is running and receive a short-lived token. Cloud IAM roles, Kubernetes service account tokens, SPIFFE identities, and service mesh certificates all move in this direction. The next lesson goes deeper on mTLS and workload identity. Here, the key point is simple: prefer credentials that can expire, be scoped, and be traced to a workload owner.

You do not need the most advanced mechanism for every caller. A low-risk partner sandbox may use an API key with a tight scope and expiry. A production backend service may use OAuth client credentials because it can store a secret in a server-side secret manager. A Kubernetes workload may use runtime identity and avoid static secrets entirely. The design pressure is to choose the weakest credential that is still operable and bounded.

One useful ladder is:

manual script -> short-lived generated token if possible
external partner -> scoped API key or OAuth client credential
backend service -> client credentials or cloud role
cluster workload -> service account token, workload identity, or mTLS identity
high-risk service -> short-lived runtime credential plus policy checks

The ladder is not a maturity badge. It is a way to avoid two mistakes: putting permanent production secrets everywhere, and deploying complex identity infrastructure where a scoped expiring key would be enough. Make the risk visible, then spend complexity where it reduces real ambiguity.

Inventory Is Part of the Control

Machine credentials fail quietly when nobody knows they exist. A user account tends to have a visible owner because a person complains when it breaks. A service account may keep running for years with no active maintainer. That makes inventory a security control, not just an admin report.

A useful inventory entry should answer operational questions without reverse-engineering a deployment:

identity: service_account:partner-acme-statement-import
type: api_key
owner: team:partnerships
runtime: Kubernetes namespace partner-imports-prod
environment: production
allowed scopes: statements:read, imports:create
secret location: secrets/partner/acme/import-key
created by: user:marina
last used: 2026-06-18T02:14:00Z
rotation due: 2026-09-01
break-glass action: disable credential k_2026_06

Now review can be mechanical. If a key has not been used in 45 days, ask whether the integration still exists. If a credential has no owner, disable it or force ownership before renewal. If a production credential is stored in a developer laptop path, move it. If one service account has scopes for billing, user management, and warehouse writes, split it into smaller identities.

This review also protects incident response. During a suspected leak, the team should be able to answer three questions quickly:

What can this credential do?
Where is it deployed?
What breaks if we disable it?

If those answers are unknown, the credential is effectively broader than its stated scopes because fear of breakage will slow revocation.

Failure Modes

Failure: one shared key for many jobs. Shared keys make audit logs vague and rotation risky. Give important workloads separate identities so one job can be disabled without breaking everything.

Failure: personal tokens used for automation. A person's token ties a machine to a human lifecycle. Offboarding, password reset, or MFA changes can break jobs, and audit logs blame the wrong actor.

Failure: no owner metadata. A credential without an owner becomes nobody's responsibility. Require owner, purpose, environment, created-by, expiry, and last-used data.

Failure: broad scopes because "it is internal." Internal automation can still corrupt production data. Scope machine credentials to the smallest action and resource boundary that works.

Failure: secrets in logs and build artifacts. API keys copied into CI logs, container layers, support bundles, or analytics events become credentials. Redaction and secret scanning should be part of the lifecycle.

Readiness Check

Close the lesson and inspect one machine credential:

What workload or integration owns it?
Who is the human/team owner?
What actions can it perform?
Which environment is it for?
Where is the secret stored?
When does it expire?
How is it rotated?
What happens if it is unused for 30 days?
What audit event appears when it is denied?
Can it be disabled without breaking unrelated systems?

If the answer to ownership is "someone created it a while ago," treat that as a production risk, not a documentation gap.

Key Takeaways

  • Machine identities should name workloads or integrations, not pretend to be human users.
  • API keys should be handles to server-side records with owner, scope, expiry, status, and audit metadata.
  • Service accounts make machine access operable: you can scope, rotate, revoke, and investigate them without tying jobs to personal accounts.
  • Long-lived secrets are sometimes pragmatic, but they need inventory, rotation, redaction, owner accountability, and a path toward shorter-lived runtime identity.
