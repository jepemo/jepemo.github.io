OpenID Connect, ID Tokens, and Claims

The core idea: OpenID Connect layers authentication evidence on top of OAuth 2.0; an ID token tells a client who authenticated and under what issuer, while access tokens remain for resource servers.

Core Insight

PlanBoard now has a clean OAuth authorization code flow with PKCE. Elena can connect the finance product and allow PlanBoard to read statement summaries. That solves delegated API access, but PlanBoard also wants a sign-in button: "Continue with Finance." After sign-in, PlanBoard wants to create a local account, show Elena's name, and know whether it has seen this finance user before.

It is tempting to reuse whatever token appears in the OAuth flow. If PlanBoard has an access token for reports.read, why not decode it and treat the sub or email inside as Elena's login identity? That temptation is the boundary mistake OpenID Connect was designed to avoid.

OAuth 2.0 says how a client obtains delegated access to a resource. It does not, by itself, define a standard authentication result for the client. OpenID Connect, or OIDC, adds that authentication layer. It defines an ID token: a signed token intended for the client, issued by an OpenID Provider, containing claims about the authentication event and the authenticated subject.

The trade-off is federated identity convenience versus claim interpretation risk. OIDC makes sign-in across systems practical: PlanBoard does not store Elena's finance password, and the finance identity provider can handle login, MFA, recovery, and enterprise policy. But PlanBoard must interpret claims carefully. A signed claim is not automatically an application account, a current authorization decision, or a forever-stable email address.

The useful question is: "Which token is evidence for which audience?" ID tokens are for the client to establish an authenticated session. Access tokens are for resource servers to authorize API calls. Mixing those purposes creates subtle security bugs.

The Actors Change Names, Not the Boundary

OIDC builds on OAuth terms but introduces identity-focused names:

end-user              Elena
relying party         PlanBoard, the client relying on identity evidence
OpenID Provider       finance identity provider
ID token              authentication result for PlanBoard
UserInfo endpoint     optional profile-claims endpoint

The relying party is the application that relies on the OpenID Provider's authentication. It is still an OAuth client, but the phrase reminds you what it is relying on: identity evidence, not just delegated API access.

The OpenID Provider authenticates Elena and issues ID tokens. It may also publish discovery metadata and signing keys so clients can validate tokens without hard-coding every endpoint and key.

The ID token is usually a JWT. It is not meant to be sent to arbitrary APIs. It is meant for the relying party named in the token's aud claim. If PlanBoard receives an ID token with aud=planboard, the finance reports API should not accept it as an access token.

That audience boundary is the lesson from the earlier token chapter applied to identity. A token can be signed and still be wrong for the receiver.

What an ID Token Contains

After Elena completes an OIDC authorization code flow, PlanBoard may receive an ID token like this:

{
  "iss": "https://auth.finance.example.test",
  "sub": "00u7a1elena",
  "aud": "planboard",
  "exp": 1781351400,
  "iat": 1781350800,
  "nonce": "n-0S6_WzA2Mj",
  "auth_time": 1781350750,
  "acr": "urn:finance:loa:mfa",
  "amr": ["pwd", "otp"],
  "email": "elena@example.test",
  "email_verified": true,
  "name": "Elena Martinez"
}

Some claims are structural:

  • iss says which provider issued the token.
  • sub identifies the authenticated subject within that issuer.
  • aud names the client that may consume the token.
  • exp and iat bound the token in time.
  • nonce binds the token to an authentication request started by the client.

Some claims describe the authentication event:

  • auth_time says when the user authenticated.
  • acr can describe an authentication assurance class.
  • amr can describe methods used, such as password plus OTP.

Some claims are profile data:

  • email
  • email_verified
  • name
  • locale, picture, or other optional values

Do not treat these categories as the same. sub plus iss is the usual stable external identity key. Email is useful display or contact data, but it can change, be reassigned, or mean different things across providers. MFA-related claims can help decide whether to require step-up, but only if the relying party understands the provider's semantics.

OIDC Authorization Code Flow

OIDC often uses the same authorization code flow from the previous lessons, with a few identity-specific additions. PlanBoard starts an authorization request:

GET https://auth.finance.example.test/authorize?
  response_type=code&
  client_id=planboard&
  redirect_uri=https%3A%2F%2Fplanboard.example.test%2Foidc%2Fcallback&
  scope=openid%20profile%20email&
  state=st_91bd&
  nonce=n-0S6_WzA2Mj&
  code_challenge=Gr9n...&
  code_challenge_method=S256

The openid scope is the signal that this is an OpenID Connect request, not only an OAuth delegation request. The profile and email scopes ask for profile claims. The nonce is created by PlanBoard and later checked inside the ID token. It helps prevent replay or token injection across authentication attempts.

After Elena authenticates, the authorization server returns an authorization code to PlanBoard. PlanBoard checks state, then exchanges the code at the token endpoint. The response may contain both tokens:

{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "id_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 600
}

Now PlanBoard must validate the ID token before establishing a local session:

1. Discover or configure the expected issuer.
2. Fetch or cache the provider's signing keys.
3. Verify the ID token signature.
4. Check `iss` equals the expected provider.
5. Check `aud` includes PlanBoard's client id.
6. Check `exp`, `iat`, and acceptable clock skew.
7. Check `nonce` matches the authentication request.
8. Extract `sub` as the provider-scoped user identifier.
9. Map (`iss`, `sub`) to a local PlanBoard account.
10. Store only the claims PlanBoard actually needs.

This is the worked mechanism. The ID token is not "accepted because it decodes." It is accepted because a specific relying party validates that a specific issuer signed an authentication result intended for that relying party and bound to this transaction.

After validation, PlanBoard should create its own local session. That session is not the ID token itself. A common shape is:

valid ID token -> local account lookup -> PlanBoard session cookie -> app-specific authorization

This separation matters. The ID token proves an external authentication event. The local session controls PlanBoard's own browser or app experience. PlanBoard can expire that session, require reauthentication for sensitive settings, or map Elena to local roles without asking the OpenID Provider on every page view. If PlanBoard stores the raw ID token as the session, it couples local behavior to a federated artifact whose audience, lifetime, and claim set were designed for sign-in evidence, not for every application decision.

Claims Are Evidence, Not Application Truth

Suppose Elena's ID token contains:

{
  "sub": "00u7a1elena",
  "email": "elena@example.test",
  "email_verified": true
}

PlanBoard can use iss + sub to find Elena's linked account:

external_identity_key = (
  issuer: https://auth.finance.example.test,
  subject: 00u7a1elena
)

It can display elena@example.test if the claim is present. It may use email_verified=true to decide whether it needs extra email verification. But it should not make email the primary account key unless it has a deliberate account-linking model. Two providers may assert the same email. A user may change email. An organization may recycle an address. A provider may stop sending a claim unless the scope or policy changes.

Claims also have freshness limits. The ID token describes an authentication event and a snapshot of claims at issuance time. If Elena changes her name or email five minutes later, PlanBoard may not learn that from an old ID token. For current profile data, the client may call the UserInfo endpoint with an access token meant for that endpoint, or it may refresh claims at the next sign-in. The important part is to know whether a value is login evidence, profile display data, or current authorization state.

Authorization remains separate. If PlanBoard has a local admin role, it should not set that role merely because the ID token has email_verified=true or a familiar domain. Enterprise authorization may use groups or policy claims, but that is an explicit trust contract. Claim names alone are not policy.

Discovery and Key Rotation

OIDC includes discovery metadata so clients can learn provider endpoints and key locations. A provider may publish a document like:

https://auth.finance.example.test/.well-known/openid-configuration

That metadata points to the authorization endpoint, token endpoint, UserInfo endpoint, supported algorithms, and JWKS URI. The JWKS endpoint exposes public signing keys used to validate ID tokens.

Discovery reduces manual configuration, but it does not remove trust decisions. PlanBoard still needs to know which issuer it intended to trust. It should not accept an arbitrary issuer URL from an untrusted login request and then auto-discover keys from that URL. Discovery tells the client how to validate a provider it already decided to trust.

Key rotation also needs operational care. If the provider rotates signing keys, PlanBoard must refresh JWKS data without accepting unknown keys blindly. Useful signals include:

unknown kid count
signature verification failures
issuer mismatch failures
nonce mismatch failures
expired-token failures
JWKS fetch latency and errors

Those signals let operators distinguish a provider rotation problem from a replay attempt or bad client configuration.

Common Failure Modes

Failure: using an access token as login proof. An access token is meant for a resource server. It may not be a JWT, may not contain authentication claims, and may have an audience that is not the client. Use an ID token for client authentication evidence.

Failure: sending ID tokens to APIs. An ID token with aud=planboard should not authorize calls to the finance reports API. APIs should expect access tokens with the correct audience and scope.

Failure: skipping nonce validation. Without nonce, the client has weaker protection against replayed or injected ID tokens from another transaction. state protects the callback; nonce binds the ID token to the authentication request.

Failure: account linking by email alone. Email is not a universal stable identifier. Use issuer plus subject as the primary external identity key, then treat email as a claim with its own verification and lifecycle.

Failure: treating claims as permissions. email_verified, name, or amr are not local application roles. Convert claims into permissions only through an explicit policy and audit trail.

Readiness Check

Close the lesson and inspect one sign-in integration:

Which issuer does the client trust?
Which token is the ID token?
Which token is the access token?
Who is the audience of each token?
Does the client validate signature, issuer, audience, expiry, and nonce?
Which claim is used as the stable account key?
Which claims are display data?
Which claims affect authorization, and where is that policy documented?
What happens when signing keys rotate?

If the answer to identity mapping is "we use email," ask what happens when the email changes, when another provider asserts the same address, or when the organization recycles it.

Key Takeaways

  • OIDC adds standardized authentication evidence to OAuth; it does not turn every OAuth token into login proof.
  • ID tokens are for relying parties, while access tokens are for resource servers.
  • Validate issuer, audience, signature, expiry, and nonce before using an ID token to establish a local session.
  • Claims need interpretation: iss + sub is usually the stable identity key, while email, profile, and MFA claims have separate trust and freshness limits.
