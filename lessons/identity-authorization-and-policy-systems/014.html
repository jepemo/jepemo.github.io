Multi-Tenant Authorization Boundaries

By the end of this lesson, you will be able to:

  • trace tenant context from an authenticated request to a protected data query;

  • distinguish a user-selected tenant from a tenant authorization decision;

  • identify cache, background-job, and audit paths that can leak data across tenants.

Idea in one sentence: A tenant identifier is a security boundary only when every identity, authorization, data, cache, and background path proves it before using or returning a resource.

Core Insight

Maya works for a consulting firm that is a member of two Northstar customers: acme-eu and zephyr-uk. In Acme, she is a billing administrator. In Zephyr, she is a read-only project viewer. Her browser currently shows the Acme workspace, but an API request contains tenant=zephyr-uk in the URL. The request asks for invoice inv-884, an identifier the API treats as globally unique.

The service must not infer “Maya is an admin” and return the invoice. Her admin role is meaningful only inside Acme. It must establish the requested tenant, verify Maya's membership and role in that tenant, prove that the invoice belongs to that same tenant, and use that tenant boundary in the data query. If any one of those checks is omitted, a valid identity in one customer can become a cross-customer data path.

A tenant is the customer, organization, workspace, or other isolation unit whose data and administration must not be visible to another tenant without an explicit cross-tenant rule. In plain language, tenant context answers “on whose behalf is this request happening?” A user interface can let Maya select a workspace, but that selection is a request for context, not authority to use it.

The trade-off is shared-platform efficiency versus isolation risk. Shared compute, databases, queues, and services can be appropriate, but they require a repeated invariant: every resource access is constrained by an authorized tenant context. A token claim, route parameter, or database column alone does not create isolation.

The Tenant Invariant

Write the central rule before designing tables or claims:

For every protected operation:
  principal is authorized in tenant T
  resource belongs to tenant T
  query, mutation, cache entry, job, and audit event are scoped to T
  otherwise deny

The first line is a membership or relationship decision. It may use a token claim, a directory lookup, or a policy check, but the service must know whether the principal can act in T and which role applies there. The second line is resource ownership. invoice inv-884 is incomplete security input unless the service also knows its tenant_id or retrieves it only through an already tenant-scoped path.

The remaining line is where good authorization designs fail in production. A route can perform a correct policy check, then call an unscoped repository method. A cache can key by invoice:inv-884 instead of tenant:acme-eu:invoice:inv-884. A worker can process a queue event without tenant context. An audit log can omit tenant identity and make a leak impossible to investigate. The boundary must survive every hop.

Useful facts have clear owners:

identity and memberships: directory or authorization data
tenant-scoped role: tenant membership or policy store
resource tenant_id: resource-owning service or database
active tenant selection: request, then verified by the service
tenant isolation policy: versioned authorization policy

Pause and predict: Maya's access token says she belongs to Acme and Zephyr. Does that allow the API to return any invoice whose global ID appears in the URL?

Check: No. The token establishes an identity and possibly memberships. The API still needs the requested tenant, Maya's permission in that tenant, and proof that the invoice belongs to it. A global ID never replaces tenant-scoped authorization.

Worked Path: Reading an Invoice Safely

Suppose Maya requests GET /tenants/acme-eu/invoices/inv-884. The service uses an explicit tenant route because it makes the requested boundary visible, but it never trusts the route parameter by itself.

1. Gateway authenticates Maya and forwards her verified principal.
2. Invoice API parses tenant=acme-eu, action=invoices.read, invoice=inv-884.
3. Authorization check asks whether Maya has invoices.read in acme-eu.
4. Repository loads with both constraints:
   SELECT ... WHERE tenant_id = 'acme-eu' AND invoice_id = 'inv-884'
5. API verifies the result exists in the authorized tenant before serializing it.
6. Cache uses key tenant:acme-eu:invoice:inv-884.
7. Audit record stores principal, tenant, action, resource ID, policy version, and result.

If step 3 succeeds but step 4 uses WHERE invoice_id = 'inv-884', the policy check is not enough. A bug, stale client context, or guessed identifier can load another tenant's resource. If the query returns no Acme invoice, the API should normally return a tenant-safe not-found or denied result rather than reveal that Zephyr owns the identifier.

The same rule applies to writes. POST /tenants/acme-eu/invoices must create an invoice with server-derived tenant_id=acme-eu, not accept a body field that can name Zephyr. A mutation should validate that every referenced customer, project, attachment, and parent object belongs to the authorized tenant. Cross-tenant relationships are possible, but they must be modeled as an explicit delegated or shared access rule, not as an accidental foreign key match.

Pause and predict: The invoice API correctly scopes database queries, but its cache key is only invoice:inv-884. What can go wrong?

Check: A cached Acme response can be returned on a later Zephyr request with the same identifier or a reused application key. Authorization must constrain cached data as well as database reads; include tenant and any other access-relevant scope in the cache key and invalidate safely.

So far: the authorization decision establishes who may act in a tenant. The resource query establishes which tenant owns the data. Both are necessary, and the same tenant context must persist into caches, writes, and logs.

Boundaries Beyond the Request Handler

Multi-tenant leakage often happens outside the obvious HTTP handler. Background work needs a tenant-aware envelope:

job:
  tenant_id: acme-eu
  principal or service identity: scheduled-exporter
  action: invoices.export
  policy or authorization context version: 42
  resource selection: scoped to acme-eu

A worker must validate that context before loading data. It should not execute export all invoices where updated_at > yesterday and rely on the scheduler to have chosen the right customer. Batch queries, search indexes, analytics exports, notification recipients, file storage paths, and support tooling all need the same tenant boundary. In an incident, “it was an internal job” is not an authorization model.

Administration is also tenant-scoped. A platform operator may need a support path across tenants, but that is not ordinary tenant membership. Model it as a distinct principal and action, require an approved reason or ticket when appropriate, restrict the scope and duration, and audit it separately. Do not grant a support engineer an invisible tenant=* role merely because they may occasionally help customers.

The storage architecture affects the blast radius but does not remove application authorization. Separate databases or namespaces can reduce the damage from a query bug. A shared database with row-level tenant constraints can be efficient. A shared table with only an application filter is cheaper to begin with but requires especially strong repository discipline and tests. Isolation is a spectrum; choose it per component based on data sensitivity, customer requirements, operational cost, and recovery needs.

Failure Modes and Evidence

Confused tenant context. The UI's last selected workspace, a token's default tenant, and a route parameter disagree. Define one request tenant, authorize it explicitly, and reject ambiguous combinations instead of quietly picking one.

Unscoped lookup. A repository method accepts only an object ID, or an ORM relation loads child records without a tenant predicate. Make tenant-scoped access the default API shape so an unscoped query is conspicuous in review.

Cross-tenant cache or search result. Keys, index filters, pagination cursors, and result aggregations omit tenant context. Treat these as resource access paths; test that identical IDs and search terms cannot cross the boundary.

Trusted internal caller. A worker or service account has broad database access and bypasses authorization. Give service identities tenant-scoped permissions where possible, carry the tenant in the job contract, and log the acting identity.

Diagnostic leakage. An error, metric label, trace, or audit event reveals another tenant's name, record count, or resource existence. Evidence needs tenant context for investigation, but response messages must not disclose unauthorized facts.

Operational evidence should answer: which tenant did the request claim, which tenant was authorized, which tenant owned the resource, and which policy version decided the result? Monitor denied cross-tenant attempts, queries lacking tenant predicates, cache-key violations, worker jobs with missing tenant IDs, and mismatches between route tenant and resource tenant. Test with a principal in two tenants, identical resource IDs, stale tenant selection, and a malicious request body that names another tenant.

Give tenant administrators an effective-access view as well. For a selected principal and tenant, it should show the memberships, roles, delegated grants, policy version, and resource scopes that produce access in that tenant only. It must not merge Maya's Acme administrator role with her Zephyr viewer role into one reassuring but false account summary. This view makes access reviews and incident investigation practical: an operator can ask why Maya may export from Acme without accidentally learning what she may read in Zephyr.

When a tenant is deleted, suspended, or placed under legal restriction, treat that state as an authorization input across the platform. Disable new sessions or tenant selection as required, stop queued jobs, prevent new storage writes, and retain only the audit and recovery paths the product policy permits. Otherwise a “deleted” tenant can continue to receive background notifications or exports through paths the interactive API correctly closed.

Design Check

Start with this case. A support agent belongs to Acme and Zephyr but may export invoices only for Acme. A nightly job receives an Acme export request.

request tenant: acme-eu
principal: support-agent or scheduled-exporter
authorization: export permission scoped to acme-eu
query: tenant_id=acme-eu AND exportable=true
storage and cache: keys prefixed with acme-eu
job envelope and audit: include acme-eu and acting identity
failure default: deny if tenant, permission, or resource ownership is unknown

Now choose one tenant-scoped operation and write:

requested tenant and source:
principal's role or relationship in that tenant:
resource ownership check:
database, cache, search, and job scopes:
cross-tenant exception, if any:
audit evidence and safe client error:

Use this rubric: a tenant chosen by the client is always verified; every resource access has a tenant predicate or stronger isolation boundary; every asynchronous path carries tenant context; and any cross-tenant access is deliberate, narrowly scoped, and auditable.

Key Takeaways

  • Tenant selection is requested context, not proof of authority; authorize the principal in the selected tenant and prove resource ownership in the same tenant.
  • Tenant isolation must survive queries, mutations, caches, search, jobs, support tools, storage, and audit trails—not only the first API check.
  • Shared infrastructure can be safe when the tenant invariant is enforced repeatedly and tested with adversarial cross-tenant cases.
  • Cross-tenant administration and sharing are explicit exceptions that require a distinct action, narrow scope, and stronger evidence.
