Sessions, Cookies, and CSRF Boundaries

The core idea: a browser session is convenient because the browser carries authority automatically; CSRF defenses exist because that same convenience can let another site cause a logged-in action without stealing the session cookie.

Core Insight

Imagine Elena is signed in to finance.example.test, the same product from the previous lesson. She opens a malicious page in another tab. The page cannot read her finance dashboard because the browser's same-origin policy blocks cross-site reads. But the page can still submit a form:

<form action="https://finance.example.test/settings/email" method="POST">
  <input name="email" value="attacker@example.test">
</form>

If Elena's browser automatically attaches her session cookie to that request, the finance service may see a valid logged-in session. If the endpoint changes the account email without another proof, the attacker has caused a state-changing action without knowing Elena's password, MFA code, or cookie value.

This is the browser-session trade-off. Cookies make normal product use smooth: sign in once, navigate pages, submit forms, refresh the browser, and the server can recognize the session. But the browser attaches cookies according to cookie rules, not according to the user's visible intent. That automatic attachment is often called ambient authority: authority present in the environment rather than explicitly supplied by the script that caused the request.

Cross-Site Request Forgery, or CSRF, exploits that boundary. The attacker usually cannot read the response. CSRF is about causing the browser to send an authenticated request that changes state. The defense is not one magic header. It is a layered design: safe method semantics, cookie attributes, per-session CSRF tokens, origin checks, session rotation, expiration, and audit evidence for rejected attempts.

What a Session Actually Does

After a successful authentication event, the application needs a way to recognize later requests. A common browser pattern is a server-side session:

login succeeds
  -> server creates session record
  -> server sends Set-Cookie with an unpredictable session id
  -> browser stores cookie
  -> browser attaches cookie on matching future requests
  -> server loads session record and establishes subject

The cookie does not need to contain all user data. Often it contains only a random session identifier:

Set-Cookie: __Host-session=sess_8f3c...;
  Path=/;
  Secure;
  HttpOnly;
  SameSite=Lax

The pieces matter:

  • Secure tells the browser to send the cookie only over HTTPS.
  • HttpOnly prevents JavaScript from reading the cookie directly.
  • SameSite limits when the cookie is sent on cross-site requests.
  • Path=/ scopes the cookie to the whole host.
  • __Host- plus no Domain attribute helps prevent weaker subdomain scoping mistakes.

The server still owns the session record. It can store subject id, login time, last activity, assurance level, MFA state, device metadata, and revocation state. That record should be treated as authentication state, not as permanent user truth. Authorization still needs action and resource checks from the first lesson.

The Browser Sends Cookies Without Asking Your App

The key mechanism is that cookie attachment is a browser decision. A JavaScript fetch, a form submission, an image tag, a link navigation, or a redirected request can all cause the browser to consider cookies for the destination site. The app handler receives the request after that decision.

For a normal same-site request, this is useful:

1. Elena visits https://finance.example.test/settings.
2. Browser sends __Host-session=sess_8f3c...
3. Server loads session: subject=user:elena.
4. Server renders the settings page.

For a cross-site state-changing request, the same automatic behavior becomes risky:

1. Elena visits https://evil.example.test.
2. Malicious page submits a form to https://finance.example.test/settings/email.
3. Browser may attach finance.example.test cookies depending on SameSite rules.
4. Finance server sees a request with Elena's session cookie.
5. Without CSRF defenses, server may perform the action.

Same-origin policy does not stop this by itself. Same-origin policy mostly controls whether one origin can read another origin's response or script-access its objects. CSRF succeeds even when the attacker cannot read the response. The damage is in the side effect.

This is why HTTP method semantics matter. GET should not perform state-changing actions. If GET /billing/cancel cancels an account, an attacker may trigger it with a link or image. State-changing operations should use methods such as POST, PUT, PATCH, or DELETE, and then require additional CSRF defenses when browser cookies carry authority.

A Worked CSRF Defense Path

Design the email-change flow for Elena:

POST /settings/email
body: email=new@example.test

The safe path starts before the POST. When the settings page is rendered, the server creates a CSRF token tied to the session or a server-side token store:

session_id = sess_8f3c
csrf_token = random unguessable value bound to sess_8f3c

The form includes the token:

<form action="/settings/email" method="POST">
  <input type="hidden" name="csrf_token" value="tok_51a...">
  <input name="email">
</form>

The browser later submits the legitimate form:

POST /settings/email HTTP/1.1
Host: finance.example.test
Cookie: __Host-session=sess_8f3c...
Origin: https://finance.example.test
Content-Type: application/x-www-form-urlencoded

email=new@example.test&csrf_token=tok_51a...

The server checks several things in order:

1. Load session from cookie.
2. Confirm session is valid and not expired.
3. Validate Origin or Referer for sensitive browser requests.
4. Validate csrf_token against the session.
5. Re-authenticate or step up if changing email is high risk.
6. Authorize user:elena to change this account setting.
7. Apply change.
8. Rotate or invalidate risky sessions if needed.
9. Audit the decision.

Now try the malicious form from another site. The attacker can submit fields, but cannot know the per-session token from the finance page. The browser sends:

POST /settings/email HTTP/1.1
Host: finance.example.test
Cookie: __Host-session=sess_8f3c...
Origin: https://evil.example.test

email=attacker@example.test

The server denies:

session valid: yes
origin allowed: no
csrf token valid: no
decision: deny
status: 403 Forbidden
audit reason: csrf_failed

The important point is not that any one check is perfect. SameSite, origin checks, and CSRF tokens cover different failure modes. Together they make "a request with a cookie" insufficient proof of user intent.

SameSite Is Helpful, Not the Whole Design

SameSite changes when the browser sends cookies in cross-site contexts. In simplified terms:

SameSite=Strict
  send cookie only in same-site contexts

SameSite=Lax
  send cookie on same-site requests and some top-level cross-site navigations

SameSite=None
  allow cross-site cookie sending, but requires Secure

Strict gives strong CSRF resistance but can break expected flows, such as opening a link from email and arriving already signed in. Lax is often a practical default for application sessions. None is needed for some embedded or cross-site use cases, but it increases CSRF exposure and requires careful defenses.

Do not treat SameSite as permission. It is a browser cookie-sending rule. Browser behavior, redirects, old clients, embedded flows, and product requirements can create edge cases. Sensitive state-changing requests should still be designed as if a cookie might arrive and must not be accepted as the only proof of intent.

CORS is also not a complete CSRF defense. CORS controls whether browser JavaScript can read cross-origin responses or send certain non-simple requests with permission. Traditional form posts can still happen without the attacker reading the response. If you rely on CORS alone, you may protect data reads while leaving state changes exposed.

CSRF Is Not XSS, but the Designs Interact

CSRF is often confused with cross-site scripting, or XSS. They are different failures. In CSRF, the attacker's site causes the browser to send a request with existing authority. The attacker may never see the cookie or response. In XSS, attacker-controlled script runs inside the trusted site. Once script runs in finance.example.test, it can usually read page content, call same-origin APIs, and submit actions as if it were part of the app.

HttpOnly cookies help with one part of XSS: injected JavaScript cannot read the session cookie value directly. That is useful, but it does not make XSS harmless. The script can still cause same-origin requests while the browser attaches the cookie. CSRF tokens embedded in the page may also be readable to same-origin injected script. That is why XSS prevention and CSRF prevention are complementary, not substitutes.

Some teams try to avoid CSRF by storing bearer tokens in browser JavaScript and sending them in Authorization headers instead of cookies. That changes the boundary. A cross-site form will not automatically attach that header, so traditional CSRF risk is lower. But if JavaScript can read the token, XSS token theft becomes more severe. There is no free storage location. Cookies reduce direct token exposure but need CSRF design. JavaScript-readable tokens reduce ambient cookie behavior but increase exposure to injected script.

For ordinary server-rendered web apps, secure HttpOnly session cookies plus CSRF defenses are a common, robust pattern. For browser APIs and SPAs, the right answer depends on the threat model, token lifetime, refresh design, backend-for-frontend options, and XSS posture. The next lesson will go deeper on token formats. Here, keep the boundary simple: know which component carries authority automatically and which attacker action each defense is meant to block.

Session Lifecycle Boundaries

Sessions need a lifecycle, just like account credentials. Important transitions include:

create session after login
rotate session id after login or privilege change
mark MFA or assurance level
expire after idle timeout
expire after absolute lifetime
revoke on logout
revoke after password reset or suspicious recovery
revoke one device or all devices

Session rotation prevents session fixation. In a fixation attack, an attacker tries to make a victim use a session id the attacker already knows. If the application keeps the same session id after login, the attacker may later use it. Rotating the session id after successful authentication breaks that path:

anonymous session = sess_old
login succeeds
server invalidates sess_old
server creates sess_new
browser receives Set-Cookie: __Host-session=sess_new

Logout should invalidate server-side session state, not merely delete a cookie in the browser. Deleting the cookie helps that browser forget the session id, but a copied session id would still work unless the server refuses it.

Expiration also has trade-offs. Short idle timeouts reduce risk from abandoned browsers but frustrate users. Long sessions improve usability but increase exposure if a device is stolen or a session id leaks. High-risk actions can use fresh authentication or step-up checks rather than forcing every page view through a short timeout.

Failure Modes

Failure: GET changes state. If clicking a link can delete, transfer, invite, or disable something, the system is exposed to accidental and malicious triggers. Keep GET safe and require CSRF defenses for unsafe methods.

Failure: session cookie accepted as user intent. A cookie proves the browser has session state; it does not prove the user intentionally submitted this action. Add CSRF tokens, origin checks, and step-up for sensitive transitions.

Failure: over-broad cookie scope. A cookie set for a parent domain may be sent to more hosts than intended. Prefer host-only cookies for session authority and use __Host- constraints where appropriate.

Failure: logout only clears the browser. If the server-side session remains valid, copied cookies or other devices may continue working. Server-side revocation is the authority.

Failure: CSRF logs are invisible. Denied CSRF attempts can reveal broken integrations, embedded-flow mistakes, or active probing. Record enough evidence: route, subject if known, origin, token result, SameSite posture, and decision.

Readiness Check

Close the lesson and trace one state-changing browser request:

Which cookie carries session authority?
When does the browser attach it?
What SameSite mode is used?
Is the method safe or unsafe?
What proves user intent beyond "cookie was present"?
Where is the CSRF token created and checked?
Is Origin or Referer checked for this route?
Does logout or password reset revoke the server-side session?
What audit record appears if the request is denied?

Now apply the same questions to "change email," "invite user," "delete project," or "rotate API key." If the answer is only "the user is logged in," the session boundary is carrying too much authority.

Key Takeaways

  • Browser cookies are convenient because the browser sends them automatically; CSRF exists because automatic authority can be triggered by another site.
  • Same-origin policy mainly blocks cross-site reads; it does not by itself prevent cross-site state-changing requests.
  • Robust browser-session design combines safe methods, scoped cookies, SameSite, CSRF tokens, origin checks, session rotation, expiration, and server-side revocation.
  • A session cookie establishes authentication state, but sensitive actions still need authorization, user-intent proof, and audit evidence.
