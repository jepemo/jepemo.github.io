Passwords, MFA, and Account Recovery

The core idea: account access is a lifecycle, not a login screen; the real security boundary includes enrollment, credential storage, MFA, passkeys, recovery, support workflows, and the evidence left when any of those paths changes control of an account.

Core Insight

Imagine Elena uses a project-management SaaS for company finance approvals. Her normal login requires a password and an authenticator app code. That looks strong on the happy path. Then she loses her phone, clicks "I cannot access my authenticator," answers two support questions, receives a reset link by email, disables MFA, and signs in. An attacker who has Elena's email inbox or enough personal information may prefer that recovery path over the normal login path.

The non-obvious lesson is that the strongest login factor does not protect the account if a weaker recovery path can replace it. Password hashing, MFA, passkeys, reset links, backup codes, device changes, and support overrides are all part of the same account-control system. A product cannot evaluate them one by one and call the account secure. It must ask which path can transfer control to a new caller.

This does not mean every account needs the most painful possible controls. People forget passwords, lose phones, change devices, leave companies, and need help. A system that prevents all recovery will lock out real users and create manual backdoors. The design pressure is usability versus takeover resistance: make recovery possible, but do not let recovery become the easiest attack.

The practical mental model is a state machine. An account moves between states such as enrolled, authenticated, challenged, recovered, locked, and credential-rotated. Each transition needs evidence, rate limits, notifications, and audit records. If the system treats login, MFA setup, password reset, and support override as separate features, attackers will look for the transition with the weakest proof.

What Must Be Protected

The first piece is the account itself: a principal such as user:elena. The account can have several authenticators attached to it:

password verifier
passkey / WebAuthn credential
TOTP authenticator app
hardware security key
backup recovery codes
verified email address
verified phone number
enterprise SSO binding
support recovery workflow

These are not equal. A password is a shared secret the user knows and the system verifies indirectly. A passkey or hardware security key uses public-key cryptography and is resistant to phishing when the browser and relying party origin are part of the ceremony. A one-time code from an authenticator app proves possession of a seed-derived factor, but the user can still be tricked into typing the code into a fake site. An email reset link proves access to an email inbox, which may itself be compromised.

The account system also needs to protect sensitive transitions:

sign in
enroll MFA
remove MFA
add passkey
change password
reset password
rotate recovery codes
change email
change phone
start account recovery
approve support override

The dangerous transitions are often the ones that change future proof. Removing MFA, changing email, adding a new passkey, or rotating recovery codes can be more sensitive than reading normal account data because they change who can control the account later.

That is why "MFA enabled" is not enough as a security claim. You also need to ask:

Can a password reset disable MFA?
Can support remove a factor without strong evidence?
Can a stolen email inbox add a new authenticator?
Can a new device immediately perform high-risk actions?
Can recovery happen without notifying existing trusted channels?

Passwords Are Verifiers, Not Plain Secrets

A service should not store user passwords in a recoverable form. Instead, it stores a password verifier: a slow, salted hash produced by a password hashing function such as Argon2id, bcrypt, scrypt, or PBKDF2. The salt prevents two equal passwords from producing the same stored value across accounts. The work factor makes large-scale guessing more expensive after a database leak.

The path looks like this:

user enters password
  -> server applies password hashing function with per-account salt
  -> server compares result to stored verifier
  -> if it matches, password proof succeeds

The important boundary is that a database leak should not immediately reveal raw passwords. It may still enable offline guessing. That is why password systems also need breached-password checks, sensible rate limits, monitoring, and user notifications. Hashing is necessary, but it does not make weak reused passwords safe.

Password policy should help users choose and keep strong secrets without creating predictable workarounds. Overly complex composition rules often produce patterns like Summer2026!. Length, blocklists for known-compromised passwords, password managers, and passkeys usually do more useful work than forcing arbitrary symbol rules.

A login failure should also avoid becoming an account oracle. If the system says "email exists but password wrong" for one input and "no account" for another, attackers can enumerate users. The user experience still needs to be understandable, but the public response should not reveal more than needed.

MFA Changes the Proof, Not the Person

Multi-factor authentication asks for more than one kind of proof. Common categories are:

something you know: password
something you have: security key, authenticator app, trusted device
something you are: platform biometric used to unlock a local authenticator

The factor is not magic by category. SMS codes prove access to a phone number, but phone numbers can be ported or intercepted. TOTP codes are better in many systems, but still phishable. Push approvals are convenient, but users can be trained to approve unexpected prompts. Hardware security keys and passkeys can resist phishing because the authenticator signs a challenge scoped to the legitimate origin.

The design question is not "do we have MFA?" It is:

Which actions require which assurance?
Can the factor be phished?
Can it be reset by a weaker channel?
Can the user recover if it is lost?
What evidence do we keep when it is changed?

For Elena's normal login, password plus TOTP may be enough for routine access. For exporting finance approvals, changing bank details, or removing MFA, the system may require step-up authentication: ask for a fresh stronger proof even if the user is already signed in. That connects this lesson back to the previous one. Authentication establishes a subject, but different actions can require different assurance.

Passkeys and WebAuthn Shift the Failure Mode

Passkeys are worth treating as a different shape, not just another MFA checkbox. In a WebAuthn-style flow, the service stores a public key for the account. The user's authenticator holds the private key. During sign-in, the service sends a challenge. The authenticator signs it for the correct relying party. The service verifies the signature with the stored public key.

The simplified path is:

registration:
  account -> authenticator creates key pair -> service stores public key

sign-in:
  service sends challenge
  authenticator checks origin / relying party
  user unlocks authenticator locally
  authenticator signs challenge
  service verifies signature

This improves several things. The server does not store a password verifier for that proof. A fake site cannot usually reuse the signature because the authenticator binds the ceremony to the expected origin. The user does not type a reusable secret into a page.

The trade-off moves elsewhere. Users need device sync, backup, or multiple authenticators. Enterprise environments may need recovery policies and hardware-key enrollment ceremonies. A passkey rollout that ignores recovery can push people back to weaker support overrides. Strong sign-in and weak recovery still produce weak account control.

Worked Path: A Safe Recovery Flow

Now design Elena's lost-phone recovery path. A weak flow might be:

1. User clicks "lost authenticator."
2. User enters email.
3. Service emails reset link.
4. Link allows disabling MFA immediately.
5. User signs in with password only.

This flow turns email inbox access into full account control. It also gives little evidence if the recovery was malicious. A stronger flow separates proof, delay, notification, and high-risk transitions:

1. User starts recovery for user:elena.
2. Service records recovery_request_id = rec_91.
3. Service verifies a first channel, such as email link.
4. Service asks for a second available proof:
   - backup recovery code
   - existing passkey on another device
   - enterprise SSO re-authentication
   - hardware key
   - admin-approved enterprise recovery
5. Service rate-limits attempts and blocks known-abusive signals.
6. Service notifies existing trusted channels:
   "Recovery started. If this was not you, revoke it."
7. Service applies a waiting period or restricted mode for risky accounts.
8. Service rotates old recovery codes and records factor changes.
9. Service allows new factor enrollment.
10. Service records audit evidence for each transition.

The exact steps depend on risk. A consumer photo app and a payroll administrator should not have identical recovery flows. The durable mechanism is that recovery changes account control, so it should require evidence comparable to the power it grants.

After recovery, the account may enter a restricted state:

can read normal data: yes
can export all finance approvals: no, wait or step up
can change billing destination: no, require admin review
can rotate recovery codes: yes, after fresh strong proof

This avoids a binary choice between "lock the real user out forever" and "give a possibly compromised caller full control immediately."

Signals That Show the Boundary Is Working

Account access controls need operational signals, not just UI screens. Credential-stuffing attempts, repeated recovery starts, many failed MFA challenges, sudden factor removals, and support overrides should be visible as security events. The goal is not to page someone on every typo. The goal is to notice when the account-control state machine is being attacked.

Useful counters include:

password_failures_by_account
password_failures_by_source
mfa_challenge_failures
recovery_requests_started
recovery_requests_completed
factor_added
factor_removed
support_override_approved
sessions_revoked_after_recovery

These signals also shape product behavior. A single failed login may just be a mistake. A thousand failures across many accounts from one network may trigger rate limiting. A recovery request for a finance admin from a new country may require stronger proof than a routine password reset for a low-risk account. Good account systems combine user-visible flows with backend evidence.

Operational Failure Modes

Failure: recovery bypasses MFA. The system proudly requires MFA at login, but password reset disables MFA through email only. Treat recovery as an account-control transition and require stronger proof, delay, or restricted mode.

Failure: factor removal is easier than factor use. A user needs a strong factor to sign in, but support can remove that factor after a weak chat conversation. Support tooling needs policy, evidence capture, approval paths, and audit logs.

Failure: password hashing is treated as the whole password program. Hashing protects stored verifiers after a leak, but it does not prevent password reuse, phishing, credential stuffing, or account enumeration. Add rate limits, breached-password checks, monitoring, and user-safe responses.

Failure: new authenticators become trusted immediately. An attacker who adds a passkey or phone number after compromising a session may lock in access. Sensitive authenticator enrollment should require fresh proof and notify existing trusted channels.

Failure: recovery evidence is not auditable. During an incident, the team cannot tell who approved support recovery, which proofs were presented, which factors changed, or which sessions were invalidated. Record the lifecycle, not just the final login.

Readiness Check

Close the lesson and trace one account-control transition from memory:

What account is being controlled?
Which authenticator or credential proves the caller?
Is this normal login, factor enrollment, factor removal, or recovery?
Which weaker path could bypass the intended protection?
What rate limit, delay, notification, or restricted mode applies?
What audit evidence proves what happened?
Which sessions or recovery codes must be rotated afterward?

Apply the same questions to a product you use. Look especially at "I forgot my password," "I lost my phone," "add a new device," and "contact support." Those paths often reveal the real account security model more honestly than the normal sign-in screen.

Key Takeaways

  • The effective strength of an account is set by the weakest path that can change control of it, not only by the normal login path.
  • Password hashing protects stored verifiers, but account security also needs rate limits, breached-password checks, phishing resistance, and safe recovery.
  • MFA and passkeys improve proof of control, but their enrollment, removal, backup, and recovery paths need equal design attention.
  • Account recovery should leave clear evidence: requested transition, proofs used, factors changed, sessions invalidated, notifications sent, and any restrictions applied.
