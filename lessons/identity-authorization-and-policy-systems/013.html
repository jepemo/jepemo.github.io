Policy Engines and Policy-as-Code

By the end of this lesson, you will be able to:

  • separate policy enforcement, policy evaluation, and the application facts an authorization decision needs;

  • trace a request through a versioned policy decision and diagnose where an allow or deny came from;

  • choose a safe failure behavior and test path before centralizing a policy.

Idea in one sentence: A policy engine makes authorization rules reviewable and reusable only when every request reaches enforcement, supplies trustworthy facts, and records which policy version made the decision.

Core Insight

Northstar has three services that expose invoice data: a customer portal, a support console, and a scheduled export API. Each service began with its own check for “can this caller read an invoice?” Over time, the portal checks account membership, the support console also checks a legal hold, and the export API trusts a role in a token claim. When a contractor's access is revoked, two services deny the next request while the export API keeps returning invoices.

The tempting repair is to declare one policy engine and move every if statement into it. That can reduce duplicated rules, but it does not make the authorization model correct by itself. A policy engine can only evaluate the principal, action, resource, relationships, and attributes it receives. If the export API sends an old group claim, omits the legal-hold flag, or bypasses the enforcement point, a perfectly written policy still produces the wrong security outcome.

A policy decision point is the component that evaluates applicable policy and returns an authorization result. A policy enforcement point is the component that asks for that result and actually blocks or permits the operation. In plain language, the decision point answers “may this happen?”; the enforcement point makes sure the answer controls the real request. They can run in one process, beside the application, or as separate services, but both responsibilities must exist.

Policy-as-code means treating authorization rules as versioned, reviewed, tested artifacts rather than scattered application conditionals or console clicks. The trade-off is consistent, inspectable enforcement versus a new operational dependency: policy publication, input schemas, evaluation latency, rollout safety, and decision evidence all become part of the security boundary.

The Contract Between Application and Policy

Policy engines do not discover an application's truth. The application supplies a decision request, and the policy evaluates it against a known contract. For an invoice export, a useful input is explicit:

principal: service:scheduled-exporter
action: invoices.export
resource: tenant:acme-eu

relationships:
  scheduled-exporter is allowed for tenant acme-eu

resource attributes:
  legal_hold = false
  classification = internal

environment:
  request_risk = normal
  time = 2026-06-23T09:00:00Z

The policy should not receive a vague is_allowed boolean from the caller. It should receive the facts needed to reach the result, with clear owners. The identity system owns the authenticated principal; the authorization data store owns relationship tuples; the invoice system owns legal-hold and classification state; a risk service may own risk context. The policy contract specifies types, names, and permitted values so that a typo or missing fact does not silently broaden access.

This is where the previous lesson matters. A policy may combine RBAC, ABAC, and ReBAC, but it should say which rule uses which fact. For example:

allow export when
  principal has export relationship to tenant
  AND legal_hold is false
  AND classification is not restricted
  AND request_risk is normal

deny export when
  legal_hold is true
  OR a required fact is unknown

The exact syntax is not the important part. The important part is that a reviewer can see the input contract, the default behavior, and the reasons an exception may override a broad allow.

Pause and predict: Can a central policy engine protect the export API if that API never asks it before returning data?

Check: No. The engine is a decision point, not a force field. The export API or a trusted gateway must be an enforcement point that makes the decision before the sensitive operation occurs.

Worked Path: A Versioned Export Decision

Northstar keeps the policy with the application contract in source control. A pull request changes export access after a legal requirement: any tenant under legal hold must deny scheduled exports even when the exporter has a normal tenant relationship.

The policy and its tests are published as bundle version export-policy-42. The export API has a local policy evaluator beside it, so evaluation does not make a network hop for every invoice. The local evaluator receives signed or otherwise verified policy updates and reports which version it is using.

The request path is:

1. scheduled-exporter authenticates to the export API.
2. Export API identifies action=invoices.export and tenant=acme-eu.
3. API reads current legal_hold and classification from its authoritative data path.
4. API builds a typed policy input with principal, action, resource, relationships, and context.
5. Local decision point evaluates export-policy-42 and returns deny, reason=legal_hold.
6. Export API enforces deny; it does not start the export job.
7. Decision record stores decision ID, policy version, input references, reason, and correlation ID.

Notice the intermediate state at step 3. If the export API reads a replica that has not yet observed the legal hold, the policy can only reason from stale evidence. Policy centralization does not erase data consistency. The product must decide whether a legal hold requires a strongly current read, a version check, a short decision lifetime, or denial while the authoritative source is uncertain.

The same policy can be evaluated remotely instead of locally. A remote decision service can simplify distribution and provide one operational control plane, but it adds network latency and an availability dependency to every protected request. A local evaluator avoids that request-time dependency, but requires safe bundle delivery, signature verification where appropriate, rollout visibility, and a way to know which nodes still run an old version. Neither topology is universally safer; the correct choice follows the failure promise of the operation.

Pause and predict: The policy bundle is unavailable during a rollout. Should the export API use its last known policy, deny the request, or allow by default?

Check: Allow by default is unsafe for a sensitive export. The choice between a validated last-known policy and denial depends on the permitted staleness and rollback design, but both must be explicit, observable, and tested. If the policy cannot be trusted or its required facts are unknown, deny is the safer default.

So far: policies are reusable rules, not independent sources of truth. Enforcement supplies authoritative facts, the decision point evaluates a known policy version, and the enforcement point must apply the result before the operation runs.

Treat Policy Changes Like Security Changes

Policy-as-code earns its name when the policy lifecycle is engineered. A policy change should have an owner, review, tests, a versioned artifact, controlled rollout, and a rollback path. Editing a production console directly may be useful for a tightly governed emergency procedure, but it should produce an equivalent reviewed artifact afterward rather than creating a hidden second source of policy.

Start with decision tests. Each test names the principal, action, resource, relevant attributes and relationships, and expected allow or deny. Include the happy path, a missing fact, a revoked relationship, an expired or stale claim, a high-risk context, and an explicit denial. Tests should assert the reason as well as the outcome when the engine supports it; otherwise a broad accidental allow can replace the intended narrow allow without changing a superficial success test.

Validate policy against a schema before deployment when the policy system supports it. A schema is the contract for valid entity types, actions, and attributes. It can catch a rule that refers to legalHold while the application provides legal_hold, or a rule that tries to apply an export action to the wrong resource type. Validation cannot prove that the application supplied the current legal-hold value or that the business rule is correct. It prevents a class of mechanical mistakes; integration and decision tests cover the rest.

Roll out restrictive changes carefully. A dry-run or shadow evaluation can compare the current policy with a candidate policy and record differences without changing production behavior. Review those differences by action, tenant, and caller type. Then canary the new version, observe allow/deny rates and latency, and retain a fast rollback to the prior verified artifact. Do not shadow-evaluate a policy using synthetic input only; production-shaped input is where missing attributes and unexpected resource types appear.

Failure Modes and Operational Evidence

The first failure mode is bypass. One endpoint calls the policy engine while a batch job, admin route, or new API version reaches data directly. Inventory enforcement points and test that a denied decision truly prevents the side effect.

The second is input drift. A policy is correct for tenant_id, but one service starts sending accountId; an old token claim outlives group removal; or a document service omits legal-hold state. Version the input contract and reject malformed or incomplete inputs instead of quietly treating them as permissive defaults.

The third is topology confusion. A remote policy service times out, and an application treats “no decision” as allow to preserve availability. A local evaluator runs a month-old bundle, and operators assume policy changed globally. Decide in advance which operations can use last-known policy, which must deny, and which telemetry proves the deployed version and evaluation result.

The fourth is opaque decisions. An operator sees 403 but cannot tell whether a relationship was missing, a legal hold applied, an attribute source failed, or the engine used an obsolete policy. Decision evidence should include a decision ID, policy or bundle version, enforcement point, result, relevant rule or reason, and carefully redacted input references. Decision logs must not become a copy of credentials, raw tokens, or private document contents.

Useful signals include:

  • allow and deny rates by action, resource class, and policy version;
  • evaluation latency and error rate at each enforcement point;
  • malformed or missing input fields;
  • policy bundle version and age on every evaluator;
  • shadow-policy decision differences before rollout;
  • denied side effects attempted after a policy result, which indicate a bypass.

Centralization is valuable when multiple services need the same rule, but do not centralize product semantics blindly. The invoice service remains the authority on legal holds. The policy expresses how that fact affects export. The export API remains responsible for enforcing the final result before data leaves the system.

Design Check

Start with a nearby case. A support console needs to let agents view an invoice only when they have a tenant relationship, the invoice is not under legal hold, and the caller has a managed device. A scheduled export must additionally require a dedicated export relationship.

enforcement points:
  support invoice endpoint
  export job creation endpoint

shared policy inputs:
  principal, action, invoice or tenant, relationship result,
  legal_hold, device_managed, policy version

expected differences:
  support view: tenant relationship + no hold + managed device
  export: all of the above + export relationship

failure default:
  deny if policy, legal_hold, or relationship evidence is unavailable

This uses one shared model but preserves an important product distinction: reading support data is not the same as exporting it.

Now choose one authorization rule and write:

enforcement point that must not be bypassed:
principal, action, and resource contract:
authoritative facts and their owners:
policy version and rollout path:
test that must deny:
behavior when policy or a required fact is unavailable:
decision evidence retained:

Use this rubric: the policy must receive facts rather than caller-supplied conclusions; every protected route must enforce the result; a schema or equivalent contract must be tested; and a reviewer must be able to reconstruct which policy version made a decision.

Key Takeaways

  • A policy engine evaluates a decision; an enforcement point must supply trustworthy facts and block the real operation when the result is deny.
  • Policy-as-code requires versioned artifacts, typed inputs, tests, controlled rollout, rollback, and evidence of the policy version actually evaluated.
  • Centralizing rules does not centralize domain truth: resource, relationship, and risk systems remain responsible for current authorization facts.
  • For sensitive actions, unknown policy state or missing security facts should have an explicit, usually denying, failure behavior rather than becoming an accidental allow.
