Day 021: Event Sourcing and Durable History

Event sourcing keeps the story of the system, not just its latest snapshot.

Today's "Aha!" Moment

The insight: Traditional storage treats current state as the main truth and history as an optional log. Event sourcing flips that. The durable truth is the sequence of facts that happened, and the current state is something you derive from those facts.

Why this matters: Many difficult product questions are really history questions. Why did this value change? What did we believe at 10:03? Who triggered this transition? A state-only model often loses that context or stores it awkwardly.

Concrete anchor: Imagine a digital wallet. Instead of storing only balance = 30, the system stores WalletOpened, MoneyDeposited(50), and MoneyWithdrawn(20). The current balance is reconstructed from the event history.

The universal pattern: Immutable facts + replay + projections -> reconstructable state.

How to recognize when this applies:

  • The history of changes matters as much as the current value.
  • You need auditability, temporal queries, or post-incident reconstruction.
  • Multiple views can be derived from the same business events.
  • The business language is naturally event-shaped: order placed, payment captured, seat reserved.
  • Correctness depends on preserving what happened, not only what is true now.

Common misconceptions:

  • [INCORRECT] "Event sourcing means storing random log lines forever."
  • [INCORRECT] "It only matters for finance or blockchain systems."
  • [CORRECT] The truth: Event sourcing stores domain facts as first-class records. It is useful when history, replay, and multiple derived views are valuable enough to justify the added discipline.

Real-world examples:

  1. Banking ledgers: Transactions are durable facts, while balances are derived views.
  2. Git history: Commits preserve what changed, and the working tree is reconstructed from that history.
  3. Order lifecycles: OrderPlaced, PaymentCaptured, and OrderShipped tell a fuller story than one mutable row.
  4. Audit-heavy systems: Compliance, forensics, and debugging become easier when the system preserves an immutable trail.

Why This Matters

The problem: State-only systems are compact, but they often discard the timeline that explains the system's behavior.

Before:

  • Storing only the latest value and losing important history.
  • Treating audit trails as an awkward add-on instead of a core design choice.
  • Struggling to answer "what happened?" after bugs, disputes, or policy changes.

After:

  • Preserving business facts as durable, replayable events.
  • Building current state and specialized views from the same underlying history.
  • Making temporal debugging, auditability, and correction workflows much more explicit.

Real-world impact: Event sourcing is useful in payment systems, inventory history, workflow engines, domain audit trails, and any product where reconstructing past decisions is part of operating the system safely.

Core Concepts Explained

Concept 1: The Source of Truth Becomes the Event History

Concrete example / mini-scenario: Our digital wallet receives three events: WalletOpened, MoneyDeposited(50), and MoneyWithdrawn(20). The system does not store those as disposable side effects. It stores them as the authoritative timeline.

What it is: Event sourcing stores domain events as immutable facts. The current state of an aggregate is reconstructed by applying those events in order.

Why it matters: This preserves causality and business intent. You do not just know that the balance is 30; you know why it became 30.

How it works: Commands are validated against current state, accepted changes are written as new events, and the aggregate state is rebuilt by replaying prior events in sequence.

Mental model: A bank statement is more informative than a sticky note that only says the current balance.

Code Example (If applicable):

def replay(events):
    state = {"opened": False, "balance": 0}

    for event in events:
        if event["type"] == "WalletOpened":
            state["opened"] = True
        elif event["type"] == "MoneyDeposited":
            state["balance"] += event["amount"]
        elif event["type"] == "MoneyWithdrawn":
            state["balance"] -= event["amount"]

    return state

Note: The important idea is not the loop itself. The important idea is that the loop can recover state from durable facts without trusting a mutable snapshot alone.

When to use it:

  • [Ideal situation] Domains where the sequence of changes matters and auditability is valuable.
  • [Anti-pattern] Small CRUD data where keeping the full history adds more operational cost than product value.

Concept 2: Projections Turn One History into Many Useful Views

Concrete example / mini-scenario: The wallet team needs three views from the same events: current balance, monthly statement, and suspicious-activity analysis. None of those needs a different source of truth.

What it is: A projection is a derived model built by consuming events and materializing a specific view for a specific query pattern.

Why it matters: Event sourcing is not useful if every read requires replaying years of events. Projections make the model operational by turning the durable event history into practical read-side views.

How it works: Events are appended once, then read by one or more projection builders that maintain specialized views such as account balance, customer statement, or activity dashboard.

Mental model: One transcript can produce subtitles, a summary, and a search index. The raw transcript stays the same; the views differ by purpose.

When to use it:

  • [Ideal situation] Systems that need several read models from the same historical facts.
  • [Anti-pattern] Treating projections as the new source of truth instead of as derived state that can be rebuilt.

Concept 3: The Hard Part Is Operational Discipline

Concrete example / mini-scenario: After three years, the wallet has millions of events. Replay still works conceptually, but startup time, schema evolution, and bad event design now matter much more than on day one.

What it is: In real systems, event sourcing requires snapshots, version-aware consumers, careful event naming, and a disciplined approach to immutable event contracts.

Why it matters: The pattern is powerful, but it makes design mistakes durable. A badly named or underspecified event can haunt future consumers.

How it works: Teams often snapshot aggregate state every N events, version event payloads carefully, and treat event schema changes as compatibility work rather than as casual refactoring.

Mental model: Writing to an event store is closer to publishing a public record than mutating a private variable.

When to use it:

  • [Ideal situation] Teams willing to treat events as durable contracts and invest in replay, versioning, and projection rebuilds.
  • [Anti-pattern] Treating event names and payloads like temporary implementation details.

Troubleshooting

Issue: Treating events as generic CRUD change logs.

Why it happens / is confusing: Teams often start from tables and fields instead of from business facts.

Clarification / Fix: Events should capture meaningful domain changes such as OrderPlaced or FundsTransferred, not vague technical mutations like RowUpdated.

Issue: Assuming replay alone makes the system production-ready.

Why it happens / is confusing: The core idea feels elegant, so the operational work can look secondary.

Clarification / Fix: Real systems need projections, snapshots, compatibility strategy, and careful operational tooling. Event sourcing is as much about discipline as about storage format.

Advanced Connections

Connection 1: Git History <-> Event Sourcing

The parallel: Both preserve an ordered history of meaningful changes and let later views be reconstructed from that history.

Real-world case: A Git commit log lets you inspect prior state, explain current state, and rebuild working trees much like an event store supports replay and derived views.

Connection 2: Accounting Ledgers <-> Immutable Event Stores

The parallel: Both prefer append-only records of what happened over destructive mutation of a current total.

Real-world case: Financial systems often derive balances and statements from durable transaction history rather than trusting one mutable balance field alone.

Key Insights

  1. Event sourcing stores facts, not just snapshots - The system keeps the sequence of business changes as durable truth.
  2. State becomes derivable - Current views are projections built from event history, not the only preserved representation.
  3. The power comes with discipline - Replay, snapshots, projection rebuilds, and versioning are part of the real pattern, not optional extras.

Knowledge Check (Test Questions)

  1. What changes most when a system adopts event sourcing?

    • A) It stops storing data in any database.
    • B) It treats the ordered history of domain events as the durable source of truth.
    • C) It eliminates the need for read models.

  2. Why are projections important in an event-sourced system?

    • A) Because they turn durable event history into practical views for specific queries.
    • B) Because they replace the event store as the primary source of truth.
    • C) Because they make event naming irrelevant.

  3. What is one real operational challenge of event sourcing?

    • A) Event contracts and replay strategy must be maintained over time.
    • B) Current state can never be reconstructed.
    • C) The pattern only works if every read replays all events from the beginning.

Answers

1. B: Event sourcing changes what the system considers authoritative. The ordered facts are primary, and current state is derived.

2. A: Projections make event histories usable for real queries. They are derived views, not replacements for the event history itself.

3. A: Production event sourcing requires compatibility, snapshots, and operational discipline. That is where much of the real engineering work lives.
