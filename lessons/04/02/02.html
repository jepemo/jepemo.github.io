Day 067: Dependency Injection and Runtime Composition

Dependency injection matters because code becomes easier to change and test when it declares what it needs instead of constructing the whole world around itself.

Today's "Aha!" Moment

The insight: Dependency injection is not mainly about containers or frameworks. It is about making dependencies explicit and moving construction decisions out of business code.

Why this matters: Tight coupling often starts with innocent-looking new calls hidden inside classes. Over time, those hidden construction choices make testing, replacement, and configuration much harder.

Concrete anchor: The learning platform's enrollment service needs a repository, a payment gateway, and a notification sender. If the service creates them internally, testing enrollment logic requires real infrastructure. If those dependencies are supplied externally, the service becomes much easier to reason about and swap.

The universal pattern: Explicit dependency contract + external wiring -> looser coupling and easier testing.

How to recognize when this applies:

  • Classes construct their own repositories or clients directly.
  • Unit tests require real databases or external services unnecessarily.
  • Environment-specific wiring leaks into business logic.
  • Replacing one dependency would require editing many consumers.
  • The code hides what it needs to do its job.

Common misconceptions:

  • [INCORRECT] "Dependency injection means using a big IoC framework."
  • [INCORRECT] "DI is only for enterprise languages and large projects."
  • [CORRECT] The truth: Dependency injection is a design style first. Framework support can help, but the core idea is simply to receive dependencies rather than instantiate them deep inside business code.

Real-world examples:

  1. Repositories in services: Inject a repository interface rather than creating a database client internally.
  2. Payment gateways: Swap a fake gateway in tests and a real one in production.
  3. Notification senders: Replace email delivery with a test recorder during local runs.
  4. Configuration-driven wiring: Compose implementations differently across environments without changing core logic.

Why This Matters

The problem: Hidden construction choices make code rigid because classes become responsible for both behavior and infrastructure assembly.

Before:

  • Creating database clients inside services.
  • Needing real infrastructure to test domain logic.
  • Hiding important dependencies from the constructor or function signature.

After:

  • Declaring dependencies explicitly.
  • Composing implementations at the application edge.
  • Testing logic with controlled substitutes and clearer contracts.

Real-world impact: This improves testability, configurability, and maintainability, especially as the backend grows and infrastructure choices diverge by environment.

Core Concepts Explained

Concept 1: Explicit Dependencies Make Code More Honest

Concrete example / mini-scenario: The enrollment service constructor lists that it needs an enrollment repository, payment gateway, and notifier. Now the reader can understand the service's external needs immediately.

What it is: Dependency injection means a component receives its collaborators from outside rather than creating them internally.

Why it matters: Explicit dependencies make coupling visible and reduce the amount of hidden infrastructure logic inside domain code.

How it works: Constructors, function parameters, or factory wiring provide the needed dependencies before the component runs its main behavior.

Mental model: A chef should state which ingredients are required, not secretly run a farm behind the restaurant.

When to use it:

  • [Ideal situation] Services, controllers, repositories, and background jobs with external collaborators.
  • [Anti-pattern] Constructing infrastructure clients inside the deepest layers of domain logic.

Concept 2: Injection Enables Testing Through Substitution

Concrete example / mini-scenario: A test supplies a fake payment gateway that always approves or always fails. Now the enrollment service can be tested around business rules without needing a real payment provider.

What it is: DI supports substitution because the consumer depends on a contract or capability rather than on one hardcoded implementation.

Why it matters: This is one of the most practical benefits of DI: domain code can be tested without bringing the whole infrastructure stack into every test.

How it works: Tests and runtime composition choose different concrete implementations that satisfy the same dependency contract.

Mental model: If a wall socket follows a standard, you can test with a lamp, a charger, or a meter without rebuilding the house wiring.

Code Example (If applicable):

class EnrollmentService:
    def __init__(self, repo, payments, notifier):
        self.repo = repo
        self.payments = payments
        self.notifier = notifier

Note: The most important part is that the constructor exposes the service's real collaborators explicitly.

When to use it:

  • [Ideal situation] Unit testing, environment-specific wiring, and infrastructure substitution.
  • [Anti-pattern] Treating fakes and mocks as impossible because the implementation is hardcoded internally.

Concept 3: Runtime Composition Belongs at the Edge of the Application

Concrete example / mini-scenario: The web application startup code wires the real repository, payment gateway, and notifier into the enrollment service once, rather than making every handler decide how to build them repeatedly.

What it is: Runtime composition is the process of assembling concrete implementations into the application's abstract dependency graph.

Why it matters: Business code should focus on behavior, not on orchestrating construction and lifecycle rules for infrastructure objects.

How it works: Startup code, factories, or IoC containers instantiate and connect dependencies near the application boundary, then pass ready-to-use collaborators inward.

Mental model: A stage crew assembles the set before the performance starts. The actors should not build the theater while performing.

When to use it:

  • [Ideal situation] App startup, module wiring, and test fixture setup.
  • [Anti-pattern] Letting every service or handler become its own object graph builder.

Troubleshooting

Issue: Overcomplicating DI with unnecessary framework machinery.

Why it happens / is confusing: Many teams first encounter DI through large IoC containers rather than through simple constructor injection.

Clarification / Fix: Start with explicit constructors and simple factories. Add framework support only when lifecycle and wiring complexity truly justify it.

Issue: Using DI but still depending on concrete details everywhere.

Why it happens / is confusing: Passing dependencies around is not enough if the consumer still assumes too many implementation-specific behaviors.

Clarification / Fix: Depend on the smallest useful contract and keep implementation assumptions out of the consumer where possible.

Advanced Connections

Connection 1: Dependency Injection ↔ SOLID

The parallel: DI is one practical route toward dependency inversion because it helps business code depend on abstractions instead of construction details.

Real-world case: Services that receive repositories or gateways are easier to evolve than services that instantiate concrete infrastructure clients directly.

Connection 2: Dependency Injection ↔ Testing Strategy

The parallel: The testability of backend logic often improves dramatically once composition moves out of the logic layer.

Real-world case: Tests can use in-memory repositories or fake notifiers without booting the full application stack.

Key Insights

  1. Dependency injection makes dependencies visible - Business code becomes more honest about what it requires.
  2. Substitution is the practical win - Tests and environments can swap implementations more easily.
  3. Composition belongs at the edge - Wiring concrete infrastructure should not clutter core domain behavior.

    • B) Because DI removes all abstractions.

  3. Where should runtime wiring usually happen?

    • A) Near application startup or composition boundaries.
    • B) Deep inside each service method.

Answers

1. A: DI makes dependencies explicit and moves construction choices out of the core logic.

2. A: Injected collaborators are easier to replace with fakes or mocks in tests.

3. A: Runtime composition is usually best handled at the edge of the application, where infrastructure assembly naturally belongs.
