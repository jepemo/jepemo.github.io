Day 053: Layered Backend Architecture

Architecture starts paying off when each part of the backend has a clear job and the code stops leaking HTTP, domain logic, and persistence concerns into each other.

Today's "Aha!" Moment

The insight: Layered architecture is not about adding ceremony. It is about creating stable boundaries so request handling, business rules, and data access can change without dragging the whole codebase with them.

Why this matters: Small backends often grow into tangled systems because they begin with handlers that do everything. Layers help organize complexity before every change becomes risky.

Concrete anchor: The learning platform exposes an endpoint to enroll a student in a course. The controller should interpret HTTP, the service should decide whether enrollment is allowed, and the repository should persist the result. When those concerns mix, the endpoint becomes brittle quickly.

The universal pattern: Boundary between delivery + boundary between business rules + boundary between data access -> maintainable backend structure.

How to recognize when this applies:

  • Controllers are accumulating validation, business rules, and SQL.
  • Swapping database details would force edits across many request handlers.
  • Testing a simple rule requires booting HTTP and real storage.
  • New engineers struggle to see where logic should live.
  • The same business rule is duplicated across routes or jobs.

Common misconceptions:

  • [INCORRECT] "Layers are unnecessary indirection."
  • [INCORRECT] "A small codebase should wait until later to introduce boundaries."
  • [CORRECT] The truth: Good layers reduce coupling. The goal is not more files for their own sake, but clearer responsibility and easier change.

Real-world examples:

  1. HTTP controllers: Parse requests, invoke application logic, map errors to responses.
  2. Services or use cases: Enforce domain rules such as enrollment limits or ownership checks.
  3. Repositories: Hide storage mechanics and query details.
  4. Background jobs: Reuse the same service layer without needing HTTP-specific code.

Why This Matters

The problem: Many backends become hard to test and change because transport concerns, domain rules, and persistence details are all mixed together.

Before:

  • Writing SQL in controllers.
  • Returning HTTP concerns from deep business code.
  • Repeating the same decision logic in several endpoints.

After:

  • Keeping request translation, domain logic, and data access in separate layers.
  • Reusing domain logic across HTTP, jobs, and admin flows.
  • Changing infrastructure with less blast radius.

Real-world impact: This improves testability, onboarding, maintainability, and the ability to evolve the backend without turning every feature into a cross-cutting rewrite.

Learning Objectives

By the end of this session, you will be able to:

  1. Explain what each layer is for - Distinguish presentation, application or domain, and data access responsibilities.
  2. Spot boundary violations - Identify code that leaks persistence or HTTP concerns into the wrong place.
  3. Reason about change impact - Understand why layered design makes testing and refactoring safer.

Core Concepts Explained

Concept 1: Controllers Should Translate Requests, Not Own Business Rules

Concrete example / mini-scenario: The enroll endpoint receives a course ID and a student identity, validates the request shape, and then delegates the actual enrollment decision to a service.

Intuition: The controller or handler layer is responsible for HTTP-facing concerns such as parsing, authentication context extraction, and response formatting.

Practical implications: When controllers also decide business policy, the same rules become harder to reuse, test, and keep consistent.

Technical structure (how it works): The controller maps transport input into an application call and maps the result back into an HTTP response.

Mental model: A receptionist should route visitors correctly, not rewrite the organization's policies.

When to use it:

  • [Ideal situation] Request parsing, DTO validation, status code mapping.
  • [Anti-pattern] Embedding authorization rules, pricing logic, or database queries directly in route handlers.

Concept 2: Services Hold Domain Decisions

Concrete example / mini-scenario: The enrollment service checks whether the course is open, whether the student is already enrolled, and whether payment status allows access.

Intuition: The service or use-case layer contains business rules and workflow coordination that are meaningful independent of HTTP or storage technology.

Practical implications: This is the layer most worth protecting from framework and infrastructure churn because it carries product behavior.

Technical structure (how it works): Services depend on abstractions such as repositories or gateways, apply domain logic, and return outcomes that presentation layers can interpret.

Mental model: This layer is the policy desk. It decides what should happen, not how the network or database happens to implement it.

Code Example (If applicable):

class EnrollmentService:
    def __init__(self, enrollment_repo, course_repo):
        self.enrollment_repo = enrollment_repo
        self.course_repo = course_repo

    def enroll(self, student_id, course_id):
        course = self.course_repo.get(course_id)
        if not course["is_open"]:
            raise ValueError("course_closed")
        return self.enrollment_repo.create(student_id, course_id)

Note: The important point is that the service speaks in domain terms, not in HTTP or SQL terms.

When to use it:

  • [Ideal situation] Workflows, rule enforcement, orchestration of several dependencies.
  • [Anti-pattern] Returning HTTP status codes or raw SQL rows directly from the service layer.

Concept 3: Repositories Keep Persistence Details Out of the Domain Path

Concrete example / mini-scenario: The enrollment repository knows how to read and write enrollment rows, but the service should not know whether the storage is PostgreSQL, MySQL, or a test double.

Intuition: A repository is a boundary around data-access details that exposes storage operations in domain-relevant terms.

Practical implications: It localizes persistence mechanics and keeps the rest of the backend from being coupled to query syntax and connection details.

Technical structure (how it works): Repositories expose methods such as get, find, or create, while the actual SQL, ORM behavior, or remote call remains inside that layer.

Mental model: A repository is the warehouse desk. The service asks for an item or submits one; it does not manage the shelving system itself.

When to use it:

  • [Ideal situation] Backends where domain logic should stay storage-agnostic.
  • [Anti-pattern] Sprinkling query logic throughout controllers and services.

Troubleshooting

Issue: Creating layers that only pass data through mechanically.

Why it happens / is confusing: Teams often copy a pattern structure before deciding what responsibility each layer should actually own.

Clarification / Fix: Keep the rule simple: each layer should remove a kind of coupling. If a layer adds no boundary value, it is probably misplaced.

Issue: Letting controllers become "small monoliths."

Why it happens / is confusing: Controllers are the most visible place to add logic quickly, especially early in a project.

Clarification / Fix: Move reusable decisions and workflows into services as soon as the same logic appears in more than one path or needs focused testing.

Advanced Connections

Connection 1: Layered Architecture ↔ API Design

The parallel: Good API contracts are easier to preserve when HTTP concerns are separated cleanly from domain and persistence logic.

Real-world case: Versioning and error mapping are much easier when controllers are thin and services are stable.

Connection 2: Layered Architecture ↔ Testability

The parallel: Isolating domain logic from HTTP and database details makes unit tests more meaningful and cheaper to write.

Real-world case: Enrollment rules can be tested with fake repositories instead of real requests and real databases.

Key Insights

  1. Layers are boundaries, not ceremony - They help isolate HTTP, domain, and persistence concerns.
  2. Controllers should stay thin - Business rules belong in services where they can be reused and tested.
  3. Repositories protect the rest of the backend from storage detail - They reduce persistence leakage across the codebase.

Knowledge Check (Test Questions)

  1. What is the strongest reason to keep controllers thin?

    • A) So transport handling stays separate from reusable business rules.
    • B) So no validation ever happens there.
    • C) So repositories can return HTTP responses directly.

  2. Why is the service layer valuable?

    • A) It keeps domain decisions independent from HTTP and persistence details.
    • B) It replaces the need for repositories.
    • C) It should contain raw SQL so controllers stay clean.

  3. What problem do repositories mainly solve?

    • A) They hide storage details behind domain-relevant operations.
    • B) They turn every query into a microservice.
    • C) They remove the need for testing.

Answers

1. A: Thin controllers keep HTTP responsibilities separate from the domain rules that should be reusable elsewhere.

2. A: The service layer is where domain behavior stays stable even as transport and infrastructure change.

3. A: Repositories localize persistence mechanics so storage detail does not leak throughout the backend.
