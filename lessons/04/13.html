Day 061: Caching Strategies for Backend Performance

Caching matters because many production bottlenecks are really repeated work problems, and the backend becomes dramatically faster when it learns which work not to repeat.

Today's "Aha!" Moment

The insight: A cache is not "extra speed sprinkled on top." It is a deliberate decision to trade freshness and memory for lower latency and lower load on the expensive part of the system.

Why this matters: Teams often treat caching as a late optimization, then discover that the database, search layer, or third-party API is already overloaded. Good caching strategy starts with identifying repeated reads and deciding how stale is acceptable.

Concrete anchor: A learning platform serves the same course catalog page to thousands of users. The underlying course data changes only a few times per hour, but the backend still rebuilds the same response on every request unless it caches it.

The universal pattern: Expensive repeated read + acceptable freshness window -> candidate for caching.

How to recognize when this applies:

  • The same data is requested far more often than it changes.
  • A slow dependency dominates response time.
  • Traffic spikes create redundant repeated work.
  • Read latency matters more than perfectly fresh state.
  • The system can tolerate cache misses and refill behavior.

Common misconceptions:

  • [INCORRECT] "Caching means hiding a bad system design."
  • [INCORRECT] "If data can ever change, it should never be cached."
  • [CORRECT] The truth: Caching is a core production trade-off. The real question is not whether data changes, but how often it changes relative to how often it is read and how stale the user can tolerate.

Real-world examples:

  1. Product catalogs: Many reads, comparatively few updates.
  2. Profile lookups: User metadata is often read repeatedly during a session.
  3. Feature flags and config: Central state can be cached briefly to protect control-plane dependencies.
  4. Rendered API responses: Aggregated read models are often cheaper to serve from cache than to rebuild every time.

Why This Matters

The problem: Production backends often fail not because one request is too expensive, but because the same moderately expensive request is repeated thousands of times.

Before:

  • Hitting the database or downstream service for every identical read.
  • Treating latency and infrastructure cost as separate problems.
  • Adding cache ad hoc without deciding on freshness rules.

After:

  • Choosing cache candidates based on read frequency, recomputation cost, and staleness tolerance.
  • Using the cache to shed repeated load from the slowest dependency.
  • Designing invalidation and refill behavior intentionally instead of reactively.

Real-world impact: Good caching improves latency, protects databases during spikes, reduces cloud cost, and gives the backend more headroom before scaling out.

By the end of this session, you will be able to:

  2. Choose a practical caching strategy - Distinguish when cache-aside, TTL-based caching, or multi-layer caching makes sense.

Core Concepts Explained

Concept 1: Caching Starts with Repeated Read Patterns

Concrete example / mini-scenario: The course catalog endpoint builds the same "featured courses" response thousands of times during the day, even though the featured set changes only every few hours.

Intuition: A cache stores the result of expensive repeated work so that future reads can be served without fully recomputing or refetching that work.

Practical implications: The value of a cache comes from avoiding repeated load on the slowest or most expensive dependency.

Technical structure (how it works): You identify a repeated read, decide the cache key, choose how long the value can remain valid, and define what happens on miss and on update.

Mental model: A cache is a short-term memory for the backend. Instead of asking the archive the same question every minute, the system remembers the recent answer for a while.

When to use it:

  • [Ideal situation] High-read, low-change data or expensive aggregations.
  • [Anti-pattern] Data that changes every moment and requires strict read-after-write freshness.

Concept 2: Cache-Aside Is the Most Common Practical Pattern

Concrete example / mini-scenario: When the course catalog request arrives, the backend first checks whether catalog:featured:v3 is already cached. If not, it fetches from the database, builds the response, stores it, and returns it.

Intuition: Cache-aside means the application explicitly checks the cache before going to the source of truth and fills the cache on a miss.

Practical implications: It is simple, explicit, and works well for read-heavy systems because the backend only caches data that is actually requested.

Technical structure (how it works): Read request -> cache lookup -> miss -> fetch from source -> populate cache -> return response. On update, the application usually invalidates or refreshes the related key.

Mental model: The system checks the nearby notepad first. If the answer is not there, it goes to the filing cabinet, then writes the answer onto the notepad for next time.

Code Example (If applicable):

def get_featured_catalog(cache, db):
    key = "catalog:featured:v3"
    cached = cache.get(key)

    if cached is not None:
        return cached

    rows = db.fetch_featured_courses()
    payload = build_catalog_response(rows)
    cache.set(key, payload, ttl_seconds=300)
    return payload

Note: The important idea is not the library syntax. It is the control flow: check cache first, then fill it on miss.

When to use it:

  • [Ideal situation] Read-heavy endpoints where occasional misses are acceptable.
  • [Anti-pattern] Treating cache-aside as enough when you have not thought through invalidation or hot-key behavior.

Concept 3: Cache Strategy Is Really a Freshness Strategy

Concrete example / mini-scenario: A course price changes at 10:00, but some users still see the old value until a five-minute TTL expires. That may be acceptable for a marketing page and unacceptable for checkout.

Intuition: Caching strategy includes the rules for how stale data may become, how long entries live, and what should happen when the source changes.

Practical implications: The technical mechanics of caching are easy compared to deciding what consistency guarantees the user experience needs.

Technical structure (how it works): You choose TTLs, invalidation triggers, or explicit refresh rules based on the domain. Not every endpoint needs the same freshness guarantee.

Mental model: A cache is a promise with an expiration policy. The real design question is how long that promise can safely last.

When to use it:

  • [Ideal situation] Systems where you can articulate a freshness budget for each read path.
  • [Anti-pattern] One global TTL for everything, regardless of business meaning.

Troubleshooting

Issue: Caching everything by default.

Why it happens / is confusing: Once caching improves one slow path, it is tempting to apply it everywhere without checking whether the data pattern actually fits.

Clarification / Fix: Start with repeated expensive reads and define freshness requirements first. Caching is selective, not universal.

Issue: Treating TTL as a purely technical detail.

Why it happens / is confusing: Teams often pick round numbers like 60 seconds or 5 minutes without connecting them to real user expectations or business rules.

Clarification / Fix: Choose TTLs from the domain outward. Ask what stale data actually means for the user or workflow.

Advanced Connections

Connection 1: Caching ↔ Database Load

The parallel: Caching is often the fastest way to reduce read pressure on the database without changing the data model itself.

Real-world case: Catalog, profile, and search-result endpoints are often limited more by repeated reads than by raw query complexity.

Connection 2: Caching ↔ API Design

The parallel: Stable resource shapes and clear read paths make caching much easier because the backend can define cache keys and invalidation boundaries more predictably.

Real-world case: Versioned read models and well-scoped endpoints often produce simpler cache behavior than highly dynamic response shapes.

Key Insights

  1. Caching solves repeated work problems - It is most useful when reads greatly outnumber changes.
  2. Cache-aside is popular because it is explicit and practical - But it still needs deliberate freshness rules.
  3. The hard part is not storing copies - It is deciding how stale the system is allowed to be and when to refresh or invalidate.

Knowledge Check (Test Questions)

  1. What makes a backend read path a good caching candidate?

    • A) The data is read repeatedly and can tolerate some freshness window.
    • B) The data changes constantly and must always be perfectly fresh.
    • C) The backend wants to avoid thinking about query design.

  2. Why is cache-aside widely used?

    • A) Because it lets the application decide explicitly when to read from cache, fetch from the source, and fill the cache on misses.
    • B) Because it guarantees global strong consistency automatically.
    • C) Because it removes the need for invalidation rules.

  3. Why is TTL selection a domain decision as much as a technical one?

    • A) Because the acceptable staleness depends on what the user or workflow can tolerate.
    • B) Because every cache entry should use the same TTL.
    • C) Because shorter TTLs always produce better performance.

Answers

1. A: Caching works best when a costly read is repeated often and a bounded freshness window is acceptable.

2. A: Cache-aside is practical because the application explicitly controls lookup, miss handling, and refill behavior.

3. A: A TTL is really a freshness promise. The right value depends on business meaning, not just engineering taste.
