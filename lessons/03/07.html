Day 039: Caching Across Storage Layers

Caching is most useful when you see it as a hierarchy problem: keep the hottest data in the cheapest fast place that still preserves the behavior you need.

Today's "Aha!" Moment

The insight: Page cache, application cache, Redis, and CDN edges are not isolated tricks. They are layers in the same general strategy for trading capacity and distance against latency.

Why this matters: Many cache problems are easier to reason about once you stop asking "should we add a cache?" and start asking "which layer is missing, hot, stale, or overloaded?"

Concrete anchor: The learning platform serves lesson metadata, user progress, video thumbnails, and static assets. Some of this data belongs in process memory, some in Redis, some behind a CDN, and some only in the origin storage tier.

The universal pattern: Hot subset + expensive miss path + limited fast storage -> caching hierarchy.

How to recognize when this applies:

  • Most requests concentrate on a minority of data.
  • Cache misses are much more expensive than hits.
  • Several storage layers exist between the user and the durable source.
  • Latency spikes correlate with load on deeper tiers.
  • Staleness and invalidation are part of the design discussion.

Common misconceptions:

  • [INCORRECT] "Caching is just a speed boost and rarely changes architecture."
  • [INCORRECT] "One cache layer should be enough if it is large enough."
  • [CORRECT] The truth: Caching changes the shape of the whole system because misses, refill behavior, eviction, and invalidation move load between layers.

Real-world examples:

  1. OS page cache: Speeds repeated reads from local files.
  2. Redis: Offloads hot reads from a database or metadata service.
  3. CDN: Moves static and semi-static content close to users.
  4. Application in-memory cache: Avoids even the network hop to shared cache layers.

Why This Matters

The problem: Caches are often added reactively, which can leave teams with fragmented mental models and unclear invalidation behavior.

Before:

  • Treating each cache as an isolated performance tweak.
  • Measuring hit rate without modeling miss cost or refill load.
  • Forgetting that cached data still has an authoritative source somewhere.

After:

  • Seeing cache layers as a coordinated hierarchy.
  • Reasoning about where data is hot, where misses fall through, and what gets evicted.
  • Designing cache strategy together with freshness and durability rules.

Real-world impact: This improves latency, cost, and failure handling because the system can shift load intentionally instead of accidentally.

Learning Objectives

By the end of this session, you will be able to:

  1. Explain cache hierarchies - Relate local page cache, shared caches, and CDN layers as one pattern.
  2. Reason about hits, misses, and refill paths - Identify how caches move load across the system.
  3. Evaluate freshness and invalidation trade-offs - Understand why cache design is about correctness as well as speed.

Core Concepts Explained

Concept 1: A Cache Layer Exists to Avoid a More Expensive Path

Concrete example / mini-scenario: Thumbnail requests are frequent and repetitive. Serving them from a CDN edge or an in-memory cache avoids repeated trips to object storage and origin processing.

Intuition: A cache stores a subset of data in a faster or closer location so repeated accesses do not pay the full miss path.

Practical implications: Without a costly or common miss path, a cache adds complexity without enough benefit.

Technical structure (how it works): The client checks the fast layer first; on miss, it falls back to the authoritative source, then optionally refills the cache.

Mental model: A cache is a shortcut that is worth maintaining only because the longer route is expensive enough to avoid repeatedly.

When to use it:

  • [Ideal situation] Read-heavy paths with repeated access and significant miss penalties.
  • [Anti-pattern] Caching highly unique or constantly changing data without a clear reuse pattern.

Concept 2: Cache Hierarchies Work Because Different Layers Solve Different Distances

Concrete example / mini-scenario: A lesson title might live in process memory for the hottest requests, in Redis for shared access across instances, and in the database as the authoritative record.

Intuition: A cache hierarchy is a stack of layers that each optimize a different distance or cost: CPU, process, node, cluster, region, or internet edge.

Practical implications: One large cache cannot always replace several smaller layers because locality and sharing needs differ by level.

Technical structure (how it works): Near caches optimize the fastest repeated paths; shared caches reduce duplicate work across instances; edge caches reduce geographic latency; deep storage remains authoritative.

Mental model: Keep a copy on your desk, another in the office cabinet, and the original in long-term archives. Each location serves a different access pattern.

Code Example (If applicable):

def read_lesson_title(lesson_id, local_cache, redis_cache, database):
    if lesson_id in local_cache:
        return local_cache[lesson_id]

    title = redis_cache.get(lesson_id)
    if title is not None:
        local_cache[lesson_id] = title
        return title

    title = database.fetch_title(lesson_id)
    redis_cache.put(lesson_id, title)
    local_cache[lesson_id] = title
    return title

Note: The important lesson is that each layer avoids a different kind of cost: local computation, network hop, or deep storage access.

When to use it:

  • [Ideal situation] Systems with repeated reads at several scales, from local process access to global user traffic.
  • [Anti-pattern] Forcing all caching into one layer and then wondering why locality is still poor.

Concept 3: Freshness and Invalidation Are Part of Correctness

Concrete example / mini-scenario: A course title changes. If the platform updates the database but not the cache layers, users keep seeing stale content even though the origin data is correct.

Intuition: Freshness is how up-to-date cached data remains relative to the source of truth. Invalidation is how the system decides old cached data should stop being served.

Practical implications: A fast wrong answer is still wrong. Cache design always includes a correctness trade-off.

Technical structure (how it works): Systems use TTLs, explicit invalidation messages, versioned keys, or immutable content patterns to balance freshness and operational simplicity.

Mental model: A cached answer is a photocopy. You need a rule for when the photocopy is too old to trust.

When to use it:

  • [Ideal situation] Any cache beyond trivial short-lived local memoization.
  • [Anti-pattern] Designing caches around hit rate alone while ignoring update behavior.

Troubleshooting

Issue: Focusing only on hit rate.

Why it happens / is confusing: Hit rate is easy to measure, but it does not explain whether misses are catastrophic, cheap, or clustered on the most important paths.

Clarification / Fix: Always pair hit rate with miss cost, refill behavior, and freshness requirements.

Issue: Treating stale reads as a minor detail.

Why it happens / is confusing: Performance wins are visible immediately, while stale-data problems often appear later and intermittently.

Clarification / Fix: Define which data may be stale, for how long, and under what invalidation rules before expanding the cache footprint.

Advanced Connections

Connection 1: Caching ↔ Storage Cost Shaping

The parallel: Caches are not only about speed; they also shape which expensive storage layers get hit and how often.

Real-world case: A CDN in front of object storage can reduce both latency and origin egress cost dramatically.

Connection 2: Cache Hierarchy ↔ Memory Hierarchy

The parallel: The same principle appears from CPU caches up through process memory, shared caches, and global edges.

Real-world case: Systems that already think in terms of hot versus cold data often design better multi-layer caches by default.

Key Insights

  1. Caches exist to avoid expensive miss paths - A cache only helps when the avoided path is common and costly enough.
  2. Different cache layers solve different distances - Local, shared, and edge caches are complementary rather than interchangeable.
  3. Freshness is part of cache design - Invalidation and staleness rules matter as much as raw hit rate.

Knowledge Check (Test Questions)

  1. What makes a cache layer worth adding?

    • A) The miss path is expensive and repeated accesses are likely.
    • B) The system has any data at all.
    • C) The team likes in-memory tools.

  2. Why might a system use both a local cache and a shared Redis cache?

    • A) Because they reduce different costs: local access versus shared cross-instance reuse.
    • B) Because one cache layer is always a mistake.
    • C) Because local caches guarantee perfect consistency.

  3. Why is cache invalidation important?

    • A) Because without it, fast responses can still be stale and incorrect.
    • B) Because it removes the need for an origin store.
    • C) Because it guarantees 100% hit rate.

Answers

1. A: A cache is worthwhile when it avoids a miss path that is expensive enough and repeated often enough to justify extra complexity.

2. A: Local and shared caches serve different locality levels, so they can complement each other rather than duplicate each other.

3. A: Cached data must still obey freshness expectations, so invalidation or expiration rules are part of correctness.
