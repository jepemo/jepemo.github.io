Day 092: Event Sourcing and CQRS

Event sourcing and CQRS matter when the system benefits from treating state changes as an explicit history and from separating write-side authority from read-side optimization.

Today's "Aha!" Moment

The insight: Event sourcing is not just "store events too." It means the event history becomes the source of truth for a domain boundary, while CQRS separates the authoritative write model from one or more read models optimized for query needs.

Why this matters: These patterns are powerful but often over-applied. They are useful when auditability, state reconstruction, or read/write model separation create real value, not just because events sound modern.

Concrete anchor: The learning platform tracks cohort enrollment state. Instead of storing only the current aggregate row, the system stores events such as cohort.created, student.enrolled, and student.withdrawn, then derives read models for dashboards and reporting.

The universal pattern: Need for durable state-change history + valuable replay/audit + read models with different shapes from write rules -> consider event sourcing and CQRS.

How to recognize when this applies:

  • History of state change has business value.
  • Reconstructing past state or auditing decisions matters.
  • Read models differ significantly from write-side rules.
  • Multiple projections or denormalized views are needed.
  • The team can handle the added conceptual and operational complexity.

Common misconceptions:

  • [INCORRECT] "Event sourcing is just regular logging."
  • [INCORRECT] "CQRS means every system should have separate databases for reads and writes."
  • [CORRECT] The truth: Event sourcing makes event history authoritative, and CQRS separates write-side behavior from read-side models where that distinction is useful. Both patterns are strong tools, not defaults.

Real-world examples:

  1. Auditability: Explain exactly how a cohort reached its current state.
  2. Replay: Rebuild a read model from historical events.
  3. Read optimization: A reporting view differs from the domain aggregate's write model.
  4. Projection lag: Read models may be eventually consistent with the write side.

Why This Matters

The problem: Traditional current-state storage can hide valuable history and force read queries to depend directly on write-oriented domain models.

Before:

  • The system stores only the latest state.
  • Audit and replay are limited.
  • Read-heavy consumers put pressure on the write model or primary store.

After:

  • State change history is explicit and meaningful.
  • Read models can be rebuilt or specialized for different consumers.
  • The team can reason more clearly about write authority versus read convenience.

Real-world impact: These patterns can improve auditability, projection flexibility, and read-model design when the domain genuinely benefits from them.

Core Concepts Explained

Concept 1: Event Sourcing Stores Domain History as the Source of Truth

Concrete example / mini-scenario: The cohort enrollment aggregate reaches "27 enrolled students" because of a sequence of events, not just because one row currently says count = 27.

Intuition: Event sourcing persists the series of domain events that produced the current state, and the aggregate state can be rebuilt by replaying that series.

Practical implications: The system gains explicit history, auditability, and the ability to reconstruct or reinterpret state from prior events.

Technical structure (how it works): Commands produce domain events, those events are appended durably, and aggregate state is derived by replaying them in order.

Mental model: Instead of storing only the final score, event sourcing stores the full play-by-play and can recompute the score from it.

When to use it:

  • [Ideal situation] Domains where history, audit, replay, or temporal reasoning matter strongly.
  • [Anti-pattern] CRUD-style domains where current state is enough and event history adds little business value.

Concept 2: CQRS Separates Write Authority from Read Convenience

Concrete example / mini-scenario: The cohort write model enforces enrollment rules, while dashboards want denormalized views such as instructor summaries, attendance counts, and recent changes.

Intuition: CQRS separates the command/write side from one or more query/read models so each can be designed for its own job.

Practical implications: Write models are usually designed around invariants and correctness, while read models are often designed around query convenience and performance.

Technical structure (how it works): The write side handles commands and emits events; read-side projections consume those events and build query-optimized models.

Mental model: The write side is the rulebook and ledger. The read side is the set of views and summaries people use to inspect that ledger.

Code Example (If applicable):

def apply_event(state, event):
    if event["type"] == "student.enrolled":
        state["enrolled_count"] += 1
    elif event["type"] == "student.withdrawn":
        state["enrolled_count"] -= 1
    return state

Note: The point is that current state is derived by applying ordered events, while read-side projections may build other shapes entirely.

When to use it:

  • [Ideal situation] Systems where read needs diverge substantially from write-side aggregate rules.
  • [Anti-pattern] Splitting reads and writes mechanically when one model would already be simple and sufficient.

Concept 3: These Patterns Add Power by Adding Complexity

Concrete example / mini-scenario: The cohort system gains audit history and flexible projections, but the team must now handle projection lag, replay tooling, event versioning, and more operational moving parts.

Intuition: Event sourcing and CQRS introduce extra concepts, operational workflows, and consistency behavior in exchange for stronger historical and read-model capabilities.

Practical implications: The patterns are only worth it when those benefits are real enough to justify the cost.

Technical structure (how it works): Teams evaluate whether auditability, rebuildability, and read-side specialization are central to the domain rather than incidental.

Mental model: These are power tools. They solve some hard problems well, but they are too heavy for simple tasks.

Troubleshooting

Issue: Confusing event sourcing with ordinary audit logging.

Why it happens / is confusing: Both preserve historical information, so they can sound similar at first.

Clarification / Fix: In event sourcing, the event history is authoritative for reconstructing state. In ordinary logging, logs usually observe a system whose truth is stored elsewhere.

Issue: Applying CQRS where one simple model is enough.

Why it happens / is confusing: CQRS can sound like a best practice rather than a specialized tool.

Clarification / Fix: Use CQRS when read and write concerns genuinely diverge in shape, scale, or semantics. Otherwise keep the model simpler.

Key Insights

  1. Event sourcing makes history authoritative - State is derived from domain events rather than only stored as a final row.
  2. CQRS separates correctness from query convenience - Write rules and read models do not have to share one shape.
  3. Both patterns are specialized tools - Their power comes with real conceptual and operational cost.

    • A) The sequence of domain events becomes the source of truth from which state can be reconstructed.
    • B) The system no longer stores any state at all.
    • C) Every event is automatically a read model.

  2. Why might CQRS be useful?

    • A) Because the write side and read side may need different models for correctness and query efficiency.
    • B) Because every system should split reads and writes into separate services.
    • C) Because read models should never lag behind writes.

  3. Why are these patterns not universal defaults?

    • A) Because they add meaningful complexity and are most justified when history and specialized read models really matter.
    • B) Because they only work in public APIs.
    • C) Because they eliminate domain modeling.

Answers

1. A: Event sourcing stores the event history as the authoritative record of state change.

2. A: CQRS is valuable when read and write concerns genuinely differ enough to justify separate models.

3. A: The patterns are strong but costly, so they fit best when their benefits are central to the domain.
