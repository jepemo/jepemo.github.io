Time, Clocks, and Causality

Core Insight

Imagine sending a message that says, "Can we meet at 3?" Your friend replies, "Yes." Even if your friend's phone clock is a little wrong, you know one useful fact: the reply happened after the question. The message created an order.

Now imagine two devices editing the same profile while offline. A phone changes the display name. A laptop changes the email address. Neither device has heard from the other yet. A wall-clock timestamp may put one edit before the other, but that does not mean one caused the other. They are independent from the system's point of view.

That is the center of distributed time. Wall clocks are useful for people, logs, deadlines, alerts, and retention windows. They are weaker when the system needs to know whether one event depended on another.

The stronger idea is causality: the relationship between events where one event could have influenced another. In distributed systems, preserving causality often matters more than sorting records by the largest timestamp. A clock can tell you when a machine thought something happened. It cannot always tell you what that event had seen.

Message Order Beats Clock Order

Use a profile service replicated in two regions. Each region can accept writes when a user is nearby.

First, consider a causal chain:

region A: user changes email
region A -> region B: replicate email change
region B: send confirmation to the new email

The confirmation depends on the email change because information flowed from the change to the confirmation. Even if region B's wall clock is wrong, the system has evidence that the confirmation happened after the change in the meaningful product story.

Now compare concurrent edits:

region A: change display_name to "Maya"
region B: change email to "maya@example.com"

no message has passed between A and B yet

These events are concurrent. Concurrent does not mean they happened in the same millisecond. It means the system has no evidence that either event observed the other before acting.

If the fields are independent, the system may merge them. If both edits changed the same field, the product needs a conflict rule. The wrong move is to pretend the larger timestamp automatically means "more correct."

Happens-Before

The foundation term is happens-before. It names the order created by local sequence and message flow.

Three rules are enough for a first mental model:

  • If one event happens earlier in the same process, it happens before the later event.
  • If one event sends a message and another receives it, the send happens before the receive.
  • If A happens before B, and B happens before C, then A happens before C.

If neither event happens before the other, they are concurrent from the system's point of view.

Here is a small timeline:

device 1:
  edit title -------- send sync -------->

device 2:
                         receive sync ---- show new title

causal order:
  edit title happens before show new title

And here is a concurrent timeline:

device 1:
  edit title

device 2:
  edit title

no sync message between them before the edits

causal order:
  neither edit happened before the other

This distinction changes the design. In the first timeline, overwriting the display after receiving the sync may be reasonable because the receiving device has learned about the earlier edit. In the second timeline, blindly choosing the higher timestamp can erase a real user action that the other device never had a chance to see.

Logical Clocks And Version Evidence

A logical clock records ordering information instead of trying to measure physical time. It does not say "the event happened at 10:00:05." It says, in effect, "this event comes after the events this participant has already seen."

A simple logical counter can help inside one ordered stream. Each new event gets a larger number. If every event flows through the same leader or log, that may be enough.

Multi-replica systems often need richer evidence. A version vector records what each replica has seen.

version seen by region A: {A: 3, B: 1}
version seen by region B: {A: 2, B: 4}

This sketch says region A has seen three events from A and one from B. Region B has seen two from A and four from B. The exact representation varies by system, but the purpose is stable: show whether one version includes another version's history, or whether the versions are concurrent.

The trade-off is cost. Richer causal metadata can make conflict handling safer, but it takes storage, code, and operational care. For some data, a timestamp tie-breaker may be acceptable. For important user edits, permissions, money movement, or configuration, losing causal information may be too expensive.

Conflict Rules

Once you can name causality, conflict handling becomes more honest.

If one update happened before another, the later update may intentionally replace the earlier one. If two updates are concurrent, the system should not claim that one "won" because it was causally later. It was not. The product needs a rule.

Different state needs different rules:

  • A shopping cart can often merge concurrent additions.
  • A note editor may keep two versions and ask the user to resolve a paragraph conflict.
  • A counter may merge increments if the operation is designed to be commutative.
  • A security setting may require coordination so conflicting updates do not happen independently.

The bad default is last write wins by wall-clock timestamp when the product cannot tolerate silent loss. It is tempting because it is simple. It is dangerous because a fast clock can make an older write look newer, and a slow clock can make a causally later write look older.

The design question is:

For this state, which events must keep causal order,
and what do we do when two events are concurrent?

That question prepares the next lesson. CAP and PACELC ask what the system does when replicas cannot coordinate. Time and causality tell you what evidence those replicas do or do not have when they later compare their histories.

Failure Modes And Trade-offs

The representative failure is silently losing an update. A laptop edits a profile field while offline. A phone edits the same field while offline. The laptop clock is ahead, so the merge rule keeps the laptop edit and discards the phone edit without showing a conflict. The timestamp produced an answer, but it did not prove the answer was meaningful.

Another failure is using clock time for a decision that requires causal order. Logs may show that one server wrote at 10:00:05 and another wrote at 10:00:03, but those numbers can be affected by clock drift, clock correction, or different measurement points. They are useful clues, not perfect proof of influence.

The trade-off is between simplicity and correctness for the state at hand. Wall-clock timestamps are cheap, familiar, and often good enough for display order, expiration, and approximate freshness. Causal tracking is more complex, but it protects workflows where silent overwrite or invented ordering would break the promise.

Key Takeaways

  • Wall clocks are useful evidence, but they are not proof of causality.
  • Happens-before captures order created by local sequence and message flow.
  • Concurrent events are independent from the system's point of view, not necessarily simultaneous.
  • Conflict rules should match the product promise instead of blindly trusting the largest timestamp.
