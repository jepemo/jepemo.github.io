Backpressure, Load, and Cascading Failure

Core Insight

Imagine a cafe kitchen that can cook 100 meals per hour. One day 300 orders arrive in an hour. If the cashier keeps accepting every order with a cheerful promise, the kitchen has not become more capable. It has created a growing pile of commitments it cannot keep.

Distributed systems behave the same way under overload. A queue, worker pool, database, or downstream API has finite capacity. If callers keep adding work faster than the system can finish it, latency rises, timeouts start, retries multiply, and a local slowdown can become a system-wide failure.

Backpressure is how a system signals that incoming work must slow down before overload spreads. It may reject work, delay work, reduce concurrency, return 429, ask a producer to send fewer items, shed optional features, or degrade to a smaller response.

The goal is not to avoid every error. The goal is to preserve the most important promises when capacity is limited. The trade-off is uncomfortable: refusing or degrading some work early can be more reliable than accepting everything and collapsing later.

When A Queue Stops Helping

Use a worker queue that writes to a database:

clients -> API -> queue -> workers -> database

At first, the queue is helpful. If clients send a short burst of requests, the queue smooths the burst and workers catch up.

brief burst:
  arrival rate > service rate for 10 seconds
  queue grows briefly
  workers catch up

Now change the situation. The database slows down for thirty minutes. Workers can finish only 100 jobs per minute, but clients are adding 300 jobs per minute.

sustained overload:
  arrivals: 300/min
  completions: 100/min
  queue growth: 200/min

The queue no longer represents resilience. It represents unkept promises. Jobs get older. Clients time out. Callers retry. Workers hold connections longer. The database receives more pressure from repeated attempts. A buffer that absorbed variation becomes storage for failure.

That is the first useful mental model: queues are good shock absorbers and bad capacity plans.

Controls That Apply Pressure Back

Backpressure is not one mechanism. It is a family of controls that keep demand closer to capacity.

Admission control decides whether new work is allowed in. If the queue is too deep or the dependency is unhealthy, the system can reject early instead of accepting work it probably cannot finish.

Concurrency limits cap how many requests, jobs, or database operations run at once. This protects a dependency from being flooded by every caller at the same time.

Rate limits bound how quickly a caller, tenant, user, or service may send work. They make overload less likely to be caused by one noisy source.

Load shedding drops or degrades lower-priority work to preserve critical paths. A checkout might skip recommendations before it fails payment authorization.

Retry budgets limit how much extra traffic retries may create. A retry can help with a temporary error. A retry storm can double or triple load during the exact moment when the system is weakest.

The controls work best when they are tied to product priorities:

preserve:
  payment commit
  order receipt
  account security action

degrade first:
  recommendations
  analytics enrichment
  noncritical notifications

This is why overload policy is not only infrastructure. It decides which promises survive pressure.

Cascading Failure

A cascading failure happens when one overloaded part causes other parts to overload too.

Consider this path:

API -> payment service -> provider

The provider becomes slow. Payment requests take longer. API threads wait longer. Users time out and retry. Each retry creates another payment attempt or status check. Payment workers spend more time on work that may already be stale. The provider receives even more traffic. Soon the API, payment service, and provider are all under stress.

The original problem may have been one slow dependency. The cascade comes from the feedback loop:

slow dependency
  -> longer waits
  -> caller timeouts
  -> retries
  -> more load
  -> even slower dependency

Backpressure breaks that loop. It can stop new work, cap concurrency, return a clear retry-after response, shed optional work, or move the workflow into a pending state with repair. The response may be less pleasant than success, but it is better than letting every path fail together.

Designing Overload Behavior

A healthy overload design names behavior before the incident.

For each important path, ask:

  • What is the capacity limit we are protecting?
  • Which work is highest priority?
  • Which work can be delayed?
  • Which work becomes worthless after a deadline?
  • Which callers may retry, and how much?
  • What response should users see when admission closes?

Deadlines matter because old work can become harmful. Sending a confirmation email two seconds late may be fine. Charging a stale payment attempt after the user has canceled may not be. A queue should know when work has expired.

Recovery also needs a policy. When load drops, the system should not instantly reopen every gate and recreate the overload. It may drain useful work, discard expired work, ramp admission gradually, and keep lower-priority features degraded until core paths are stable.

Good backpressure makes overload visible. Metrics such as queue age, queue depth, concurrency, rejection rate, retry rate, and deadline expiration show whether the system is protecting itself or merely delaying collapse.

Failure Modes And Trade-offs

The representative failure is accepting too much work. The system tries to be available by saying yes, but it accumulates so much delayed work that eventually it cannot serve anything well.

Another failure is unbounded retries. Callers trying to be helpful multiply the work. Without jitter, budgets, and deadlines, many callers retry together and turn a slowdown into a surge.

A third failure is shedding the wrong work. If optional background jobs keep running while checkout fails, the system is preserving the wrong promise. Priority should be explicit, tested, and visible in dashboards.

The trade-off is between completeness and survival under pressure. Serving every request at full fidelity is ideal when capacity exists. Under overload, a smaller honest promise can be more correct: reject early, degrade optional work, preserve critical state transitions, and repair later when necessary.

Key Takeaways

  • Backpressure protects limited capacity by slowing, rejecting, or degrading incoming work.
  • Queues smooth short bursts, but sustained queue growth is evidence of an unkept promise.
  • Cascading failure often comes from feedback loops: slow dependencies, timeouts, retries, and more load.
  • Overload policy is a product decision because it chooses which promises survive under pressure.
