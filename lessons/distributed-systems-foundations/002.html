Day 002: Network Boundaries, Latency, and Partial Failure

Aha!

Imagine changing your display name in an app. You press Save, wait, and then the page says there was an error. A few seconds later, you refresh and the new name is there anyway. Did the save fail? Did it work? Why did the product seem to say both things?

That small confusion is what a network boundary creates. Inside one process, a function call shares memory, stack, and fate with its caller. If it returns, the caller gets the result. If it raises, the caller gets the error. Across a network boundary, the caller sends a message to an independent participant with its own queue, clock, process state, disk, deployment version, and ways to fail.

The important lesson is not merely that networks can be slow. It is that messages create uncertainty. The caller may know that it sent a request, that its own timer expired, or that a response arrived. It does not automatically know whether the remote service never received the request, received it and became slow, completed the work but lost the response, completed the work and crashed before reporting, or is still working.

Two terms help name that experience. Latency is the time a message or response takes to arrive. In real systems it is not one neat number: many requests are fast, some are slower, and a few are much slower. Partial failure means one part of the system is broken, slow, isolated, overloaded, or unreachable while other parts continue to run. The whole product has not vanished, but it no longer behaves like one simple local program.

This is why a timeout is a policy boundary, not a proof. It means, "I stopped waiting after this much time." It does not mean, "The remote operation did not happen." The central trade-off is between waiting longer for clearer evidence and moving on sooner to protect the caller's latency budget. Good distributed design gives that missing answer a named behavior instead of pretending uncertainty is the same thing as failure.

Why This Matters

This lesson matters because Distributed Systems Foundations is not just a sequence of distributed-systems terms. It is a way to reason about user-visible promises when state, time, messages, and failure are spread across independent components. The practical value is being able to name what the system can know, what it cannot know yet, and which promise should survive while uncertainty is resolved.

Core Walkthrough

Worked Example

Now slow that profile update down and inspect it. A web gateway receives the user's request, calls a profile service, and the profile service writes the change to its database before returning a response.

On an ordinary day, the story feels simple:

user
  -> gateway: change display name
  -> profile service: apply update
  <- profile service: success
  <- gateway: show updated profile

Now add a network slowdown between the gateway and the profile service:

gateway -- update request --> profile
gateway <-- ? -------------- profile

possible truths:
  request never arrived
  request arrived but is queued
  update was written
  response was lost
  profile is slow but healthy
  profile is overloaded

From the gateway's local view, the request took too long. From the profile service's local view, it may have applied the update correctly. From the user's view, the product must still make sense. If the page says "failed" but the name changes later, the product feels inconsistent. If the gateway retries without a stable operation identity, the update may be applied twice when the operation is not naturally idempotent. If the gateway waits forever, a small slowdown can tie up resources and make unrelated requests fail.

The distributed design lives in this gap between the product story and the evidence story. The product story says, "The user changed a profile field." The evidence story says, "The gateway sent request op-413, timed out after 800 ms, and does not yet know whether the profile service wrote version 52." A reliable design gives that gap a name and a repair path.

Latency Budgets

Once a system can be late, it needs a rule for how long to wait. A latency budget is that rule: the amount of time a participant is willing to spend before choosing another behavior. It is not only a number in a config file. It is part of the product promise. A checkout page, search box, bank transfer, multiplayer game, and incident alert can all need different budgets because users and downstream systems need different guarantees.

Those budgets should come from the shape of latency, not only from the average. If most calls finish in 40 ms but ordinary slow calls take 900 ms, a 100 ms timeout will turn normal tail latency into artificial failure. If a timeout is so long that callers pile up while waiting, one slow dependency can consume threads, connections, memory, or worker slots and cause a larger outage.

The budget also has to be shared across the whole path. If a user request has a two-second product budget, the gateway cannot safely give every downstream dependency two seconds of its own. Each hop spends part of the remaining time. Good systems pass deadlines or budget context so downstream services know whether useful work is still possible.

product budget: 2000 ms

gateway work:       100 ms
profile timeout:    700 ms
cache fallback:     150 ms
render response:    100 ms
reserved slack:     950 ms

The exact numbers are less important than the habit. A timeout should express what the caller will do next, not merely how impatient the caller feels.

Partial Failure

Partial failure is harder than total failure because the system still has enough working parts to make decisions. A dead process is often obvious. A slow process, isolated region, full queue, stuck connection pool, stale cache, or one-way packet loss is harder. Some requests may succeed while others time out. One observer may see health checks pass while another sees user-facing errors.

This means every participant should separate local fact from remote inference:

local fact:
  I sent request op-413 at 12:00:01.
  I stopped waiting at 12:00:02.

remote inference:
  The profile service might not have updated.
  The profile service might update later.
  The response might have been lost.

Designs become clearer when they store enough evidence to recover. A stable operation id lets a retry mean "continue the same logical action" instead of "start a new action." A version number lets the service reject an update based on stale state. A durable status such as pending_confirmation is more honest than a boolean that pretends the outcome is already known.

The system also needs to decide who owns the official state. If the profile service owns profile updates, the gateway should not invent a final answer that contradicts the profile service's durable record. It can show an uncertain state, schedule a read-after-timeout, or ask the user to refresh, but it should not pretend to know what only the owner can know.

Retry Pressure

Retries are useful because many failures are temporary. They are dangerous because they add traffic exactly when a dependency may already be slow. A retry storm happens when many callers time out and retry together, doubling or tripling load against the same struggling service. The original slowdown can become a wider incident.

Safe retry design connects four decisions:

  • Identity: how does the receiver know two attempts are the same logical operation?
  • Budget: how many retries are allowed before the caller chooses another behavior?
  • Spacing: how does the caller avoid retrying in lockstep with everyone else?
  • Meaning: what should the user or downstream system believe while the outcome is unknown?

Backoff and jitter help with spacing. Idempotency keys help with identity. Deadlines help with budgets. A named status helps with meaning. None of those tools replaces the design question: what promise must survive if the first answer is missing?

For the profile example, the gateway might send operation_id=op-413. If it times out, it can retry with the same id. The profile service can return the existing result if it already applied the operation. If the operation is still unknown, the gateway can show "updating" and reconcile later. The user-visible promise becomes: "The system will not silently apply two different profile changes because one response was late."

Failure Modes and Misconceptions

The first misconception is that a timeout means failure. A timeout means the caller stopped waiting. The remote work may still be absent, queued, active, complete, or complete with a lost response.

The second misconception is that average latency describes user experience. Distributed systems often fail in the tail. The rare slow requests can consume shared resources, trigger retries, and create visible incidents even when the average looks fine.

The third misconception is that partial failure is an implementation detail hidden below the product. It becomes product behavior whenever a user sees a pending state, duplicate action, stale page, delayed notification, failed checkout, or support case.

The fourth misconception is that "just retry" is a complete policy. Retrying without identity, budget, spacing, and repair can turn uncertainty into duplicated work or overload.

Key Takeaways

  • A network boundary turns a call into message exchange under uncertainty.
  • Latency is a distribution, so tail behavior matters.
  • A timeout is a local decision to stop waiting, not proof about remote state.
  • Partial failure means some parts keep acting while others are slow, isolated, or ambiguous.
  • Retries need identity, budgets, spacing, and a user-visible meaning.
  • Good designs preserve a named promise while the outcome is unknown.
