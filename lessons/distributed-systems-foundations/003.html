Fault Tolerance, Retries, and Idempotency

Core Insight

Imagine buying a book online. You press Pay once. The page waits, then says something went wrong. Behind the page, the payment service may already have sent the charge to the card provider. What should the store do now?

If it blindly sends a second charge, the customer may pay twice. If it never tries again, the order may stay stuck even though the customer still wanted the book. The system has to preserve one user-visible promise while the evidence is incomplete: one customer intent should produce at most one successful charge.

That is the practical meaning of fault tolerance in this lesson. Fault tolerance means the workflow keeps its important promise when ordinary faults happen: timeouts, process restarts, duplicate messages, lost responses, slow queues, or late provider callbacks.

The key mechanism is idempotency. An operation is idempotent when repeating the same logical request does not repeat the side effect. For a payment, a retry with the same idempotency key should continue or return the original payment attempt, not create a second charge.

Retries are therefore useful only when they are part of a larger policy. The system needs stable operation identity, receiver-side memory, bounded retry behavior, and a repair path for cases that cannot finish inside the live request.

From Timeout To Policy

Use a checkout flow as the worked example. The customer submits order order-42. The gateway asks the payment service to authorize the card. The payment service calls the external provider. The provider accepts the charge, but the response back to the gateway arrives too late.

customer intent:
  buy order-42 once

gateway:
  -> payment service: authorize order-42
  <- ? timeout

payment service:
  -> provider: charge card
  <- provider: accepted
  -> local record: order-42 charged

From the gateway's local view, the request did not produce a timely answer. From the payment service's local view, the charge may already be successful. From the customer's view, the store should not turn uncertainty into either a duplicate charge or a lost order.

A safer design gives the payment attempt a stable identity:

idempotency key: pay:order-42

attempt 1:
  gateway -> payment service: authorize, key=pay:order-42
  gateway <- timeout

attempt 2:
  gateway -> payment service: authorize, key=pay:order-42

receiver behavior:
  if key is new: start the operation and store the key
  if key succeeded: return the stored result
  if key is still running: return pending
  if key was reused with different details: reject it

The idempotency key does not make the network reliable. It gives the receiver a way to see that two messages represent one logical intent.

Idempotency As A Contract

Idempotency is a contract between caller and receiver. The caller promises to reuse the same key for repeated attempts of the same logical operation. The receiver promises to check durable state before applying the side effect again.

For payments, the side effect is the charge. For a message system, it might be delivering one message to one conversation. For a seat booking system, it might be reserving one seat. The identity should match the promise. A key such as pay:order-42 is useful because it names the payment attempt for one order. A random per-attempt request id is not enough.

This distinction matters:

trace id:
  useful for following one attempt through logs
  may change on each retry

idempotency key:
  useful for preserving one logical operation
  must stay the same across retries of that operation

The receiver also needs to remember enough about the original request. If a client reuses pay:order-42 but changes the amount or currency, the service should reject the duplicate instead of treating it as the same payment. Otherwise the key can hide a real conflict.

Idempotency also has a lifetime. Keeping keys forever may be expensive. Expiring them too early may let a late retry create a duplicate side effect. The right retention window depends on how long retries, callbacks, queues, and human repair can continue.

Retry Policy

Retries recover from temporary faults. They also add load at the exact moment when a dependency may already be slow. A retry policy must therefore answer four questions.

  • Identity: how does the receiver know this is the same logical operation?
  • Budget: how many attempts fit inside the user-facing deadline?
  • Spacing: how do callers avoid retrying at the same instant?
  • Meaning: what does the product show while the result is unknown?

Backoff helps with spacing by waiting longer between attempts. Jitter helps by adding small randomness so many callers do not retry in lockstep. A deadline stops stale work from continuing after the result is no longer useful to the product.

payment deadline: 3 seconds

attempt 1 at 0 ms
attempt 2 after 200 ms plus jitter
attempt 3 after 600 ms plus jitter
then stop live retries and mark payment_pending

This policy makes a trade-off explicit. The system tries to complete temporary failures quickly, but it does not let retries grow without bound. If the payment remains uncertain after the deadline, the workflow moves into a repairable state instead of pretending that the answer is known.

Repair When The Live Path Cannot Finish

Some failures last longer than a web request. The user may close the page. The provider callback may arrive minutes later. A worker may restart after writing one record but before publishing the next event.

That is why fault-tolerant workflows need durable states. A state such as payment_pending or needs_reconciliation tells the system that the operation is neither lost nor complete. It is waiting for more evidence.

One simple state machine might look like this:

new
  -> authorizing
  -> charged
  -> order_confirmed

authorizing
  -> payment_pending
  -> failed_safely

payment_pending
  -> charged
  -> failed_safely
  -> needs_human_review

The exact names depend on the product. The useful habit is separating product state from evidence state. "The gateway timed out" is evidence. It is not the same as "the payment failed." "The provider accepted the charge" is evidence. It still needs to be joined with order state before the customer promise is complete.

Reconciliation is the repair loop that joins those pieces later. It may ask the payment service for the final status, read provider receipts, compare order records, and choose the next safe transition. Repair is not a failure of design. It is how the design admits that distributed evidence can arrive late.

Failure Modes And Trade-offs

The first failure mode is duplicate side effects. Retrying an operation without a stable identity can repeat the work that matters most: charging a card, sending an email, booking a seat, or creating a shipment.

The second failure mode is a retry storm. If many callers time out and immediately retry, they can multiply traffic against the dependency that is already struggling. Backoff, jitter, deadlines, and circuit breakers reduce this risk, but they do not replace a clear product policy.

The third failure mode is hiding uncertainty behind a boolean. A field such as paid=true or paid=false may be too small for a workflow that can be authorizing, charged but not confirmed, failed safely, waiting for provider evidence, or under review.

The main trade-off is between responsiveness and certainty. Waiting for stronger evidence can reduce ambiguity, but it may make the product feel slow or unavailable. Showing pending quickly keeps the interface responsive, but it requires honest repair and communication. Rejecting new work during overload protects capacity, but it reduces availability. The right choice depends on which promise would be most costly to break.

Practice Prompt

Pick one workflow with a visible side effect: charging a card, sending a notification, creating an account, reserving a seat, or submitting a form. Write these lines:

user-visible promise:
side effect owner:
idempotency key:
retry budget:
state after live retries stop:
repair evidence:

If the idempotency key changes on every attempt, it is not protecting the logical operation. If the state after retries is only failed, ask whether the system really knows that the side effect did not happen.

Key Takeaways

  • Fault tolerance protects a user-visible promise when ordinary faults interrupt the happy path.
  • Retries are safe only when the receiver can recognize repeated attempts as one logical operation.
  • Idempotency needs durable receiver-side records, not just a random request id.
  • When live retries cannot finish, named pending states and reconciliation preserve the workflow without pretending certainty.
