Observability Basics for Backend Services

By the end of this lesson, you will be able to... Choose useful logs, metrics, traces, and events for a backend request; connect observability to user-visible promises; and diagnose why a service with "lots of logs" can still be hard to operate.

Idea in one sentence. Observability is the evidence a backend emits so operators can explain what happened to a request, dependency, or release without guessing from symptoms alone.

Core Insight

Imagine the orders API starts returning intermittent 500 responses after a release. The logs show stack traces, but they do not include request IDs, route names, customer or tenant context, release version, payment provider result, or database timing. Operators can see that errors happened. They cannot reliably answer which requests failed, whether checkout is broken for everyone, whether one dependency is slow, or whether the new release caused the spike.

This is not a lack of text. It is a lack of usable evidence. A backend can print thousands of lines and still be poorly observable if those lines do not connect symptoms to the system's real boundaries. The useful question is not "do we log?" It is "could a person explain one failed request from client contract through handler, database, dependency, and response?"

Observability is the practice of designing the service to emit evidence about its behavior. The common pillars are logs, metrics, and traces. Many systems also use structured events, audit records, and deployment metadata. These are tools for reconstructing what happened, noticing when promises are failing, and deciding where to look next.

The beginner mistake is to add observability only after an incident, one print statement at a time. Better instrumentation starts from user-visible promises: checkout should succeed, authenticated users should be denied correctly, order reads should be fast enough, and releases should not increase error rates. The service should emit signals around those promises before failure forces guesswork.

The central trade-off is signal richness versus noise, cost, and privacy risk. More data can help, but unbounded logs, high-cardinality metrics, full request bodies, and secret-bearing traces can become expensive or dangerous. Good observability is selective, structured, and connected to decisions.

The Visible Pieces

Use one recurring scenario: POST /orders sometimes fails after a release that changed idempotency and payment authorization.

The request path includes:

client request
  -> route POST /orders
  -> auth and validation
  -> database transaction
  -> payment provider call
  -> API response

Useful observability pieces include:

  • Logs: discrete records of what happened, ideally structured with fields.
  • Metrics: numeric measurements over time, such as request count, error rate, and latency.
  • Traces: connected spans that show work across components for one request.
  • Structured events: meaningful domain or operational facts, such as order_created or payment_authorization_failed.
  • Correlation IDs: identifiers such as request_id or trace_id that connect evidence across logs, traces, and responses.
  • Release metadata: version, image digest, migration version, and feature flag state.
  • Alerts: notifications tied to symptoms that need action.

Those pieces should answer different questions. A metric can tell you checkout failures increased at 10:05. A trace can show the payment call took four seconds. A log can show the provider returned a timeout for request_id=req_481. A structured event can show no order was committed. Release metadata can show version abc123 started at 10:02.

A Request Evidence Trace

Trace a successful checkout request with evidence:

client receives request_id=req_481
  -> log: route_started route=POST /orders request_id=req_481 release=abc123
  -> metric: http_requests_total{route=POST /orders,status=started}
  -> trace span: validate_json duration=4ms
  -> trace span: authorize_user duration=8ms
  -> trace span: db.transaction duration=35ms
  -> trace span: payment.authorize duration=180ms
  -> event: order_created order_id=ord_1001 payment_status=authorized
  -> metric: http_request_duration_ms{route=POST /orders,status=201}
  -> log: route_finished status=201 duration_ms=252

Now trace a failure:

client receives request_id=req_982 and status=500
  -> log: route_started route=POST /orders request_id=req_982 release=abc123
  -> trace span: db.transaction duration=41ms status=ok
  -> trace span: payment.authorize duration=3000ms status=timeout
  -> event: payment_authorization_failed provider=payco reason=timeout
  -> log: route_failed status=500 error_code=payment_timeout request_id=req_982
  -> metric: checkout_failures_total{reason=payment_timeout}

This is a much better operating position than "stack trace in a file." The request ID lets support connect a user report to server evidence. The trace shows where time went. The metric shows whether it is one request or a trend. The event says what domain step failed. The release field helps compare before and after deploy.

So far, observability is not a dashboard collection. It is a designed evidence path through one request.

Logs, Metrics, Traces, and Events

Logs are best for discrete facts that need detail. Prefer structured logs over free-form strings when possible:

level=error
event=payment_authorization_failed
request_id=req_982
route=POST /orders
provider=payco
duration_ms=3000
error_code=timeout
release=abc123

Avoid logging secrets, raw tokens, full payment payloads, passwords, or private request bodies. Redaction should be deliberate, not a hope that nobody logs the wrong field.

Metrics are best for trends and alerting. They should have bounded labels. Good labels include route template, status class, dependency name, and error category. Dangerous labels include raw URL, customer email, order ID, request ID, or arbitrary exception message. Those create high cardinality and can make the metrics system expensive or unusable.

Traces are best for following one request through multiple steps. A trace is made of spans. Each span has a name, start time, duration, and attributes. In the orders service, spans might be http.request, auth.check, db.insert_order, and payment.authorize. Traces are especially useful when latency crosses service or dependency boundaries.

Structured events are best for domain facts that matter later. order_created, order_canceled, and payment_authorization_failed are not just debug strings. They are business-relevant evidence. Some events become audit records or analytics inputs, so design them carefully.

Quick check: should request_id be a metric label on every request duration metric?

Answer: no. request_id is high-cardinality and belongs in logs and traces. Metrics need bounded labels so they can aggregate trends cheaply and reliably.

User Promises and Alerts

Observability should start from promises. A backend promise is a behavior users or clients rely on:

POST /orders creates one order or returns a clear recoverable error.
GET /orders/:id returns within an acceptable latency for normal traffic.
Admin product deletion is denied for unauthorized users.
Deployments do not increase checkout failure rate beyond a small threshold.

For each promise, choose signals:

checkout success:
  request count
  success rate
  validation failure rate
  payment timeout rate
  duplicate idempotency conflict rate
  latency percentiles

authorization:
  deny count by action
  suspicious repeated denies
  admin route access failures

release health:
  error rate by release
  restart count
  readiness failures
  database migration version

Alerts should fire on symptoms that require action, not on every internal detail. "CPU is 80%" may matter, but "checkout success dropped from 99.5% to 92%" is closer to the user promise. Internal alerts are useful when they predict user harm, but they should not drown out the signals that describe actual service failure.

The trade-off is cost and attention. Every metric, log, trace, and alert has a maintenance cost. If everything alerts, nothing is trusted. If every request logs a huge payload, debugging becomes expensive and privacy risk rises. Keep the signal tied to decisions: page someone, investigate a release, rollback, tune a dependency, or fix a client contract.

A useful alert often pairs a symptom with likely causes in the investigation path. The page may be "checkout success below threshold," while the dashboard beside it shows payment timeout rate, database error rate, queue age, and the current release. That structure keeps the alert focused on user impact while giving responders a first map of where to look. Do not page separately for every possible cause unless each one needs a different urgent action.

Failure Modes and Signals

Poor observability has recognizable failure modes:

  • Logs have stack traces but no request ID, route, release, or tenant context.
  • Metrics use raw paths or request IDs as labels and explode in cardinality.
  • Traces exist for happy paths but not error paths.
  • Dashboards show infrastructure health but not checkout success or API error contracts.
  • Alerts fire on noisy internals but miss user-visible failure.
  • Sensitive data appears in logs or trace attributes.
  • Release metadata is missing, so incidents cannot be tied to deploys.
  • Background workers emit different evidence from web requests, making queue failures hard to connect.

The corrective move is to instrument boundaries. At the request boundary, record route, status, duration, request ID, and release. At dependency boundaries, record dependency name, operation, duration, and outcome. At domain boundaries, record meaningful events. At release boundaries, record artifact and migration version. The fields should let a human reconstruct the path without reading source code first.

Quick check: an API has logs for every exception but no route name, request ID, or release version. What will be hard during an incident?

Answer: connecting one user report to a specific request, grouping failures by endpoint, and determining whether the errors correlate with a release. The logs contain errors but weak operational context.

Background workers need the same discipline, even though there may be no live HTTP client waiting for a response. A checkout request may enqueue authorize_payment or send_receipt. If that worker fails silently, the API may have returned 202 Accepted while the real workflow stopped later. Good worker observability carries the originating request ID or trace ID when possible, adds a job ID, records queue name, attempt number, delay, duration, and final outcome, and emits a domain event when the job changes business state.

For example:

event=job_started job=authorize_payment job_id=job_77 request_id=req_982 attempt=1
event=payment_authorization_failed job_id=job_77 order_id=ord_1001 reason=timeout
event=job_retry_scheduled job_id=job_77 next_attempt_in_ms=30000

This evidence answers a different operational question from a web request log. It tells you whether accepted work is draining, retrying, stuck, or failing permanently. Useful worker metrics include queue depth, oldest job age, success count, retry count, dead-letter count, and processing latency. Those signals prevent a backend from looking healthy at the HTTP edge while background work quietly piles up.

Readiness Check

Close the lesson and design observability for this incident:

Symptom:
  After release abc123, POST /orders returns intermittent 500s.

Known path:
  validation -> auth -> database transaction -> payment provider -> response

Support has:
  a user screenshot with request_id=req_982

Use this rubric:

  • Name three log fields you need.
  • Name two metrics that show whether this is widespread.
  • Name one trace span that would localize latency or failure.
  • Name one sensitive field that should not be logged.
  • Name one alert condition tied to user-visible behavior.

A solid answer might ask for request_id, route, status, release, error_code, dependency name, and duration in logs. Metrics could include checkout failure rate, payment provider timeout rate, and latency percentiles by route. A useful trace span is payment.authorize with duration and safe error category. Raw bearer tokens, payment keys, card data, and full request bodies should not be logged. A good alert condition is checkout success rate dropping below an agreed threshold after release abc123.

Key Takeaways

  • Observability is designed evidence, not just more log lines.
  • Logs, metrics, traces, and events answer different questions and should be connected by request, trace, release, and domain identifiers.
  • Good signals start from user-visible promises such as checkout success, latency, authorization correctness, and release health.
  • More observability is not automatically better; useful instrumentation balances signal, cost, cardinality, and privacy.
