Git, Branches, and Reviewable Change History

By the end of this lesson, you will be able to... Explain how commits, branches, diffs, and reviews turn backend work into inspectable units; split a risky backend change into reviewable steps; and identify what evidence a reviewer needs before trusting a change.

Idea in one sentence. Git is not only a save button for code; it is a structured history of intent, and good backend work uses that history to make risky changes small enough to inspect.

Core Insight

Imagine the orders API again. It now starts reliably, and the team wants to add a new field called delivery_window to every order. The change sounds simple: add a database column, update the API response, change validation, adjust tests, and deploy. One developer puts all of that into a single large branch with dozens of files changed. The tests pass locally, but the reviewer cannot tell which lines create the schema change, which lines change the response contract, and which lines are just formatting.

That is when Git stops being a background tool and becomes an engineering communication surface. Git stores snapshots of the project as commits. A branch lets you build a line of work without mixing it immediately into the main line. A diff shows what changed between two points. A review asks another person or automated system to inspect the change before it becomes shared history.

The beginner shortcut is "commit when the code works." That is better than no history, but it misses the point for backend systems. Backend changes often affect contracts outside one file: database shape, API behavior, startup configuration, tests, deployment order, and rollback options. Reviewers need to understand the change as a sequence of decisions, not as a pile of final text.

The central trade-off is small reviewable changes versus large context-heavy rewrites. Small changes take discipline. You may need to split work, write clearer commit messages, and delay unrelated cleanup. Large changes feel faster while coding, but they transfer the cost to review, debugging, rollback, and future archaeology.

The Visible Pieces

Use one recurring scenario: add delivery_window to the orders API without breaking existing clients.

There are several moving pieces:

  • The working tree is the files currently on disk.
  • The staging area is the set of changes selected for the next commit.
  • A commit is a recorded snapshot with metadata and a parent pointer.
  • A branch is a movable name pointing at a commit.
  • A diff is a comparison between two versions of files.
  • A remote is another copy of the repository, often on a shared server.
  • A pull request or merge request is a review conversation around a branch.

Those pieces matter because they separate three activities that often blur together: editing, recording, and sharing. Editing changes the working tree. Recording creates commits. Sharing pushes a branch so other people and systems can inspect it.

For a backend developer, the useful question is not "did I use Git?" It is "can someone inspect the intent and risk of this change without reconstructing my whole afternoon?" If the answer is no, the history is technically present but not reviewable.

A Change Walkthrough

Start with a naive path:

edit schema + edit handler + edit response + edit tests + reformat files
  -> one commit: "update orders"
  -> one large diff
  -> reviewer must infer every decision at once

The change may work, but the evidence is hard to inspect. A reviewer sees database migration, API contract changes, test updates, and unrelated formatting in one unit. If production later fails, git log shows "update orders," which says little about what decision introduced the risk.

A more reviewable path separates the work:

branch: delivery-window
  -> commit 1: add nullable delivery_window column
  -> commit 2: read and write delivery_window in order model
  -> commit 3: expose delivery_window in API response
  -> commit 4: add tests for old and new response shapes
  -> review: inspect migration, behavior, and compatibility

Now each commit answers a smaller question. Does the migration safely add storage? Does the backend model handle missing values? Does the API response remain compatible with clients that do not expect the new field? Do tests prove the intended behavior?

The formal term to learn here is atomic commit. In practical backend work, an atomic commit is a commit that represents one coherent change that can be explained, reviewed, and, if necessary, reverted without dragging in unrelated work. It does not always mean one file. It means one reason.

For example, a commit that changes a migration file, one model, and one migration test can still be atomic if all three support the same storage change. A commit that changes the migration, renames a utility, updates CSS, and reformats half the repository is not atomic, even if it passes tests.

Reading the Diff Like a Reviewer

The diff is the reviewer's primary artifact. It shows what changed, but it does not automatically explain why. Your job as the author is to make the diff easy to trust.

Suppose the reviewer sees this simplified migration:

+ ALTER TABLE orders ADD COLUMN delivery_window TEXT;

That line raises real backend questions:

  • Is the column nullable, or will old rows fail?
  • Is there a default value?
  • Do existing API clients need this field immediately?
  • Is the deployment order safe if old code and new schema overlap?
  • Is there a rollback plan if the API change is wrong?

Those questions are not nitpicks. Backend systems have state. Once a database migration runs, the world may not return to the exact previous shape just because a Git commit is reverted. A good reviewable history makes the state transition visible.

Here is a better pull request description for this beginner-level change:

Change:
  Add optional delivery_window to orders.

Deployment order:
  1. Add nullable column.
  2. Deploy code that reads and writes the column.
  3. Start sending delivery_window in responses after clients tolerate it.

Compatibility:
  Existing orders keep delivery_window = null.
  Existing clients may ignore the extra JSON field.

Evidence:
  Added model test for missing delivery_window.
  Added API response test for delivery_window present.

Notice what happened: Git did not replace engineering judgment. It gave the team a place to record and inspect that judgment.

Quick check: if a pull request changes a database migration and reformats unrelated files, what should you ask for first?

Answer: split unrelated formatting from the migration work. The reviewer needs to inspect the state change without noise from unrelated edits.

Branches as Isolation, Not Hiding Places

A branch is useful because it gives work a temporary line of history. You can make commits, push them, get feedback, and adjust before merging. But a branch is not a place to hide ambiguity until the end.

Think of a branch as a draft of shared history. While you are still exploring, rough commits are fine. Before review, the branch should tell a coherent story:

main
  A---B---C
           \
delivery-window
            D---E---F

Commits D, E, and F should be understandable as steps away from C. If D is "try stuff," E is "fix," and F is "more fixes," the final code might work, but the history does not help review. You can clean that up before sharing by editing commits, squashing exploratory noise, or creating a fresh branch with a clearer sequence. The exact Git commands are less important than the goal: review should inspect deliberate change, not your scratchpad.

There is a limit. Do not rewrite history that other people are already depending on unless your team agrees. Locally, before review, history cleanup is usually fine. On a shared branch where others have based work, rewriting can confuse collaborators. The safe beginner rule is: clean your own unpublished or review branch; be careful with shared branch history.

What Review Protects

Code review is not only a style check. In backend work, review protects system boundaries.

A reviewer may ask:

  • Does this change preserve the API contract for existing clients?
  • Does it change database state safely?
  • Does it require a specific deployment order?
  • Does it update tests at the right boundary?
  • Does it make startup configuration or operational behavior clearer?
  • Does the commit message explain intent, not just file names?

This connects to the earlier lessons. The request path taught you that failures happen across boundaries. The process lesson taught you that startup depends on explicit inputs. Git adds another boundary: the boundary between private work and shared system history. Once a change is merged, teammates, CI, deployment tools, and future debuggers treat it as part of the system's record.

The operational signal for poor history often appears later. A production bug happens, someone runs git log or git blame, and every clue says "misc fixes." The code is present, but the reason is gone. Good history keeps enough intent that future debugging can ask, "What changed, when, and why?"

Quick check: should every tiny syntax correction be a separate commit?

Answer: no. Reviewability is about coherent reasons, not maximum commit count. A small fix belongs with the change it supports if it helps that same reason. It should be separate when it creates a different risk or distracts from the main review.

Failure Modes

Several habits make Git history less useful:

  • Vague commit messages: fix stuff gives future readers no decision to inspect.
  • Mixed concerns: one commit changes schema, route behavior, unrelated formatting, and test setup.
  • Review after the fact: the branch is treated as done before feedback can shape it.
  • Hidden generated changes: generated files or lockfiles change without explanation.
  • Unsafe rollback assumptions: the author assumes reverting code also reverts database reality.

The corrective pattern is to make the unit of review match the unit of risk. If a change affects API compatibility, show that as a review topic. If a migration affects persistent state, isolate it and explain deployment order. If formatting is needed, do it separately. If tests prove compatibility, place them where the reviewer can connect them to the behavior.

Readiness Check

Close the lesson and split this backend task into reviewable commits:

Task:
  Add "archived" orders.
  Archived orders should not appear in the default list endpoint.
  Admins can still fetch archived orders by ID.

Use this rubric:

  • Name two to four commits.
  • Keep each commit tied to one reason.
  • Include at least one test or evidence commit.
  • Say what the pull request description must warn reviewers about.

A solid answer might be:

commit 1: add nullable archived_at column to orders
commit 2: update order list query to exclude archived orders by default
commit 3: preserve admin fetch-by-id behavior for archived orders
commit 4: add tests for default list and admin lookup

The pull request description should call out the data change, the default API behavior change, and the compatibility question: clients using the list endpoint will stop seeing archived orders by default.

Key Takeaways

  • Git history is an engineering communication surface, not just a backup of files.
  • Reviewable commits group changes by coherent reason and risk.
  • Branches isolate work temporarily, but a branch should become a clear story before review.
  • Backend reviews must make state, API compatibility, deployment order, and test evidence visible.
