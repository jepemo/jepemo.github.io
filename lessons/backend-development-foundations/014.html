CI/CD, Migrations, and Release Checks

By the end of this lesson, you will be able to... Trace a backend release from commit to production; explain why database migrations need compatibility windows; and choose release checks that reduce blast radius without pretending deployment is risk-free.

Idea in one sentence. CI/CD turns delivery into a controlled state transition: build the artifact, verify evidence, coordinate code and data changes, roll out gradually, and stop when signals show the system is not healthy.

Core Insight

Imagine the orders API adds a new required database column, orders.idempotency_key, after the JSON API lesson made idempotency part of checkout. A migration adds the column as NOT NULL. The migration reaches production while some old application instances are still running. Those old instances do not write idempotency_key, so checkout starts failing.

No single developer typed "break production." The failure came from release ordering. Code and database state changed as if every part of the system moved at once, but production is usually a transition. Some instances may run old code while new code starts. Some requests may arrive during rollout. Migrations may complete before or after application deploys. Queues may still contain old message shapes.

CI/CD is the set of practices and automation that move a change from commit to running service. Continuous integration checks that a change can build and pass tests with the rest of the code. Continuous delivery or deployment prepares and sometimes automatically releases the verified artifact. For backend systems, delivery also includes migrations, configuration, container artifacts, rollout gates, and operational checks.

The beginner mistake is to think a green CI build means the release is safe. A green build is evidence, not a guarantee. It may prove tests passed on one artifact. It may not prove a migration is compatible with old code, that the readiness check is meaningful, that rollback can handle data changes, or that production traffic behaves like test fixtures.

The central trade-off is release speed versus blast-radius control. Fast releases reduce batch size and help teams fix problems quickly. Controlled releases add checks, gates, staged rollout, and sometimes manual judgment. The goal is not to slow everything down. The goal is to know which state transition is happening and what signal would make you stop.

The Visible Pieces

Use one recurring scenario: the orders service releases idempotency support for POST /orders.

The intended change includes:

application:
  require idempotency_key in new checkout requests
  store idempotency_key with order
  reject duplicate key safely

database:
  add orders.idempotency_key
  eventually enforce uniqueness

delivery:
  build image
  run tests
  apply migration
  roll out new app instances
  watch checkout errors and duplicate attempts

The visible CI/CD pieces are:

  • Commit: the source change to code, tests, migration, and docs.
  • Build: creation of the deployable artifact, such as a container image.
  • Test stages: unit, integration, contract, security, and migration checks.
  • Artifact registry: where the built image or package is stored.
  • Migration step: database schema or data change.
  • Deployment step: updating running service instances.
  • Rollout strategy: all-at-once, rolling, canary, blue/green, or staged by environment.
  • Release checks: automated or human gates based on evidence.
  • Rollback or roll-forward plan: what happens if the release fails.

The important thing is ordering. A backend release is not just "merge and deploy." It is a set of state transitions across code, artifact, configuration, database, and traffic.

A Safe Migration Shape

The dangerous migration is:

ALTER TABLE orders ADD COLUMN idempotency_key text NOT NULL;

This assumes every writer immediately supplies the new column. In a running production system, that assumption is often false. Old application instances, background workers, scripts, or queued jobs may still write orders without the new field.

A safer shape is often called expand and contract. First expand the database so both old and new code can run. Then deploy new code. Then contract once old paths are gone.

For idempotency:

Step 1: Expand schema
  add nullable idempotency_key column
  add non-enforced or partial supporting index if needed
  old code still writes orders successfully

Step 2: Deploy compatible code
  new code writes idempotency_key when present
  API validates new clients according to contract
  old workers still tolerate nullable column

Step 3: Backfill or handle existing rows
  decide what historical orders should contain
  populate safe values if required

Step 4: Enforce rule
  add uniqueness or NOT NULL only when all writers comply
  remove old compatibility code after evidence confirms no old writers

This is not the only migration pattern, but it teaches the mechanism: database changes and application changes need a compatibility window. The database must temporarily support both the old and new shape when rollout is not instantaneous.

So far, the release is a sequence of compatible states, not a leap from old world to new world.

Build and Test Evidence

CI should produce evidence that matches the risk. For the idempotency release, useful checks include:

  • Unit tests for duplicate-key decision logic.
  • API contract tests for the new required field and error shape.
  • Integration tests with a real database for creating and retrying orders.
  • Migration tests that apply schema changes to a database shaped like the previous release.
  • A check that the deployable image starts and validates configuration.
  • Static or dependency checks if the repo has those gates.

A test that passes against a fresh empty database may miss migration risk. Production does not start empty. It has old rows, current indexes, data volume, and sometimes long-running locks. A migration test should ask: can this change apply to the previous schema, with representative data, without breaking old code during the transition?

The artifact matters too. If CI runs tests on source code but production deploys a newly built image, the artifact boundary is weak. A stronger path builds once, tags the image immutably, tests that artifact or equivalent output, and promotes it through environments with environment-specific configuration.

Quick check: if a migration test only creates a brand-new database from the final schema, what production risk does it miss?

Answer: it misses upgrade risk. Production moves from the previous schema to the new schema with existing data and running code. A fresh schema test does not prove the transition is safe.

Rollout Gates and Blast Radius

Rollout strategy controls how much traffic sees the new release before you trust it broadly.

Common shapes:

  • All-at-once: replace every instance quickly. Simple, but high blast radius.
  • Rolling deploy: replace instances gradually. Requires old and new versions to coexist.
  • Canary: send a small slice of traffic to the new version first.
  • Blue/green: prepare a full new environment, then shift traffic.
  • Manual approval gate: pause until humans inspect evidence.

For a beginner foundation, the most important idea is not to memorize names. It is to connect rollout to evidence. If checkout is critical, a canary or staged rollout might watch:

checkout success rate
validation_failed rate
duplicate idempotency conflict rate
payment authorization error rate
database error rate
latency percentiles
container restart count

If those signals move badly, the release should stop. A gate is not a ritual. It is a decision point with a threshold and an owner.

Blast-radius control has a cost. Too many gates can slow harmless changes and encourage people to bypass the system. Too few gates can let a bad migration affect every request. Good teams tune gates to the risk of the change: a README edit should not need the same release ceremony as a checkout schema migration.

Rollback Is Not Always Undo

Rollback means returning service behavior to a safer state. It does not always mean reversing every change.

Code rollback can be straightforward: redeploy the previous image. Data rollback is harder. If a migration deleted a column, transformed data destructively, or wrote new values that old code cannot understand, simply redeploying old code may not work.

For the idempotency release, a rollback-aware design asks:

If new app code fails:
  can old code still run with idempotency_key column present?

If the migration succeeds but rollout fails:
  can the column remain nullable while old code runs?

If new code wrote idempotency_key:
  does old code ignore the extra column safely?

If uniqueness constraint causes lock or error:
  can enforcement be paused without losing data?

This is why expand-and-contract helps rollback. Adding a nullable column is usually easier to live with than adding a required column immediately. Backward-compatible database changes give you more options when application rollout fails.

Sometimes the safer action is roll forward: ship a small fix that works with the new schema instead of trying to reverse data changes. The release plan should say which path is expected before the incident starts.

Quick check: after adding a nullable column, the new app fails for unrelated reasons. Can old app instances usually keep running?

Answer: often yes, if old code ignores the extra nullable column and the migration did not break existing reads or writes. That is the point of the expand step.

Failure Modes and Signals

Release failures usually involve mismatched state:

  • Migration requires a field before every writer supplies it.
  • New code expects a column before the migration has reached all environments.
  • Old and new instances cannot coexist during a rolling deploy.
  • CI tests a different artifact than production deploys.
  • Migration locks a large table longer than the service can tolerate.
  • Rollback plan assumes data changes are reversible when they are not.
  • Release checks watch generic CPU while the real risk is checkout failure.
  • Manual approval happens without concrete evidence.

Operational signals should connect release identity to service behavior. Track release version, image digest, migration version, deploy start time, error rates, latency, database locks, failed jobs, restart counts, and business-level success metrics for the affected workflow. When an incident happens, you need to answer: what changed, where is it running, which migration version is applied, and what user-visible promise is failing?

The limit is that no release system removes judgment. Automation can build, test, deploy, stop rollout, and surface signals. Engineers still need to design compatible changes and choose meaningful gates.

Readiness Check

Close the lesson and review this release plan:

Change:
  Add orders.idempotency_key as NOT NULL.
  Deploy new app code that writes idempotency_key.
  Rolling deploy across 10 instances.

Current reality:
  Old app instances will run during rollout.
  Background worker can still create orders.
  Existing orders do not have idempotency_key.

Use this rubric:

  • Identify the compatibility problem.
  • Propose an expand-and-contract sequence.
  • Name one migration test.
  • Name one rollout signal.
  • State whether rollback to old code is safe after the first migration.

A solid answer might say: adding NOT NULL immediately breaks old writers and existing rows. Expand first by adding a nullable column, deploy code that writes it, update background workers, backfill or decide historical values, then enforce uniqueness or non-null when all writers comply. A migration test should apply the migration from the previous schema with existing orders. Rollout should watch checkout success, database errors, idempotency conflicts, and worker failures. Rolling back to old code after adding a nullable column is usually safe if old code ignores the column.

Key Takeaways

  • CI/CD is a controlled delivery path from commit to artifact to running service, not just a green test badge.
  • Database migrations need compatibility windows when old code, new code, workers, and existing data can coexist.
  • Release gates should watch signals tied to the actual risk of the change, such as checkout success for checkout releases.
  • Rollback is easy for some code changes and hard for data changes; migration shape decides how many recovery options remain.
