Authentication, Authorization, and Session State

By the end of this lesson, you will be able to... Separate authentication from authorization; trace how session state turns a login into repeated backend requests; and identify where stale roles, missing resource checks, and unsafe token handling create security bugs.

Idea in one sentence. Authentication proves who the caller is, authorization decides what that caller may do, and session state carries that evidence between requests with trade-offs around scale, revocation, and freshness.

Core Insight

Imagine the orders API now has a staff dashboard. A staff member signs in and sees POST /admin/products, DELETE /admin/products/:id, and GET /admin/orders/:id. The team added login, so every admin request must include a session cookie or bearer token. During a review, someone finds a bug: a logged-in support user can delete products even though only catalog admins should do that.

The login check worked. The caller was real. The failure was that the backend confused "we know who this is" with "this person may do this action." Those are different decisions. Authentication answers, "Who is the caller, and how did they prove it?" Authorization answers, "Given that caller, this action, this resource, and current policy, should the backend allow it?"

Session state is the bridge between those questions across requests. HTTP requests are independent at the protocol level. A user does not send their password with every click. Instead, after login, the system gives the client some session evidence: often a cookie-backed server session, a signed token, or an opaque bearer token. Later requests present that evidence so the backend can recover identity and apply policy.

The beginner shortcut is to look for one "auth" step. Real systems need several boundaries: credential proof at login, session transport, token or session validation on each request, authorization for the requested action, resource-level checks, and audit context for later investigation. A request can pass one boundary and fail the next.

The central trade-off is stateless scaling versus revocation and policy freshness. A self-contained signed token can be validated without a database lookup, which helps scaling. But if a user is disabled or loses a role, the token may still carry old claims until it expires unless the system checks freshness somewhere. A server-side session can be revoked centrally, but it adds storage and availability concerns. There is no magic choice. There is only a boundary you must understand.

The Visible Pieces

Use one recurring scenario: the staff dashboard sends this request:

DELETE /admin/products/prod_9
Cookie: session_id=sess_abc123

The intended rule is narrow:

Only an active staff user with the catalog_admin role may delete a product,
and the product must not have shipped order history that requires preservation.

The visible pieces are:

  • Credentials: proof supplied at login, such as password plus a second factor, SSO assertion, or another login mechanism.
  • Principal: the authenticated actor, such as staff_user_id=17.
  • Session evidence: a cookie, token, or session ID presented on later requests.
  • Claims: facts carried or looked up about the principal, such as user ID, tenant, roles, or token expiry.
  • Policy: the rule that decides whether an action is allowed.
  • Resource: the thing being acted on, such as product prod_9.
  • Audit context: evidence recorded for later review, such as actor, action, resource, decision, request ID, and time.

Authentication can establish the principal. It does not automatically prove the policy decision. Authorization usually needs at least four inputs:

actor -> action -> resource -> context

For the delete request:

actor: staff_user_id=17, roles=[support_agent]
action: delete_product
resource: product prod_9
context: admin dashboard request, request_id=req_610
decision: deny

The support agent may be authenticated and still denied. That is not a system failure. That is the system enforcing a boundary.

A Request Walkthrough

Trace a successful catalog admin request:

HTTP request
  -> DELETE /admin/products/prod_9
  -> session cookie: sess_abc123

The backend path might run:

parse request
  -> read session cookie
  -> find session record
  -> verify session is active and not expired
  -> load principal staff_user_id=17
  -> load current roles or permissions
  -> route says action is delete_product
  -> load product prod_9
  -> evaluate policy
  -> if allowed, call handler
  -> write audit event
  -> return response

Make the intermediate states visible:

  1. Before authentication, the backend has only a request with a cookie value. A cookie value is not yet a user.
  2. Session validation checks whether sess_abc123 is known, signed or stored correctly, unexpired, and not revoked.
  3. If valid, the backend has a principal: for example, staff_user_id=17.
  4. The route and method identify the intended action: delete_product.
  5. The backend loads the resource so policy can consider the actual product.
  6. Authorization evaluates actor, action, resource, and context.
  7. The handler runs only after the decision is allow.
  8. The audit event records what decision happened and why enough to investigate later.

Now compare a broken path:

parse request
  -> read session cookie
  -> verify session is active
  -> load principal staff_user_id=21
  -> handler deletes product

This path authenticates the caller but never checks whether that caller has the right permission for this product. The bug can hide because local tests often use an admin fixture for every dashboard route. The system seems protected because unauthenticated users are blocked. Authenticated but underprivileged users are the missing case.

So far, the useful distinction is plain: authentication gets an identity into the request; authorization uses that identity to decide on one specific action.

Session State Choices

A backend needs a way to remember login across requests. Three common shapes are server-side sessions, signed cookies, and bearer tokens.

With a server-side session, the client stores an opaque ID:

client cookie: sess_abc123
server store:
  sess_abc123 -> user_id=17, expires_at, revoked=false

The cookie alone does not contain the user's roles. Each request can look up the session and then load current user state. Revocation is straightforward: mark the session revoked or delete it. The cost is that each request depends on the session store, so the store must be fast and available.

With a signed or encrypted cookie, the cookie may carry session facts protected by cryptography. The server can verify the cookie without a central lookup. That can be efficient, but large or stale cookies create risk. If roles are embedded and a user loses a role, old cookies may still say the user has it until expiry unless the system adds freshness checks.

With a bearer token, such as an access token sent in an Authorization header, the rule is simple: whoever presents the token can use it until it expires or is rejected. Some tokens are opaque and require lookup or introspection. Some are self-contained signed tokens. Bearer tokens are common for APIs, but they demand careful storage, short lifetimes for sensitive contexts, and safe logging practices. Never log raw tokens.

The trade-off is visible:

server-side session -> easier central revocation, more shared state
self-contained token -> easier stateless validation, harder immediate revocation
short lifetime -> limits stale access, more refresh complexity
long lifetime -> smoother UX, more damage if stolen or stale

Quick check: a user loses the catalog_admin role, but their token still contains roles=["catalog_admin"] for another six hours. What kind of problem is this?

Answer: policy freshness. The token may be valid cryptographically while its authorization claims are stale. The system needs shorter expiry, role lookup, revocation, token versioning, or another freshness check for sensitive actions.

Authorization Is More Than Roles

Roles are a common starting point: support_agent, catalog_admin, finance_admin. They group permissions so teams do not assign every action one by one. Roles are useful, but they are not enough for every policy.

Consider these two requests:

GET /customers/cus_42/orders
DELETE /admin/products/prod_9

The first might be allowed for a customer only when cus_42 is their own account. The second might be allowed for catalog admins, but only if the product has no shipped order history or if deletion actually means deactivation. These are resource-level rules. They depend on the object, not just the user's role.

A healthy authorization check asks:

  • Who is the actor?
  • What action are they trying to perform?
  • Which resource is affected?
  • What current state matters?
  • Which policy owns the decision?
  • What evidence should be recorded?

This is why putting if user.is_admin inside scattered handlers becomes fragile. One handler checks role. Another forgets resource ownership. A third uses old policy names. Centralizing policy decisions, or at least using consistent policy helpers, makes the boundary reviewable.

For the product delete request, a policy sketch might be:

allow delete_product when:
  actor is active staff
  actor has catalog_admin permission
  product exists
  product has no shipped order references requiring history

otherwise:
  deny with safe error
  record actor, action, resource, decision, request_id

The handler should not run until this decision is made. If deletion is not truly safe, the policy may choose deactivate_product instead of physical deletion. Authorization protects actions, and good domain modeling defines what the action actually means.

Failure Modes and Signals

Authentication and authorization bugs usually come from boundary confusion:

  • Treating "logged in" as enough for admin actions.
  • Checking a broad role but missing resource ownership or tenant boundary.
  • Trusting role claims in a long-lived token after policy changed.
  • Logging session IDs or bearer tokens in request logs.
  • Returning different error details that let attackers learn which accounts exist.
  • Forgetting to audit sensitive allow and deny decisions.
  • Applying authorization only in the UI while the API still accepts direct calls.

Operational signals should separate the stages. Track authentication failures, expired sessions, revoked sessions, authorization denies by action, suspicious repeated denies, token validation failures, and sensitive action audit events. During an incident, ask which boundary failed: credential proof, session validation, current user loading, policy evaluation, or resource-specific rule.

The error contract matters too. Missing or invalid authentication usually maps to 401 Unauthorized. A known caller without permission usually maps to 403 Forbidden. Many systems intentionally return 404 for resources the caller should not know exist. Choose a project rule and apply it consistently so clients and operators know what the response means.

Quick check: a customer changes the URL from /customers/cus_42/orders to /customers/cus_99/orders and sees another customer's orders. Which check failed?

Answer: resource-level authorization. Authentication identified a real customer, but authorization did not verify that the actor may read orders for cus_99.

Readiness Check

Close the lesson and review this request:

PATCH /admin/users/17/roles
Cookie: session_id=sess_support_8
Body: {"add": ["catalog_admin"]}

Use this rubric:

  • Identify the authentication evidence.
  • Name the actor, action, and resource.
  • Decide which policy question must be answered before the handler runs.
  • Name one session freshness risk.
  • Name one audit field that should be recorded.

A solid answer might say: the authentication evidence is the session cookie, but it must be validated before it proves an actor. The actor is the staff user behind sess_support_8, the action is changing roles, and the resource is user 17 plus their role set. The policy must decide whether this actor can grant catalog_admin, not merely whether they are logged in. A freshness risk is that the actor's own roles may have changed after the session or token was issued. The audit event should include actor ID, target user ID, action, old and new role intent, decision, request ID, and timestamp.

Key Takeaways

  • Authentication proves an identity; authorization decides whether that identity may perform one action on one resource.
  • Session state carries identity evidence between requests, but each storage style trades off scale, revocation, and freshness.
  • Roles are useful shortcuts, but sensitive systems also need resource-level and context-aware policy checks.
  • Good auth systems log safe audit evidence and keep secrets such as session IDs and bearer tokens out of ordinary logs.
