JSON APIs, Validation, and Error Contracts

By the end of this lesson, you will be able to... Describe the contract of a JSON endpoint; separate parsing, schema validation, and business validation; and design error responses that let clients decide whether to fix input, retry later, or stop.

Idea in one sentence. A JSON API is a boundary contract: the backend must say what shape it accepts, what rules it enforces, and what each error means for the caller's next action.

Core Insight

Imagine the orders API now has a mobile client. The client sends POST /orders with a JSON body. Most users place orders successfully, but a few see a spinner, then the app retries. Some retries create no order, some create duplicate attempts, and some return a vague body like {"error":"bad request"}. The backend logs show different causes: malformed JSON, missing shipping address, inactive product, and temporary payment provider failure.

To a user, these may all feel like "checkout failed." To a client application, they are different situations. Malformed JSON is a client bug. A missing field is fixable before retry. An inactive product means the app should refresh catalog state. A payment timeout may be retryable, but only if the operation is designed safely. If the API reports all of them with the same status and body, the client cannot choose the right next action.

JSON is only the encoding. The API contract is larger. It includes the HTTP method and path, expected headers, request body shape, allowed field values, response body shape, status codes, and error format. The contract also includes what the server promises not to do, such as accepting unknown dangerous fields silently or leaking internal exception details to clients.

The beginner mistake is to treat validation as one generic "check the input" step. A backend usually needs several checks at different depths. First, can the server parse the body as JSON? Next, does the decoded object match the expected schema? Then, do the values satisfy business rules against current system state? Each failure should map to an error response that carries enough meaning for the client and enough evidence for operators.

The central trade-off is strictness versus compatibility. Strict validation catches mistakes early and keeps stored state clean. Overly rigid contracts can break older clients when a harmless new field appears or when an old client does not know a new optional feature. A good JSON API is explicit about what is required, what is optional, what is ignored or rejected, and how clients should interpret errors.

The Visible Pieces

Use one recurring scenario: a mobile checkout screen sends an order creation request.

POST /orders
Content-Type: application/json
Authorization: Bearer ...

{
  "customer_id": "cus_42",
  "shipping_address_id": "addr_12",
  "items": [
    {"product_id": "prod_7", "quantity": 2},
    {"product_id": "prod_9", "quantity": 1}
  ],
  "idempotency_key": "checkout-2026-06-25-abc123"
}

The visible contract has several parts:

  • The method and path say this request creates an order.
  • Content-Type says the body is JSON.
  • Authentication says who is attempting checkout.
  • The body schema says which fields and types are expected.
  • Validation rules say which values are acceptable.
  • Business rules say whether the referenced products, customer, and address are valid now.
  • The response says whether an order was created, rejected, or not completed.
  • The error body says what the client should do next.

The formal term schema means a declared shape for data. A schema can be documented in OpenAPI, JSON Schema, typed code, validation libraries, or framework declarations. The syntax differs, but the purpose is stable: a schema tells both humans and tools what the body should look like before business logic treats it as trustworthy.

Three Layers of Validation

Trace the request through three validation layers.

Layer 1 is parsing. The server receives bytes and tries to decode JSON.

body bytes -> JSON parser -> decoded object or parse error

If the body is {"customer_id":, the server cannot even inspect fields. This should become a parse error, often 400 Bad Request, with a safe message such as "Request body is not valid JSON." The client cannot fix this by retrying the same bytes later.

Layer 2 is schema validation. The decoded object must match the endpoint's expected shape:

decoded object
  -> customer_id is required string
  -> shipping_address_id is required string
  -> items is required non-empty array
  -> each item has product_id string and quantity integer >= 1
  -> idempotency_key is required string
  -> schema-valid command or field errors

If quantity is "two" instead of 2, or items is empty, the body is syntactically JSON but not a valid order request. Many APIs use 400 or 422 for this category depending on their convention. The exact status matters less than consistency. The body should point to fields the client can correct.

Layer 3 is business validation. The shape is valid, but the requested operation may still be impossible:

schema-valid command
  -> customer exists and matches authenticated caller
  -> address belongs to customer
  -> products exist and are active
  -> requested quantities are available
  -> operation allowed or business error

If product prod_9 is inactive, the client may need to remove it from the cart and refresh catalog data. If the address does not belong to the customer, the request should be rejected even though shipping_address_id has the right type. This is where validation connects to the relational model and query lessons: shape alone cannot prove business state.

So far, validation is a funnel. Bytes become JSON, JSON becomes a schema-valid command, and the command becomes an allowed operation only after business rules check current state.

Designing an Error Envelope

An error contract should be stable enough for clients to code against. A common pattern is an error envelope: one predictable top-level shape used for failures.

For a schema validation failure:

{
  "error": {
    "code": "validation_failed",
    "message": "The request body has invalid fields.",
    "request_id": "req_481",
    "fields": [
      {
        "path": "items[0].quantity",
        "code": "must_be_integer",
        "message": "Quantity must be an integer greater than or equal to 1."
      }
    ]
  }
}

For a business rule failure:

{
  "error": {
    "code": "product_unavailable",
    "message": "One or more products are no longer available.",
    "request_id": "req_482",
    "details": {
      "product_id": "prod_9"
    }
  }
}

The field names are project choices. The design goal is not to copy this exact envelope. The goal is to include stable machine-readable codes, a human-readable message, a request identifier for support, and specific field or detail information when it is safe to expose.

Avoid exposing stack traces, SQL fragments, internal class names, raw tokens, or secret values. Operators need detail in logs and traces. Clients need a safe contract. The request_id connects those worlds without leaking internals.

Quick check: if the client receives code: validation_failed for items[0].quantity, should it retry the same request automatically?

Answer: no. The same invalid body will fail again. The client should correct the field, show feedback, or stop until the user changes input.

Status Codes and Client Decisions

HTTP status codes are part of the contract. They should align with the client's next decision.

Useful beginner categories:

  • 200 or 201: the request succeeded.
  • 400: the request could not be understood or accepted as a valid client request.
  • 401: authentication is missing or invalid.
  • 403: the caller is known but not allowed to do this.
  • 404: the target resource is not visible or does not exist under the API's rules.
  • 409: the request conflicts with current state, such as duplicate idempotency key semantics or version mismatch.
  • 422: the body is well-formed but semantically invalid, if this is your project's convention.
  • 429: the client is rate limited.
  • 500: unexpected server failure.
  • 503: service temporarily unavailable.

Do not use status codes as decoration. A mobile app can use them to choose behavior:

400/422 -> fix request before trying again
401     -> refresh login or ask user to sign in
403     -> stop and show permission problem
409     -> reload state or handle duplicate/conflict path
429     -> wait according to rate-limit guidance
500/503 -> retry only if operation is safe and policy allows

The phrase "safe to retry" hides a real backend requirement. Retrying POST /orders without an idempotency design can create duplicate orders. That is why the request includes idempotency_key. The key lets the server recognize repeated attempts for the same intended checkout and return the same result or a clear conflict instead of running the operation twice.

This connects to error contracts: an error should not merely say "failed." It should help the client know whether the same request is invalid, whether refreshed state is needed, whether identity must change, or whether a careful retry is reasonable.

Compatibility and Versioning Pressure

Strict contracts are useful, but APIs live longer than one release. Mobile clients may remain in the wild for months. Browser code may be cached. Third-party integrations may upgrade slowly. A backend change that feels small can break older clients if the contract was not designed for evolution.

Good compatibility habits include:

  • Add optional response fields without requiring old clients to understand them.
  • Avoid renaming or removing fields without a migration plan.
  • Treat unknown request fields deliberately: reject them for sensitive operations, or ignore them only when that is an explicit policy.
  • Add new required request fields through a versioned endpoint, negotiated feature, or compatibility window.
  • Keep error code values stable even if human messages improve.

The trade-off is visible in unknown fields. Rejecting unknown fields catches typos such as quanity. Ignoring unknown fields makes clients more tolerant of forward-compatible additions. For checkout, strict rejection may be better because a misspelled field could change money movement. For a low-risk filter endpoint, ignoring unknown optional filters might be acceptable if documented.

Quick check: a client sends {"quanity": 2} instead of {"quantity": 2} for an order item. What policy would catch this fastest?

Answer: rejecting unknown fields and requiring quantity would catch the typo. If the API silently ignores unknown fields, the client may receive a confusing missing-field or default-value outcome.

Failure Modes and Signals

JSON API failures often come from blurry contracts:

  • Every failure returns 500, so clients retry invalid requests.
  • Parse errors, schema errors, and business errors share the same vague body.
  • Error messages are human-readable only, with no stable machine code.
  • Field validation reports do not include paths, so clients cannot highlight the bad input.
  • The backend accepts unknown fields that hide client typos in important operations.
  • New required fields break older clients without a compatibility plan.
  • Retried creates are not idempotent, so network ambiguity produces duplicates.

Operational signals should match the error contract. Track counts by route, status, error code, and client version. Watch validation failures after a mobile release. Watch duplicate idempotency key conflicts during checkout incidents. Include request_id in client-visible errors and internal logs so support can connect one user report to server evidence.

There is a boundary to this lesson. Full API lifecycle management includes OpenAPI governance, generated SDKs, backward compatibility test suites, and deprecation policy. The foundation is simpler: make request shape explicit, validate in layers, map failures consistently, and tell the client what kind of action is reasonable.

Readiness Check

Close the lesson and classify these failures for POST /orders:

A. Body is not valid JSON.
B. items[0].quantity is "two".
C. product_id "prod_9" is inactive.
D. Payment provider times out after the order request starts.

Use this rubric:

  • Name the validation layer or failure category.
  • Choose the kind of error response the client needs.
  • State whether retrying the same request is reasonable.
  • Name one piece of evidence operators need.

A solid answer: A is a parse failure; return a safe bad-request error and do not retry the same bytes. B is schema validation; return a field-level validation error and let the client fix input. C is business validation; return a stable code such as product_unavailable and prompt a cart refresh. D is a dependency or processing failure; retry policy depends on idempotency and what state was committed, so operators need request ID, idempotency key, payment attempt evidence, and order state.

Key Takeaways

  • JSON is an encoding; the API contract also includes schema, validation rules, status codes, and error bodies.
  • Parse validation, schema validation, and business validation fail for different reasons and should produce different client guidance.
  • Error envelopes should provide stable codes, safe messages, field details when useful, and a request ID for support.
  • Strictness protects correctness, but compatibility choices must be deliberate when clients may lag behind the server.
