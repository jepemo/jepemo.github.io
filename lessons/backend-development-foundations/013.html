Containers, Local Development, and Deployment Artifacts

By the end of this lesson, you will be able to... Explain what a container image preserves about a backend runtime; distinguish local development services from deployable artifacts; and review an image, entrypoint, and health check for common deployment failures.

Idea in one sentence. A container packages the runtime filesystem and startup command for a backend, so the same artifact can move across environments while configuration and dependency services stay outside the image.

Core Insight

Imagine the orders API passes tests on a developer laptop and in CI. The release builds successfully. Then the deployed service crashes on startup because the image does not include a native library required by the database driver. The application code did not change between CI and production. The runtime package did.

This is the problem containers are meant to narrow. A backend is not only source code. It depends on a language runtime, operating-system packages, compiled native libraries, installed dependencies, filesystem paths, environment variables, startup commands, ports, and sometimes helper binaries. If those assumptions differ between a laptop, CI, and production, a release can fail even when tests were honest.

A container image is a packaged filesystem plus metadata that says how to start a process. It can include the operating-system layer, runtime, application code, installed packages, and entrypoint command. A running container is an instance of that image with configuration, network, volumes, and resource limits supplied by the environment.

The beginner mistake is to think "Docker means production is solved." Containers improve reproducibility, but they do not remove every deployment boundary. The image should not contain production secrets. The database is usually outside the image. A health check must still say whether the process is ready. A local compose file may include convenience services that are not the deployable artifact.

The central trade-off is reproducibility versus image complexity and build cost. The more you bake into an image, the more runtime assumptions travel with the artifact. But larger, more complex images can build slowly, contain unnecessary packages, increase attack surface, and hide environment-specific choices that should remain configuration.

The Visible Pieces

Use one recurring scenario: the orders service is a web API that talks to PostgreSQL, a queue, and a payment provider. Developers run it locally with a database and queue. CI builds and tests it. Production deploys a container image.

The visible pieces are:

  • Source code: handlers, migrations, tests, configuration loader, and application logic.
  • Build context: the files made available to the image build.
  • Dockerfile or build recipe: the instructions that create the image.
  • Image: the built artifact containing runtime files and metadata.
  • Entrypoint or command: what process starts when the container runs.
  • Runtime configuration: environment variables and secret references injected at run time.
  • Dependency services: database, queue, cache, payment API, or object store outside the app image.
  • Health checks: probes that say whether the process is alive and ready.
  • Registry and deployment platform: where images are stored and where containers run.

A simplified image build might look like:

base runtime image
  -> install OS packages needed by native dependencies
  -> install language dependencies
  -> copy application source
  -> build or compile if needed
  -> set entrypoint
  -> produce image tag orders-api:abc123

The image should include what is required to run the application process. It should not include production-only values such as PAYMENT_API_KEY or DATABASE_URL. Those belong to the configuration boundary from the previous lesson.

A Build-to-Run Trace

Trace one release from source to running process:

git commit abc123
  -> CI builds image orders-api:abc123
  -> tests run against that image or same build output
  -> image is pushed to registry
  -> production pulls orders-api:abc123
  -> platform injects env and secrets
  -> container starts entrypoint
  -> app validates config
  -> readiness check passes
  -> traffic is sent to the instance

Each arrow is a boundary. Source code becoming an image is one boundary. Image becoming a running container is another. A running process becoming eligible for traffic is another. When a release fails, locate which boundary lied.

If the image lacks a native library, the build boundary is suspect:

source code expects library -> image build does not include it -> process crashes

If the image is correct but DATABASE_URL is missing, the runtime configuration boundary is suspect:

image starts -> config loader fails -> container never becomes ready

If the app starts but receives traffic before migrations or database connectivity are ready, the readiness boundary is suspect:

process is alive -> readiness check too shallow -> traffic reaches broken instance

So far, the container model gives you a concrete artifact to inspect. It does not make every boundary disappear. It makes the package boundary explicit.

Local Development Is Not the Artifact

Local development often uses a file such as compose.yaml to start the app plus dependencies:

orders-api
postgres
redis
fake-payment-provider

This is useful. It gives developers a repeatable local environment and makes integration tests easier. But the local stack is not the same thing as the deployment artifact. The app image may be one artifact. The database image, queue, and fake provider are supporting services. Production may use a managed database, a cloud queue, and a real payment provider.

That distinction prevents two mistakes.

First, do not bake local dependency services into the app image. A web API image should usually run the web API process, not PostgreSQL and a queue inside the same container. Keeping one main process per container makes health, logs, scaling, and failure boundaries easier to reason about.

Second, do not assume local convenience equals production readiness. A local compose setup might mount source code directly, run a debug server, disable TLS, use weak passwords, or skip production build steps. That can be fine for development if it is explicit. It should not be mistaken for the artifact that ships.

Quick check: should the production orders-api image contain the production database files so the app and database always move together?

Answer: usually no. The app image and database state have different lifecycles. The image should contain the app runtime. The database should be an external dependency with backups, migrations, access control, and its own operational boundary.

Entrypoints and Health Checks

The entrypoint is the command the container runs. For a web API, it might start the server:

./bin/orders-api serve --host 0.0.0.0 --port 8080

For a worker, it might start queue processing:

./bin/orders-api worker --queue orders-production

Entrypoints matter because deployment platforms manage processes. If the entrypoint runs a shell script that hides failures, starts background processes and exits, or ignores termination signals, the platform may not know what is really happening. A good container process exits when the app cannot start, writes logs to stdout/stderr, and responds correctly to shutdown signals.

Health checks are the deployment platform's evidence. A liveness check asks whether the process should be restarted. A readiness check asks whether the instance should receive traffic. They are related but not identical.

For the orders API:

liveness:
  process event loop responds
  app has not deadlocked

readiness:
  config loaded
  server accepts requests
  database connection is usable enough for this service
  required migrations are compatible

A bad readiness check returns 200 OK just because the process started. That can route traffic to an instance that cannot reach the database. A readiness check that is too deep can also cause trouble if it depends on a slow downstream service that should not block all traffic. The right check depends on what the service must have to answer its core requests.

Image Design Trade-offs

Images can be built in different ways. A simple image may install build tools and runtime tools together. A more refined image may use a multi-stage build: one stage compiles or builds the app, and a smaller final stage contains only what is needed to run.

The trade-offs are practical:

  • Smaller images transfer faster and usually contain fewer unnecessary tools.
  • Larger images may be easier to debug but carry more packages and potential vulnerabilities.
  • Pinning base images improves reproducibility but requires planned updates.
  • Floating tags such as latest are convenient but can make builds change without source changes.
  • Building inside CI gives repeatability, but local builds still need a clear path for developers.

The deployment artifact should be identifiable. Tagging an image only as latest weakens release evidence. Tagging with a commit SHA, build number, or immutable digest lets operators answer: which exact artifact is running?

This connects to testing. If tests run on one build output but production deploys a different rebuild, evidence is weaker. A stronger pipeline builds the artifact once, tests that artifact or an equivalent output, and promotes the same artifact through environments with different configuration.

Failure Modes and Signals

Container and artifact failures have recurring shapes:

  • The image lacks a runtime library that existed on developer laptops.
  • The image contains dev dependencies or debug tools not needed in production.
  • The app starts with a development entrypoint in production.
  • A local bind mount hides files that are missing from the image build.
  • The image bakes in secrets or environment-specific config.
  • The readiness check passes before the app can reach required dependencies.
  • The container ignores shutdown signals and drops in-flight requests during deploy.
  • The release cannot be traced from running container back to source commit and build.

Useful signals include image tag or digest, source commit, build logs, software bill of materials when available, startup logs, config validation result, health check status, container exit code, restart count, and deployment events. During an incident, ask: did the image contain the expected runtime, did the environment inject the expected config, did the entrypoint start the right process, and did readiness honestly represent service ability?

The limit is that containers are not full isolation from all operational risk. They do not replace database migrations, secret management, observability, backups, or release checks. They give the backend a more reproducible runtime package so the other boundaries are easier to reason about.

Quick check: CI tests source code on the host machine, then production builds a fresh image with a different base image. What evidence is missing?

Answer: evidence that the deployable image itself works. Tests should run against the image or the same build output that will be promoted, otherwise production can fail because the artifact differs from the tested runtime.

Readiness Check

Close the lesson and review this deployment artifact:

Image:
  tag: orders-api:latest
  includes source code, runtime, dev compiler, debug shell
  has PAYMENT_API_KEY baked into image at build time

Entrypoint:
  ./start-dev-server

Health:
  readiness returns 200 if process is running

Deployment:
  production injects DATABASE_URL at runtime

Use this rubric:

  • Identify one artifact traceability problem.
  • Identify one secret/config boundary problem.
  • Identify one entrypoint problem.
  • Identify one readiness problem.
  • Propose a safer deployment artifact shape.

A solid answer might say: latest is weak traceability because it does not identify the exact source or build. Baking PAYMENT_API_KEY into the image violates the config and secret boundary; it should be injected at runtime through a secret mechanism. ./start-dev-server suggests the production container may use a development command. Readiness only checking process existence can route traffic before database connectivity or config validation is safe. A safer artifact uses an immutable tag or digest, excludes secrets, runs a production entrypoint, validates config at startup, and exposes readiness based on the service's real requirements.

Key Takeaways

  • A container image packages runtime assumptions with the backend, but runtime configuration and dependency services remain separate boundaries.
  • Local development stacks are useful support environments; they are not automatically the deployable production artifact.
  • Entrypoints and health checks decide how the platform starts, stops, and trusts a running container.
  • Good deployment artifacts are reproducible, identifiable, free of baked-in secrets, and validated before receiving traffic.
