Testing Backends: Unit, Integration, and Contract Tests

By the end of this lesson, you will be able to... Choose whether a backend behavior needs a unit, integration, or contract test; trace what evidence each test boundary can and cannot provide; and design a focused test set for one API change.

Idea in one sentence. Backend tests are useful when their boundary matches the failure they are meant to catch: unit tests isolate local logic, integration tests exercise real collaborators, and contract tests protect agreements with clients or providers.

Core Insight

Imagine the orders API adds payment authorization during checkout. The team writes unit tests for the function that calculates the order total. They pass. The team writes unit tests for the handler branch that calls authorizePayment(). They pass too, because the payment provider is mocked. The release goes out, and production checkout fails: the real provider expects amount_cents, but the backend sends amount.

The unit tests were not useless. They answered a different question. They proved that local calculation and local branching behaved as expected under controlled inputs. They did not prove that the backend and payment provider agreed on the wire-level request shape. That failure lived at a boundary the unit tests intentionally replaced with a mock.

Backend testing is about choosing the right boundary for the risk. A boundary is where one piece of code, process, service, database, queue, or client contract meets another. Every test draws a boundary around some real behavior and replaces the rest with setup, mocks, fixtures, fake services, or live dependencies. The boundary decides what evidence the test can provide.

The beginner mistake is to ask "do we have tests?" as if all tests prove the same thing. A fast unit test, a database-backed integration test, and a consumer contract test each buy different confidence. If you use the wrong one, you can get a green build that still misses the failure production cares about.

The central trade-off is fast feedback versus production-like evidence. Unit tests are usually fast, precise, and easy to run constantly, but they prove less about real dependencies. Integration and contract tests give stronger boundary evidence, but they cost more setup, runtime, maintenance, and debugging attention. A good backend test suite uses several test types deliberately rather than making every test as large as possible.

The Visible Pieces

Use one recurring scenario: POST /orders creates an order, validates JSON, checks authorization, writes rows in a database transaction, and asks a payment provider to authorize the amount.

The simplified path is:

HTTP request
  -> JSON validation
  -> authentication and authorization
  -> calculate order total
  -> create order rows in database transaction
  -> call payment provider
  -> map provider result to API response

Different tests can draw different boundaries around that path:

  • A unit test isolates a small piece of code, such as calculateOrderTotal.
  • An integration test exercises multiple real components together, such as handler plus database transaction.
  • A contract test verifies that two sides agree on a boundary shape, such as the API response promised to a mobile client or the request expected by a payment provider.
  • An end-to-end test drives a larger path through deployed or near-deployed pieces. It is useful, but this lesson focuses on the three foundational backend categories in the title.

The key is not vocabulary purity. The key is matching the test to the failure. If the risk is arithmetic, a unit test may be ideal. If the risk is database rollback, a test with a real database is more convincing. If the risk is client compatibility, a contract test is closer to the problem than an isolated handler test.

Unit Tests: Small Boundary, Fast Signal

A unit test checks a small unit of behavior with most collaborators replaced or avoided. The "unit" is not always one function, but it should be small enough that a failure points to local logic.

For checkout, the total calculation might be:

items:
  prod_7 quantity 2 unit_price 1999
  prod_9 quantity 1 unit_price 499
discount:
  10 percent
expected total:
  (1999 * 2 + 499) - 10 percent

A unit test can check rounding, empty items, discount limits, tax rules, and invalid quantities without starting a web server or database. That makes it fast and precise.

input: order items and discount
run: calculateOrderTotal(input)
expect: total_cents and line breakdown

The evidence is strong for local calculation. It is weak for database schema, SQL transaction behavior, JSON parsing, auth middleware, provider request shape, and API response mapping. That weakness is not a flaw if the test is used for the right purpose.

Unit tests are also useful around policy decisions. From the previous lesson, a policy function can be tested with actor, action, resource, and context:

actor: support_agent
action: delete_product
resource: product with shipped order history
expect: deny

That does not prove the route actually calls the policy. It proves the policy logic returns the right decision when used. Another test boundary must prove pipeline wiring.

Quick check: if a unit test mocks the payment provider, can it prove the real provider accepts your JSON field names?

Answer: no. The mock may match your expectation, not the provider's real contract. You need a contract test, integration test with a provider sandbox, or another boundary test that checks the actual request shape.

Integration Tests: Real Collaborators, Real Wiring

An integration test checks that multiple pieces work together. In a backend, common integration boundaries include:

  • route plus middleware plus handler
  • handler plus database
  • repository plus migrations
  • transaction behavior across several writes
  • service code plus fake or sandbox dependency

For checkout, an integration test might run the real API handler against a test database:

setup:
  customer cus_42 exists
  address addr_12 belongs to cus_42
  product prod_7 is active

request:
  POST /orders with valid JSON and authenticated customer

expect:
  201 response
  orders row exists
  order_items rows exist
  total_cents is stored
  audit event exists

This test proves more wiring than a unit test. It can catch a missing route middleware, broken JSON validation setup, database constraint mismatch, migration error, transaction mistake, or wrong SQL query. It is slower and needs careful test data isolation. If it fails, debugging may involve several components.

Integration tests are especially valuable for transaction failures. Suppose payment authorization fails after the order row is inserted. What should be durable? Maybe no order should be committed, or maybe an order should remain in payment_failed state. The system must choose. A database-backed integration test can prove that the chosen durable state actually happens.

setup valid checkout
payment provider fake returns declined
call POST /orders
expect response code maps to payment failure
expect no paid order exists
expect order event records failure if that is the design

The important design point is to state the durable outcome. Without that, a test may merely assert today's implementation details rather than the behavior the backend owes the business.

Contract Tests: Boundary Agreements

A contract test protects an agreement between a provider and a consumer. The consumer might be a mobile app consuming your JSON API. The provider might be a payment API your backend calls. Contract tests are useful when both sides can change independently and a mismatch would break runtime behavior.

There are two common directions.

First, your API as provider:

consumer expectation:
  POST /orders returns 201 with:
    order_id: string
    status: "pending" or "paid"
    total_cents: integer
  validation errors use:
    error.code
    error.fields[].path

A contract test can verify that your backend still returns the fields and error shape a client depends on. This is different from testing every internal branch. It protects compatibility at the API boundary.

Second, your backend as consumer:

payment provider expectation:
  request includes amount_cents
  request includes currency
  idempotency key is sent in expected header
  declined card response includes provider_error_code

This is the failure from the opening. A unit test with a homemade mock may accept amount. A provider contract test should fail if the expected field is amount_cents.

Contract tests require discipline. If the contract file or fake provider is never checked against the real provider, it can drift. If every internal response field is treated as contract, harmless refactors become painful. Keep contracts focused on what consumers truly rely on.

So far, the ladder is: unit tests prove local logic, integration tests prove real wiring and state changes, contract tests prove boundary agreements.

Choosing a Test Boundary

When deciding what to test, start from the failure you want to prevent.

Failure: discount rounding is wrong
Likely test: unit test for calculation

Failure: admin route skips authorization middleware
Likely test: route integration test

Failure: database transaction leaves half-created order
Likely test: integration test with real database transaction

Failure: mobile client cannot parse validation error response
Likely test: API contract test

Failure: payment provider rejects request field names
Likely test: provider contract test or sandbox integration test

A useful test also has a clear assertion. "It works" is not an assertion. A better assertion names the outcome:

  • returns 401 before validation for unauthenticated admin request
  • creates exactly one order for repeated idempotency key
  • rolls back order items when transaction fails
  • returns validation_failed with field path for invalid quantity
  • sends amount_cents and idempotency key to provider

Avoid making every test cover the entire stack. Large tests are expensive, slower to run, and often harder to diagnose. Use a few broad tests for critical workflows, then many smaller tests for local rules and edge cases. The suite should resemble a portfolio of evidence, not a pile of duplicate happy paths.

Quick check: a route has perfect unit tests for policy logic, but one endpoint forgot to call the policy. Which test boundary catches that wiring failure?

Answer: an integration-style route test that sends a request as an underprivileged actor and expects denial before the handler performs the action.

Failure Modes and Signals

Backend test suites fail in predictable ways:

  • Too many mocks make tests green while real dependencies disagree.
  • Too many end-to-end tests make feedback slow and failures hard to localize.
  • Tests assert implementation details instead of durable behavior.
  • Fixtures drift away from production schema or realistic API bodies.
  • Contract tests are generated once and never checked against real consumers or providers.
  • Integration tests share state and become flaky.
  • The suite has happy paths but no tests for auth denial, validation errors, retries, or transaction failure.

The operational signal for a weak test boundary is a production incident that the suite could not possibly have caught. After an incident, ask which boundary failed. Did local logic return the wrong value? Did route wiring skip middleware? Did SQL or transaction behavior differ from the mock? Did a client/provider contract drift? Add or adjust the smallest test that would have made that failure visible before release.

The trade-off remains practical. Tests cost runtime and maintenance. The answer is not "test everything through the browser" or "mock everything." The answer is to choose boundaries intentionally and make the reason visible in test names and assertions.

Readiness Check

Close the lesson and choose test boundaries for this change:

Change:
  POST /orders now requires idempotency_key.

Risks:
  A. Missing key should return validation_failed with field path.
  B. Repeating the same key should not create a duplicate order.
  C. Payment provider request must send the key in the provider's expected header.
  D. Order total calculation must round discounts correctly.

Use this rubric:

  • Pick unit, integration, or contract for each risk.
  • State what the test proves.
  • State one thing the test does not prove.
  • Prefer the smallest boundary that gives useful evidence.

A solid answer: A can be an API contract or route integration test because it protects the public error shape. B needs an integration test with the database or idempotency store because it proves durable duplicate prevention. C needs a provider contract test or sandbox integration because it proves the outbound boundary shape. D is a unit test for calculation because no database or HTTP pipeline is needed to prove rounding.

Key Takeaways

  • A test boundary decides what evidence a test can provide and what failures it cannot see.
  • Unit tests are best for local logic; integration tests are best for real wiring and state; contract tests are best for client or provider agreements.
  • The right test starts from a failure you want to prevent, then chooses the smallest boundary that can reveal it.
  • A healthy backend suite mixes fast feedback with enough production-like evidence for the riskiest boundaries.
