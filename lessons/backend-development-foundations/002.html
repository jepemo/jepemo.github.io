Command Line, Processes, and Environment Variables

By the end of this lesson, you will be able to... Explain what a backend process receives when it starts; separate command-line arguments, environment variables, files, ports, standard streams, and exit status; and diagnose why a service runs on one machine but fails somewhere else.

Idea in one sentence. A backend service is a process with an explicit startup contract, and reliable systems make that contract visible instead of depending on hidden machine state.

Core Insight

Imagine the same small API from the previous lesson. Yesterday you traced a browser request from the client through the edge and into the backend. Today the backend does not even start on a teammate's laptop. It works on yours with npm run dev, but on theirs it exits immediately with database url missing. In staging, the container starts, listens on the wrong port, and the proxy returns 502 Bad Gateway.

This is not yet a web-framework problem. Before an API can receive requests, the operating system must start a process. A process is a running program with a process ID, memory, open file descriptors, environment variables, command-line arguments, current working directory, permissions, and a parent process that started it. Your web framework lives inside that process. If the process starts with the wrong inputs, the handler code may never get a chance to run.

The beginner shortcut is to say "run the app." That is fine while learning locally, but it hides the startup contract. Which command starts the service? Which port should it bind? Which environment variables must exist? Which files does it expect relative to the current directory? Where should logs go? What exit code means a clean shutdown versus a startup failure?

The central trade-off is simple process contracts versus hidden machine-specific assumptions. A simple process contract can be repeated by a shell, a test runner, a container entrypoint, or a deployment platform. Hidden assumptions are faster at first: your laptop has the right .env file, your shell already exports a variable, your current directory is correct, your database is running locally. Those assumptions break as soon as the service moves.

What Starts a Backend

Use one scenario through the lesson. The service is an orders API. A developer starts it like this:

PORT=3000 DATABASE_URL=postgres://localhost/orders ./orders-api --mode dev

That line looks like one thing, but it creates several distinct inputs:

  • ./orders-api is the executable path.
  • --mode dev is command-line argument data.
  • PORT=3000 and DATABASE_URL=... are environment variables.
  • The shell has a current working directory where ./orders-api is resolved.
  • The process inherits standard input, standard output, and standard error.
  • The operating system gives the process permissions, a process ID, and a parent.
  • The service chooses to bind a network port and open a database connection.

The shell is just one possible parent. A test runner, systemd, Docker, Kubernetes, a platform-as-a-service launcher, or an IDE can also start the process. That is why it is useful to think in terms of process contract instead of "the command I type."

A process contract is the set of startup expectations the program needs in order to run correctly. For a backend service, it usually includes:

executable + arguments + environment + working directory
  + readable files + writable locations + network ports
  + standard streams + signal handling + exit status

The contract is not a separate technology. It is the boundary between "some parent starts my service" and "my service can now accept requests." If the boundary is clear, you can move the service from your laptop to a container without rediscovering every local habit.

A Startup Walkthrough

Follow the orders API from shell command to listening service.

developer types command
  -> shell parses text
  -> shell creates environment for child process
  -> operating system starts executable
  -> process reads arguments and environment
  -> process validates required configuration
  -> process opens logs and dependencies
  -> process binds PORT
  -> process reports ready or exits with failure

Step by step:

  1. The shell receives a line of text. It expands paths, handles quoting, and decides which program should run.
  2. The shell asks the operating system to create a child process for ./orders-api.
  3. The new process receives an argument vector. In many languages this appears as argv: the program name plus values such as --mode and dev.
  4. The new process receives an environment. This is a map of string keys to string values, such as PORT=3000 and DATABASE_URL=postgres://localhost/orders.
  5. The process starts in a working directory. Relative paths such as ./config/routes.json are resolved from there.
  6. The process inherits standard streams: stdin for input, stdout for normal output, and stderr for diagnostic output.
  7. The application validates its required settings before accepting traffic.
  8. If validation passes, it opens dependencies and binds a port. If validation fails, it writes a useful message and exits with a nonzero status.

That last point is more important than it looks. A backend that starts with missing configuration and fails later under traffic is harder to diagnose than a backend that refuses to start. Startup validation turns an ambiguous runtime failure into a clear process-contract failure.

Quick check: if DATABASE_URL is missing, should the service start and wait for the first request to fail?

Answer: usually no. If the database is required for normal service behavior, the process should fail fast with a clear message and a nonzero exit status. That lets the parent process, deploy system, or developer see that startup did not satisfy the contract.

Arguments, Environment, and Files

Arguments, environment variables, and files can all configure a backend, but they are not interchangeable.

Command-line arguments are good for explicit mode and one-off choices:

./orders-api --mode dev --migrate

They are visible in the command that starts the process. They are useful when the parent is intentionally choosing behavior for this run. They are less suitable for secrets because process listings and logs can accidentally expose them.

Environment variables are good for deploy-time configuration:

PORT=3000
DATABASE_URL=postgres://db.internal/orders
LOG_LEVEL=info

They let the same artifact run in development, staging, and production with different external settings. But they are strings, so the program must parse and validate them. PORT=abc is still an environment value; it becomes a configuration error only when your code checks that it is a valid port.

Files are good for structured data that is versioned or mounted deliberately:

config/routes.json
schema.sql
public/logo.png

They carry richer structure than environment variables, but they introduce path and packaging questions. Is the file in the image? Is it mounted by the platform? Is the current working directory what you expect? Can the process read it with its permissions?

A common failure is mixing these roles. For example, a developer keeps DATABASE_URL in an untracked local .env file and forgets that the deployment platform will not have it. Another developer stores the port in source code, so staging and production fight over the same assumption. The cleaner design is to decide which values are part of the artifact and which values are supplied by the environment that runs it.

The Small Contract That Prevents Drift

Now make the contract concrete. A minimal orders API contract might say:

Required environment:
  PORT: integer from 1 to 65535
  DATABASE_URL: database connection string
  LOG_LEVEL: debug, info, warn, or error

Expected files:
  ./migrations exists if --migrate is used

Startup behavior:
  validate configuration before binding PORT
  print startup errors to stderr
  print readiness line to stdout
  exit 0 on intentional clean shutdown
  exit nonzero on missing config or failed startup dependency

This contract can be checked locally:

PORT=3000 DATABASE_URL=postgres://localhost/orders LOG_LEVEL=info ./orders-api

It can be checked in a container:

docker run -e PORT=3000 -e DATABASE_URL=postgres://db/orders orders-api

It can be checked by a deployment platform that injects environment values and watches exit status. The exact parent changes, but the contract remains inspectable.

The process should also separate normal output from diagnostic output. stdout is useful for ordinary status or structured logs, depending on the runtime convention. stderr is the right place for startup errors. Exit status matters because parents automate decisions. A status of 0 usually means success. A nonzero status means failure. If a process prints "failed" but exits 0, automation may treat a broken startup as healthy.

Quick check: a service prints Listening on 3000, but the deploy platform expected it to listen on the port in PORT=8080. Which contract was violated?

Answer: the service ignored its runtime environment and used a hard-coded or default port. The fix is not in the proxy first; the process must read and validate the port supplied by its parent.

Failure Modes

The most common failures are small but expensive because they hide behind the phrase "works on my machine."

  • Hidden environment: the service depends on a variable exported in one developer's shell, but the value is not documented or checked at startup.
  • Wrong working directory: a relative path works in an IDE but fails in a container because the process starts from a different directory.
  • Silent defaults: the service falls back to development settings in production when a required value is missing.
  • Bad exit status: the service reports failure in text but exits successfully, so automation continues as if it is healthy.
  • Mixed secrets and logs: startup diagnostics print full connection strings or tokens, creating a security problem while trying to debug.

The corrective mental model is simple: every value the process needs should come from one of a few explicit places, and the service should say clearly whether those values were acceptable. That does not mean every setting needs a complex configuration system. It means the required minimum is named, validated, and observable.

There is also a limit. Environment variables are a process boundary, not a complete secrets-management strategy. They can carry secret references or secret values, but rotation, access control, auditing, and leak prevention need more care. Later lessons will handle secrets and deployment boundaries in more depth. Here the goal is narrower: make the process start predictably.

Readiness Check

Close the lesson and design a startup contract for this tiny service:

image-resizer --workers 4

It reads jobs from a queue, writes resized images to object storage, and exposes a health endpoint.

Use this rubric:

  • Name two required environment variables.
  • Name one command-line argument and why it belongs there.
  • Name one startup validation check.
  • Name what should go to stderr if startup fails.
  • Name one exit-status rule that a parent process could rely on.

A solid answer might say: require QUEUE_URL and OBJECT_STORE_BUCKET as environment variables because they vary by deployment; use --workers 4 as an explicit runtime sizing choice; validate that workers is a positive integer and that required environment values exist before accepting work; print missing configuration to stderr without dumping secrets; exit nonzero on startup failure and 0 on intentional shutdown.

Key Takeaways

  • A backend service starts as an operating-system process before it becomes a request handler.
  • Arguments, environment variables, files, streams, ports, signals, and exit status form the startup contract.
  • Hidden local assumptions make services hard to move; startup validation makes failures explicit.
  • Good process contracts keep deployment flexibility without letting machine-specific state silently control behavior.
