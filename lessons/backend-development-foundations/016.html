Backend Service Capstone: Build, Ship, and Operate One API

By the end of this lesson, you will be able to... Design a small backend API from contract to deployment evidence; trace one request through validation, authorization, database state, tests, and observability; and judge whether the service is ready to operate beyond a local demo.

Idea in one sentence. A backend is ready to ship when one important request can be explained from client contract to durable state and production signals, not merely when the handler returns the right response once.

Core Insight

Imagine you are asked to build the first version of an orders API for a small shop. It needs to let authenticated users create orders, read their own orders, and let administrators manage the product catalog. The feature list sounds ordinary: a few HTTP routes, a relational database, some validation, tests, a container, and deployment. The capstone question is not "can you code each piece?" It is "can the pieces hold one coherent service boundary?"

The most useful way to answer is to follow one request. Take POST /orders. A client sends JSON. The service validates the shape, checks who the caller is, confirms the product exists, starts a database transaction, records an order, handles duplicate retries, returns a response, emits evidence, and later survives a deploy. Every earlier lesson in this track shows up along that path. HTTP status codes matter because the client needs to know what happened. SQL constraints matter because the database is the durable authority. Tests matter because the team needs evidence before release. Configuration, containers, CI, deployment, and observability matter because production is not the same environment as a laptop.

A common beginner mistake is to treat these topics as separate checklist items. That creates a service that looks complete in screenshots but is hard to trust. It may have an endpoint without a contract, a database without constraints, tests that do not cover real boundaries, a deployment without rollback evidence, or logs that cannot explain a failed order. The individual pieces exist, but they do not reinforce each other.

The capstone mental model is one request, many boundaries, one chain of evidence. At each boundary, ask what the service promises, what state becomes authoritative, what can fail, and what signal would prove the behavior. This does not require enterprise architecture. It requires ordinary backend discipline applied end to end.

The central trade-off is speed of feature delivery versus confidence in behavior under real conditions. You can ship faster by skipping contracts, migrations, integration tests, release metadata, and observability. You also move uncertainty from development into production. A good beginner backend does not remove all risk. It makes the important risks visible before users are forced to discover them.

The Service Boundary

Use a deliberately small service. The API supports:

POST /orders
GET /orders/:id
GET /orders
POST /admin/products
PATCH /admin/products/:id

The service owns orders and product catalog state. It does not own payment processing, email delivery, or warehouse fulfillment. Those can be future dependencies or mocked external systems. Naming ownership matters because it prevents every route from becoming a place where unrelated responsibilities leak in.

The main tables might be:

users(id, email, role)
products(id, sku, name, price_cents, active)
orders(id, user_id, status, total_cents, idempotency_key, created_at)
order_items(id, order_id, product_id, quantity, unit_price_cents)

The API contract should be concrete enough that a client, test, and operator can reason about the same behavior. For POST /orders, an informal contract might say:

Request:
  Authorization: Bearer <token>
  Idempotency-Key: <client-generated-key>
  Body: { "items": [{ "product_id": "p1", "quantity": 2 }] }

Success:
  201 Created
  Body: { "order_id": "ord_123", "status": "created", "total_cents": 5000 }

Client errors:
  400 if JSON is malformed or quantity is invalid
  401 if no valid user is authenticated
  403 if the user is not allowed to perform the action
  404 if a product does not exist or is not visible
  409 if the same idempotency key conflicts with different input

This contract is not decoration. It tells the handler what to validate, the database what invariants to protect, the tests what to assert, and observability what labels and events to emit. If the contract is vague, every later layer becomes a place for accidental interpretation.

The database should enforce facts the service cannot afford to merely hope are true. Examples include foreign keys from order_items to orders and products, a positive quantity check, and a uniqueness constraint on (user_id, idempotency_key) for order creation. Application code still validates friendly errors, but the database remains the durable authority when concurrent requests arrive.

Quick check: if two identical POST /orders requests arrive because a client retried after a network timeout, which layer should make duplicate creation impossible?

Answer: the service should design for idempotency across layers. The API requires an idempotency key, the handler uses it, the database enforces uniqueness, and tests prove the retry returns the existing result rather than creating a second order.

One Request, End to End

Now trace the request as if you were reviewing the design before implementation:

client
  -> POST /orders with token, idempotency key, JSON body
  -> route identifies the operation
  -> auth middleware resolves user id and role
  -> validation rejects malformed or impossible input
  -> transaction reads products and checks availability
  -> transaction inserts order and order_items
  -> unique idempotency constraint prevents duplicates
  -> response returns order id and status
  -> logs, metrics, trace, and event record what happened

The starting state is simple: a user exists, products exist, and no order exists for this user's idempotency key. The local decision in the handler is also simple: this looks like a valid order creation request. The important transition happens inside the transaction. The service converts a client intention into durable records that either all commit together or all roll back together.

A naive implementation might insert the order first, then insert items, then calculate the total, then hope no product changed in between. A better beginner design narrows the transaction:

begin transaction
  find products by id where active = true
  verify every requested product was found
  compute total from database prices
  insert orders(user_id, status, total_cents, idempotency_key)
  insert order_items(order_id, product_id, quantity, unit_price_cents)
commit

The total uses database prices, not client-provided prices. The transaction gives the order and items one shared commit point. The idempotency uniqueness constraint handles retry pressure. If the same key and same request arrive again, the service can return the existing order. If the same key arrives with different items, 409 Conflict is clearer than silently creating a surprising result.

This path also clarifies authorization. A regular user may create and read their own orders. An admin may create and update products. The API should not rely on the frontend hiding buttons. The backend decides from authenticated identity, route, and policy. Tests should include denied cases because authorization bugs are often invisible in happy-path demos.

The response should expose enough information for the client to continue, but not more than the client should know. GET /orders/:id should return 404 or 403 consistently according to the product's privacy policy when one user requests another user's order. That is a design decision, not an accident left to the ORM.

So far, the service is more than a set of handlers. It is a chain where request shape, identity, domain rules, durable state, and client-visible response agree with each other.

Evidence Before Release

A backend capstone is not finished when the code compiles. It needs evidence at several levels.

Unit tests are useful for pure logic: total calculation, request validation helpers, role checks, and mapping domain errors to HTTP responses. They should be fast and narrow. If total calculation changes, a unit test should fail without needing a running server.

Integration tests are useful for real boundaries: route, middleware, database, transaction, constraints, and migrations. For POST /orders, an integration test should hit the HTTP route against a test database, create an order, assert database rows, retry with the same idempotency key, and confirm no duplicate order exists. That test is slower than a unit test because it buys stronger evidence.

Contract tests or API schema checks are useful when clients depend on stable request and response shapes. Even a small OpenAPI file can prevent accidental response drift. The schema does not need to be elaborate, but it should name required fields, status codes, and error bodies for important routes.

Migration checks matter because schema changes are part of the release. A service that works only after manually editing the database is not ready to operate. The migration path should be repeatable in CI or a staging environment. If the service adds idempotency_key, the migration should create the column and the unique index intentionally.

CI should run the evidence in a predictable order:

format and lint
  -> unit tests
  -> integration tests with a test database
  -> migration check
  -> build container image
  -> publish image with version metadata

The container image is the deployable artifact. It should not depend on a developer's local environment. Configuration such as database URL, secret keys, and external service endpoints should come from the environment or deployment platform, not from code committed into the repository. Secrets should not appear in logs, tests, images, or examples that invite copy-paste mistakes.

Quick check: which test gives the strongest evidence that idempotency survives a real request retry?

Answer: an integration test through the HTTP route and test database. A unit test can check helper logic, but the strongest beginner-level evidence includes middleware, transaction behavior, uniqueness constraints, and response mapping together.

Operating the Service

Production readiness means the service can be explained when it misbehaves. Start with the promises users and operators care about:

POST /orders creates one order or returns a clear recoverable error.
GET /orders/:id returns only orders the caller may see.
Admin product changes require an admin role.
Deployments do not sharply increase order creation failures.

Each promise needs signals. For HTTP behavior, track request count, error rate, and latency by route template and status class. For database behavior, track query latency, migration version, connection pool pressure, and transaction failures. For domain behavior, emit structured events such as order_created, order_create_rejected, and idempotency_replayed. For release behavior, attach version or image digest to logs, traces, and metrics.

A useful trace for POST /orders might include:

http POST /orders request_id=req_712 release=2026.06.25
  span auth.check user_id=u17 role=customer
  span validate_order_items count=2
  span db.transaction status=committed duration_ms=38
  event order_created order_id=ord_123 total_cents=5000
  response status=201 duration_ms=71

A failed trace might show:

http POST /orders request_id=req_884 release=2026.06.25
  span auth.check status=ok
  span validate_order_items status=ok
  span db.transaction status=rolled_back reason=duplicate_idempotency_conflict
  response status=409 duration_ms=28

Those records let support and engineering answer practical questions. Did the request authenticate? Was it rejected before the database? Did the transaction commit? Was a retry replayed safely? Did failures start after one release? Without this evidence, the team is left with symptoms.

Readiness also includes failure boundaries. If the database is unavailable, the service should return a clear server error and emit a dependency failure signal. If a client sends bad JSON, the service should return 400, not a generic 500. If a migration has not run, deployment should fail fast or refuse traffic rather than corrupting behavior gradually. If a secret is missing, startup should fail with a sanitized error rather than accepting requests in a broken state.

Rollback is part of the same operating story. A release that changes only application code may be rolled back by redeploying the previous image. A release that changes schema needs more care: the old and new code may need to tolerate the same columns during the transition. For this capstone, that means avoiding a migration plan where the service writes orders in a format that the previous version cannot read seconds later. Even a small service benefits from asking, "What version is running, what schema does it expect, and what signal tells us the rollout is unhealthy?"

The goal is not to build a perfect platform. The goal is to avoid pretending that production is just a bigger laptop. A beginner-ready backend has explicit inputs, durable state, repeatable release steps, and evidence that follows the request.

Capstone Review

Before calling the service complete, close the code and reconstruct POST /orders from memory:

contract -> auth -> validation -> transaction -> constraints -> response -> tests -> deployment -> observability

Then review the design with these questions:

  • What request shape and status codes does the client rely on?
  • Which identity is authenticated, and which role decisions happen on the backend?
  • Which facts are enforced by database constraints instead of application hope?
  • What happens when the client retries after a timeout?
  • Which tests prove the route, transaction, and idempotency behavior together?
  • What artifact is deployed, and where does configuration come from?
  • Which logs, metrics, traces, or events would explain one failed order?

A strong capstone answer does not need many features. It needs a clear path through the features it has. If you cannot explain one request through the whole service, adding more endpoints will usually make the design less trustworthy, not more complete.

Now transfer the same review to PATCH /admin/products/:id. The request should require an admin identity, validate the patch body, update only allowed fields, preserve price and active-state rules, run inside a database operation that protects invariants, return a clear response, and emit evidence. The details differ from order creation, but the review path is the same: contract, authority, state change, tests, release, and signals.

Use this compact rubric for your own implementation:

Ready:
  one critical request has a written contract
  durable state and constraints match the contract
  retries and authorization are tested
  CI builds and tests the deployable artifact
  production signals can explain success and failure

Not ready:
  important behavior exists only in developer memory
  state can be duplicated or partially written under retry
  tests avoid the database and route boundary entirely
  deployment depends on manual local steps
  logs cannot connect a user report to a request path

Key Takeaways

  • A backend capstone should trace one important request through contract, identity, validation, durable state, response, tests, release, and observability.
  • The database, API contract, tests, and operational signals should agree about the same behavior instead of acting as separate checklist items.
  • Idempotency, authorization, migrations, configuration, and traces are not advanced extras; they are how a small service becomes safe enough to ship.
  • A service is ready when the team can prove what should happen and explain what did happen.
