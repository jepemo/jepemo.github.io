Configuration, Secrets, and Twelve-Factor Boundaries

By the end of this lesson, you will be able to... Separate code from deploy-time configuration; identify which values are secrets; and design startup validation that catches missing, wrong, or drifted configuration before a backend handles traffic.

Idea in one sentence. Configuration is the deploy-time information a release needs to run in one environment, while secrets are sensitive configuration that need controlled storage, rotation, and careful logging boundaries.

Core Insight

Imagine the orders API passes tests and deploys to production. A worker starts processing checkout jobs. It connects successfully, logs look normal, and then payment authorizations begin failing. After an hour of investigation, the team discovers the production worker is using the staging payment API key. The code was correct. The build artifact was correct. The deploy-time configuration was wrong.

This is a different kind of backend failure from a bad SQL query or missing authorization check. The behavior changed because a value outside the source code pointed the same code at a different dependency. A backend service may need database URLs, payment provider keys, feature flags, allowed origins, log levels, queue names, token issuers, and timeout values. Those values often vary by local development, test, staging, and production.

Configuration is how one codebase runs in different places without editing the code for each place. That is powerful. It is also risky because the difference between "safe staging behavior" and "real production money movement" may be one environment variable or secret reference.

The beginner mistake is to treat configuration as a bag of strings the app reads whenever it needs them. A healthier model is a boundary. At startup, the service should load its required configuration, validate shape and meaning, refuse impossible combinations, and make safe summaries visible to operators. Secrets should be loaded through a controlled path and never printed as ordinary diagnostic data.

The central trade-off is flexible deployment versus configuration drift. Moving deploy-time choices out of code lets the same artifact run in many environments. It also means environments can silently diverge. The goal is not to hard-code everything. The goal is to make variation explicit, validated, observable, and safe to rotate.

The Visible Pieces

Use one recurring scenario: the orders service needs to run locally, in staging, and in production.

It needs values like:

APP_ENV=production
DATABASE_URL=postgres://...
PAYMENT_API_BASE_URL=https://api.payments.example
PAYMENT_API_KEY=...
SESSION_COOKIE_SECRET=...
ORDER_QUEUE_NAME=orders-production
LOG_LEVEL=info
FEATURE_NEW_CHECKOUT=false
REQUEST_TIMEOUT_MS=3000

These values are not all the same kind of thing.

  • Code is the source and built artifact: handlers, policies, SQL, tests, and runtime package.
  • Configuration is deploy-time input that changes behavior without changing code.
  • Secrets are sensitive values, such as API keys, private keys, database passwords, and signing secrets.
  • Environment is the deployment context where the service runs: local, test, staging, production, or a preview environment.
  • Startup validation is the app's check that required configuration exists and makes sense before serving traffic.
  • Rotation is replacing a secret safely without breaking running systems.

The Twelve-Factor App guideline "store config in the environment" is often summarized as using environment variables. The deeper idea is separation: config that varies between deploys should not be baked into source code. Environment variables are one common interface. Secret managers, deployment manifests, and platform configuration systems can also feed that boundary.

The important question is: what does this release need to know at deploy time, and which system is authoritative for that value?

A Startup Configuration Trace

Trace the worker start from process launch to readiness:

process starts
  -> read environment variables and secret references
  -> parse values into typed settings
  -> validate required settings
  -> reject unsafe combinations
  -> initialize clients
  -> report safe config summary
  -> become ready for work

Make the intermediate states visible.

First, the process receives raw strings. REQUEST_TIMEOUT_MS="3000" is a string until parsed. FEATURE_NEW_CHECKOUT="false" is a string until converted to a boolean. PAYMENT_API_KEY may be absent, empty, or accidentally set to a staging key.

Second, the app should parse into a typed settings object:

Settings:
  app_env = production
  payment_api_base_url = https://api.payments.example
  payment_api_key = present secret
  order_queue_name = orders-production
  request_timeout_ms = 3000
  new_checkout_enabled = false

Third, validation should check more than presence:

required:
  DATABASE_URL exists
  PAYMENT_API_KEY exists
  SESSION_COOKIE_SECRET exists

type and range:
  REQUEST_TIMEOUT_MS is an integer between 100 and 30000
  LOG_LEVEL is one of debug, info, warn, error

environment consistency:
  APP_ENV=production does not use staging payment base URL
  production queue name does not end with "-staging"
  debug logging is not enabled in production by accident

Fourth, the app should expose a safe readiness result. It might log:

config loaded: app_env=production payment_base=api.payments.example
order_queue=orders-production timeout_ms=3000 payment_key=present

It should not log:

PAYMENT_API_KEY=sk_live_full_secret_value_here
SESSION_COOKIE_SECRET=...

So far, the mechanism is a boundary at startup. The service turns raw deploy input into validated settings, refuses unsafe states, and reveals enough non-secret evidence to debug environment mismatch.

Secrets Need Different Handling

All secrets are configuration, but not all configuration is secret. LOG_LEVEL=info is config but usually not secret. PAYMENT_API_KEY is both config and secret. Treating them the same creates avoidable risk.

Secrets require different handling because possession often grants access. A leaked database password may allow data access. A leaked signing secret may allow forged sessions. A leaked payment key may move money or expose transaction data.

Good secret handling includes:

  • Store secrets outside source control.
  • Inject secrets through deployment or a secret manager.
  • Do not print secrets in logs, error messages, metrics labels, or test output.
  • Keep separate secrets for local, staging, and production.
  • Rotate secrets with a planned overlap when clients and servers need time to switch.
  • Limit each secret to the permissions it needs.

Rotation is where many beginner designs break. Suppose SESSION_COOKIE_SECRET signs user sessions. If you replace it instantly, every existing session may become invalid. That may be acceptable during an incident, but not for routine rotation. A rotation-friendly design might allow a new signing key and one or more old verification keys:

sign with: key_2026_06
verify with: key_2026_06, key_2026_05
after old sessions expire: remove key_2026_05

For payment provider keys, the plan may be different: deploy support for reading PAYMENT_API_KEY_NEW, switch traffic, verify success, then revoke the old key. The exact mechanism depends on provider and platform. The constant idea is that rotation is a workflow, not just editing a value.

Quick check: should startup logs print the first eight characters of a production API key to help debugging?

Answer: usually no. Even partial secrets can become sensitive when combined with other leaks or provider conventions. Prefer safe presence checks, secret version IDs, or secret manager metadata that does not reveal key material.

Environment Drift and Feature Flags

Configuration drift means environments differ in ways nobody intended or can quickly explain. Local may use one timeout. Staging may use a different provider URL. Production may have an old feature flag. Drift is not always bad; environments are supposed to differ. The danger is untracked or unvalidated difference.

Feature flags are a common source of drift. A flag such as FEATURE_NEW_CHECKOUT=true can be useful for gradual rollout. It can also mean staging and production are testing different code paths. A backend team should know which flags affect critical paths, who owns them, when they expire, and what evidence proves which value was active during an incident.

For the checkout worker, safe operational evidence might include:

app_env=production
release_sha=abc123
config_version=orders-prod-2026-06-25
new_checkout_enabled=false
payment_provider=live
payment_api_key_version=payments-prod-v4

This evidence is not a substitute for secret protection. It is a way to debug without exposing secrets. When payment failures rise, operators can quickly see whether production is pointed at the live provider, whether a rollout flag changed, and whether a new secret version was deployed.

The trade-off is noise. If every config value is logged on every request, logs become expensive and risky. Prefer startup summaries, metrics dimensions for safe low-cardinality values, and deployment records that connect release, environment, and config version.

This also makes rollback decisions faster.

Failure Modes and Signals

Configuration failures usually look like ordinary runtime failures until you ask what varied at deploy time:

  • Production uses a staging API key or base URL.
  • A required environment variable is missing and defaults to unsafe behavior.
  • A string value such as "false" is treated as truthy by careless parsing.
  • Local development relies on a .env value that deployment never sets.
  • A secret is committed to source control or printed in logs.
  • A rotated secret breaks old sessions or background workers.
  • Staging and production use different feature flags without a recorded reason.
  • A timeout is set too high or too low for one environment.

The operational signals include startup validation failures, readiness probe failures, safe config summaries, secret version metadata, deployment change records, error rates by environment, and alerts when required config is absent. A service should fail fast for missing required configuration. Running with a silent fallback such as PAYMENT_API_KEY="" is worse than refusing to start.

The limit is that configuration validation cannot prove every dependency is healthy. A syntactically valid database URL may still point to a down database. That belongs to connection checks and readiness. The configuration boundary proves the service received coherent instructions; health checks prove dependencies are usable enough to serve.

Quick check: APP_ENV=production and PAYMENT_API_BASE_URL=https://staging-payments.example are both present and parseable. Should startup validation pass?

Answer: no. This is an unsafe environment combination. Validation should reject production pointed at a staging payment endpoint unless there is an explicit, controlled exception.

Readiness Check

Close the lesson and review this deployment configuration:

APP_ENV=production
DATABASE_URL=postgres://orders-prod
PAYMENT_API_BASE_URL=https://staging-payments.example
PAYMENT_API_KEY=present
SESSION_COOKIE_SECRET=present
LOG_LEVEL=debug
REQUEST_TIMEOUT_MS=ten_seconds

Use this rubric:

  • Identify which values are config and which are secrets.
  • Name at least two startup validation failures.
  • State what should be logged safely.
  • State whether the service should become ready.
  • Name one rotation concern.

A solid answer might say: all values are deploy-time configuration; DATABASE_URL, PAYMENT_API_KEY, and SESSION_COOKIE_SECRET include secret or sensitive connection material. Startup validation should reject production using the staging payment base URL, REQUEST_TIMEOUT_MS not being an integer, and possibly LOG_LEVEL=debug in production. Logs can safely say the payment key is present and name a secret version, but not print the key. The service should not become ready. A rotation concern is that changing the session cookie secret may invalidate existing sessions unless the system supports old verification keys during a transition.

Key Takeaways

  • Configuration is deploy-time input; secrets are sensitive configuration that need stricter storage, logging, and rotation rules.
  • A backend should parse and validate configuration at startup, then refuse unsafe or incoherent environment combinations.
  • Separating code from config enables flexible deployment, but it also creates drift unless values are versioned, validated, and observable.
  • Safe operational evidence should reveal environment and config state without exposing secret material.
