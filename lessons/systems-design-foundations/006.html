Writing and Reviewing Architecture Proposals

By the end of this lesson, you will be able to... frame an architecture proposal as a reviewable argument, trace one happy path and one degraded path through the design, and review a proposal for assumptions, rollout risk, and operating cost.

Idea in one sentence. A strong architecture proposal turns private design intuition into shared evidence, so the team can challenge the reasoning before the system is expensive to change.

Core Insight

Imagine the whiteboard team is redesigning progress tracking. Today, a learner can complete a lesson on a laptop, open the same course on a phone, and briefly see stale progress. During traffic bursts, notification jobs sometimes slow the user-facing write path. Analytics consumers want richer events, but product engineers do not want reporting work to interfere with the moment a learner saves progress.

Several designs sound plausible. The team could harden the current synchronous write path, add an event log and asynchronous projections, split notifications into a separate worker path, or redesign ownership around a single progress service. The hard part is not inventing one possible architecture. The hard part is making the reasoning visible enough that other engineers can test it.

That is the job of an architecture proposal. It is not a performance, a vendor comparison, or a diagram with more boxes. It is a decision instrument. A good proposal explains the problem, the constraints, the options considered, the chosen mechanism, the failure behavior, the rollout path, and the cost the team is accepting.

The common misconception is that proposal quality comes mostly from polish. Clear writing matters, but the deeper question is whether the document exposes the design's assumptions. If a reviewer cannot tell what must remain true, what can fail safely, why rejected alternatives lost, or how operators will know the rollout is healthy, the proposal is not yet reviewable.

Start With The Decision Frame

The first useful move is to frame the decision before naming tools. A weak opening says:

We propose moving progress tracking to an event-driven architecture.

That sentence names a shape, but it does not give the reader enough context to disagree productively. A stronger opening says:

Learner progress can diverge across devices under retries and burst traffic.
Notification and analytics work currently share the user-facing write path.
We need accepted progress to be durable immediately, visible across devices
within a few seconds, and isolated from downstream consumer slowdowns.
This proposal does not redesign quiz scoring, billing, or course enrollment.

Now the reader has a decision frame. They can inspect the problem, the success criteria, the boundaries, and the non-goals. If they disagree, the disagreement has a useful target: maybe the convergence window should be shorter, maybe billing is actually affected, or maybe the real issue is missing idempotency rather than architecture shape.

A proposal's opening should usually include:

problem observed
-> user or operational impact
-> invariants that must hold
-> constraints and non-goals
-> evidence that the current design is stressed

An invariant is a rule the design must protect. In the progress scenario, one invariant might be: once the API accepts a valid progress update, that update must not disappear, even if notification workers are down. Another might be: analytics lag must not block the learner-facing save path.

The trade-off is that strong framing exposes uncertainty early. That can feel slower than jumping to the diagram. But uncertainty found in the proposal is cheap. Uncertainty found during migration, after clients and workers depend on the new path, is expensive.

Show The Mechanism, Not Just The Components

After the frame, the proposal should show how the chosen design changes the movement of data, control, and failure. Component names are not enough. A diagram that says "API, event log, projector, notifier, analytics" may be accurate and still leave the hard questions hidden.

For the whiteboard team, suppose the chosen design is:

Client
  -> Progress API
  -> durable progress event store
  -> learner progress projection
  -> notification worker
  -> analytics consumers

The mechanism is the decoupling of acceptance from derived work. The user-facing path validates a progress update and records it durably. Projection, notification, and analytics become consumers of accepted progress events. The design buys isolation: a slow notification worker should no longer make the learner wait to save progress.

That mechanism should be written as a trace:

Input:
  learner completes lesson 006 on laptop

Step 1:
  client sends progress update with learner_id, lesson_id, attempt_id

Step 2:
  API validates ownership and idempotency key

Step 3:
  API appends accepted progress event to durable store

Step 4:
  API returns success after durable acceptance

Step 5:
  projection consumes event and updates cross-device progress view

Step 6:
  notification and analytics consumers process the same event later

The trace makes intermediate states visible. After step 4 but before step 5, the update is accepted but may not yet be reflected on every device. That is not automatically a bug if the proposal explicitly promises convergence within a few seconds. It is a bug if the product promise was immediate cross-device visibility.

Prediction check: If the notification worker is down at step 6, should the learner-facing progress save fail?

No. In this proposal, notification work is derived work. The accepted progress event should remain durable, the learner should keep moving, and operators should see a notification backlog. If the save fails because the notifier is down, the implementation has violated the proposal's central mechanism.

Compare Options With Honest Losses

A proposal becomes credible when it shows that the team compared real alternatives. The point is not to fill a ritual section called "options considered." The point is to prove that the chosen design beat plausible choices under the stated constraints.

For progress tracking, the proposal might compare:

Option A: keep synchronous writes and improve retry logic
  Wins:
    simpler mental model, fewer moving parts
  Loses:
    downstream notification and analytics work still threaten the write path

Option B: append accepted progress events and build async consumers
  Wins:
    durable acceptance, isolated downstream work, better audit trail
  Loses:
    lag, duplicate delivery handling, consumer backlog operations

Option C: build a full event-sourced progress platform immediately
  Wins:
    strong history model, flexible replay, rich audit semantics
  Loses:
    more migration risk and operational complexity than the current pressure earns

This section should not pretend every option is equally good. It should state why the selected design is the best fit for the current pressure. In this scenario, option B may be the right middle move: it separates accepted progress from derived consumers without forcing the team into a full event-sourcing platform before it needs one.

The useful review question is: "Did the chosen option lose in a way we can live with?" If option B introduces lag and duplicate delivery, the proposal must say how much lag is acceptable and how consumers will be idempotent. If the team cannot answer that, the alternative comparison is not finished.

Walk The Degraded Path

Most architecture mistakes hide in degraded behavior. The steady-state diagram looks calm; production is where dependencies stall, consumers retry, messages duplicate, and migrations pause halfway.

A strong proposal includes at least one degraded path:

Scenario:
  notification worker is unavailable for 20 minutes

Expected behavior:
  Progress API continues accepting valid updates.
  Accepted events remain durable.
  Progress projection continues if it does not depend on notifier.
  Notification backlog grows.
  Alert fires when backlog age exceeds threshold.
  Worker resumes and drains idempotently.

User-visible result:
  learner progress is saved and visible;
  notifications may arrive late or be skipped according to policy.

Operator signal:
  backlog age, retry count, dead-letter count, consumer lag.

This path reveals whether the design's promises are coherent. If notification lag is acceptable, the product team should know. If some notifications become worthless after a time window, the proposal should say whether to send them late, drop them, or compact them. If duplicate events can create duplicate notifications, the proposal should require an idempotency rule.

The same proposal should include a rollout path. A design that works only after every client, API, projection, and consumer moves at once is risky. A safer migration may look like this:

1. write current path and new event path in parallel
2. compare projection output against existing progress view
3. enable read traffic for a small cohort
4. expand cohort while watching lag and mismatch metrics
5. cut over default reads
6. keep rollback path until event path has survived peak traffic

The trade-off is extra engineering work. Dual writes, comparison jobs, and rollback plans are not free. But they convert one large bet into a sequence of measured steps. That is often the difference between an architecture proposal and an architecture gamble.

Review The Proposal Like A System

Reviewing an architecture proposal is not voting on whether the diagram looks reasonable. It is testing the argument. A reviewer should be able to reconstruct the design from problem to mechanism to failure behavior.

Use this checklist:

Problem:
  Can I restate the pressure without naming the chosen technology?

Invariants:
  Can I name what must remain true under retries, lag, and partial failure?

Mechanism:
  Can I trace one accepted request through the design?

Alternatives:
  Do I understand why the rejected options lost?

Degraded behavior:
  Can I describe what happens when one dependency is slow or unavailable?

Rollout:
  Is there a measured migration and rollback path?

Operations:
  Do we know which metrics, alerts, and ownership boundaries are required?

Review comments should attach to one of those categories. "This seems complex" is a start, but it becomes useful when converted into a sharper claim: "The proposal accepts consumer lag, but does not define a maximum backlog age or a product policy for late notifications." That comment tests an operational gap rather than expressing a vague preference.

Quick check: A reviewer says, "Why not just use Kafka?" What is missing from that question?

The question jumps to a tool before naming the design pressure. A better version is: "Which property do we need from the event path: durable ordering, replay, consumer isolation, throughput, or operational familiarity? Once that is clear, we can compare Kafka, a database-backed outbox, or another mechanism fairly."

Common Failure Modes

The proposal is mostly a diagram. Diagrams are useful, but they compress reasoning. Add problem framing, invariants, alternatives, traces, degraded paths, and operating signals. The diagram should support the argument, not replace it.

The proposal hides the cost of the chosen design. Every mechanism buys something by spending something else. Async consumers buy isolation by spending consistency simplicity. Edge placement buys latency by spending invalidation complexity. A proposal that names only the benefit is not yet honest enough to review.

The review becomes a taste debate. This usually means the proposal lacks shared criteria. Bring the conversation back to user promises, invariants, failure behavior, rollout risk, and operational ownership.

The document freezes after approval. A proposal should become team memory, not a dead artifact. If the rollout teaches the team that an assumption was wrong, record the change in the proposal or in a follow-up architecture decision record.

Practice: Review A Proposal Fragment

Read this fragment:

We will move progress tracking to an event-driven architecture.
The API will publish progress events. A projection service will update the
read model. Notification and analytics services will consume the events.
This makes the system scalable and easier to extend.

Before rereading the lesson, write the five most important review questions. A strong answer should include questions like:

  • What exact user or operational pressure is forcing this change?
  • What invariant protects accepted progress updates?
  • What lag is acceptable between event acceptance and read-model visibility?
  • What happens if a consumer is down, slow, or processes an event twice?
  • Which alternatives were considered, and why did they lose?
  • How will the rollout compare old and new progress views?
  • Which metrics prove the design is healthy?

Now improve the fragment in one sentence:

We will append accepted progress updates to a durable event path so the
learner-facing save can succeed independently of notification and analytics
work, while projections converge within a defined window and operators track
consumer lag, duplicate handling, and rollout mismatches.

That sentence is not a full proposal, but it is reviewable. It names the mechanism, the user-facing promise, the accepted trade-off, and the operational evidence needed to trust the design.

Key Takeaways

  1. A proposal is a reviewable argument, not just a diagram or tool choice.
  2. The strongest proposals expose invariants, alternatives, failure paths, rollout plans, and operating signals.
  3. Good review comments test assumptions against concrete behavior under lag, retries, migration, and partial failure.
  4. Architecture proposals become valuable team memory when they record why a cost was accepted, not only what was built.
