Writing and Reviewing Architecture Proposals

By the end of this lesson, you will be able to...

  • Turn a design intuition into a proposal with a clear decision, invariants, alternatives, and evidence.

  • Trace both normal and degraded behavior through the proposed boundary.

  • Review a proposal by testing its assumptions, rollout plan, operating signals, and accepted costs.

Idea in one sentence: A useful architecture proposal makes a decision challengeable before implementation makes changing it expensive.

Core Insight

Lina completes lesson 006 on her laptop. A moment later, she opens the course on her phone and does not see the completion. Meanwhile, a launch campaign creates a burst of notifications and analytics work. Some progress saves now wait behind that downstream work.

An engineer says, “We should make progress tracking event driven.” That might be a good direction, but it is not yet a proposal. It names a technology shape without saying what promise failed, what must remain true, how the new path behaves when consumers fail, or how the team will know that migration is safe.

The naive model is that a proposal is a polished diagram plus a preferred tool. It works only when everyone already shares the problem, assumptions, and operational context. It breaks when a reviewer needs to ask: Can a learner lose accepted progress? How long may cross-device visibility lag? What happens when notifications are down? Can we roll back after half the readers move?

The stronger model treats the proposal as a reviewable argument:

pressure -> promises and limits -> alternatives -> chosen boundary
-> normal and degraded traces -> rollout evidence -> accepted cost

The document does not eliminate uncertainty. It puts uncertainty where a team can test it.

The Promise We Need to Keep

Start with the decision frame, before naming a log, broker, or vendor.

Observed pressure:
  notification and analytics work share a path with learner progress saves.

Product promises:
  once a valid progress update is accepted, it must not disappear;
  the save should not wait for notification or analytics work;
  another device should show accepted progress within a stated window.

Non-goals:
  this decision does not redesign billing, quiz scoring, or course enrollment.

Evidence needed:
  trace time on the current write path; consumer lag; cross-device mismatch rate.

An invariant is a rule the design must protect. Here, a useful invariant is: an accepted progress update remains durable even if a downstream worker is unavailable. The stated convergence window is a different kind of promise. It may permit a brief delay after acceptance, but it must be measurable.

Check: Why is “move progress tracking to an event-driven architecture” an unready opening?

Think first, then reveal.

Answer: It proposes a shape before the decision criteria. A reviewer cannot tell whether the current failure is durability, latency, duplicates, consumer coupling, or something simpler such as missing idempotency. The frame makes disagreement productive.

The Naive Design

The current path writes progress and waits for several kinds of work:

client
  -> Progress API
  -> primary progress record
  -> notification work
  -> analytics work
  -> return success

This is easy to understand while traffic is low and downstream work is quick. It breaks when a slow notification provider or analytics consumer adds waiting to a learner action that should be accepted independently. Adding retries can reduce transient failures, but it does not separate the responsibility for accepted progress from derived side effects.

The design question is therefore narrower than “Should we adopt events?” It is: where should the authority to accept progress end, and which work may follow it asynchronously?

Design Alternatives

Compare options by the promises they keep and the costs they create.

Option Helps Loses or risks
Keep one synchronous path and tune retries fewer moving parts slow consumers can still threaten saves
Durable acceptance, then asynchronous projections and consumers isolates accepted saves from derived work lag, duplicate delivery, backlog operations
Full event-sourced platform now rich replay and audit history migration and operating complexity beyond the current evidence

The second option is a reasonable current boundary if traces show downstream coupling is the active pressure. It is not automatically superior. If the trace shows that an idempotency bug in the primary write is causing the symptom, a new event path would be a costly distraction.

This is the useful test from lesson 005: a familiar mechanism earns transfer only after local evidence identifies the pressure it addresses.

A Better Boundary

The proposal chooses durable acceptance before derived work:

Client
  -> Progress API
  -> durable accepted-progress record
  -> progress projection
  -> notification consumer
  -> analytics consumer

In plain English, the API first decides whether the update counts. It records that decision durably. Other components can learn from the accepted decision later.

In this scenario, the technical pattern is an accepted event path with projections and consumers. The name matters less than the boundary: notification and analytics are no longer allowed to decide whether the learner's progress save succeeds.

The proposal must also state ownership:

authoritative:
  accepted progress record and its idempotency rule

derived:
  cross-device projection, notifications, analytics

operational owner:
  the team responsible for backlog, replay, dead letters, and projection health

Without this, an asynchronous design merely moves ambiguity into a queue.

Worked Path: Accepted, Then Visible

Trace one update. This is a teaching model; the names and timing are illustrative.

Starting state:
  Lina has not completed lesson 006 on either device.

Step 1:
  The laptop sends {learner_id, lesson_id, attempt_id} to the Progress API.

Step 2:
  The API validates that Lina owns the course and checks attempt_id so a retry
  cannot create a second accepted completion.

Step 3:
  The API writes the accepted progress record durably.

Step 4:
  The API returns success to the laptop. The save promise is now kept.

Step 5:
  A projection updates the cross-device view. The phone may be briefly stale
  until this step completes within the stated convergence window.

Step 6:
  Notification and analytics consumers process the same accepted record later.

The intermediate state after step 4 matters. Lina's completion is accepted even though the phone view and notification may not yet be updated. That is acceptable only because the proposal says which result is immediate and which result may lag.

So far, the boundary preserves durable acceptance while making derived delay observable. It does not make every view instantly consistent, and it does not remove the need for idempotent consumers.

What This Changes

Before this model, a design review can get stuck on a question such as “Should we use a broker?” That question is too late and too narrow. It assumes the team already agrees on the pressure, the immediate promise, the permitted delay, and the facts that must survive a failure.

After this model, the reviewer can inspect each claim separately. If the real pressure is a duplicate-write bug, the event path may not earn its cost. If the learner needs immediate cross-device visibility, the projection cannot be treated as ordinary derived work. If notification delivery is legally or commercially required, its outage policy needs a stronger promise than “eventually.” The proposal has not made the choices for the team. It has made the choices visible enough to challenge.

This changes the decision from “adopt an architecture” to “accept this boundary under these observable conditions.” That is a smaller and safer claim. It also gives future operators a reason for every important signal: the signal exists because a stated promise or risk needs evidence.

The Degraded Path

Now test the argument when a dependency fails:

Scenario:
  notification consumer is unavailable for 20 minutes.

Expected behavior:
  the API continues to accept valid progress updates;
  accepted records stay durable;
  the progress projection continues if it is independent of notifications;
  notification backlog age grows and an alert fires;
  recovery drains work idempotently under a stated policy for late messages.

User-visible result:
  progress is saved; a notification may arrive late or be omitted if its value expires.

This degraded trace reveals a trade-off that a diagram can hide. The design buys isolation for learner saves. It costs consumer lag, replay behavior, duplicate handling, and an operations commitment. If the team cannot say whether a twenty-minute-late notification should send, compact, or drop, the proposal has left a product decision undefined.

Operational Consequences and Rollout

The proposal needs signals tied to both the promise and the new risk:

Outcome signals:
  accepted-save latency; cross-device projection freshness; mismatch rate

Safety signals:
  consumer backlog age; retry and dead-letter counts; duplicate side effects

Decision signals:
  projection comparison mismatch; rollback trigger; percentage of traffic on new reads

Do not migrate every writer and reader at once. A bounded rollout can make the decision reversible:

1. record the new accepted path alongside the current result;
2. compare the projection with the existing progress view;
3. enable new reads for a small cohort;
4. expand only while freshness and mismatch guardrails remain healthy;
5. retain a tested rollback path until the new path survives representative traffic.

This adds temporary complexity. Dual paths and comparison jobs cost engineering time. That cost is worthwhile when it discovers a false assumption before a full cutover. It becomes wasteful when the team keeps both paths without a decision metric or removal plan.

Design Review

A review should test the proposal's argument, not vote on its diagram. Ask questions in these categories:

Review lens Question
Pressure Can we restate the observed problem without naming the chosen technology?
Invariant What remains true under retries, lag, and a consumer outage?
Boundary Which component has authority to accept progress, and which work is derived?
Alternative Why did the simpler and broader options lose under current evidence?
Degraded path What does a learner see, and what does an operator see, when a consumer is down?
Rollout Which comparison, guardrail, and rollback rule make migration safe enough?

Convert taste into testable comments. “This seems complex” becomes “The proposal introduces consumer lag but never states its maximum acceptable age or who owns the dead-letter queue.” That is a comment the author can answer with a decision, evidence, or a changed boundary.

Common Confusions

Confusion: “Asynchronous means reliable.”

Why it is tempting: a queue separates callers from a slow consumer.

Better model: it can isolate the accepted path, but it creates lag, duplicate delivery, backlog, and recovery obligations. Reliability comes from the whole rule set, not from the word asynchronous.

Confusion: “A rollout plan belongs after the architecture decision.”

Why it is tempting: rollout sounds like implementation detail.

Better model: a design that cannot be measured, compared, and safely reversed may be too risky for the stated pressure. The migration path is evidence that the boundary can be introduced responsibly.

Practice: Repair a Proposal Fragment

Review this fragment:

We will use an event-driven architecture for progress tracking.
The API will publish events, and several services will consume them.
This will make the platform scalable and extensible.

A good review should request:

  • the user and operational pressure that justifies the change;
  • the invariant for an accepted progress update and the idempotency rule;
  • the allowed projection lag and behavior when consumers are unavailable;
  • alternatives with their concrete losses;
  • rollout comparison signals, a rollback condition, and an operational owner.

Then write one replacement sentence. A reasonable answer is:

We will record a valid progress update durably before derived notification and
analytics work, so learner saves survive consumer outages while projections
converge within a stated window and operators watch backlog, duplicates, and
old-versus-new view mismatches during rollout.

Key Takeaways

  • A proposal begins with a pressure, promises, non-goals, and evidence—not a tool name.
  • The chosen boundary must show who accepts the authoritative fact and which work may lag.
  • A normal trace and a degraded trace expose different assumptions; both belong in a reviewable decision.
  • Rollout metrics, guardrails, ownership, and rollback conditions are part of the architecture, not postscript operations.
