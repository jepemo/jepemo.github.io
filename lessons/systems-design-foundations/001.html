Constraint-Driven System Design

By the end of this lesson, you will be able to... frame a system design problem before choosing tools, use rough numbers to find pressure points, and explain why each major component exists.

Idea in one sentence. A system design becomes defensible when every important component can be traced to a constraint, an invariant, or a cost the team intentionally accepted.

Core Insight

Imagine a team building a global learning platform. Students stream lessons, resume progress across devices, submit quizzes, search for courses, and receive notifications when new material is published. A weak design discussion starts with familiar boxes: API service, database, cache, queue, CDN, Kubernetes. Those boxes may all appear eventually, but naming them first hides the real work.

The stronger starting point is to ask what the system must protect. A quiz submission should not be duplicated because the user retried on a bad connection. A learner's progress should converge to the newest valid position, even if mobile and laptop updates arrive out of order. Video analytics can lag. Search indexing can lag. Billing and entitlements cannot be ambiguous. These are not implementation details. They are constraints on the architecture.

Constraint-driven design means you first expose the pressures that shape the system, then choose mechanisms that fit those pressures. A cache is not good because caches are common. It is good when it relieves a read-heavy path without pretending to be the source of truth. A queue is not good because asynchronous systems sound scalable. It is good when it removes derived work from the user-facing path and gives operators a visible backlog to manage.

The misconception to avoid is that architecture is mainly about drawing the correct topology. The topology is the residue of the reasoning. A diagram becomes useful only when each box and arrow answers a concrete question: what invariant does this protect, what pressure does this relieve, what failure does this isolate, and what new cost did we accept?

Start With What Must Stay True

The first design move is to name invariants. An invariant is a property the system should keep true across retries, crashes, delays, concurrency, and partial failure. In plain language, it is one of the promises the architecture is not allowed to casually break.

For the learning platform, useful invariants might be:

  • a paid learner should not lose access because a retry arrived twice
  • a quiz submission should be recorded at most once for the same attempt
  • lesson progress should eventually reflect the newest valid position
  • billing and entitlement state should be authoritative
  • analytics and recommendation events may lag without corrupting user-visible state

Notice that these statements are more precise than "the platform should scale." They tell you what kind of correctness matters. They also split the product into different paths. Quiz attempts and entitlements need stronger authority. Video analytics can be derived later. Progress updates are frequent and small, so they need idempotency and ordering rules more than they need a perfectly synchronous global transaction.

That split is the beginning of architecture. The team can now avoid a common failure: giving every feature the same consistency, latency, and durability model. Treating every path as equally strict makes the system slow and expensive. Treating every path as loose makes correctness leak into the product. Constraint-driven design is the discipline of separating those paths before choosing components.

Quick check: If a mobile client sends progress 12:40, then retries and sends 12:30 after a delay, what should the progress service do?

It should not blindly accept the later-arriving request. A reasonable rule is to keep the newest valid progress position for that lesson attempt, or to attach monotonic sequence numbers so stale updates are ignored. The exact rule depends on product semantics, but the important move is that the invariant is named before the storage design is chosen.

Use Rough Numbers To Find Pressure

After invariants, use order-of-magnitude estimates. These estimates are not predictions. They are pressure detectors. They reveal which paths deserve early architectural attention and which ones can remain simple.

Suppose the platform expects:

  • 3 million daily learners
  • 250,000 peak concurrent video viewers
  • one progress update every 10 seconds while a lesson plays
  • 20,000 notification fan-outs when a major course launches
  • 5,000 quiz submissions per minute during a certification deadline

The progress path alone could produce about 25,000 writes per second at peak:

250,000 concurrent viewers / 10 seconds between updates = 25,000 progress updates per second

That number does not prove you need a particular database, broker, or cache. It does tell you what to inspect. Are progress writes idempotent? Can hot lessons create uneven write patterns? Can updates be batched without hurting user experience? What happens if a device reconnects and replays stale progress events? Which metric would show that the path is falling behind?

Now compare that with video delivery. Video traffic is not mainly a transactional-write problem. It is bandwidth-heavy and geographically sensitive, so object storage, CDN behavior, cache hit rate, and regional latency matter more. Search indexing is different again: it is read-heavy and can tolerate freshness delay, so a derived index is often appropriate. Notifications are bursty fan-out work, so queues and worker capacity become central.

The useful design artifact is not a single total traffic number. It is a pressure map:

Path                         Main pressure              Likely design concern
---------------------------  -------------------------  ------------------------------
Video playback               bandwidth + geography      CDN, object storage, cache hit rate
Progress updates             frequent small writes      idempotency, ordering, write load
Quiz submissions             correctness under retry    attempt identity, transactions
Search                       derived read model         indexing lag, freshness boundary
Notifications                burst fan-out              queues, worker capacity, backlogs

So far, the design has become easier, not harder. The team no longer needs one grand architecture that treats all work the same. It needs several paths with different constraints and an explanation for each boundary.

Work Through A Small Design Pass

Start with a naive design:

Learner app -> API -> primary database
                    -> send notification
                    -> update search
                    -> write analytics
                    -> store progress

This is simple, but it hides several coupled risks. If search indexing slows down, progress writes may slow down. If notification fan-out spikes, quiz submissions may share the same failure surface. If analytics ingestion fails, the user-facing request may now depend on a non-critical subsystem.

A constraint-driven pass separates authority from derived work:

Learner app
  -> API gateway
  -> authoritative services
       -> enrollment and entitlement store
       -> quiz attempt store
       -> progress store
  -> event log or queue
       -> search indexing workers
       -> notification workers
       -> analytics pipeline

Video playback
  -> CDN
  -> object storage

The key is not that this diagram has more boxes. The key is that each box has a reason:

  • The entitlement store protects the invariant that access decisions are authoritative.
  • The quiz attempt store protects against duplicate or ambiguous submissions.
  • The progress store is optimized for frequent, idempotent progress updates.
  • The event log or queue decouples derived work from the user-facing path.
  • Search, notifications, and analytics can lag because they are downstream projections.
  • The CDN exists because video playback is dominated by geography and bandwidth, not by the same write path as progress.

Now trace one request. A learner completes a lesson on a phone:

1. Client sends: user=42, lesson=9, progress=complete, event_id=abc.
2. API authenticates the learner and checks entitlement authority.
3. Progress service sees event_id=abc and records completion if it has not already processed it.
4. Progress service emits LessonCompleted(user=42, lesson=9).
5. User receives success after the authoritative progress write.
6. Search, notifications, analytics, and recommendations consume the event later.

If step 6 falls behind, the learner should not lose the completion. Operators should see queue lag, worker errors, or retry counts, but the authoritative user promise is already protected. If step 3 fails, the user-facing request should not pretend success merely because analytics accepted an event. Authority and derivation stay separate.

This is the central mechanism: constraints shape ownership, ownership shapes the write path, and the write path defines what can safely become asynchronous.

Trade-offs And Failure Modes

Constraint-driven design does not automatically make the system smaller. It often makes the reasoning clearer before it makes the topology simpler. Sometimes the right answer is still a modular monolith with a single database, especially when the team is small and the load is modest. The point is not to distribute early. The point is to know which pressure would justify distribution later.

The main trade-off is complexity versus fit. Separating search indexing from progress writes makes the user-facing path more resilient, but it introduces queue operations, replay semantics, and freshness questions. Adding a cache can reduce read latency, but it creates invalidation and stale-read behavior. Splitting services can isolate ownership, but it adds network failure, deployment coordination, and observability burden.

Common failure modes include:

  • Tool-first design: The team picks Kafka, Redis, or microservices before naming the pressure. The fix is to write the invariant and workload shape next to each proposed component.
  • Uniform guarantees: Every feature gets the same strict consistency or the same loose eventual behavior. The fix is to classify paths by authority, latency, durability, and acceptable lag.
  • Fake precision: The team refuses rough estimates because they are not exact. The fix is to use estimates as ranges that reveal order-of-magnitude pressure, not as forecasts.
  • Hidden derived state: A cache, index, or analytics table starts acting like truth. The fix is to name the authoritative owner and document what derived views may lag or lose.

Operational signals should match the constraints. For progress writes, watch write latency, duplicate event rate, stale update rejection, and storage saturation. For notifications, watch queue depth, worker retries, and time-to-delivery. For video, watch CDN hit rate, origin load, startup latency, and rebuffering. A design is not fully explained until it says which signals would prove its assumptions are holding.

Practice: Review A Tiny Architecture

Consider this proposal for the learning platform:

All learner actions write to one database.
A background job reads changed rows every minute and updates search, analytics, and notifications.
The API returns success after the database write.

Before rereading, classify the design:

  1. Which part is authoritative?
  2. Which work is derived?
  3. What pressure might break first?
  4. What signal would you watch?

One reasonable answer:

  • The primary database is authoritative for learner actions.
  • Search, analytics, and notifications are derived.
  • The background job may become the bottleneck if change volume grows or if notification fan-out spikes.
  • Watch job lag, rows scanned per minute, retry counts, and time from learner action to derived update.

This design may be acceptable early. It is simple, and it keeps derived work off the request path. It becomes risky if the polling job creates database load, if derived updates need tighter freshness, or if different downstream systems need independent replay. At that point, a durable event log or queue may become justified. The important thing is that the move would be explained by pressure, not by fashion.

Key Takeaways

  • Start system design by naming user promises, invariants, and acceptable failure modes before choosing tools.
  • Rough estimates are pressure detectors: they show which paths deserve architectural attention first.
  • A useful architecture diagram is an argument where every component maps to a constraint, invariant, or accepted cost.
  • Derived work can lag only when the authoritative path is explicit and protected.
