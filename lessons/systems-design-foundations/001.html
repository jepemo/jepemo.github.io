Constraint-Driven System Design

By the end of this lesson, you will be able to...

  • Turn a vague system request into promises, invariants, and pressures that a design must address.

  • Use a small, explicitly illustrative estimate to identify which path deserves attention first.

  • Explain why a proposed component belongs in a design, including the cost it introduces.

Idea in one sentence: A design is defensible when every important box exists to protect a promise, relieve a measured pressure, or accept a named cost.

Core Insight

A team is planning a learning platform. Learners watch video, resume lessons on several devices, submit quizzes, search for courses, and receive notifications. The first architecture meeting produces a familiar shopping list: an API, a database, a cache, a queue, a content delivery network (CDN), and perhaps several services.

The list is not wrong. The problem is that it does not yet answer a useful question: what must each part protect?

Suppose a learner finishes a lesson while their phone has a poor connection. Retrying the request must not record two completions. A notification may arrive late without damaging the learner's progress. A video may need to start quickly in several regions. Those are different promises. They create different pressures and allow different kinds of delay.

Constraint-driven design starts there. It does not ask, “Which technology should we use?” It asks, “What must remain true, what can wait, and what will become painful first?” Only then can a cache, queue, database, or CDN earn its place.

The Confusion This Concept Solves

It is tempting to treat a system design as a diagramming exercise. The team draws a client, an API, a database, and arrows between them. Then it adds components that look common in large systems.

That approach works for a tiny product when every action has roughly the same cost and importance. One database can hold the small amount of state. A background task can do secondary work. A delayed notification is only a minor annoyance.

The model breaks when different paths need different treatment. Consider these statements:

  • “A learner who paid must keep access after a retry.”
  • “A lesson completion must not disappear once the system accepts it.”
  • “Search can be a few minutes behind.”
  • “Video should start quickly for learners far from the origin server.”

If the design gives all four statements the same latency, durability, and consistency behavior, it will either do too much coordination or not enough. The missing move is to name the constraint before proposing the mechanism.

From Product Language to Design Constraints

Start with product language. A learner does not ask for “an idempotent write path.” They expect not to lose progress or be charged twice. The technical term comes after the promise is clear.

Plain meaning: some outcomes must stay true even when requests retry, messages arrive late, or a worker fails.

In this lesson's scenario: one accepted completion must remain one completion, even if the phone sends the same request twice.

Technical name: an invariant is a property the system is designed to preserve. An authoritative path is the path whose accepted result the product treats as the answer.

Now make the distinction visible:

Path User promise Must stay true Can wait? Likely pressure
Lesson completion The learner's progress is saved once A valid accepted completion is durable and not duplicated No, for acceptance retries and write rate
Search A course can be found The index reflects course data eventually Yes indexing lag and read load
Notification A learner hears about a new course A delivery attempt is tracked by policy Usually burst fan-out and retries
Video playback A video begins quickly The right content is served with acceptable delay Not fully bandwidth and geography

This table is a teaching model, not a universal architecture. A medical alert, for example, could make a notification much less tolerant of delay. The value of the table is that it forces the team to state the condition instead of treating every feature as equally strict.

Check: A mobile client sends progress 12:40, times out, and later retries an older update for 12:30. What is the first design question?

Think first, then reveal.

Answer: Ask which progress rule the product promises: perhaps “keep the newest valid position” or “accept only increasing client sequence numbers.” Do not begin by choosing a database. The rule determines what counts as stale and what the write path must preserve.

Rough Numbers Reveal Pressure, Not Destiny

After naming promises, use rough estimates. These numbers are illustrative. They are not a forecast and they do not select a product for you. Their job is to turn “we need to scale” into an inspectable question.

Assume the platform has 250,000 learners watching at peak. If every player sends one progress update every 10 seconds, the progress path receives about 25,000 update attempts per second:

250,000 concurrent learners / 10 seconds = 25,000 updates per second

That estimate does not prove that the team needs a particular queue, database, or cache. It does change the review questions:

  • Can the progress path identify a retry without recording it twice?
  • Are some courses or events much hotter than others?
  • Can a client send fewer updates without breaking the product promise?
  • Which signal will show that accepted updates are falling behind?

Different paths lead to different questions. Video delivery is mainly sensitive to bandwidth, geography, cache behavior, and start-up delay. Search is read-heavy and can usually tolerate a freshness boundary. Notifications can be bursty, so backlog age and retries matter. A single total “requests per second” number hides these differences.

Worked Classification: One Lesson Completion

Now use the constraint map to inspect one small path. A learner completes lesson 009 on a phone. The phone uses an event identifier so a retry can be recognized.

Client -> Progress API -> progress store -> downstream workers

The worked path is:

Starting point:
  learner 42 completes lesson 009; the phone sends event_id=abc.

Step 1:
  The API checks that learner 42 is entitled to update this course.

Step 2:
  The progress path checks whether event_id=abc was already accepted.

Step 3:
  It records the completion and the event identity together.

Step 4:
  The API returns success only after that authoritative write succeeds.

Step 5:
  Search, analytics, recommendations, and notifications consume the accepted
  completion later, according to their own freshness and retry policies.

The important intermediate state is after step 4 and before step 5. The learner may see the completion immediately while a recommendation is still stale. That is acceptable only because the design has explicitly separated the authoritative promise from derived work.

If this fails... The system should do... Why
The progress write fails Return failure or a retryable result The system must not claim that completion was saved when it was not.
A notification worker is down Keep the accepted completion and expose backlog or retries Notification delivery is downstream work in this example.
The same event retries Recognize event_id=abc and preserve one completion The invariant is about the accepted outcome, not the number of network attempts.
Search is behind Let the existing course and progress path continue Search is a derived view, not proof that the course exists.

So far, we have not selected a final topology. A durable event log or queue may be a good later choice for downstream work. A periodic job may be enough for a small product. The constraint map tells us what any chosen mechanism must accomplish and what signal will show its limit.

What This Is Not

Constraint-driven design is not a rule that every feature needs a separate service. A small team may keep progress, search updates, and notifications inside one modular application. The boundaries still matter because the team can decide which work is allowed to delay the user.

It is also not fake precision. An estimate such as 25,000 updates per second is useful even when it is wrong by a factor of two. It tells the team to investigate the frequent-write path. It does not replace load tests or production measurements.

Finally, it is not an excuse to say “eventual consistency” whenever a path is inconvenient. A path may lag only after the team identifies the authoritative result and checks that users can tolerate the delay.

Consequences, Trade-offs, and Limits

Separating authoritative writes from derived work often improves the user-facing path. A slow analytics consumer no longer needs to block lesson completion. It also creates work: retry policies, replay behavior, freshness expectations, and signals for backlog or stale data.

This is a situated preference, not a universal law. For a small platform with modest traffic, one database and a periodic job may be the clearest design. It becomes risky when the job scans too much data, a derived path needs independent retries, or the acceptable freshness window gets shorter.

The signals should follow the promises. Watch write latency, duplicate-event handling, and storage saturation for progress. Watch backlog age, retry count, and delivery latency for notifications. Watch cache hit rate, origin load, start-up delay, and rebuffering for video. A design is incomplete when it names a component but cannot say what would reveal that the component is under pressure.

Common Confusions

Confusion: “Scaling means adding a cache and a queue.”

Why it is tempting: these components appear in many architecture diagrams.

Better model: add a mechanism only after naming the pressure it relieves and the cost it introduces.

Confusion: “All data needs the same consistency.”

Why it is tempting: one global rule feels safer and easier to explain.

Better model: give each promise the lightest guarantee that protects it. A payment and a search index are not the same product contract.

Confusion: “A derived system can become the source of truth if it is fast.”

Why it is tempting: cached and indexed answers are often convenient.

Better model: convenience does not create authority. Name the owner of the fact and the allowed freshness of each derived view.

Check Your Understanding

Check: A team says, “We need Kafka because notifications may spike.” What is missing from that statement?

Think first, then reveal.

Answer: The pressure is plausible, but the team still needs the notification promise, expected burst shape, acceptable delay, retry policy, and failure signal. Kafka may be one fit; the pressure does not prove it is the only fit.

Check: Which is a better invariant: “the platform should scale” or “an accepted quiz attempt is not recorded twice when the client retries”?

Answer: The second. It states an observable property that a write path and its tests can protect. “Scale” is a broad goal that must be decomposed into paths and pressures.

Practice: Make a Pressure Map

An online course runs a certification event. At the deadline, many learners submit answers, the leaderboard updates, certificates are generated, and emails are sent.

Create a four-row pressure map for that event. For each row, name:

  • the user promise;
  • what must stay true;
  • whether the work may wait;
  • one pressure or signal to inspect.

A strong answer distinguishes the accepted exam submission from the leaderboard, certificate generation, and email delivery. It might say that a submission needs a durable attempt identity and a clear acceptance result, while a leaderboard may lag and an email worker should expose backlog rather than block submission. The exact components are secondary to the reasoning.

Key Takeaways

  • Start with the promise and invariant; components come later.
  • Rough estimates reveal which path deserves investigation. They do not predict production exactly.
  • An authoritative path decides what the product can honestly call successful; derived paths may lag only by an explicit policy.
  • Every component should answer a named pressure and expose a signal that shows when its assumptions stop holding.
