Capstone: Comprehensive Integration and Architecture Review

By the end of this lesson, you will be able to... run a complete architecture review loop, map design mechanisms to the pressures they solve, and identify the main failure signals that should shape rollout readiness.

Idea in one sentence. A systems design review is strongest when it compresses many concepts into one inspectable loop: pressure, actors, state, invariant, mechanism, cost, failure signal, and next decision.

Core Insight

Imagine the learning platform from the previous lessons is now real. It supports collaborative whiteboards, course progress, live cursors, offline edits, exported board snapshots, notifications, search, analytics, and regional failover. Product asks for a new architecture because large customers are using the platform during workshops, traffic spikes are no longer rare, and incidents increasingly involve more than one subsystem.

At this point, isolated concepts are not enough. You may know about queues, caches, event logs, regional control, proposals, case studies, and bounded automation. But in a real review, nobody hands you a problem labeled "use this mechanism." You see symptoms: stale progress, slow notifications, overloaded workers, confusing ownership boundaries, and a diagram with too many arrows.

The capstone move is integration. You reduce the system to a small set of questions that reveal the real pressure. Who acts? What state is shared? Which state is authoritative? What promise must not break? What work can lag? Which failure is acceptable, and which one is not? What is the lightest mechanism that protects the important invariant?

The misconception to avoid is that comprehensive review means mentioning every topic. It does not. A good review is selective. It uses the track's ideas only where they help explain a decision. If consensus is not needed, do not invoke it. If a queue solves the pressure but creates lag, say that plainly. If an edge cache helps static assets but not permission checks, keep the boundary sharp.

The Review Scenario

The proposed redesign has these pieces:

Clients:
  browser app, mobile app, offline editor

User-facing services:
  board session gateway
  progress API
  permission service

Durable state:
  board edit log
  progress event store
  ownership and permission database

Derived paths:
  notification workers
  search indexer
  analytics consumers
  export/render workers

Distribution:
  regional gateways for live sessions
  central authority for ownership and permission changes
  edge cache for static assets and exported snapshots

The team wants three outcomes:

1. live collaboration should feel local during workshops
2. accepted progress and committed board edits must not disappear
3. notification, search, analytics, and export work must not slow the user path

Those outcomes already contain tension. Local collaboration wants low latency. Durable truth wants careful ownership. Derived work wants decoupling. A naive architecture may try to optimize every path with the same mechanism, but that usually creates either unnecessary coordination or unsafe shortcuts.

The review should begin by separating promises:

authoritative promises:
  accepted progress is durable
  committed board edits preserve order for a board
  permission changes are enforced before protected access

derived promises:
  notifications are delivered or skipped by policy
  search catches up after lag
  analytics may trail production state
  exports can be regenerated

experience promises:
  live cursors feel responsive
  board saves do not wait for analytics
  static assets load quickly near users

This separation is the backbone of the review. It prevents the team from treating every subsystem as equally strict. It also prevents the opposite mistake: making a low-latency path responsible for state it cannot safely own.

Run The Structural Pass

Before choosing mechanisms, name the structure:

Actors:
  clients, regional gateways, APIs, durable stores, workers, operators

Shared state:
  board edits, cursor presence, learner progress, permissions, search index

Authoritative state:
  committed board edit log
  accepted progress events
  ownership and permission database

Derived state:
  notifications, analytics tables, search index, exports, edge snapshots

Failure model:
  retries, duplicate events, worker backlog, stale cache, regional latency,
  partial outage, offline client resync

Scope:
  per-board real-time interaction
  per-learner progress
  tenant-level traffic isolation
  global ownership policy

This pass turns a messy diagram into reviewable claims. It says what each part sees and what it is allowed to change. It also makes one key distinction visible: not all state deserves the same coordination cost.

For example, cursor presence can be approximate. If a live cursor disappears for a moment and returns, the product may tolerate it. A permission change is different. If a user loses access to a private board, stale permission state can become a security problem. Board edits sit somewhere else again: they need a consistent committed history for each board, but not necessarily one global order across every board in the company.

Quick check: Which state in this scenario can safely lag: permissions, accepted progress, search index, or committed board edit order?

The search index can lag most safely. Notifications and analytics can often lag too, depending on policy. Permissions and committed board edit order are stricter because they protect access and the user's durable work. Accepted progress must be durable immediately after acceptance, even if projections take a short time to converge.

Map Pressures To Mechanisms

Now choose mechanisms by pressure, not by fashion:

Pressure                                  Mechanism
----------------------------------------  ---------------------------------
static assets are large and global         edge cache with versioned assets
live cursors need low latency              regional session gateway
board edits need per-board order           board-scoped append log
progress must be durable after acceptance  durable progress event store
notifications/search/analytics are bursty  async workers with backpressure
one customer's workshop can spike traffic  per-tenant or per-board limits
permission changes must be authoritative   central policy/ownership boundary
operators face multi-signal incidents      bounded automation or playbooks

This map compresses the whole track. Constraint-driven design appears in the pressure column. Product promises appear in the split between authoritative, derived, and experience guarantees. Hybrid local/distributed design appears in the regional gateway plus central authority boundary. Optimization and trade-off work appears in choosing the lightest sufficient mechanism. Case-study discipline appears in not copying a famous architecture wholesale. Proposal discipline appears in making the choices reviewable. Future-systems discipline appears in bounding automation instead of trusting novelty.

The important part is that mechanisms do not compete globally. They specialize. Edge caching is appropriate for static assets and exported snapshots; it is not the owner of permissions. Async workers are appropriate for notification and analytics work; they are not allowed to decide whether a progress update was accepted. Regional gateways can improve live feel; they should not silently fork authoritative board history.

Walk One End-To-End Path

Review becomes much sharper when you trace one realistic request. Suppose a learner joins a workshop, edits a shared board, completes a lesson, and triggers notifications and analytics.

Starting state:
  learner has permission to board B
  board B has committed edit sequence 100
  learner has not completed lesson 008
  notification workers are healthy
  search index is 2 seconds behind

Step 1:
  client connects to nearest regional session gateway

Step 2:
  gateway checks current permission through authoritative policy path

Step 3:
  learner draws a shape; gateway accepts a low-latency session event

Step 4:
  board service commits the edit as sequence 101 in board B's edit log

Step 5:
  progress API accepts lesson completion and appends durable progress event

Step 6:
  projection updates learner progress view

Step 7:
  notification, search, export, and analytics workers consume derived events

Now inspect intermediate states. After step 3 but before step 4, a cursor or provisional shape may be visible locally, but the durable board history has not yet advanced. After step 5 but before step 6, the lesson completion is accepted and durable, but another device may briefly show the old progress view. After step 7, search and analytics may still trail.

Those intermediate states are not automatically failures. They are design promises that must be explicit. The architecture is acceptable only if the product and operations teams agree on which lag is visible, which lag is hidden, and which lag violates the promise.

The naive failure would be to let every downstream consumer participate in the user-facing path:

complete lesson
-> progress API
-> notification send
-> search update
-> analytics write
-> response to user

That path feels simple because it is linear, but it couples user success to derived work. A slow analytics sink can make the learner wait. A notification outage can make progress saving fail. The reviewed design separates acceptance from derived effects, then adds metrics so lag does not become invisible.

Review The Degraded Path

A useful capstone review must ask what happens when the system is stressed. Consider this incident:

Incident:
  one enterprise workshop creates 10x normal board activity
  export workers saturate shared capacity
  notification backlog grows
  live collaboration must remain usable
  accepted edits and progress must remain durable

Run the review loop:

Invariant:
  accepted board edits and progress events must not disappear

Can lag:
  exports, notifications, analytics, search

Must stay responsive:
  live board interaction and user-facing saves within defined limits

Mechanisms:
  per-board backpressure
  lower priority for export workers
  async notification retry
  backlog alerts
  tenant-level rate visibility

Failure signal:
  edit commit latency, progress acceptance errors, worker backlog age,
  dropped session events, regional saturation, retry storm

The right response is not "scale everything." It is to protect the core promises first. Pause exports. Reduce lower-priority worker concurrency. Apply per-board or per-tenant limits if one workshop threatens shared capacity. Keep accepting valid progress and committed edits if the durable path is healthy. Alert on backlog age rather than pretending derived work is instantaneous.

This degraded path also reveals a boundary for future automation. A bounded local agent might be allowed to pause export workers when live collaboration latency is threatened. It should not be allowed to rewrite permission policy, discard committed edits, or silently disable user writes. That is the same research-to-production boundary from the previous lesson, now applied inside a full architecture review.

Turn The Review Into A Rollout Plan

A design review is incomplete if it approves only the final shape. Real systems have to move from old behavior to new behavior while users are still active. That migration period is often riskier than the steady state because two versions of the truth, two code paths, or two operational dashboards may exist at the same time.

For this platform, a careful rollout could look like this:

1. instrument the current system before changing behavior
2. add the new event path in shadow mode
3. compare old progress views with new projections
4. route a small set of boards through regional gateways
5. enable derived workers behind backpressure and lag alerts
6. cache only versioned static assets first
7. expand tenant cohorts after peak-hour drills
8. keep rollback criteria visible until the new path survives incidents

The review should ask what each step proves. Instrumentation proves the team knows the baseline. Shadow mode proves the new path can observe the right events without owning user-visible behavior yet. Projection comparison proves that the derived view matches the old source closely enough. Small cohorts prove that regional gateways improve latency without confusing ownership. Backpressure proves that derived work can fall behind without damaging the user-facing path.

This is where architecture proposals become operational. A reviewer should not accept "we can roll back" as a vague comfort phrase. Rollback has to say what state can be reversed and what state cannot. If progress events have already been accepted in the new durable store, rollback cannot pretend those events never existed. The safer rollback may be to stop routing new traffic to the new path while continuing to drain or reconcile already accepted events.

Rollout also forces the team to name irreversible moves. Changing a cache policy is usually reversible. Changing the authoritative owner of board edit order is much more serious. Granting an automation layer production authority is reversible only if the team can revoke credentials, audit actions, and return to a manual playbook without losing operational skill.

Common Review Failures

Treating derived state as authoritative. Search, analytics, notifications, and exports are useful, but they should not decide whether the user's work exists. If a search index misses a newly edited board, that is a lag or indexing problem. If the edit log loses the board change, that is a durability problem. The review should keep those failure classes separate.

Hiding product promises inside infrastructure language. "Eventually consistent" is not enough. Eventually within seconds, minutes, or hours? Visible to whom? Acceptable for which path? A learner seeing stale progress for three seconds may be fine. A permission change taking three minutes to apply may not be fine. The review should translate technical consistency into user and operator promises.

Using one mechanism for every pressure. A team that likes event logs may try to event-source everything. A team excited about edge systems may move too much authority outward. A team worried about correctness may overuse global coordination. The capstone habit is to choose per pressure: cache what can be cached, coordinate what must be coordinated, queue what can lag, and keep authority where the invariant requires it.

Approving a design without failure signals. If no one can say which metric proves the design is failing, the review has not finished. For this platform, different promises need different signals: edit commit latency for durable collaboration, progress acceptance errors for learning state, permission freshness for access control, backlog age for derived work, and regional saturation for live experience.

Letting ownership blur during compromise. Many designs fail not because the chosen mechanisms are weak, but because the team never says who owns the final answer. A regional gateway can improve latency, but it should not quietly become the authority for global permissions. A projection can serve reads, but it should not become the only place where accepted progress is recoverable. When a compromise adds speed, the review must restate where truth still lives.

Decide Whether The Design Is Ready

Readiness is not "the diagram looks complete." A design is ready when its promises, mechanisms, costs, and signals line up.

Use this readiness checklist:

Problem:
  Do we know which user or operational pressure forced the redesign?

Promises:
  Are authoritative, derived, and experience promises separated?

Ownership:
  Is there one clear owner for each authoritative state?

Mechanism:
  Does each mechanism match a named pressure?

Intermediate states:
  Do we know what can be visible between acceptance and convergence?

Degraded path:
  Can the system shed or delay derived work without losing durable state?

Operations:
  Are the key metrics tied to the promises they protect?

Rollout:
  Can we migrate in measured steps and compare old and new behavior?

For this platform, the highest-risk questions are likely:

  • Can regional gateways improve live interaction without creating ambiguous board ownership?
  • Are permission checks fresh enough for the threat model?
  • Are progress events idempotent under retries?
  • Can worker backlogs be drained without duplicate notifications or repeated exports?
  • Do tenant limits protect shared capacity without surprising important customers?
  • Can operators distinguish a harmless derived backlog from a core durability problem?

Those questions are stronger than a generic approval. They tell the implementation team what must be proven before rollout.

Practice: Run The Capstone Review

Close the lesson for a moment and reconstruct the review loop from memory:

pressure
-> actors
-> shared state
-> authoritative state
-> invariant
-> mechanism
-> intermediate state
-> degraded path
-> operational signal
-> rollout decision

Now apply it to this proposal fragment:

To improve workshop performance, we will move board sessions closer to users,
publish progress events asynchronously, cache snapshots at the edge, and add
automation to pause background work during incidents.

A strong review should ask:

  • Which state is local, and which state remains authoritative elsewhere?
  • What exact promise does "closer to users" improve?
  • What happens to board edit order during regional failover?
  • When is a progress event considered accepted?
  • Which snapshots can be cached, and how are permission changes handled?
  • What background work can automation pause without human approval?
  • Which metric proves the design protected the user path?

One compact review answer:

The proposal is directionally reasonable if it keeps authority boundaries sharp:
regional gateways may own low-latency session handling, but committed board
history and permissions need explicit authoritative paths. Progress acceptance
should be durable before derived consumers run. Edge caching should apply to
versioned static assets or permitted snapshots, not live permission decisions.
Automation may pause derived work such as exports, but must preserve durable
edits, progress events, and access policy. Rollout readiness depends on commit
latency, progress acceptance errors, backlog age, cache staleness, and regional
failover drills.

That is the standard to carry forward. The review does not merely name technologies. It explains what each mechanism is allowed to solve, what it must not own, and which signals reveal whether the trade-off is working.

Key Takeaways

  1. Comprehensive review starts by separating actors, state, promises, invariants, and failure scope.
  2. Mechanisms should be chosen because they match a named pressure, not because they are broadly impressive.
  3. Intermediate states reveal whether lag, retries, and derived work are acceptable or promise-breaking.
  4. A design is ready when its operational signals prove that the chosen trade-offs are holding under stress.
