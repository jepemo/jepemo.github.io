Product Promises and Subsystem Guarantees

By the end of this lesson, you will be able to...

  • Classify product promises as authoritative, interactive, or derived work.

  • Assign each promise a subsystem guarantee and name what that subsystem must refuse to own.

  • Review a design for a guarantee that is too weak, too expensive, or attached to the wrong path.

Idea in one sentence: A product becomes easier to design when each promise gets the lightest guarantee that can keep it true.

Core Insight

Priya creates a shared project board. She invites Mateo. Both start drawing at the same time. Mateo sees Priya's cursor move, finds the board in search, and later receives a notification when Priya mentions him.

It is tempting to call all of that “the whiteboard system.” But the product has made several different promises. Board ownership must have a clear answer. Live cursors should feel immediate. Search may be briefly behind. A notification can retry later without undoing a drawing operation.

The first lesson taught us to name the pressure before choosing a component. This lesson takes the next step: assign each product promise to a subsystem guarantee. A guarantee says what a subsystem is responsible for making true, what delay it accepts, and what it must not quietly become responsible for.

The Promise We Need to Keep

Write promises in user language before drawing services. For the board, the team might agree on these:

P1. A board has one durable identity and owner.
P2. Only authorized people may open or edit the board.
P3. Collaborators in one active board see drawing changes quickly.
P4. A reconnecting collaborator can recover accepted recent work.
P5. Search can find saved boards after a bounded delay.
P6. Mentions create notifications without blocking drawing.
P7. Analytics records activity without deciding product correctness.

These promises differ in a useful way:

Promise class Plain meaning Typical guarantee Example
Authoritative The product needs one answer it can defend. Commit or reject the change clearly. Board ownership and access grants.
Interactive The user needs a fast local experience. Respond within a short latency target for the active session. Cursor and stroke fan-out.
Derived The work follows from an accepted fact. Process later with a stated freshness, retry, or loss policy. Search indexing, notifications, analytics.

This is a teaching model, not a universal taxonomy. Reconnect recovery is often mixed: the live session needs speed, while accepted edits need durable evidence. The point is to expose the tension instead of using one vague word such as “reliable.”

The Naive Design

A reasonable first design puts every step in one synchronous pipeline:

client
  -> write board metadata
  -> update live room
  -> index search
  -> send notification
  -> write analytics
  -> return success

This works while the product is small and all dependencies respond quickly. It is attractive because there is one visible path and one success result.

It becomes insufficient when the promises conflict. A slow notification provider should not make a stroke appear to fail. A search indexing error should not remove board ownership. Conversely, a fast session process should not invent permanent access rights merely because it sees who is currently connected.

The initial model treats every action as one unit of work. The stronger model separates the promises before it separates the deployment units.

Design Alternatives

There are several plausible ways to respond. Each one buys something and leaves a different risk.

Alternative What it buys What it risks
One strict path for every action A simple success rule and fewer moving parts. High latency and broad failure coupling; secondary work blocks the user.
Loose replication for every action Fast local responses. Ambiguous ownership and unsafe permission decisions.
Separate promise classes Each path pays for only the coordination it needs. More interfaces, metrics, and explicit failure policies.

The third option is usually the better fit for this scenario, but only under its stated constraints. It assumes that search and notifications can lag, while access decisions and accepted board state cannot be ambiguous. If the product promise changed—for example, a legal compliance alert must be delivered immediately—the classification would need to change too.

A Better Boundary

Now turn the promise map into subsystem guarantees. A subsystem is not defined only by the data it stores. It is also defined by what it refuses to decide.

client
  -> identity and access check
  -> board metadata authority
  -> board session service
  -> accepted edit record
  -> downstream workers
       -> search projection
       -> notification delivery
       -> analytics pipeline
Subsystem Guarantee it provides Must refuse to own Signal to watch
Metadata authority Board identity, ownership, and permission changes are committed or rejected clearly. Live cursor fan-out and search freshness. write latency, conflicts, permission failures
Board session service Active collaborators receive ordered room updates quickly enough for the interaction. Final authority for ownership and permanent membership. room latency, connected clients, dropped updates
Accepted edit record Accepted edits can be recovered after an ordinary reconnect. Sending notifications or deciding access. append latency, recovery failures, storage errors
Search projection Saved boards become discoverable within a freshness target. Proof that a board exists or that a user may access it. indexing lag, failed documents, freshness age
Notification worker Accepted mention events are delivered or retried by policy. Blocking a completed board action. backlog age, retries, dead-letter rate

“Authority” here means the official answer for a specific fact. It does not mean that one service controls the entire product. The session service can make a room responsive without becoming the final source of truth for access. The search index can be useful without deciding permissions.

Worked Example: Priya Invites Mateo

Follow one path through the design. This example uses illustrative identifiers and timings.

Starting point:
  Priya owns board 84. Mateo does not yet have access.

Step 1:
  Priya sends an invitation request for Mateo.

Step 2:
  The metadata authority checks Priya's ownership and records Mateo's grant.

Step 3:
  The metadata authority returns success after the grant is accepted.

Step 4:
  Priya and Mateo join board session 84. The session service checks the
  authoritative access result before admitting them.

Step 5:
  Priya draws stroke S1. The session service assigns room sequence 501 and
  fans the stroke out to active collaborators.

Step 6:
  The accepted edit is recorded for reconnect recovery.

Step 7:
  Workers later index the board and attempt the invitation notification.

After step 3, Mateo has access even if the notification worker is down. After step 5, Mateo may see the stroke before analytics has processed it. After step 7, search may still be behind. Those states are not automatically bugs. They are the stated costs of giving the user-facing actions a narrower dependency set.

Check: The notification provider fails after the invitation is accepted. Should the metadata authority undo Mateo's grant?

Think first, then reveal.

Answer: No. The access grant is the authoritative promise in this path. Notification delivery is a derived promise with a retry or visibility policy. Undoing the grant would let a downstream side effect rewrite the product's source of truth.

So far, we have separated three questions that often blur together: who may act, what is happening now, and what should happen later. The next lesson will ask how wide each of those decisions must travel through the system.

The Trade-off

Separate guarantees reduce unnecessary coupling. A notification provider can fail without changing whether Mateo has access. A search delay can affect discovery without deciding whether the board exists. That is the benefit.

The cost is extra boundary work. Each path needs an owner, a failure policy, and a way to observe whether it is keeping its promise. For a small application with modest load, one modular application and a periodic worker may be the clearest implementation. Splitting it into network services before a pressure appears can add latency, retries, and deployment work without improving a user promise.

Operational Consequences

Separate guarantees make failures easier to classify, but they do not make failures disappear.

If the metadata authority slows down, access changes and board creation may wait. That is serious because the affected promises are authoritative. If the session service slows down, collaborators may see delayed strokes while durable board ownership remains correct. If the notification worker slows down, operators should see a growing backlog while drawing continues.

This separation also changes what the team measures. A generic “whiteboard availability” metric is not enough. The team needs signals that match the promise:

  • permission decision latency and conflict rate for the metadata path;
  • room fan-out latency and reconnect success for live collaboration;
  • append failures and recovery gaps for accepted edits;
  • freshness age and failed updates for search;
  • queue age, retry count, and delivery delay for notifications.

This operational work is worthwhile when the product genuinely has different classes of work. It is over-design when a small application gains separate services without a concrete pressure or owner.

Common Confusions

Confusion: “A fast cache can own permissions.”

Why it is tempting: cached answers feel available and convenient.

Better model: a cache may accelerate an authoritative decision, but it needs a clear freshness and invalidation policy. It does not become the authority by being fast.

Confusion: “Interactive means eventually consistent.”

Why it is tempting: live interfaces often need low latency.

Better model: interactive work still needs a stated guarantee. In this case, the session service orders updates within a board and records accepted edits for recovery.

Confusion: “Separate promises require separate microservices.”

Why it is tempting: diagrams often map every boundary to a network process.

Better model: guarantee separation can exist inside a modular monolith. Deployment separation should earn its network and operations cost.

Design Review

Review this mapping before reading the answer:

Board ownership       -> eventually consistent search index
Live cursor updates   -> global transaction for every cursor movement
Notifications         -> synchronous call before the stroke succeeds
Analytics             -> async worker

Check: Which two mappings are most clearly wrong, and why?

Think first, then reveal.

Answer: Board ownership should not be decided by search because search is a derived view. Notifications should not usually block a stroke because they are a derived side effect. The global cursor transaction is also suspect: it gives a low-latency interaction a coordination cost that the stated promise may not need.

Practice: Write a Promise Map

Choose a shared document, marketplace, booking system, or another product with both user actions and background work. Write five promises. For each one, state:

  • whether it is authoritative, interactive, derived, or mixed;
  • the subsystem guarantee it needs;
  • what the subsystem must refuse to own;
  • one failure signal.

A good answer does not begin with product names. It makes the product promise and failure boundary visible first. For example, a booking confirmation may require a clear authoritative result, a seat map may need fast reads with a freshness limit, and a confirmation email may retry later without changing whether the booking exists.

Key Takeaways

  • Product promises become design constraints only when the system names its authority, delay tolerance, and failure boundary.
  • Authoritative, interactive, and derived work need different guarantees; a single uniform path is often either too weak or too expensive.
  • A subsystem has a healthy boundary when it can state both what it owns and what it refuses to own.
  • Service boundaries are optional early. Explicit guarantees and signals are not.
