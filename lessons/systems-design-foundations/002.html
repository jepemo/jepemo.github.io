Product Promises and Subsystem Guarantees

By the end of this lesson, you will be able to... separate product requirements into promise classes, assign each class to an appropriate subsystem guarantee, and review a design for mismatched coordination cost.

Idea in one sentence. A product is easier to design when you stop treating it as one system and instead map each user promise to the lightest subsystem guarantee that can protect it.

Core Insight

Imagine a collaborative whiteboard product used by remote teams. Users create boards, invite collaborators, draw at the same time, see live cursors, reconnect after a flaky network drop, search for old boards, and receive notifications when someone mentions them. If the design conversation starts with "we need a database, WebSockets, Kafka, Redis, and search," the team may build a plausible stack without knowing which promises the stack is protecting.

The better starting point is to split the product into promises. Some promises need one authoritative answer: a board exists, a user has access, an invitation was accepted, a saved object has an owner. Some promises need low latency but can tolerate temporary looseness: cursors should feel live, strokes should appear quickly, presence should update soon. Other promises are derived consequences: search should eventually find a board, notifications should be sent, analytics should record usage.

Those promises should not all receive the same coordination style. If every live cursor update waits for global agreement, the product will feel slow. If board ownership is propagated loosely with no clear authority, the product may expose private content or lose access decisions. The design skill is to match each promise to a guarantee: authority where ambiguity is unacceptable, local or session-level coordination where responsiveness matters, and asynchronous processing where lag is acceptable.

This is the project-level version of constraint-driven design. The previous lesson asked what the system must protect. This lesson asks a sharper follow-up: which subsystem owns each promise, what guarantee does it provide, and what cost or failure mode comes with that guarantee?

Classify Product Promises Before Drawing Components

Start by writing product promises in user language. Do not translate them to services yet. For the whiteboard, the list might look like this:

P1. A board has a durable identity and owner.
P2. Only authorized users can open or edit the board.
P3. Drawing should feel live to collaborators in the same session.
P4. A disconnected client should be able to recover recent work.
P5. Search should find saved boards.
P6. Notifications should be sent when someone is mentioned.
P7. Analytics should record board activity.

Now classify each promise by the kind of guarantee it needs:

Promise                     Class             Reason
--------------------------  ----------------  ---------------------------------------
board identity + owner      authoritative     ambiguity breaks the product contract
access control              authoritative     wrong answers leak or block content
live strokes + cursors      interactive       latency dominates user experience
reconnect recovery          mixed             recent state must be recoverable
search indexing             derived           useful if fresh, tolerable if delayed
notifications               derived/bursty    should happen, but not block drawing
analytics                   derived           valuable, not user-path authority

An authoritative promise needs a clear source of truth. In plain language, there must be one place or protocol the system treats as the official answer. An interactive promise needs fast coordination within a narrow scope, often a board session or room. A derived promise is downstream work produced from authoritative or accepted events; it may lag without invalidating the core user action.

Quick check: If search is down for five minutes, should users still be able to draw on an already-open board?

Usually yes. Search is a derived discovery path, not the authority for board existence or live collaboration. If search downtime prevents drawing, the architecture has probably coupled a downstream projection to the core interaction path.

Turn Promise Classes Into Subsystem Guarantees

Once the promises are classified, the architecture begins to take shape. You can now ask what guarantee each subsystem must offer, rather than asking which component sounds impressive.

One reasonable whiteboard design might look like this:

client
  -> edge/auth gateway
  -> board metadata service
       -> authoritative metadata store
  -> board session service
       -> in-memory room state + live fanout
       -> accepted stroke/event log
  -> async workers
       -> search index
       -> notification sender
       -> analytics pipeline

The metadata service owns durable board identity, ownership, and access control. Its guarantee is not "fast live drawing." Its guarantee is a clear answer about who may do what. It should be careful about idempotent board creation, invitation acceptance, and permission changes.

The session service owns low-latency collaboration within a board. Its guarantee is not eternal truth about every user in the product. Its guarantee is that active collaborators see responsive updates and that accepted drawing operations have enough order and recovery information to survive ordinary reconnects.

The worker systems own derived consequences. Their guarantee is not immediate user-visible correctness. Their guarantee is eventual processing with visible lag, retries, and failure handling. If notification workers fall behind, the board should not stop accepting strokes. If analytics drops a non-critical event after exhausted retries, it should not corrupt ownership.

So far, the design has separated three questions that are often confused:

Who is allowed?       -> authoritative metadata / access control
What is happening now? -> session service / live collaboration
What should happen later? -> async projections and side effects

That separation is the central mechanism of the lesson. Product promises become promise classes. Promise classes become subsystem guarantees. Subsystem guarantees determine coordination cost, failure behavior, and operational signals.

One useful way to test the mapping is to ask what each subsystem must refuse. A guarantee is not only what a subsystem does; it is also what the subsystem deliberately refuses to own.

Subsystem              Must accept                         Must refuse
---------------------  ----------------------------------  --------------------------------
metadata service       board identity, ownership, ACLs     live cursor fanout
session service        active room state, stroke order     permanent access authority
event log              accepted collaboration events       direct user authorization
search worker          searchable board projections        source-of-truth board existence
notification worker    mention/share side effects          blocking core edit success
analytics pipeline     usage facts and aggregates          product correctness decisions

This refusal list prevents a common drift. A session service often starts with a simple job: keep a room responsive. Then someone asks it to remember permanent membership because it already sees everyone online. Then another feature reads presence state as if it were access control. The system slowly turns temporary session knowledge into authority. The reverse can happen too: a metadata service that should answer ownership questions starts carrying live collaboration traffic and becomes too slow for interactive work.

Clear subsystem guarantees keep those pressures separated. The metadata service can be slower and more careful because wrong permission answers are serious. The session service can be faster and more local because it is not the final authority on every durable fact. Workers can retry and lag because they do not define whether the board action happened. The architecture becomes easier to review because each component has a job, a boundary, and a known way to fail.

It also becomes easier to change, because a new feature has to declare which promise class it belongs to before it borrows an existing path.

Walk Through One User Action

Trace a concrete action: Priya creates a board, invites Mateo, and both start drawing.

1. Priya creates board "Q3 Roadmap".
2. Metadata service assigns board_id=84 and owner=Priya.
3. Metadata store commits the board record.
4. Priya invites Mateo.
5. Metadata service records Mateo's access grant.
6. Both clients join board session 84.
7. Session service checks access, then admits both clients.
8. Priya draws stroke S1.
9. Session service assigns room sequence 501 and fans S1 to Mateo.
10. Session service appends accepted stroke event for recovery.
11. Async workers index the board title and send notification events later.

There are several intermediate states worth noticing. After step 3, the board exists even if notifications are down. After step 5, Mateo has access even if search has not indexed the board. After step 9, Mateo may see the stroke before every derived system has processed it. After step 10, reconnect recovery has something to replay.

Now compare that with a naive design:

all actions -> one synchronous pipeline
  -> write metadata
  -> update live room
  -> update search
  -> send notification
  -> write analytics
  -> return success

This feels simpler on a diagram but creates the wrong guarantee. A slow notification provider can delay live drawing. A search indexing failure can make board creation appear broken. Analytics ingestion can become part of the user contract by accident. The design has not separated authoritative, interactive, and derived promises.

Prediction check: If the notification provider is unavailable after Priya mentions Mateo, what should the product promise?

A reasonable answer is: the mention event should be accepted or recorded if the board action itself succeeds; notification delivery may lag and should be retried or surfaced as a worker problem. The user should not lose the board edit merely because the notification side effect is unavailable.

Trade-offs And Failure Boundaries

Mixed guarantees make the product fit reality better, but they add boundary work. The team has to document what success means in each subsystem.

For the metadata service, success means the authoritative change was committed or rejected clearly. Its main risks are duplicate creation, stale permissions, inconsistent ownership, and slow writes. Useful signals include write latency, conflict rate, permission check failures, and idempotency-key reuse.

For the session service, success means active collaborators receive responsive updates and can recover from ordinary disconnections. Its risks are hot rooms, fanout overload, lost room state, inconsistent ordering, and retry storms. Useful signals include room p95/p99 fanout latency, connected clients per board, reconnect success, dropped events, and per-room backpressure.

For worker systems, success means downstream work is processed within an acceptable freshness window. Their risks are queue lag, poison messages, duplicate side effects, and silent data loss. Useful signals include backlog age, retry counts, dead-letter rate, notification delivery latency, and search freshness.

The trade-off is that this design is more explicit and more operationally honest, but it is not free. Separate guarantees mean more interfaces, more metrics, and more careful documentation. The benefit is that failures stay closer to the promise they threaten. Search lag hurts discovery. Notification lag hurts communication. Metadata ambiguity threatens the product contract. Those are different severities and should not be hidden behind one generic "the whiteboard is down" bucket.

This is also where over-design can sneak in. A small prototype may not need all subsystems split into separate deployable services. It can still use the same promise map inside one modular codebase. The important point is not physical separation. It is guarantee separation. You can keep modules local today and still know which boundaries would deserve distribution later.

Practice: Review A Promise Map

Review this proposed mapping:

Board metadata       -> eventually consistent cache
Live drawing         -> strongly coordinated global database transaction
Search indexing      -> async worker
Notifications        -> synchronous call before draw succeeds
Analytics            -> async worker

Before checking the answer, identify two mismatches.

One reasonable critique:

  • Board metadata should not be owned by an eventually consistent cache. Metadata and access control are authoritative promises, so the cache may accelerate reads but should not become the source of truth.
  • Live drawing probably should not require a global database transaction for every stroke. The interactive path needs low latency and room-level ordering more than global serialization.
  • Notifications should usually not block drawing success. They are derived side effects and should normally be processed asynchronously with retries and visibility.

A better mapping would be:

Board metadata       -> authoritative metadata store + cached reads
Live drawing         -> board session service + accepted event log
Search indexing      -> async projection with freshness metric
Notifications        -> async worker with retry/dead-letter handling
Analytics            -> async pipeline with loss/quality policy

Close the lesson by applying the same review to a product you know. Pick five user promises. Mark each one as authoritative, interactive, or derived. Then write the subsystem guarantee and one metric that would reveal trouble.

Key Takeaways

  • Product requirements become clearer when you classify them as authoritative, interactive, or derived promises.
  • Subsystems should provide the lightest guarantee that protects the promise they own.
  • A design is production-minded when each promise has a failure boundary and an operational signal.
  • Physical service separation is optional early; guarantee separation is not.
