Designing Hybrid Local and Distributed Systems

By the end of this lesson, you will be able to...

  • Choose the narrowest coordination scope that can keep a stated product promise.

  • Distinguish authority, acceleration, and derivation in one hybrid request path.

  • Explain what pressure justifies widening a boundary and which new cost that move creates.

Idea in one sentence: Keep work local until a named pressure makes a wider scope worth its new coordination cost.

Core Insight

Priya and Mateo are editing board 84. A stroke should appear quickly for the people in that board. An invitation must have a durable, authoritative answer. Search may catch up later. Static app code should load quickly for people far from the origin.

All four needs belong to one product. They do not need one execution scope.

The false choice is “monolith or distributed system.” A useful architecture is often hybrid: a local function call for one decision, a room-level coordinator for another, a durable authority for a third, a worker for derived work, and an edge cache for geographic latency. The design question is not how many technologies appear in the diagram. It is how far each decision needs to travel before it has enough information and enough authority.

The Boundary We Need to Design

Lesson 002 separated product promises by guarantee. Now add one more question: what is the smallest scope that can provide that guarantee?

Work Smallest useful scope Why that scope is enough
Validate a drawing command already in a session process or session owner It needs local state and cheap execution.
Fan out a stroke to active collaborators one board room These collaborators share one interaction.
Decide whether Mateo may edit authoritative metadata path A local presence list is not a permission decision.
Recover an accepted edit after reconnect durable accepted-edit record Recovery needs evidence that survives the session.
Update search asynchronous worker and index Discovery can use a bounded freshness policy.
Serve static code edge cache or CDN Geography dominates this read path.

The table is a teaching model. The exact implementation might be one modular application, not six deployable services. Scope describes who must coordinate and where state must be known; it does not automatically decide the process layout.

The Naive Designs

Two simple designs are tempting.

Everything local:
  fast in one process, but no durable authority or recovery after failure.

Everything globally coordinated:
  one careful answer for every action, but live strokes pay remote latency,
  retries, and tail delays that their promise may not require.

The first model works while one process can hold the needed state and ordinary failure does not matter. It breaks when ownership, recovery, or geographic access matters.

The second model works when every operation truly needs one global answer. It breaks when a low-latency interaction is forced to wait for unrelated durable or downstream work.

The stronger model chooses scope per promise. That is not a claim that local work is always better. It is a claim that a wider boundary must earn its cost.

Authority, Acceleration, and Derivation

Hybrid systems become confusing when a convenient layer quietly becomes authority. Name the role of each layer before discussing its technology.

Authority is the official answer for a fact. In this scenario, it decides board ownership, access grants, and which edits count as accepted for recovery.

Acceleration makes a common path faster. An edge cache may serve static code. A cached permission result may reduce repeated lookups. Neither one should silently decide permanent ownership.

Derivation follows from an accepted fact. Search, notifications, and analytics can consume accepted events later under a stated freshness or retry policy.

authoritative:
  board metadata and accepted edit record

accelerating:
  edge cache, local room cache, cached permission reads

derived:
  search index, notification delivery, analytics aggregates

The same technology can serve different roles in different systems. A cache can be a safe acceleration layer or an unsafe source of truth. An event log can preserve accepted edits, while a queue can only deliver side effects. The role, not the product name, explains what failure is acceptable.

Worked Path: One Stroke, Several Scopes

Use a deliberately small trace. Priya is allowed to edit board 84 and draws stroke S1.

Starting point:
  Board 84 has an authoritative access record. Priya is connected to its room.

Step 1:
  The browser loads static code from an edge cache. This is acceleration.

Step 2:
  The session service checks Priya's already-authorized access for board 84.

Step 3:
  Priya sends stroke S1. The room assigns sequence 501 and fans it out to
  the active collaborators. This is room-level interactive coordination.

Step 4:
  The system records the accepted stroke for replay after a reconnect. This
  is durable authority for recovery, not a notification step.

Step 5:
  A worker later delivers a mention, updates search, and records analytics.
  These are derived consequences.

After step 3, Mateo can see S1 before the search index changes. After step 4, a reconnecting client has evidence to replay. If step 5 is delayed, drawing should still succeed. If step 4 fails, the system must apply the product's chosen recovery rule rather than pretending that a durable accepted edit exists.

Check: Notification workers are failing, but the accepted edit record is healthy. Should the session service roll back S1?

Think first, then reveal.

Answer: No. Notification delivery is derived work. Rolling back an accepted drawing operation would let a downstream side effect change the core product promise. Operators should instead see queue age, retries, and delivery failures.

So far, the path has several scopes, but none is present merely to look scalable. Each one owns a narrow job and a visible failure boundary.

What This Changes

Before this model, a team might ask whether the entire whiteboard should be “local” or “distributed.” That question is too coarse to guide a review. After this model, the team can ask a smaller question for every path: which scope has enough information, authority, and capacity to keep this promise?

That changes the design discussion. A slow board session is no longer evidence that all metadata needs to move. A stale search result is no longer evidence that board authority failed. The important decision is to change only the scope that contains the active pressure, then observe the signal tied to that promise.

When to Widen the Scope

Widen a boundary only when the current scope has a concrete limit. The decision should have this shape:

current scope
  -> observed or expected pressure
  -> wider option
  -> new failure mode
  -> signal that proves the move helped

Suppose one session owner handles a board well until a public workshop attracts 2,000 viewers. The pressure is no longer “the system is large.” It is room fan-out latency and slow subscriber buffers. A wider option might use relays or regional fan-out. The cost is harder ordering, replay, and relay-failure handling. The evidence to watch is p99 stroke-delivery latency and dropped-update rate under the large room.

The inverse is equally important. If a board remains small, the session owner has headroom, and recovery is simple, adding relays creates coordination work without protecting a new promise. Keeping the design local is then an engineering choice, not a lack of ambition.

The Trade-off

Hybrid boundaries buy fit. A room-level path can stay responsive, a durable path can preserve authority, and downstream workers can absorb bursts without blocking users.

They also charge rent. A remote boundary adds network delay, timeout policy, retries, tracing, and deployment coordination. A cache adds staleness and invalidation. A queue adds lag, duplicate delivery, and dead-letter handling. An edge layer adds propagation delay and versioning concerns.

The boundary is justified when its benefit protects a named promise better than the local design can. It becomes risky when no one owns its failure policy or watches the signal that reveals its cost.

Common Confusions

Confusion: “Distributed means more scalable.”

Why it is tempting: a wider system can add machines and regions.

Better model: distribution can solve load, locality, isolation, or ownership pressure. It also adds coordination costs. The pressure must be explicit.

Confusion: “A cached result is good enough to authorize access.”

Why it is tempting: cached reads are fast.

Better model: cached data may accelerate a decision, but authority and allowed staleness must remain explicit.

Confusion: “A queue makes a path reliable.”

Why it is tempting: queues absorb bursts and support retries.

Better model: a queue changes when work happens and how it retries. It does not by itself prove that the accepted fact is durable or that a side effect succeeded.

Design Review

Review this scope map:

board ownership       -> local browser memory
live drawing          -> global metadata transaction for every stroke
static app code       -> primary API on every page load
search                -> source of truth for board existence
notifications         -> asynchronous worker

Check: Which three entries are mismatched?

Answer: Board ownership needs durable authority, not browser memory. Live drawing usually should not pay a global metadata transaction for every stroke. Static code is a strong candidate for edge acceleration. Search can be useful, but it is a derived view rather than proof of existence or access.

Practice: Draw a Scope Map

Choose one path in a product you know: booking a seat, submitting an assignment, placing an order, or editing a document. Label each step as local, room or session scoped, authoritative, accelerated, queued, edge, or derived.

For every boundary, add:

  • the pressure it relieves;
  • the new cost it introduces;
  • the signal that would show it is failing.

A good answer can justify a simple local implementation when it fits. It does not need to invent distributed services to be architecture work.

Key Takeaways

  • Choose the narrowest scope that can protect the promise; widen only for a named pressure.
  • Authority, acceleration, and derivation must be named separately, even when they use the same technology.
  • Every boundary buys a capability and introduces a failure and operations cost.
  • A hybrid system is coherent when each scope has a reason, a limit, and a signal.
