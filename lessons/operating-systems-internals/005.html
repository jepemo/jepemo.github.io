Memory Hierarchies and Distributed State

By the end of this lesson, you will be able to... explain why memory and cache hierarchies exist, trace a request through hit, miss, refill, and eviction paths, and diagnose when a small drop in locality can overload a deeper authority.

Idea in one sentence. Memory hierarchies keep hot state close to computation, but every fast layer buys lower latency by accepting limits in capacity, freshness, coordination, or failure behavior.

Core Insight

Imagine an API that serves user profiles. The handler needs a display name, a feature-flag set, an account status, and sometimes an avatar URL. Some of that state may already be in the process heap because the user was just seen. A broader set may live in Redis. The durable profile row lives in a database. The avatar may sit in object storage and be cached by a CDN. A request that looks like "read profile" is really a path through a hierarchy of state.

That hierarchy exists because no single place wins at everything. The closest layer is fast, but small and usually less durable. The authoritative layer is more complete and durable, but slower and more contended. Caches, page caches, CPU caches, Redis, databases, and CDNs all express the same pressure: the data you need most wants to be near the computation, while the total data you own is too large, expensive, or shared to keep entirely in the fastest place.

The non-obvious part is that a cache is not just an optimization after the real design. It changes the request path, the failure path, and the load path. A cache hit can make the system look effortless. A cache miss can push work into a slower layer. A cluster of misses can turn a harmless-looking traffic burst into a database incident.

The practical mental model is a ladder of state with movement between layers. Reads check nearby layers first. Misses fall through to deeper layers. Refills copy selected data back upward. Eviction decides what gets pushed out when fast space is scarce. The system's real behavior is often determined less by the presence of a cache than by what happens when locality breaks.

The Layers Exist Because Each One Gives Up Something

A memory hierarchy is a ranked set of places where state can live. In a local machine, the layers may look like registers, CPU caches, RAM, page cache, and storage. In a service architecture, the layers may look like process memory, local cache, shared cache, database, object storage, and CDN. These are not identical mechanisms, but they rhyme because the trade-off is structural.

For the profile API, one possible ladder is:

closest / fastest / smallest
-> handler local variables
-> process heap or in-process cache
-> shared cache
-> database row
-> object storage and CDN-managed media
farthest / slower / larger / more durable

Each step upward usually buys speed and lower contention. Each step downward usually buys capacity, durability, sharing, or authority. The database is not "worse" than a cache. It answers a different question: what is the durable, authoritative state? The cache answers: what copy is worth keeping close because it is likely to be used again soon?

This is where the word hierarchy matters. The layers are ordered by access cost and responsibility. A fast layer is useful because many requests can finish before they touch a slower layer. A deep layer is necessary because the fast layer cannot safely own everything. The design works only when both facts remain visible.

One common mistake is to ask only, "Do we have a cache?" A better question is, "What path does a request take on a hit, what path does it take on a miss, and which layer is authoritative when copies disagree?"

Locality Is the Source of the Win

Small fast layers are powerful only when access is uneven. If every request touched a random user exactly once, a profile cache would do little. It would fill with objects that are not reused. But real workloads often have locality: recent items are likely to be used again, popular users or tenants receive more traffic, and related data is touched together.

Locality has two common forms:

temporal locality: recently used data is likely to be used again
spatial or related locality: nearby or associated data is likely to be used together

CPU caches rely on both. If code reads one memory address, nearby addresses may be loaded because the program may soon read adjacent data. Application caches often rely more visibly on temporal locality: if a user opens several pages in a short session, their profile data is likely to be needed repeatedly.

In the profile API, a small cache might hold only a fraction of all users, yet absorb most profile reads if active users repeat. That is why cache size alone is not the design center. A small cache with a good match to the working set can be excellent. A large cache with a random workload can still be disappointing.

The working set is the subset of data the current workload is actively touching. When the working set fits in the fast layers, hit rates are high and deeper layers are protected. When the working set grows beyond the fast layers, eviction churn rises, misses increase, and the deeper authority starts seeing more traffic.

Active check: if Redis memory doubles, does the system automatically become twice as fast? No. More space helps only if the extra space captures data that the workload will reuse. If the workload has poor locality or the miss path is dominated by something else, the improvement may be small.

Worked Path: Read, Miss, Refill, Evict

Trace one request for user 42.

request: GET /profiles/42
goal: return display name, account status, feature flags
fast layer: process cache
shared layer: Redis
authority: relational database

A simple read path might be:

def read_profile(user_id):
    profile = process_cache.get(user_id)
    if profile is not None:
        return profile

    profile = redis.get(user_id)
    if profile is not None:
        process_cache.put(user_id, profile)
        return profile

    profile = database.fetch_profile(user_id)
    redis.set(user_id, profile, ttl=300)
    process_cache.put(user_id, profile)
    return profile

This code hides several important states. Expand the path:

1. process cache lookup
   hit: return quickly, no network request
   miss: ask shared cache

2. shared cache lookup
   hit: pay network/cache cost, refill process cache
   miss: ask database

3. database fetch
   authority supplies current durable state
   refill shared cache and process cache

4. later insertion into a full cache
   eviction policy chooses what leaves

The hit path is cheap because the request stays high in the hierarchy. The miss path is expensive because it falls through to a deeper layer and may trigger refill work. Refill is the upward movement of a useful object after a miss. Eviction is the decision about what object loses its place when fast space is full.

Now imagine user 42 becomes popular for a few minutes. After the first miss, the profile is refilled upward. Later requests hit the process cache or Redis. The hierarchy converts repeated access into lower latency and lower database load. If user 42 is touched once and never again, the refill was mostly wasted and may evict something more valuable.

That is the central mechanism: the hierarchy bets that recently or frequently used state will be used again. The bet is powerful, but it can be wrong.

Miss Cascades and Refill Pressure

Most cache incidents are not caused by one miss. They are caused by many related misses. Suppose a deploy clears every process cache at once. Redis still has many profiles, so the database may survive. But Redis now receives a sudden burst from every instance. If Redis has evicted hot entries or is near capacity, many requests fall through to the database at the same time.

The path can look like this:

deploy restarts many API instances
-> process caches are empty
-> Redis receives burst of lookups
-> Redis misses on some hot keys
-> database receives burst of reads
-> database latency rises
-> refills slow down
-> more callers wait and retry
-> database receives even more work

This is a miss cascade. The hierarchy did not just fail to optimize. It actively changed how load propagated. A cold fast layer pushed pressure downward. A slow refill path kept the fast layer cold for longer. Retries and concurrent callers could multiply the work.

There is a familiar operating-system analogy. When the working set no longer fits in memory, page faults can dominate execution. The CPU may be available, but the process spends its time waiting for pages to move from slower storage. In a distributed service, the same shape appears when hot data no longer fits in cache or when refill paths become saturated.

The trade-off is that hierarchies improve common-case performance by adding uncommon-case complexity. Hits are fast and cheap. Misses need authority, refill policy, coordination, and protection from stampedes. You buy speed by accepting that the miss path must be engineered, not ignored.

Freshness, Authority, and Eviction

Distributed state adds a second difficulty: copies can disagree. The profile in process memory might be a few seconds old. Redis might have a five-minute time-to-live. The database might have the latest durable update. If an account is suspended, which layer is allowed to answer?

Every hierarchy needs an authority rule. The authority is the place treated as the source of truth for a decision. A cache may answer many reads, but it should not silently override the authority for decisions that need current state. Some data tolerates staleness, such as display names or avatar URLs. Other data may not, such as account lock status, payment eligibility, or authorization decisions.

Eviction policy also expresses values. Least-recently-used tries to keep recently touched objects. Least-frequently-used tries to keep frequently touched objects. TTL-based caching keeps objects for a time window, whether or not the next request will need them. No policy is universally correct; each one guesses what future access will look like.

The design questions are practical:

what layer is authoritative?
how stale may this copy be?
what happens on miss?
what gets evicted under pressure?
how do we prevent many callers from refilling the same key at once?

Active check: should every profile field share the same caching rule? Probably not. A biography or avatar URL may tolerate a stale read. An account-disabled flag may need a shorter TTL, invalidation, or a direct authority check. The hierarchy should follow the consequence of being wrong, not just the shape of the object.

Failure Modes and Design Checks

Failure: treating cache hit rate as the whole story. Hit rate matters, but it hides which keys miss and how expensive those misses are. A 2 percent miss rate on a cheap path may be fine; a 2 percent miss rate on a hot authorization path may overload the authority.

Failure: no stampede protection. If one popular key expires and thousands of callers all refill it at once, the hierarchy multiplies work. Use single-flight behavior, request coalescing, jittered TTLs, or background refresh when the path is important.

Failure: caching data without an authority rule. If no one knows which layer wins when copies disagree, freshness bugs become policy bugs. Decide whether stale reads are acceptable, how long they may last, and which decisions bypass cache.

Failure: eviction without workload evidence. Default eviction may be good enough, but it is still a guess. Watch evictions, miss latency, refill latency, hot-key distribution, and downstream saturation together.

Design review:

An API caches profile objects in Redis for 10 minutes.
The same object contains avatar URL, display name, account status, and fraud hold.
Traffic spikes after a marketing campaign.
Hit rate drops from 96 percent to 92 percent.
Database CPU jumps and login latency rises.

What should you inspect first? Do not stop at "hit rate dropped." Ask which keys missed, whether misses clustered on login paths, whether refill latency rose, whether account status should share a TTL with cosmetic profile fields, and whether many callers refilled the same keys concurrently. A good answer traces the miss path and identifies the authority under pressure.

Learner action: close the lesson and reconstruct the read path from memory: local hit, shared-cache hit, authority miss, refill, eviction. For each step, name the latency effect and the operational signal you would watch. A strong answer mentions both fast-path metrics and downstream load, not just cache size.

Key Takeaways

  1. Memory and cache hierarchies exist because no single layer gives the best latency, capacity, durability, sharing, and cost at once.
  2. Locality makes small fast layers useful; when the working set stops fitting, misses and evictions expose the deeper system.
  3. Hit, miss, refill, and eviction paths are part of the architecture, not incidental implementation details.
  4. Distributed caches need authority and freshness rules so faster copies do not silently answer questions they are not safe to answer.
