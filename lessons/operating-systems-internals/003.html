OS Concurrency and Synchronization Primitives

By the end of this lesson, you will be able to... explain why interleavings create race conditions, choose between mutexes, semaphores, and condition variables by purpose, and reason about a bounded producer-consumer queue without hiding overload.

Idea in one sentence. Synchronization is the set of rules that makes shared progress safe when the scheduler is free to interleave threads in orders your source code did not spell out.

Core Insight

Imagine a worker process with two threads sharing a bounded queue. One thread receives incoming jobs and pushes them into the queue. Another thread removes jobs and processes them. When you read the code one function at a time, everything looks reasonable: producers append, consumers pop, and the queue has a maximum size so memory cannot grow forever.

The trouble starts because the scheduler does not execute the source file as a neat story. It interleaves instructions from both threads. The producer may be halfway through updating the queue when the consumer observes it. Two producers may both think there is space. A consumer may check that the queue is empty and then go to sleep exactly as a producer adds work. The bug is not that one thread is nonsensical. The bug is that correctness depends on timing unless you define coordination rules.

That is what synchronization primitives are for. A mutex defines exclusive access to a critical section. A condition variable lets a thread sleep until some state may have changed. A semaphore can represent a count of available capacity or resources. These are not interchangeable decorations. Each primitive answers a different coordination question.

The practical mental shift is to ask what must be true, not which lock to add. What state must not be observed halfway changed? What condition should wake sleeping work? What capacity limit should make producers wait instead of growing an invisible backlog? Once you ask those questions, synchronization stops feeling like folklore and starts looking like explicit state design.

The Failure Is in the Interleaving

Start with the familiar counter example:

counter = 0

def increment():
    global counter
    counter = counter + 1

The line looks atomic in source code, but conceptually it contains separate steps:

read counter
compute counter + 1
write new counter

If two threads both run increment, the bad schedule is easy to miss:

counter = 0

Thread A reads 0
Thread B reads 0
Thread A writes 1
Thread B writes 1

final value = 1, even though two increments happened

Both threads executed valid local code. The global result is wrong because their operations overlapped through shared mutable state. That is a race condition: correctness depends on the relative timing of concurrent actions.

The protected region is called a critical section. The important point is that the critical section is not "the lines where a mutex appears." It is the region where an invariant can be temporarily broken. For the counter, the invariant is simple: each completed increment should increase the count exactly once. For a queue, the invariant is richer: the length, head, tail, storage slots, and wake-up conditions must agree.

The trade-off is direct. Protecting critical sections gives correctness and predictability, but it can introduce waiting, contention, and deadlock if the protected regions are too broad or acquired in inconsistent order.

Three Primitives, Three Questions

Return to the bounded queue. It has two shared facts:

queue contents
queue capacity

It also has two conditions that matter:

not_empty: a consumer can pop
not_full: a producer can push

Different synchronization primitives map to different questions:

Primitive Question it answers Bounded queue role
Mutex Who may inspect or mutate this shared state right now? Protect queue internals
Condition variable When should a waiting thread recheck a state condition? Wake consumers or producers
Semaphore How many units of a resource are available? Represent slots or items

A mutex alone is not enough for the bounded queue. It can stop two threads from corrupting the queue structure, but it does not explain when a consumer should sleep or how a producer should wait for space. Without a waiting primitive, the consumer may spin in a loop burning CPU, or the producer may keep allocating memory until pressure becomes a failure.

The condition-variable pattern makes the state relationship visible:

with mutex:
    while queue_is_empty():
        not_empty.wait()
    item = pop_item()

The while is part of the mechanism. A waiting thread wakes because the condition may now be true, not because it is guaranteed to remain true. Another consumer may run first. A spurious wakeup may occur. The thread must recheck the queue state while holding the mutex before it acts.

So far: the mutex protects the invariant while a thread observes or changes shared state. The condition variable avoids wasting CPU while waiting for that invariant to enter a useful state.

Worked Mechanism: Push and Pop Without Losing the State

Here is a compact design for the queue:

state:
  queue
  capacity
  mutex
  not_empty
  not_full

Producer path:

lock mutex
while queue is full:
  wait on not_full, releasing mutex while asleep
push item
signal not_empty
unlock mutex

Consumer path:

lock mutex
while queue is empty:
  wait on not_empty, releasing mutex while asleep
pop item
signal not_full
unlock mutex

The subtle part is the wait operation. It must release the mutex while the thread sleeps, otherwise the producer and consumer can block each other forever. If the consumer held the mutex while sleeping on an empty queue, no producer could acquire the mutex to push the item that would wake it. Real condition-variable APIs make "release lock and sleep" one atomic operation with respect to the condition wait.

Walk through one empty-queue case:

consumer locks mutex
consumer sees empty queue
consumer waits on not_empty and releases mutex
producer locks mutex
producer pushes item
producer signals not_empty
producer unlocks mutex
consumer wakes and re-acquires mutex
consumer rechecks not_empty condition
consumer pops item
consumer signals not_full
consumer unlocks mutex

This is synchronization as state choreography. Each part sees, changes, waits for, or signals a specific fact. The design does not rely on "the scheduler probably runs the producer next." It remains correct across many legal interleavings.

The signal placement is also intentional. The producer signals not_empty after it has changed the queue state, not before. The consumer wakes to recheck a fact that can now be true. Likewise, the consumer signals not_full after it removes an item, because that removal creates capacity for a producer. Signals are not messages with the item inside them. They are nudges that say "some protected state changed; recheck your predicate."

That distinction prevents a common misunderstanding. If a producer signals when no consumer is waiting, the signal may be lost. That is fine when the queue state itself is the source of truth. A later consumer should not depend on remembering the old signal; it should lock the mutex, inspect the queue, and see the item. Correct designs make the durable state carry the fact, while condition variables only help sleepers stop sleeping.

Semaphores can express the same bounded-buffer shape in a different style. One semaphore can count available slots, another can count available items, and a mutex can still protect the queue structure itself:

producer:
  wait for one free slot
  lock mutex
  push item
  unlock mutex
  signal one available item

consumer:
  wait for one available item
  lock mutex
  pop item
  unlock mutex
  signal one free slot

This version makes capacity counts explicit. It is useful when the problem is naturally counted: N slots, N permits, N identical resources. It is less expressive when each waiter needs to recheck a richer predicate over shared state. The lesson is not that one primitive is always more advanced. The design question chooses the primitive.

Backpressure Is Part of Correctness

Producer-consumer examples are often taught as lock exercises, but the deeper lesson is capacity. If producers are faster than consumers, the queue absorbs mismatch for a while. If the queue is unbounded, the system can pretend everything is fine while memory usage and latency grow. The failure is only delayed.

A bounded queue makes overload visible:

producers -> [ bounded queue ] -> consumers
              full: producers wait or shed
              empty: consumers wait

That visibility is a feature. It gives the system a place to apply backpressure, which means slowing, blocking, rejecting, or shedding incoming work before hidden backlog becomes collapse. The same pattern appears in socket buffers, runtime work queues, message brokers, and request pools.

The trade-off is that bounded capacity can reduce apparent throughput in the short term. A producer may be forced to wait even though it could keep generating work. But the alternative, unbounded acceptance, often converts a manageable overload signal into memory pressure, missed deadlines, and eventual failure.

Active check: if a bounded queue is full and producers are waiting, is that automatically a bug? No. It may be the system correctly exposing that consumers cannot drain work fast enough. The bug would be ignoring that signal or sizing the queue so large that the signal arrives too late.

Failure Modes and Design Checks

Failure: protecting the wrong region. A lock around one line may not protect the invariant. If the invariant spans length, head, tail, and storage slots, all related changes must be observed consistently.

Failure: waiting without a condition. A sleeping thread must know what state it is waiting to recheck. "Wake me later" is not enough. Good waits are tied to predicates such as queue_is_not_empty or space_is_available.

Failure: using if instead of while. A condition-variable wakeup is not a permanent promise. Recheck the condition under the mutex before consuming or producing.

Failure: hiding overload in an unbounded queue. Buffering can be useful, but infinite-looking buffering is often just latency and memory pressure in disguise.

Failure: assuming tests cover the bad schedule. A race can disappear under logging, debugging, or a slower machine because the interleaving changed. Review the invariant and the synchronization contract directly; do not treat one clean run as proof that the design is synchronized.

Review this small design:

if queue is empty:
  wait on not_empty
pop item

The missing piece is the loop and the protected predicate. A stronger answer is: hold the mutex, use while queue_is_empty(), wait through the condition variable, and recheck before popping. If the queue is part of a capacity boundary, also signal producers when a pop creates space.

Key Takeaways

  1. Concurrency bugs often come from legal interleavings that break shared-state invariants.
  2. Mutexes protect exclusive access, condition variables coordinate waiting, and semaphores represent counted capacity.
  3. Correct waiting means sleeping until a condition may have changed, then rechecking that condition under protection.
  4. Bounded queues teach both synchronization and backpressure: correctness includes making overload visible.
