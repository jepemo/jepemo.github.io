How Plumtree Combines Fast Broadcast with Epidemic Repair

By the end of this lesson, you will be able to:

  • trace eager payload delivery, lazy notification, GRAFT, and PRUNE for one broadcast;

  • explain why a tree alone can miss a whole branch and why full epidemic forwarding can waste bandwidth;

  • identify signals that distinguish missing-delivery repair from duplicate-payload cost.

Idea in one sentence: Plumtree sends full messages along a lean eager tree most of the time, while lazy notifications preserve alternate paths that can repair a missed delivery without flooding every payload everywhere.

Core Insight

An alerting service broadcasts a 64 KB event, m42, to a large cluster. The event should reach every connected subscriber quickly enough to trigger local action. Sending the full 64 KB payload along a tree is attractive: each node normally receives it once and forwards it to a few children. Bandwidth is predictable.

But a tree has a brittle failure shape. If one internal edge is stale, or one forwarding process pauses, every node below that edge can miss m42. A pure epidemic design has the opposite behavior: forward the full payload to many peers, and alternate paths make a miss less likely to matter. The price is that many nodes receive and deduplicate the same 64 KB payload repeatedly.

Plumtree separates the common path from the repair path. It maintains eager links that carry the full message and form a tree-like forwarding structure. It also keeps lazy links that carry a small announcement, often called IHAVE: “I have message m42.” A lazy receiver that hears an announcement but still lacks the payload can request it using GRAFT.

Plain meaning:

Use a small set of fast delivery roads for the package, and use cheap postcards on other roads to reveal that a package was missed.

In this scenario:

The 64 KB m42 travels over eager links. A short IHAVE(m42) travels over lazy links. Only a node that discovers a gap asks for the full 64 KB payload.

Technical name:

Plumtree is an epidemic broadcast tree: a self-adjusting eager tree for efficient payload delivery plus lazy epidemic repair edges for missed broadcasts.

The two incomplete extremes

Start with a pure tree.

        A
      /   \
     B     C
     |
     E

If A sends m42 and every link works, A sends the payload to B and C; B forwards to E. E gets one copy. This is excellent common-case behavior. The tree directs the payload instead of allowing every connected edge to carry it.

Now let B pause before forwarding. E does not merely receive a delayed copy. It may receive no indication that m42 exists. The tree has no alternate path for this event, so a single missed parent edge hides the message from a whole branch.

Pure epidemic broadcast reverses the risk. A, B, C, and D might all forward the full payload to several peers. E is likely to see m42 through more than one route, but each redundant path carries the entire 64 KB object. At high message rate, that means more network traffic, larger receive queues, and more message-ID bookkeeping for duplicates.

Design Normal path What a broken edge does Main cost
Pure tree One preferred parent-to-child route Can hide a whole subtree Fragile delivery
Pure epidemic forwarding Many full-payload routes Another payload path may repair it Duplicate payload traffic
Plumtree Full payload on eager routes; small notices on lazy routes A notice exposes a missing payload and starts repair Control state, timers, and adaptive link management

The central trade-off is common-case payload cost versus repair responsiveness. Plumtree pays a little ongoing notification and state cost so it does not need to pay full epidemic payload cost for every successful broadcast.

Eager and lazy links do different work

Each node keeps two broadcast-neighbor sets over an underlying peer overlay.

Link kind Carries Normal purpose When it becomes important
Eager push Full message payload Deliver quickly with few duplicates Normal broadcasts and recently useful repair paths
Lazy push IHAVE notification with message identity Preserve low-cost evidence that another path has the message When an eager branch misses delivery

When node N receives a full message for the first time, it records the message ID in a cache, delivers the payload locally, forwards the full payload to eager peers, and announces the ID to lazy peers. The cache is important: it lets N recognize whether a later payload is new, duplicated, or still missing after an announcement.

A simplified receive rule is:

receive full payload m:
  if m is new:
    remember and deliver m
    forward full m to eager peers
    send IHAVE(m) to lazy peers
  else:
    send PRUNE to the eager sender that produced an unnecessary duplicate

receive IHAVE(m):
  wait briefly for the eager path
  if m is still missing:
    send GRAFT for m to the notifier

The short wait after IHAVE is not wasted time. Without it, a node might request a second full payload even though its normal eager parent was about to deliver one. The delay is a tuning boundary: longer waits reduce unnecessary repair traffic but leave a real miss unresolved for longer.

A worked trace: repair a missing branch, then trim a duplicate

Use this small topology for m42:

eager links for payloads:  A -> B -> E
                           A -> C -> D

lazy link for notices:     D -> E

The lazy direction means D can notify E about a message D has seen without normally sending E the full payload. Now trace one broadcast.

Step Message and state What E knows Why the step matters
1 A sends full m42 to B and C E knows nothing Eager path starts efficient delivery
2 C sends full m42 to D; D stores it and sends IHAVE(m42) to E E knows a message exists but lacks the payload Lazy edge supplies gap evidence cheaply
3 B pauses before forwarding m42 to E E still lacks the payload after its brief wait The eager branch has failed for this event
4 E sends GRAFT(m42) to D E asks an alternate path for repair Repair is demand-driven, not a full flood
5 D sends full m42 to E; E stores and delivers it E now has m42 The missed branch is repaired
6 B recovers and later sends a duplicate full m42 to E E recognizes m42 as already seen Duplicate is evidence that two eager routes are unnecessary
7 E sends PRUNE to one redundant eager sender E keeps one useful full-payload path and makes the other lazy Future broadcasts carry fewer duplicate payloads

The input is one broadcast, m42. The first transition is eager full-payload forwarding. The intermediate state is uneven knowledge: D has the payload while E has only an IHAVE notice. The repair decision is E's GRAFT after the wait expires. The output is delivery at E, followed by PRUNE to remove a wasteful duplicate route. The naive contrast is clear: a pure tree leaves E silent after B pauses; full epidemic forwarding would have sent the 64 KB payload over the D-to-E backup even when B was healthy.

GRAFT and PRUNE make the tree adaptive rather than fixed. A path that successfully repairs a gap can become a useful eager path. A path that repeatedly creates duplicates can be demoted to lazy. Exact set-management details vary by implementation, but the reusable mechanism is stable: promote evidence-backed repair paths and demote wasteful payload paths.

What the protocol needs underneath

Plumtree is not an alternative to membership. It assumes that nodes already have a peer overlay with enough useful alternative paths. HyParView's active and passive views are a natural companion: they help maintain a partial overlay under churn. Plumtree decides how broadcast traffic should use that overlay.

It also needs bounded message-ID state. To decide whether m42 is new, duplicate, or missing, a node remembers recently seen IDs for a retention period. Forget too quickly and a delayed duplicate can be delivered again or a late IHAVE cannot be interpreted correctly. Remember forever and the cache grows without bound. Message lifetime, expected delay, and broadcast rate determine the retention policy.

Neither requirement is cosmetic. A perfect eager/lazy algorithm cannot repair a partition with no alternate overlay edge, and it cannot reliably suppress duplicates without enough recent identity history.

Observe delivery and repair separately

Do not judge Plumtree only by average broadcast latency. Its value is in how payload efficiency and repair behave under different conditions.

Signal What it reveals Boundary to inspect
Full-payload copies per delivered message Whether eager structure is near-tree-like or drifting toward flooding Excess eager links or ineffective PRUNE
IHAVE to GRAFT rate How often lazy notices discover missing payloads Broken eager branches, too-short wait, or poor overlay
Repair latency after injected edge loss How quickly a lazy path fills a real gap Lazy delay, notifier reachability, and payload retrieval
Duplicate payload rate by sender Which links repeatedly waste bandwidth Eager-set selection and prune behavior
Missing-delivery rate in fault tests Whether repair covers expected churn and edge failures Underlying membership and alternate-path diversity
Recently-seen cache size and eviction rate Whether deduplication state fits the workload Message retention period and broadcast rate

These signals prevent a misleading tuning move. A team might lengthen the lazy wait to reduce GRAFT traffic and call the system more efficient, while silently increasing the time that real misses remain unresolved. Or it might make repair immediate and reduce observed loss while creating duplicate payload spikes. The metrics must show both sides of the trade-off.

Common confusions

Confusion: lazy links carry a second copy of every payload

Why it is tempting:

They are called backup paths, so they sound like redundant full delivery.

Better model:

Lazy links normally carry only a compact announcement. They become payload paths when a receiver detects that its eager delivery is missing and requests repair.

Confusion: PRUNE means the sender is unhealthy

Why it is tempting:

It is sent after receiving a duplicate full message.

Better model:

PRUNE is usually a bandwidth-shaping signal: this eager payload edge is redundant for the current tree structure. It is not a membership failure verdict about the peer.

Confusion: GRAFT guarantees durable or exactly-once delivery

Why it is tempting:

It repairs a missing payload after a branch breaks.

Better model:

It requests another broadcast path under the protocol's assumptions. Durability, exactly-once processing, and state reconciliation need separate storage and application semantics.

Check your understanding

Check: E receives IHAVE(m77) from D, but E expects a full m77 from its eager parent B. Why should E wait briefly before sending GRAFT(m77), and what does E do if the full payload never arrives?

Think first, then reveal.

Answer: The wait gives B's normal eager delivery a chance to arrive, preventing unnecessary duplicate repair. If the payload remains missing, E sends GRAFT(m77) to D and requests the full message over that previously lazy alternate path.

Practice: review a broadcast repair policy

Your event system delivers 256 KB messages. It has low duplicate-payload traffic in normal operation, but fault tests show that a lost eager edge leaves some nodes without a message for eight seconds. The team proposes sending every full payload over every lazy link as well.

Write a short review that states:

  • what the proposal improves and what it makes expensive;
  • one smaller change you would test first;
  • three signals needed to decide whether the repair is fast enough without becoming a flood.
Review rubric A strong review recognizes that full payloads on every lazy edge improve redundancy but discard Plumtree's common-case bandwidth advantage. It first tests the lazy wait, `IHAVE` coverage, graft retrieval latency, and alternate-overlay reachability. Its signals include missing-delivery and repair latency under fault injection, full-payload copies per delivered message, `IHAVE`-to-`GRAFT` rate, duplicate payload rate, and cache pressure. It does not confuse a broadcast repair path with durable state replication.

Connections and boundaries

Lifeguard showed how membership detection needs a fast path plus guardrails for degraded conditions. Plumtree applies that pattern to broadcast: an efficient eager path carries ordinary traffic, and a lazy repair path handles missed delivery. The earlier overlay lessons remain necessary because lazy repair only works when alternate peers exist.

The next lesson moves from repairing one broadcast message to locating divergence in replica state. Anti-entropy may use later, broader comparison to find missing state; Plumtree tries to repair an individual broadcast promptly. Neither replaces application merge rules, durable replication, consensus, or a security trust model.

Key Takeaways

  • Eager links carry full payloads efficiently, while lazy links normally carry compact evidence that a message exists.
  • GRAFT repairs a detected gap through a lazy alternate path; PRUNE removes a redundant eager payload path.
  • The protocol adapts broadcast structure from delivery evidence instead of fixing one tree forever.
  • Evaluate payload copies, repair latency, missing-delivery rate, and cache pressure together; broadcast repair is not durable state reconciliation.
